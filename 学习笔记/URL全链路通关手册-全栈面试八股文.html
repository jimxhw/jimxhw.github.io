这份文档怎么用，才能在面试里拿分

同一个知识点，从「懂」到「能答」之间隔着一套表达结构。先把表达结构固定下来，再往里填内容。

面试官问这道题，从来不是想听你背 20 个步骤。他真正在判断三件事： 你有没有全局链路感（能不能自己把线串起来）、 你有没有纵深（随便挑一环能不能往下钻三层）、 你有没有工程意识（知不知道每环的性能与故障点）。

① 先背骨架（10 分钟）
  • 只看本页的「全链路总览图」和「18 字口诀」
  • 目标是能空手默画出六个阶段和它们的顺序
  • 骨架错了，后面细节再多也是散沙
② 再练表达（每关 5 分钟）
  • 先读绿色「一句话答案」——这是面试主答
  • 再用蓝色「口语模板」练成自己的话
  • 不要背诵书面语，面试要的是「像在讲事情」
③ 最后自测（折叠块）
  • 所有 Q&A 默认折叠，先自己想，再展开
  • 答不出来的，做标记，第二天只复习标记项
  • 用底部「30 秒速答卡」做最终验收
④ 面试时的答题结构
  • 第一层（30 秒）：六个阶段说清顺序
  • 第二层（2 分钟）：每阶段点一到两个关键机制
  • 第三层（等追问）：被问到哪儿往哪儿钻，钻深
  • 禁忌：一上来就讲 DNS 细节，格局先丢了
「想记住」和「能答出」是两种能力 想记住靠结构化（阶段 → 关卡 → 机制），能答出靠口语化。 所以本文档每关都给了两套内容：绿色的一句话答案（结构化、精准、可用于写简历/复盘）和蓝色的口语模板（可直接说出口）。 两者都要看，但优先级是：先骨架、再口语、最后细节。

三层记忆法：为什么这样背不会忘

第一层：位置记忆（记 6 个阶段）

浏览器发起 → 网络传输 → 请求上行 → 服务端处理 → 响应返回 → 浏览器渲染。这 6 个词是物理顺序，只要按「数据在哪儿」去想就不会乱。

第二层：口诀记忆（记 18 个字）

每个阶段挂 2~3 个字。先默念口诀，再让每个字自动展开成具体机制，比硬背机制清单可靠得多。

第三层：因果记忆（记为什么）

每一关都问自己：如果这一步不存在会怎样？比如「没有三次握手，服务端怎么知道客户端收到了 SYN+ACK？」——由问题反推机制，记的是逻辑而非文字。

一个常见错误，务必避开 很多人把这条链路背成「DNS → TCP → HTTP → 渲染」，一共四步。 这样答格局太小，因为它把「服务端处理」整段吞掉了——而服务端恰恰是全栈面试官最想考你的部分。 正确的骨架必须是六段，其中「服务端处理」和「浏览器渲染」各占三段，权重相当。

① 浏览器发起（0:20 – 0:49）

0:20 – 0:49

解析 URL、多进程导航与缓存分级

关 1–2 · ≈132 字

按下回车，第一步是 URL 解析。有个细节：hash 不会发给服务器，只留在前端做路由。

接着是决定命运的一步：查缓存。先看强缓存 Cache-Control 的 max-age，命中就用本地副本，连请求都不发；失效才走协商缓存，带 If-None-Match 问服务器，没变返回 304——只回响应头，不带响应体。

另外导航请求由浏览器进程发起、网络进程转交，这个交接本身就是链路的一环。

钩子 这一段埋了三个可被追问的点：304 到底省了什么（省了响应体，但仍有一次往返）、hash 为什么不发服务器、多进程架构为什么这么设计（安全隔离与稳定性）。如果面试官顺着任何一条问下去，你都已经准备好了。

② 网络传输（0:49 – 1:26）

0:49 – 1:26

DNS 递归、三次握手、TLS 与 QUIC

关 3–5 · ≈171 字

接下来 DNS 把域名变成 IP：先查本地缓存和 hosts，没有就交给本地 DNS 服务器递归查询，最后拿到权威服务器的 A 记录。

拿到 IP 后是三次握手：SYN、SYN + ACK、ACK。为什么必须三次？一是防止历史连接的残留报文建出无效连接，二是确认双方的收发能力都正常——只握两次，服务端不知道自己的 SYN+ACK 有没有被收到。

HTTPS 还要叠加 TLS 握手：客户端发 ClientHello，带 SNI 和 ALPN；服务端下发证书链，客户端校验签发链和域名。价值就三件事：防窃听、防篡改、防冒充。

旁白 这一段是全链路里最容易被追问细节的地方，但不要主动展开。三次握手只讲「为什么三次」，TLS 只讲「客户端校验了什么」，其余等追问。如果面试官问「为什么不两次」，你刚才那句话已经答完了。

1:26 – 1:57

报文构造、协议版本、CDN 与网关

关 6–7 · ≈143 字

连接建好后组装 HTTP 报文：请求行、请求头、空行、请求体。

这里澄清一个高频误区：跨域是浏览器的行为，不是服务端拒绝——请求其实已经发出去了，只是响应被浏览器拦下。

协议上，HTTP/1.1 有队头阻塞，HTTP/2 用多路复用解决，但 TCP 层的队头阻塞要靠 HTTP/3。

报文出网后先到 CDN 边缘节点，回源后过四层、七层负载均衡，最后是 API 网关做鉴权限流。原则是：越靠前越便宜。

旁白 这一段最重要的其实是那句「跨域是浏览器的行为，不是服务端拒绝」——这是高频的表述错误，讲对了立刻显专业。另外「越靠前越便宜」是一句很有分量的总结，值得放慢语气说。

④ 服务端处理（1:57 – 3:28）

1:57 – 3:28

全场最重的一段：从内核收包到事务提交

关 8–10 · ≈421 字

请求到服务器，先在内核层收包、交给协议栈解包，最后放进 socket 接收缓冲区。

关键是谁来处理。一个连接一个线程的阻塞 IO 撑不起高并发，所以都用 IO 多路复用。Linux 上是 epoll，红黑树管理 fd、就绪链表存事件，取事件 O(1)。澄清一句：epoll 是同步非阻塞 IO 加事件通知，不是异步 IO。

到 Java 这一层就是 Tomcat 的 Reactor 模型：Acceptor 接连接、Poller 注册 epoll、Worker 线程池读写。线程数和数据库连接池必须匹配，配错一个高并发下就会雪崩。

请求进容器，走 Filter 链处理编码、跨域和 traceId，再进 Spring MVC：DispatcherServlet 本身就是个 Servlet，把 URL 映射到方法、JSON 反序列化成 DTO。Controller 只做协议转换，不写业务。

业务在 Service 层，事务边界也在这里，通过 AOP 自动开启提交。必须知道的坑是：同类内部方法调用不走代理，@Transactional 会失效。

最后，发积分、发通知扔进消息队列，代价是幂等和最终一致性。主从延迟就是写完立刻读却读不到的原因。

1.2 百分号编码：为什么中文 URL 会变乱码

URL 规范只允许 ASCII 中的一部分字符直接出现，其余必须按 UTF-8 字节序列转成 %XX。 所以中文、空格、&、#、= 这些字符在真正传输前都会被编码。

API编码范围典型用途
encodeURI保留 URL 的结构字符（/ ? # & = : @ + $ ,）编码整条 URL
encodeURIComponent除 A-Za-z0-9-_.!~*'() 外全部编码，连 / ? # & 也编码编码参数值（日常用这个）
❌ 错误 url = '/search?q=' + encodeURI(keyword)
关键词里的 & 不会被编码，直接把后面的参数截断，造成参数丢失
✅ 正确 url = '/search?q=' + encodeURIComponent(keyword)
参数值里的结构字符一律编码，语义不会被破坏
口语模板（被问「URL 编码怎么用」） 「编码的核心不是「转成百分号」，而是区分结构字符和数据字符。 拼整条 URL 用 encodeURI（保留结构），拼参数值用 encodeURIComponent（连结构字符也编码）。 反过来的坑是：有人用 encodeURIComponent 编码了整条 URL，结果 / 也被编码，路由直接坏掉。 另外服务端默认按 UTF-8 解码，前端如果按 GBK 编码就会出乱码。」

1.3 浏览器进程模型：谁在处理这个 URL

现代浏览器是多进程架构，这点必须说清楚，因为它解释了后面所有「为什么响应回来了还没渲染」的问题。

进程职责与本链路的关系
Browser 主进程界面、标签页管理、地址栏、导航决策解析 URL、发起导航在这里
Network 网络进程所有网络请求的发起与接收DNS、TCP、TLS、HTTP 全在这里完成（现代浏览器中已独立为 Network Service）

Plugin / Utility插件、解码等辅助旁路，一般不影响链路
为什么这段值得讲 面试官问「浏览器是多进程还是多线程」，标准答案不是「多进程」三个字，而是： 多进程是为了稳定性和安全性——一个标签页崩溃不影响其他页面（稳定性）， 不同站点的渲染进程互相隔离、无法直接读取对方内存（安全性，即 Site Isolation / 站点隔离）。 代价是内存占用高、进程间通信（IPC）有开销。这就顺带解释了「那个 200ms 里数据其实在进程间搬了两次家」。

1.4 导航流程：从回车到发出请求

用户回车→ 判定：搜索词 or URL→ 旧页面 beforeunload→ 导航是否被取消→ 旧页面 unload→ 判定：导航 or 下载→ 交给网络进程
  1. 判定输入：符合 URL 规则 → 导航；否则拼成搜索引擎地址（?q=关键词）。
  2. beforeunload：旧页面可以在这里阻止离开（「确定要离开吗？」就是这么来的）。用户点「取消」，整条链路在这里终止。
  3. unload：旧页面清理资源。这里不能做异步请求，因为页面马上销毁，可以用 navigator.sendBeacon 替代。
  4. Content-Type 判定：如果响应头是 application/octet-stream 或 Content-Disposition: attachment，浏览器走下载分支，不启动渲染流程。
高频追问（先自测，再展开）
输入 baidu.com，浏览器怎么知道要加 https://？
先按 URL 解析：没有协议时默认补 http://。但浏览器内置 HSTS 预加载列表（Chrome 内置了一份常见站点的 HTTPS 强制列表），命中则直接升为 https://。此外主流浏览器还会先尝试 443/HTTPS，失败再回落到 80/HTTP。HSTS 的作用是消灭「首次访问被劫持」的窗口，但第一次未在列表内的访问仍可能是 HTTP——这就是为什么 HSTS 响应头只对「下一次」访问生效。
同源策略里的「源」由哪几部分组成？
协议 + 域名 + 端口，三者完全相同才算同源。任一不同即跨域。注意几个易错点：http://a.com 与 https://a.com 不同源；a.com 与 www.a.com 不同源；https 省略端口时是 443，与显式写 :443 算同源。路径和查询参数不参与判断——所以 /api/a 和 /api/b 是同源的，CORS 无法按路径粒度做限制（这也是很多人误以为能按接口配跨域的根源）。
为什么 #hash 不发给服务端？前端路由怎么利用这一点？
因为 fragment 的设计目的是指向文档内部的锚点，属于纯客户端概念，规范上就不进入请求行。前端路由因此有两种模式：Hash 模式靠监听 hashchange，优势是永不 404、无需服务端配合，劣势是 URL 丑、不参与 SEO；History 模式靠 pushState + popstate，URL 干净但刷新时真实路径会打到服务端，必须配 Nginx try_files $uri $uri/ /index.html 兜底。
为什么 unload 里发请求可能丢？
页面销毁时浏览器不会等待异步请求完成。可靠做法是 navigator.sendBeacon()（浏览器接管发送，不阻塞卸载）或用
fetch(url, {keepalive:true})。面试加分点：统计埋点用 sendBeacon，它专门为「页面卸载时上报」设计，且不占用主线程。
一个标签页崩溃，为什么其他标签页没事？
因为每个标签页（严格说每个站点）跑在独立渲染进程里，进程间通过 IPC 通信、内存互相隔离。这就是 Site Isolation。代价是多进程带来的内存开销——所以浏览器会对同站点复用进程、对 iframe 按站点拆分。

为什么线上发版后用户看到的还是旧页面 因为 index.html 被强缓存了，用户根本没机会拿到新的 HTML，也就没机会引用到新的 JS 文件名。 标准解法：HTML 用 no-cache（每次校验），静态资源用「内容哈希文件名 + 一年 max-age」。 内容变了文件名就变，天然绕开缓存；内容没变就永远命中缓存。 这是「缓存策略」这道题最标准的工程答案，务必能脱口而出。

为什么 Service Worker 必须 HTTPS？
因为它能拦截并改写页面发出的所有请求。如果允许 HTTP，中间人就能注入一个恶意 SW，永久劫持该站点所有流量（比 XSS 更持久）。所以规范要求安全上下文。例外：localhost 被视为安全上下文，方便本地开发。这点常被追问，记住能加分。
304 响应到底省了什么？
省的是响应体，不是请求。协商缓存依然要发一次完整请求（含请求头），服务端依然要处理。所以 304 的价值在于大文件（图片、JS）——省掉几十上百 KB 的传输。反之，如果资源很小或服务端处理很贵，304 的收益就有限，这时 immutable 或长 max-age 更值。
为什么大厂用文件名哈希而不是 query 参数（a.js?v=1）做版本控制？
三个理由：① 新 URL 一定是新资源，缓存天然失效，最可靠；② 有些代理/CDN 会忽略 query 做缓存，导致版本更新不生效；③ 文件名哈希是内容寻址，内容不变哈希不变，天然支持长期缓存与多版本共存（灰度时可同时存在两份）。用 query 版本号则每次发版全部失效，缓存命中率归零。
ETag 是怎么生成的？有什么坑？
Nginx 默认用「最后修改时间 + 文件长度」拼成十六进制，不是内容哈希，所以多机部署时可能不一致，导致同一资源在不同机器上 ETag 不同、缓存来回失效。这也是为什么有人干脆用 Last-Modified。若要用 ETag，需保证全集群的生成算法一致，或直接由应用计算内容摘要。此外，Nginx 的 gzip 开启与否会影响 ETag 强弱标记。
Service Worker 更新后为什么用户还是旧版本？
因为 SW 文件本身更新后，新的 SW 会进入 waiting 状态，等所有旧页面关闭才 activate。这是故意设计的（防止一个站点同时有两个版本）。想让用户立刻用上，可在 install 里调 self.skipWaiting()，在 activate 里调 clients.claim()，同时给页面加「新版本可用，点击刷新」的提示。注意：SW 文件本身默认不参与 HTTP 缓存（浏览器 24 小时内仍可能用旧副本），所以更新时最好改文件内容或路径。
强缓存和协商缓存能同时存在吗？
可以，而且是推荐组合。典型配置：Cache-Control: max-age=60 加 ETag——60 秒内直接用本地副本（不发请求，最快）；60 秒后带 ETag 去校验，内容没变返回 304（省流量）。这样兼顾了「快」和「新」。

阶段 ② 网络传输 DNS 域名解析：把域名变成 IP

分布式数据库的经典设计——可缓存、可分层、可负载均衡

面试热度 ★★★★★
一句话答案 DNS 是一个分层、可缓存的分布式数据库，作用是把域名翻译成 IP。 查询顺序是：浏览器 DNS 缓存 → 操作系统缓存 / hosts 文件 → 本地 DNS 服务器（递归查询）→ 根域名服务器 → 顶级域服务器 → 权威域名服务器。 其中「本地 DNS → 根 → TLD → 权威」这段是迭代查询，由本地 DNS 逐级代问，最终把结果缓存并返回给客户端。 DNS 默认走 UDP 53（快、无连接），报文超 512 字节或做区域传送时改用 TCP。

问题：解析慢

高频追问（先自测，再展开）
DNS 为什么用 UDP 而不是 TCP？
因为 DNS 查询是一次问答、报文极小、要求极快。TCP 三次握手 + 四次挥手本身就比查询内容还重，得不偿失。但两种情况下会用 TCP：① 响应报文超过 512 字节（UDP 单包上限）且不支持 EDNS0 扩展；② 区域传送（AXFR/IXFR），主从 DNS 同步数据量大且要求可靠，必须 TCP。另外 DoT 用 TCP 853、DoH 用 HTTPS 443。
浏览器怎么知道该解析哪个域名？代理场景下呢？
正常情况解析URL 的 host。但如果配了 HTTP 代理，浏览器会把完整 URL 交给代理，由代理去解析域名——客户端根本不解析。这也是「挂了代理后 hosts 不生效」的原因。若是 HTTPS + CONNECT 隧道，客户端只发域名给代理，DNS 由代理完成。
为什么说 DNS 是最容易被忽视的性能瓶颈？
因为它是串行链路中的一环：解析不完成，TCP 都建不了。首次访问时 4 次往返叠加，移动端可能吃掉 100~300ms，比 TCP + TLS 加起来还多。优化手段按性价比排序是：① 减少域名数量（合并静态资源域）、② 关键域名加 preconnect（一次搞定 DNS + TCP + TLS）、③ 非关键域名用 dns-prefetch、④ 使用 HTTPDNS。注意：HTTP/2 支持多路复用后，「多域名并行下载」的收益消失，反而每个域名都要付出解析 + 连接成本——这是 HTTP/2 时代域名收敛的理论依据。
preconnect、dns-prefetch、prefetch 有什么区别？
dns-prefetch：只做 DNS 解析，开销最小；
preconnect：DNS + TCP + TLS 全做完，为后续请求备好连接，最值钱也最贵（占资源，控制数量，一般 2~4 个）；
prefetch：提前下载资源到缓存，供下一次导航使用，不做解析准备；
preload：当前页面立即需要的资源，提升优先级（不做的话发现晚）。
一句话记忆：prefetch 是给下一页的，preload 是给本页的。
一次 DNS 查询，结果会被缓存多久？
由权威服务器返回的 TTL 决定，各级缓存都遵守它（浏览器、OS、Local DNS）。但注意两点：① 有些 Local DNS 不严格遵守 TTL，会自行延长（这也是故障切换慢的常见原因）；② 浏览器还有自己的「最小缓存时间」策略，TTL 过短时会被强制拉长。所以「改了解析为什么没生效」——大概率是本地缓存没到期。
口诀 · 关 3 浏览器 → 系统 → 本地 → 根 → 顶级 → 权威；前是递归，后是迭代
六个查询层级、两组关系（递归/迭代）。优化手段记「减域名 · 预连接 · 短 TTL · HTTPDNS」四个词。

阶段 ② 网络传输 TCP 三次握手与连接管理

可靠传输的起点；也是「为什么三次不是两次」这类经典题的产地

面试热度 ★★★★★
一句话答案 拿到 IP 后，浏览器先查 ARP 得到网关 MAC（同网段则直接是目标 MAC），逐跳路由到目标主机。 然后在传输层发起三次握手：客户端发 SYN（携带初始序列号 seq=x）→ 服务端回 SYN+ACK（seq=y, ack=x+1）→ 客户端发 ACK（ack=y+1），连接进入 ESTABLISHED。 三次的根本原因是：双方都需要确认「自己的发送能力」和「对方的接收能力」都是通的， 两次只能确认单向，四次则冗余（第二步可以合并 ACK）。

4.1 三次握手时序与状态迁移

疑问答案
为什么必须三次？三次是确认双向通道都可用的最小次数。第一次让服务端知道「客户端能发」；第二次让客户端知道「服务端能收能发」；第三次让服务端知道「客户端能收」。两次的话，服务端无法确认自己的 SYN+ACK 被收到，可能为一条已废弃的连接分配资源。
为什么不是四次？因为服务端的 SYN 和 ACK 可以在同一个报文中发送（捎带确认），合并成一步。
为什么 ISN 是随机的？防止历史连接的报文被误认为当前连接的数据，同时提高序列号猜测难度（防伪造攻击）。
SYN 会携带数据吗？规范上可以，但实践中几乎不——因为有 SYN Flood 风险，且携带数据的 SYN 要等握手完成才能处理，收益低。不过 TCP Fast Open（TFO）正是利用这点在 SYN 里带 Cookie + 数据，省掉一个 RTT。

4.2 四次挥手与连接的结束

FIN→ ACK
半关闭→ FIN→ ACK→ TIME_WAIT
2MSL
关键点解释
为什么挥手要四次？因为 TCP 是全双工的，关闭是双向独立的。收到 FIN 只表示「对方没数据要发了」，我方可能还有数据要发，所以 ACK 与自己的 FIN 不能合并。
为什么要有 TIME_WAIT？两个原因：① 确保最后一个 ACK 能到达——若丢了对端会重发 FIN，此时我方还在 TIME_WAIT 才能重新 ACK，否则会回 RST 导致对端异常；② 让本次连接的残余报文在网络中消散，避免污染使用相同四元组的新连接。2MSL = 报文最大存活时间的两倍。
TIME_WAIT 过多怎么办？它出现在主动关闭方。手段：net.ipv4.tcp_tw_reuse=1（复用，安全）、tcp_max_tw_buckets 限流、让客户端主动关闭（服务端设 SO_LINGER 或由 Nginx 作为被动方）。不要用 tcp_tw_recycle，NAT 环境下会误杀连接，已被内核移除。
CLOSE_WAIT 过多说明什么？是应用 bug，不是内核问题。说明收到了对端 FIN，但程序始终没调用 close()——典型原因是连接没归还连接池、流没关闭、异常路径漏了 finally。这是排查「连接泄漏」的第一线索。
「TIME_WAIT 多怎么优化」是道陷阱题 如果面试官问「我们服务端 TIME_WAIT 特别多怎么办」，先反问一句： 「TIME_WAIT 出现在主动关闭方，是服务端在主动关连接，还是客户端关的？」 如果服务端是主动关闭方，更本质的问题是为什么连接不能被复用—— 是不是 HTTP 响应头没带 Connection: keep-alive、是不是 keepalive_timeout 配得太短。 先问清场景再给方案，这个动作本身就是加分项。

4.3 队列与攻击：SYN Flood 的原理

服务端在完成握手前，会把连接放进 半连接队列（SYN Queue）； 三次握手完成后移入 全连接队列（Accept Queue），等待应用调用 accept() 取走。 两条队列都有上限，一旦溢出就会出现「连不上、超时」这类最诡异的故障。

概念说明相关参数
SYN Flood攻击者发大量 SYN 但不回最后的 ACK，占满半连接队列，使正常用户无法建连防护：tcp_syncookies=1、tcp_syn_retries、tcp_max_syn_backlog
Accept Queue 溢出内核已完成握手，但应用 accept() 太慢（如 Tomcat 线程池打满），导致队列积压somaxconn、backlog；溢出后内核按 tcp_abort_on_overflow 决定丢包还是发送 RST
观测手段ss -lnt 看 Send-Q（队列上限）与 Recv-Q（当前积压）；netstat -s | grep -i listen 看溢出计数线上排障必备
口语模板（被问「大量请求超时但服务器 CPU 不高」） 「这种情况我第一个怀疑的是连接建立阶段被卡住，而不是应用处理慢。 排查顺序是：先 ss -lnt 看 Recv-Q 是否接近 Send-Q——如果是，说明全连接队列溢出， 应用 accept() 跟不上，要看工作线程是不是被慢业务占满了； 如果队列正常，再 netstat -s 看 SYN 重传和半连接溢出，怀疑 SYN Flood 或 syncookies 未开； 最后才去看应用日志。关键在于：TCP 层的问题不会体现在 CPU 使用率上，只看 CPU 会一直找不到原因。」

4.4 拥塞控制与性能相关的两个经典坑

拥塞控制四阶段
  • 慢启动：窗口指数增长到阈值
  • 拥塞避免：过阈值后线性增长
  • 快重传：收到 3 个重复 ACK 立即重传，不等超时
  • 快恢复：阈值减半而非归零，避免重新慢启动
  • 现代算法：CUBIC（Linux 默认）、BBR（基于带宽与时延探测，弱网提升明显）
Nagle 算法 × 延迟确认 = 40ms 卡顿
  • Nagle：小包先攒着，凑够一个 MSS 或等到 ACK 才发
  • 延迟确认：收到数据后不马上 ACK，等 40ms 左右攒一个
  • 两者相遇互相等：Nagle 等 ACK，ACK 在等 40ms → 出现固定 40ms 延迟
  • 解法：设置 TCP_NODELAY 关闭 Nagle（实时性要求高的场景必配）
高频追问（先自测，再展开）
握手可以携带应用数据吗？为什么现在很多场景不需要三次了？
传统上不行（安全考虑）。TCP Fast Open 允许客户端在 SYN 里携带数据和 TFO Cookie，若服务端认可，可在握手完成前就处理数据，省掉 1 个 RTT。但它需要客户端缓存过 Cookie（首次无效），且受中间设备兼容性影响，普及度一般。真正革命性的是 QUIC：把 TCP + TLS 合为一体，首次 1-RTT、再次 0-RTT，还彻底解决了队头阻塞。面试谈到「如何减少连接建立开销」时，把 TFO 和 QUIC 一起说，层次就出来了。
HTTP 的 keep-alive 和 TCP 的 keepalive 是一回事吗？
完全不是，只是名字撞了。
HTTP keep-alive（Connection: keep-alive）：应用层约定，一个 TCP 连接上发多个 HTTP 请求，减少握手开销。
TCP keepalive（SO_KEEPALIVE）：内核层保活探测，连接空闲久了发探测包，判断对端是否还活着。
面试常考这个区别，答错很掉分。
RST 和 FIN 有什么区别？
FIN 是优雅关闭，表示「我没数据要发了」，走四次挥手，剩余数据仍会送达。RST 是强制重置，立即断开，未处理的数据全部丢弃，接收方会看到「Connection reset by peer」。常见触发 RST 的场景：往已关闭的连接发数据、端口未监听、队列溢出且 tcp_abort_on_overflow=1、SO_LINGER 设为 0。线上看到大量 RST，通常意味着「服务端认为连接不该存在」，比如负载均衡把请求转给了一台没有该连接的机器。
连接复用了，为什么还有性能问题？
因为 HTTP/1.1 上复用连接会引入 队头阻塞（HOL Blocking）：同一连接上的请求必须串行返回，前一个慢会拖住后面所有请求（经典表现是「浏览器 6 个并发连接全被一个慢接口占住」）。解法是 HTTP/2 多路复用（帧化 + Stream ID，逻辑上并行）。追问点：HTTP/2 也只在 TCP 层解决了应用层队头阻塞，TCP 层丢包仍会阻塞整条连接的所有流，所以才有 HTTP/3 over QUIC。
一个 TCP 连接的四元组是什么？为什么需要它？
源 IP + 源端口 + 目标 IP + 目标端口。它是内核区分不同连接的唯一标识。它的推论很有价值：客户端能同时建立的连接数受「源端口范围（约 2.8 万）× 目标 IP 数」限制，这就是「单机压测打不满、加机器立刻提升」的原因；也是 NAT 环境下大量设备共享一个公网 IP 时端口耗尽的根因。
为什么说「TCP 是可靠的」，但它真的不会丢数据吗？
TCP 保证的是「在连接存活期间，字节流按序、不重不漏地交付，否则报错」。但注意三件事：① 连接断了未确认的数据会丢（应用层感知为异常）；② 应用层没读、缓冲区满了仍会阻塞；③ 「可靠」不等于「一定送达」——它保证的是失败会被发现，不是失败不会发生。因此业务上必须自己做幂等和重试。
口诀 · 关 4 SYN → SYN+ACK → ACK；三次是为双向确认，四次是因全双工
必背四组数字与名词：1 RTT 建连、2 MSL 的 TIME_WAIT、 半连接队列（SYN Queue）、全连接队列（Accept Queue）。
05
阶段 ② 网络传输 TLS 握手与 HTTPS

在已建立的 TCP 之上，谈一把只有双方知道的钥匙

面试热度 ★★★★★
一句话答案 HTTPS = HTTP + TLS。TLS 握手要解决三件事：身份验证（证书链校验，确认对端是它自称的那个服务器）、 密钥协商（通过 ECDHE 等算法，双方各自算出相同的会话密钥，密钥本身不在网络上传输）、 算法协商（密码套件 + ALPN 选择 h2 或 http/1.1）。 TLS 1.2 需要 2 个 RTT，TLS 1.3 精简到 1 个 RTT（会话恢复可 0-RTT）。 之后所有 HTTP 报文都用对称密钥加密传输。

5.1 为什么必须「非对称 + 对称」混合

非对称加密（RSA / ECDHE）
  • 公钥加密、私钥解密；速度慢，比对称慢几个数量级
  • 只用它来「协商密钥」和「验证身份」
  • 解决「怎么在不安全的信道上安全地约定一个密钥」
对称加密（AES / ChaCha20）
  • 加解密同一把密钥；速度极快，可硬件加速
  • 握手完成后所有数据都用它
  • 问题：密钥怎么给对方？必须靠非对称加密送过去
摘要 / MAC（SHA-256 + HMAC）
  • 保证完整性：数据被篡改一定能被发现
  • AEAD 模式（AES-GCM）把加密与认证合为一体
证书（X.509）
  • 解决身份问题：证明公钥真的属于这个域名
  • 本质是「CA 用自己的私钥，对『域名 + 公钥』这个绑定关系签了个名」

5.2 TLS 1.3 握手时序（1-RTT）

版本握手往返关键差异（面试答到这些就够）
TLS 1.22 RTT密钥交换在 Hello 之后，还要 ChangeCipherSpec 通知切换加密；支持 RSA 密钥交换（无前向安全）
TLS 1.31 RTT

前向安全（Forward Secrecy）：一个高频加分点 如果用的是 RSA 密钥交换，会话密钥由客户端用服务器公钥加密后传输。 一旦服务器的私钥在未来某天泄露，攻击者可以把当年抓到的历史流量全部解密——因为密钥一直躺在那里。 ECDHE 每次握手都临时生成一对密钥，用完即弃，即使服务器长期私钥泄露，历史流量依然安全。这就是「前向安全」。 TLS 1.3 直接强制了这一要求，所以它不只是「快」，更是「更安全」。

5.4 SNI 与 ALPN：两个握手期的「协商」

SNI（Server Name Indication）
  • 明文放在 ClientHello 里，告诉服务器「我要访问哪个域名」
  • 解决「一个 IP 上部署多个 HTTPS 站点」的问题——没有它就无法选择证书
  • 它是隐私缺口：加密了内容却暴露了你要访问谁，所以有了 ECH（Encrypted Client Hello）
  • 排查经验：服务器有多个站点但没配 SNI，会返回默认站点证书，表现为「证书域名不匹配」
ALPN（Application-Layer Protocol Negotiation）
  • 在握手期协商使用 h2 还是 http/1.1
  • 取代了旧的 NPN，省掉一次额外的协议切换往返
  • 排障相关：如果 Nginx 没配 http2，客户端就会降级到 1.1，表现为「连接数上不去、性能不升」

5.5 HTTPS 的性能开销与优化

开销量级说明
握手：2~3 个额外 RTTTCP 1 RTT + TLS 1~2 RTT。首屏延迟的固定成本
计算：非对称运算发生在握手期，现代 CPU 有 AES-NI 与专用指令集，对称加解密开销很小
证书链：多传几个包证书链太长（有的服务商塞 4 张）会显著增加握手字节数，应精简到 2 张
握手期优化
  • 会话复用：Session ID / Session Ticket，恢复握手只需 1 RTT 甚至 0 RTT
  • TLS 1.3：默认少一个往返
  • OCSP Stapling：省掉客户端查吊销的往返
  • ECDSA 证书：比 RSA 证书体积更小、验签更快
  • 证书链精简：只配必要的那几张
架构期优化
  • SSL 卸载 / 终止：在 Nginx 或 LB 上解密，后端走内网 HTTP，省掉每台应用机的握手负担
  • CDN 边缘终止 TLS：让用户就近握手，回源另建连接
  • connection: preconnect 提前完成握手
高频追问（先自测，再展开）
HTTPS 能防止抓包吗？用 Charles 为什么还能看到内容？
HTTPS 防的是中间人，不防你自己。Charles/Fiddler 这类工具的工作方式是：在你电脑上装一个自己的根证书，然后充当「客户端与服务端之间的中间人」——它和浏览器建立一条 TLS，和服务端建立另一条，各自解密再转发。前提是你手动信任了它的根证书。这也正是「企业可以做 HTTPS 流量审计」的原理。反过来说：如果 App 做了证书固定（Certificate Pinning），只信任自己指定的证书，中间人就会失效。面试答到这里，基本就满分了。
为什么 HTTPS 页面会报「混合内容」警告？
因为页面本身是 HTTPS，但里面引用了 HTTP 的图片/脚本/接口。这会造成安全降级：攻击者可以篡改那个 HTTP 资源（比如注入脚本），从而完全控制 HTTPS 页面——一条链的强度等于最弱的一环。现代浏览器对「混合的主动内容（脚本、样式、iframe）」直接阻止加载，被动内容（图片）只警告。解法：全站 HTTPS，或用 upgrade-insecure-requests CSP 指令自动升级。
中间人攻击怎么防？证书校验之外还需要什么？
证书链校验本身就是防中间人的核心机制。在此之上还有几层：① HSTS 强制 HTTPS 并阻止用户忽略证书警告，消灭降级攻击窗口；② 证书透明度（CT），所有证书必须记入公开日志，误签可被发现；③ 证书固定（Pinning），客户端只信任特定证书；④ 双向 TLS（mTLS），服务端也校验客户端证书，用于服务间通信。注意 HSTS 一旦启用就很难回退（浏览器会记住），上线前务必确认全站 HTTPS 已就绪。
「HTTPS 就是 HTTP 加了一层加密」这种说法对吗？
不算错，但太浅。准确的表述是：HTTPS 在 HTTP 与 TCP 之间插入了 TLS 层，提供机密性（加密）、完整性（防篡改）、身份真实性（证书）三个保证。少了任何一个都不成立——只加密不验身份，中间人照样能伪装成服务器。面试时主动补上「三个保证」这三个词，能立刻体现你理解的是设计目标而非流程。
会话复用（Session Ticket）为什么会有安全争议？
Session Ticket 由服务端用一把「票据密钥」加密后交给客户端保管（客户端不解密，只是下次握手时带回来）。问题是：这把票据密钥是长期有效的，一旦泄露，攻击者可以伪造有效的 Ticket，从而冒充服务器或解密会话，等于绕过了前向安全。所以实践上必须定期轮换票据密钥。而 TLS 1.3 的 0-RTT 数据还有个额外风险：可被重放，因此只能用于幂等请求（GET），不能用于下单支付这类操作——这是一个很能体现工程素养的细节。
HTTPS 的握手能跳过吗？QUIC 做了什么？
传统上 TCP 和 TLS 是串行的，总开销 2~3 RTT。QUIC（HTTP/3 的传输层）把两者合并为一次握手：首次 1-RTT，再次 0-RTT。同时 QUIC 基于 UDP 实现，从根本上消除了 TCP 层的队头阻塞（每个 Stream 独立重传），并把连接标识从「四元组」改为「Connection ID」，支持连接迁移——手机从 WiFi 切到 4G 时连接不中断，这在移动端是极大的体验提升。
口诀 · 关 5 三保证 · 两套加密 · 一个 RTT · 零往返恢复
三保证：机密性、完整性、身份真实性； 两套加密：非对称谈密钥、对称加密数据； 1 RTT：TLS 1.3 的握手成本； 0-RTT：会话恢复。再加一组词：SNI 选证书、ALPN 选协议、OCSP Stapling 省往返。
阶段 ③ · 请求上行

敲门：发、转

连接建好了，终于可以把请求发出去了。但请求不会直接落到你的应用上——它要先穿过 CDN、负载均衡、Nginx、网关四道关卡，每一道都可能改写它、拒绝它、或者把它转给别的机器。

这一阶段是全栈面试的交叉区：前端关心 CORS 与 Cookie，后端关心网关与限流，运维关心负载均衡。 能把「请求在到达你的代码之前经历了什么」讲清楚的人，通常会被认为有线上思维。

阶段 ③ 请求上行 HTTP 请求构造、报文与协议版本

最熟悉的协议，但面试问的往往是它的语义而非格式

面试热度 ★★★★★
一句话答案 浏览器按 请求行 + 请求头 + 空行 + 请求体 的格式组装报文： 请求行是 方法 路径 HTTP版本，请求头携带 Host（HTTP/1.1 必需，用于虚拟主机路由）、 Cookie、Accept-Encoding、Origin（跨域判断依据）等元信息， 请求体只在 POST/PUT 等方法上出现。若是跨域的复杂请求，浏览器会先发一个 OPTIONS 预检请求， 通过后才发真实请求。传输层之上，协议本身不再关心「你是谁」，只按字节流搬运。

6.1 报文结构与关键请求头

POST /api/order HTTP/1.1          ← 请求行：方法 + 路径 + 版本
Host: api.example.com             ← HTTP/1.1 必需，虚拟主机靠它区分
User-Agent: Mozilla/5.0 ...       ← 客户端标识（可用于埋点与兼容判断）
Accept: application/json          ← 期望的响应类型（内容协商）
Accept-Encoding: gzip, br         ← 支持的压缩算法
Accept-Language: zh-CN            ← 语言协商
Content-Type: application/json    ← 请求体的格式（服务端据此选择反序列化器）
Authorization: Bearer eyJhbGci... ← 凭证
Origin: https://www.example.com   ← 跨域请求的来源（CORS 判断依据）
Referer: https://www.example.com/cart ← 来源页面（可用于防盗链、统计）
Cookie: sid=abc123; theme=dark    ← 每次请求自动携带（注意体积！）

两个容易被忽略的限制 ① 请求头体积有限制：Nginx 默认 large_client_header_buffers 8KB，超过会返回 400/414。 所以「把大量数据塞进 Cookie 或自定义头」是一个真实事故源。
② URL 长度有限制：浏览器约 2KB~8KB（IE 最窄），服务器侧 Nginx 默认约 8KB。 所以 GET 不适合传大参数，批量查询要用 POST。
面试话术：被问「为什么批量查询用 POST」，答「不是语义不符，而是 URL 与请求头有体积上限，且 URL 会被完整写入 access log 造成两个问题：日志膨胀 + 敏感参数泄露」。

6.3 CORS：浏览器唯一的「主动拦你」机制

跨域是浏览器施加的限制，不是服务器。请求其实发出去了、服务器也处理了， 只是浏览器发现响应头里没有允许的 Access-Control-Allow-Origin，于是不给你的 JS 看结果。 理解这一点，很多「CORS 报错但服务端日志显示 200」的困惑就解开了。

类型触发条件行为
简单请求方法是 GET/POST/HEAD，且 Content-Type 是三种表单类型之一，且无自定义头直接发，浏览器事后校验响应头
预检请求方法为 PUT/DELETE/PATCH，或 Content-Type: application/json，或有自定义头先发 OPTIONS 询问，通过后再发真实请求。代价：多一个 RTT
带凭证请求设置了 credentials: 'include'响应头不能用 * 通配符，必须回显具体源，且服务端要在预检里返回 Allow-Credentials: true
预检缓存：一个高频优化点 OPTIONS 预检本身可以被缓存。服务端返回 Access-Control-Max-Age: 86400， 浏览器在 24 小时内对同一 URL、同一方法、同一组头不再重复预检。 不设这个头的话，每个跨域请求都要多花一个 OPTIONS 往返——这是很典型的「不报错但白慢一倍」的性能问题。
口语模板（被问「CORS 怎么解决」） 「首先确认这是浏览器行为，不是网络不通——请求实际到达了服务端。解决位置在服务端： 返回 Access-Control-Allow-Origin（注意不能和 Allow-Credentials: true 同时用 *， 必须回显白名单匹配到的源）；复杂请求还要在网关或过滤器里统一处理 OPTIONS 预检， 并让它在我们自己的鉴权逻辑之前返回——因为预检请求不带 Cookie 和凭证， 如果被鉴权拦掉会返回 401，跨域就永远过不去。这是最常见的踩坑点。 另外记得设 Max-Age 减少预检次数。」

6.4 Cookie / Session / Token：三种状态保持方案

方案状态存在哪优缺点（面试重点）
Cookie + Session服务端内存/Redis优点：可随时失效、数据在服务端安全。
缺点：多机部署需要共享存储（粘性会话或 Redis）；跨域受限；每次请求自动携带，浪费带宽

缺点：无法主动失效（签发后到期前一直有效）、体积较大、payload 只是 Base64，不是加密，不能放敏感数据

JWT 无法失效怎么办？—— 一道高频追问 「JWT 签发后无法主动失效」是它的固有缺陷。工程解法有三种，按复杂度递增： ① 双 Token：access token 短期（15 分钟）+ refresh token 长期，靠 refresh 的有效性来间接控制； ② 黑名单：注销时把 jti 写入 Redis，校验时查一次——但这又回到了有状态，等于放弃了 JWT 的最大优势； ③ 版本号：用户表存一个 tokenVersion 放进 payload，改密码时自增，旧 token 校验失败。 答到这里记得补一句「所以选型要看场景：内部管理系统用 Session 更简单可靠，对外开放的 API 才用 JWT」——展现取舍意识。

HTTP/1.0每个请求一个连接问题：每次都要握手，开销巨大

HTTP/2二进制分帧 + Stream 多路复用、HPACK 头压缩、服务端推送解决应用层队头阻塞。遗留：TCP 层队头阻塞（一个包丢了，整条连接所有流都等）；Server Push 因收益不佳已被主流废弃
HTTP/3基于 QUIC（UDP）、连接迁移、0-RTT彻底解决队头阻塞，握手更快，弱网表现大幅改善。遗留：UDP 在某些企业网络被限制、中间设备兼容性
一个会被追问的细节 既然 HTTP/2 是多路复用，为什么实践中「域名收敛」依然有价值？ 因为它仍然受制于 同一域名下的 TCP 连接数、拥塞窗口与 TCP 层队头阻塞， 所以「关键资源用少量独立域名做连接隔离」在弱网下仍然有效。 但总体趋势毫无疑问是收敛域名——能同时讲出「趋势」和「例外」，是资深与初级的分别。

6.6 方法语义：安全性与幂等性

方法安全幂等语义与常见误用
GET✅✅只读。误用：用 GET 做删除（会被爬虫/预取触发）
HEAD✅✅只要响应头，用于探测资源是否存在与大小
POST❌❌创建/提交。重复提交会重复创建，必须靠业务幂等键防重
PUT❌✅全量替换。重复执行结果相同
PATCH❌❌局部更新。若写成「balance += 100」就不再幂等
DELETE❌✅删除。第二次删已不存在的资源返回 404 或 204 都不算违约
幂等性为什么这么重要（高频追问） 因为网络不可靠，重试是必然的：用户连点两次、网关超时重发、RPC 框架自动重试、手机弱网切网。 如果支付接口不幂等，用户就会被扣两次钱。标准解法：客户端生成唯一业务号（如订单号 + 请求 ID）， 服务端用「唯一索引 + 去重表」或「Redis SETNX」拦截重复请求，命中则直接返回上次结果。 面试答到「分布式唯一 ID + 去重表/唯一索引」这个组合，就足够扎实了。
高频追问（先自测，再展开）
GET 和 POST 的本质区别是什么？
语义区别，不是技术区别。「GET 参数在 URL、POST 在 body」「GET 有长度限制」都是实现细节或历史遗留，不是规范规定。真正的区别是：GET 是「取回一个表示」，必须安全且幂等；POST 是「提交一份数据给服务端处理」，语义上会改变状态。因此中间设施（缓存、预取、爬虫、CDN）可以自由缓存和重试 GET，而不敢对 POST 这么做。一句话收尾：所有把 POST 当 GET 用（或反之）的设计，都会在未来被某个中间设施狠狠教育。
Cookie 的 SameSite 属性解决什么问题？
解决 CSRF。攻击者在自己的站点发起一个指向银行站的请求，浏览器会自动带上银行的 Cookie，于是「转账」就执行了。SameSite 让浏览器在跨站请求时不发送 Cookie。
Strict：最严，从外站点链接过来也不带（会导致「从搜索引擎点进来是未登录状态」）；
Lax（现代浏览器默认）：GET 顶级导航带、POST 与 iframe 不带，是友好的默认值；
None：必须同时加 Secure，用于需要跨站的第三方嵌入场景。注意：这是「缓解」而非「根治」，CSRF Token 仍是必要的第二道防线。
为什么响应头要加 Vary: Accept-Encoding？
因为同一 URL 可能返回不同编码的版本（gzip、br、未压缩）。如果 CDN 缓存了 gzip 版本，却把它返回给一个不支持 gzip 的老客户端，就会乱码。Vary 告诉缓存「这个响应还取决于这些请求头」，必须按 Vary 的维度分别缓存。忘记设是 CDN 场景的经典事故。相关头还有 Vary: Origin（跨域接口必备，否则会把 A 站的 CORS 响应返回给 B 站）。
状态码里 301、302、307、308 怎么选？
301 / 308 是永久重定向，会被浏览器强缓存（下次直接跳，不再请求原地址）——所以配错了极难纠正，用户浏览器会一直跳错地方。 302 / 307 是临时重定向，不缓存，可随时改。
301 / 302 允许把 POST 改成 GET（多数浏览器确实这么做），307 / 308 严格保持原方法，不会改。
实践建议：HTTP 升 HTTPS 用 301，业务跳转用 302，需要保持 POST 的跳转（如 OAuth 回调）用 307。301 上线前务必确认目标地址正确——这是「改不回来」的坑。
为什么说「请求发出去了但被浏览器拦下」这件事很重要？
因为它直接影响排查方向。CORS 失败时，服务端日志会显示 200 且业务逻辑已执行——如果这是「扣款」接口，钱已经扣了，而前端只看到报错。所以：① 排查 CORS 问题必须同时看浏览器控制台和服务端日志；② 涉及写操作的跨域接口要格外小心重试；③ 后端做 CORS 配置时不能只配成功响应，错误响应（4xx/5xx）也要带 CORS 头，否则前端连错误信息都读不到，只能看到「CORS 错误」而看不到真正的 500。

报文四段（请求行 / 请求头 / 空行 / 请求体）；CORS 两分支（简单 / 预检）； 方法两属性（安全 / 幂等）；版本一句话（1.1 复用连接、2 多路复用、3 基于 QUIC 解决队头阻塞）。

就近调度→ 边缘节点

CDN 的关键点
  • 就近接入靠 DNS：GSLB 按用户 IP 返回最近的边缘节点 IP，与关 3 的「智能解析」是同一套机制
  • 缓存策略由源站响应头决定：Cache-Control、s-maxage、Vary 都会影响 CDN 行为
  • 缓存刷新 vs 预热：刷新是「删掉旧缓存」，预热是「提前把新文件推到边缘」。发版时两者要配合使用
  • 动静分离：静态资源走 CDN，动态接口直连源站
CDN 的常见坑
  • 缓存了不该缓存的接口：把用户私有数据缓存到公共节点，造成数据泄露（必须加 Cache-Control: private）
  • 发版后用户拿到旧 JS：HTML 被 CDN 缓存。
  • 回源带宽被打满：缓存命中率低，CDN 变成「加速的转发器」
  • 跨域接口没设 Vary: Origin：把 A 站响应给了 B 站
一个高频追问：CDN 加速了，为什么接口还是慢？ 因为 CDN 主要加速静态资源。API 请求通常是动态的（不能缓存），CDN 只能帮你把 TCP/TLS 的握手缩短到「用户到边缘节点」这一段， 但回源那一段（边缘节点 → 源站）依然要完整走一遍。 所以对动态接口，真正有效的手段是：后端多机房部署 + 动态加速（走专线回源）+ 数据层就近（异地多活）， 而不是指望 CDN。能说出这一层，就说明你真懂 CDN 的边界。

7.4 Nginx 在链路中的具体职责

Nginx 做的六件事

  • SSL 卸载：在 Nginx 解密，内网走明文 HTTP，减轻应用负担
  • 静态资源：直接读盘返回，比 Java 处理快一个数量级
  • gzip / brotli 压缩

必知的超时配置与级联
  • proxy_connect_timeout：与后端建连超时
  • proxy_read_timeout：读后端响应超时
  • keepalive_timeout：客户端连接空闲多久关闭
  • 铁律：超时必须逐层放大——客户端 > 网关 > 服务 A > 服务 B。否则上游超时重试，下游却还在执行，造成重复处理
口语模板（被问「超时时间怎么设计」） 「核心原则是沿调用链逐层递增。假设最底层一次 DB 查询最长 200ms， 那 B 服务处理上限设 500ms，A 服务调用 B 的超时设 800ms，网关到 A 设 1200ms，客户端设 1500ms。 如果反过来——上游比下游先超时——就会出现：客户端已经放弃并重试了，服务端还在跑第一次请求， 结果是同一个业务被执行两次，写操作就会重复扣款。 所以我一般会要求每个服务的超时配置必须显式声明，不允许用无限等待的默认值。」

高频追问（先自测，再展开）
正向代理和反向代理的区别？
正向代理代表客户端（你想访问外网，通过代理出去，服务器不知道真实客户端是谁）——科学上网、企业出口代理。反向代理代表服务端（客户端以为在直连，其实前面有一层在转发，客户端不知道真实服务器是谁）——Nginx、负载均衡。一句话记忆：正向代理隐藏客户端，反向代理隐藏服务端。两者都是「中间人」，区别只在立场。
限流的几种算法怎么选？
固定窗口：简单但有临界问题（窗口边界处可能瞬间双倍流量）；
滑动窗口：把窗口切成小格，平滑了很多，内存占用可控；
漏桶：无论来多少都以恒定速率流出，强制平滑，但无法应对突发；
令牌桶：按固定速率放令牌，桶里攒着，允许一定程度的突发，是最常用的；
分布式限流：单机限流在集群下不准（10 台机器各限 100，总量变 1000），需用 Redis + Lua 做全局计数，或用 Sentinel 的集群流控。加分点：限流阈值要靠压测得出，不能拍脑袋。
灰度发布怎么做？
核心是在网关或服务网格层做「标签路由」：给新版本实例打上 version=v2 标签，网关按规则匹配——① 按请求头（内部测试加特定 Header）、② 按用户 ID 取模（稳定命中同一批用户，体验一致）、③ 按百分比（逐步放量 1% → 10% → 50% → 100%）。关键配套：必须有实时监控和秒级回滚能力，否则灰度只是「慢速事故」。另外要保证灰度期间同一用户的请求始终落到同一版本，否则新旧数据格式不一致会出问题。
为什么 Nginx 用 limit_req 限流后还是被打挂？
几种常见原因：① limit_req 是按 IP 限流，攻击者用代理池换 IP 就绕过了；② 限流发生在 Nginx，但慢请求已经占住了连接与 upstream 连接池，真正的问题是后端处理慢而非流量大；③ burst 配置过大，允许的突发量本身就足以压垮后端；④ Nginx 本身的连接数 worker_connections 成为瓶颈。正确姿势是多层防护：CDN 层清洗 → WAF 拦恶意特征 → Nginx 限流 → 应用层限流，任何一层都不该被单独依赖。
用户说「网站很慢」，你怎么定位是哪一层？
按链路从外到内砍：
① curl -w 或浏览器 Network 面板看 DNS / TCP / TLS / TTFB / Content Download 各段耗时——TTFB 长就是服务端问题，Content Download 长就是带宽或体积问题；
② 若 TTFB 长，看是网关慢还是应用慢（用 traceId 查链路追踪）；
③ 若应用慢，看是 CPU（计算密集）、I/O（等待 DB/下游）、还是 GC；
④ 若 DB 慢，看慢查询日志与执行计划。
这一套「分段测量、二分定位」的方法论比任何具体命令都重要——面试官想听的是这个。

阶段 ④ 服务端处理 内核到应用：epoll 与 Tomcat 线程模型

字节流如何被唤醒成一个 Java 对象；回答「高并发」类问题的地基

面试热度 ★★★★★
一句话答案 数据包到达网卡后经 DMA 写入内核缓冲区，触发硬中断 → 软中断，内核协议栈逐层解封装 （链路层 → IP 层 → TCP 层，校验、排序、重组），把数据放入该 socket 的接收缓冲区。 Tomcat 的 Poller 线程通过 epoll 多路复用感知到就绪事件， 从工作线程池取一个线程去读取并解析 HTTP 报文，最终构造出 HttpServletRequest。 核心认知：一个请求占用一个线程，线程数与连接数、队列长度三者必须匹配，否则高并发下必然雪崩。

8.1 数据包进入应用的完整路径

网卡收包→ DMA 写环形缓冲→ 硬中断 / 软中断→ 内核协议栈逐层解封装→ socket 接收缓冲区→ epoll 就绪→ 应用 read
环节做了什么性能相关
网卡 → 内核DMA 直接把数据写入内存，不经过 CPU高流量下中断风暴是瓶颈，用 NAPI（中断 + 轮询混合）缓解
协议栈处理校验和、序号排序、去除重复、TCP 接收窗口更新、ACK 回复全部由内核完成，应用完全感知不到
接收缓冲区数据就绪，等待应用读取缓冲区满 → TCP 窗口收缩为 0 → 发送方停止发送（这就是「背压」）
唤醒机制内核通知应用「有数据了」就是 IO 多路复用——epoll 在这一步起作用

8.2 五种 IO 模型与 epoll 的关键设计

模型行为问题
阻塞 IOread 一直等到数据来一个线程守一个连接，连接数 = 线程数，撑不住
非阻塞 IOread 立即返回，没数据就轮询空转浪费 CPU
IO 多路复用一个线程用 select/poll/epoll 同时监听大量 fd主流方案
信号驱动 IO内核发信号通知实际很少用
异步 IO（AIO）内核完成拷贝后通知Linux 原生 AIO 不成熟；io_uring 是新兴方向
select / poll 的缺陷
  • 每次调用都要把整个 fd 集合从用户态拷贝到内核态
  • 内核要线性扫描所有 fd 才知道谁就绪，O(n)
  • select 还有 1024 个 fd 的硬上限
  • 结论：连接数一多就退化得厉害
epoll 的三个改进
  • 红黑树存 fd：增删改 O(log n)，不用每次重传集合
  • 就绪链表：内核通过回调把就绪 fd 直接挂到链表，epoll_wait 只需取链表，O(1)
  • 无 fd 数量上限（受限于内存与文件句柄数）
  • 三函数：epoll_create / epoll_ctl / epoll_wait
水平触发（LT）与边缘触发（ET）—— 追问点 LT（默认）：只要缓冲区还有数据就一直通知，编程简单，容错好。 ET（高性能）：只在状态变化时通知一次，必须一次把数据读干净并循环处理，否则剩余数据会「丢」，编程复杂但系统调用更少。 Netty 默认用 ET（配合非阻塞读循环），这是它吞吐高的原因之一。 面试加分句：「epoll 并没有消灭阻塞，它只是把『等待多个连接』变成了一次系统调用；真正的非阻塞建立在 ET + 循环读之上。」

8.3 Reactor 模型：Tomcat 与 Netty 的分野

模型结构代表
单 Reactor 单线程一个线程做 accept + read + 业务Redis 的命令处理（单线程但极快）
单 Reactor 多线程一个线程做 IO，业务交给线程池Tomcat 的 NIO 模型
主从 Reactor 多线程MainReactor 只做 accept，SubReactor 做 IO，业务再进线程池Netty 默认模型
为什么「Redis 单线程却很快」和「Tomcat 要多线程」不矛盾 因为瓶颈位置不同。Redis 的操作是纯内存 + 无阻塞，单线程反而避免了锁竞争与上下文切换，CPU 几乎全用在计算上； Tomcat 的业务代码会阻塞在数据库、下游 RPC、磁盘 IO 上，此时线程在傻等，多线程才能提高 CPU 利用率。 一句话总结：CPU 密集看单线程，IO 密集靠多线程。 这个对比答出来，面试官会认为你真正理解并发的本质。

8.4 Tomcat 的三个关键参数（高频必背）

参数含义配错的后果
maxThreads处理请求的工作线程池上限（默认 200）太小 → 请求排队；太大 → 线程上下文切换开销大，且会把压力打给数据库
maxConnections同时可接受并处理的连接数（NIO 默认 10000）超过后 Tomcat 不再 accept，连接留在操作系统队列里
acceptCount全连接队列长度（默认 100）。队列满了，新连接直接被拒或超时太小时突发流量会丢连接，用户看到「连接超时」而不是「服务繁忙」
口语模板（被问「Tomcat 怎么调优」） 「这三个参数是一层套一层的关系： 连接先进 acceptCount 队列；被 accept 后进入 maxConnections；真正交给 maxThreads 个线程去执行。 所以调优顺序应该是自内向外：先确定线程池应该多大—— 如果每个请求都要查一次数据库，而数据库连接池只有 50，那把 maxThreads 调到 500 只会让更多线程去抢连接、排队更长， 反而变慢。所以我一般让 maxThreads 略大于连接池大小，再根据压测结果调。 核心原则：并发能力由整条链路上最窄的那个环节决定，单独调一个参数没有意义。」
高频追问（先自测，再展开）
为什么「每请求一线程」模型在高并发下会出问题？
因为线程是重量级资源：每个线程占用约 1MB 栈空间，创建/销毁与上下文切换都有开销。当并发上万时：① 线程栈内存消耗巨大；② CPU 大量时间花在上下文切换而非计算（观察指标：cs 上下文切换数飙升、CPU sy 占比高）；③ 线程池满后请求在队列里堆积，响应时间急剧恶化。解法演进路线：线程池调优 → 异步 Servlet / 响应式（WebFlux、Netty，少量线程处理大量连接）→ 虚拟线程（JDK 21），把「每请求一线程」的编程模型保留下来但成本降到极低。能说出虚拟线程这一层，说明你在关注技术演进。
为什么高并发下 CPU 不高但服务已经不可用了？
这是「等待型雪崩」的典型特征。线程都阻塞在等待上——等数据库响应、等下游 RPC、等锁、等连接池归还。关键现象：CPU 空闲、但 RT 爆炸、吞吐归零。排查手段：jstack 抓线程栈，看大量线程卡在哪个方法；jstack + grep 统计状态分布（大量 WAITING / TIMED_WAITING 指向 SocketRead）；连接池监控看 activeCount 是否打满。结论：CPU 高和 CPU 不高是两类完全不同的故障，先分类再排查，能省掉大量时间。
零拷贝是什么？在链路哪里用得上？
传统 read + write 要经历「磁盘 → 内核缓冲 → 用户缓冲 → socket 缓冲 → 网卡」，4 次拷贝、4 次上下文切换。零拷贝（sendfile、mmap、splice）让数据不经过用户态，直接在内核里搬运，减少到 2 次拷贝。链路中的位置：Nginx 返回静态文件、Kafka 写盘与发送、Netty 的 FileRegion。这就是「Nginx 发静态文件比 Tomcat 快得多」的底层原因之一。
IO 多路复用和异步 IO 到底差在哪？
多路复用（epoll）是「同步非阻塞」：内核告诉你「可以读了」，但读数据这个动作还是要你自己做（会阻塞在这一个 fd 的读上）。真正的异步 IO 是「内核告诉你已经读完了」，数据已经拷到你的缓冲区，应用完全不参与。io_uring 是 Linux 上真正成熟的异步 IO 方案，被广泛看好。面试时如果能明确指出 epoll 属于同步 IO（这是常见的概念混淆点），是很好的加分项。
一个 HTTP 请求在 Tomcat 内部经历了哪些组件？
Tomcat 是分层容器：
Connector（Coyote）接收并解析报文 → Engine（引擎，可含多个 Host）→ Host（虚拟主机，按域名区分）→ Context（一个 Web 应用，即你的 war/应用）→ Wrapper（一个 Servlet，在 Spring Boot 里就是那个唯一的 DispatcherServlet）。
核心洞察：Spring Boot 内嵌 Tomcat 后，你的整个应用就是一个 Context，而 Wrapper 只有一个 DispatcherServlet——所有请求最终都汇聚到它。理解了这一点，「为什么 Spring MVC 的性能瓶颈不在匹配路由」就说得通了。

必背三组：IO 五模型（阻塞 / 非阻塞 / 多路复用 / 信号驱动 / 异步）； epoll 三函数 + 红黑树 + 就绪链表；Tomcat 三参数（maxThreads / maxConnections / acceptCount）。

机制所属层次能拿到什么典型用途

9.3 参数绑定与校验

注解来源注意点
@PathVariableURL 路径变量 /user/{id}路径参数要防越权（改 ID 就能看别人数据）
@RequestParamQuery String 或表单可设 required=false 与默认值
@RequestBody请求体，只能读一次流只能读一次，Filter 里读过就会导致后续为空——这是经典坑
@RequestHeader请求头常用于取 Authorization、X-Trace-Id
@ModelAttribute表单字段自动封装对象传统 MVC 用法
❌ 危险写法 @GetMapping("/order/{id}") 里只校验了登录， 然后直接 orderService.findById(id) 返回。
用户改一下 ID 就能看别人的订单——这是真实世界最高频的数据泄露原因，叫越权访问。
✅ 正确写法 查询条件里必须带上当前登录用户： WHERE id = ? AND user_id = ?； 或者查出后显式校验归属，不匹配就抛 403。
原则：任何涉及资源的接口，都必须做数据归属校验。
服务端校验是安全底线，不是「重复劳动」 前端校验只是为了体验好（少一次往返），服务端校验才是唯一可信的防线—— 请求可以完全绕过前端直接发送（Postman、curl、抓包重放）。 实践上要做三层：① 参数格式校验（@Valid + Bean Validation，拦截格式错误）； ② 业务规则校验（余额是否够、状态是否允许，在 Service 层）； ③ 权限校验（数据归属、角色权限）。 只做第一层是最常见的疏漏。

9.4 统一异常处理与统一响应

统一响应结构
  • { code, message, data } 三段式
  • 让前端能统一处理，而不是每个接口一套结构
  • HTTP 状态码 + 业务码并存：HTTP 表示传输层结果，业务码表示业务结果
异常分类设计
  • 业务异常（余额不足、订单已取消）：可预期，返回 4xx + 明确提示，不记 error 日志
  • 系统异常（NPE、DB 连接失败）：不可预期，返回 500 + 泛化提示，必须记 error 日志并告警
  • 区分二者的意义：避免业务异常刷屏告警，让真正的故障不被淹没
两条安全红线 ① 不要把原始异常信息返回给前端。 堆栈里可能包含 SQL 语句、数据库表结构、内部文件路径、类名——这些都是攻击者的情报。 对外只返回泛化的错误码和用户可读的提示，真实堆栈只进服务端日志。
② 不要 catch (Exception e) {} 吞掉异常。 静默失败会让问题在很久之后以更诡异的形式爆发（数据不一致），排障成本极高。 至少要记日志，或者包装成业务异常往上抛。
高频追问（先自测，再展开）
为什么 Filter 里读过请求体，Controller 里就拿到了空值？
因为 HttpServletRequest 的输入流是只能读一次的（底层是 socket 流，读完就没了，无法 reset）。Filter 里调用 getInputStream() 或 getReader() 读了之后，后面的 @RequestBody 就只能是空。解法：用 ContentCachingRequestWrapper 包装请求，它把读过的内容缓存起来，允许重复读。需要注意这个 Wrapper 必须显式传下去（chain.doFilter(wrapper, response)），否则下游拿到的还是原对象。这也是「接口防重放需要读 body 签名」时的必备技巧。
Interceptor 和 Filter 的执行顺序是什么？
顺序是：Filter.doFilter 前置 → Interceptor.preHandle → Controller → Interceptor.postHandle → Interceptor.afterCompletion → Filter.doFilter 后置。多个 Filter 按 @Order 或注册顺序执行，前置正序、后置倒序（类似洋葱模型）。实践要点：跨域 CorsFilter 必须排在最前面，因为预检请求不带凭证，如果被后面的鉴权 Filter 拦掉就会返回 401，跨域永远过不去——这是线上最常见的配置错误。
Spring MVC 怎么找到 URL 对应的那个方法？
启动时 RequestMappingHandlerMapping 扫描所有 @Controller 里的 @RequestMapping，为每个方法构造一个 RequestMappingInfo（含路径、方法、参数条件、Header 条件、consumes/produces），注册到多棵 Trie 树或映射表里。运行时按 URL 做最长匹配 + 条件过滤，得到 HandlerMethod，再在一堆 HandlerAdapter 里选一个能处理它的（通常是 RequestMappingHandlerAdapter）。加分点：路径匹配支持通配与正则，但复杂正则会让匹配变慢——不要把正则用在超高频接口的路径上。
接口幂等怎么做？在链路的哪一层做？
位置：Service 层，且必须在事务内用唯一约束保证。方案优先级：
① 数据库唯一索引（最可靠，用「订单号」做主键或唯一键，插入冲突即视为重复请求）；
② 去重表（记录业务唯一键 + 处理状态）；
③ Redis SETNX（快，但有丢失风险，适合作为前置拦截）；
④ 状态机（订单状态只能从「待支付」到「已支付」，重复调用直接返回成功，是天然的幂等）。
注意：幂等必须做到「第一次的响应能被第二次复用」——即重复请求返回与首次相同的结果，而不是报错。这需要把首次的响应结果也存下来。
为什么说「Controller 层不应该有业务逻辑」？
三个理由：
① 事务边界——事务要加在 Service 层，如果把业务写在 Controller，事务注解要么失效要么范围过大；
② 复用性——同一段业务逻辑可能被 HTTP 接口、定时任务、MQ 消费者、RPC 接口共同调用，放在 Controller 里就无法复用；
③ 可测试性——Controller 依赖 Web 上下文，单测要起 MockMvc，而 Service 是纯 POJO，单测成本低得多。
Controller 的唯一职责：把 HTTP 协议世界翻译成 Java 对象世界，再把结果翻译回去。

三层拦截记住「Filter 管进没进门、Interceptor 管去哪个房间、AOP 管房间里干什么」； 两大坑：请求体只能读一次、同类内部调用 AOP 失效。

阶段 ④ 服务端处理 Service 业务、事务与数据层

10.1 分层结构与事务边界

层职责绝对不要做的事
Controller协议转换：HTTP ↔ Java 对象、参数校验、组装响应不写业务、不直接访问 DAO、不加事务
Service业务编排、事务边界、多个 DAO 的组合、跨服务调用不做 HTTP 相关处理（拿不到也不该拿 request）
DAO / Mapper纯粹的数据访问，一条 SQL 一件事不写业务判断、不跨表组装复杂逻辑
Entity数据库表的映射不直接返回给前端（会泄露表结构、暴露可写字段）
DTO / VO接口的输入输出契约不含持久化注解
为什么 DTO 和 Entity 必须分开（高频追问） 「全用 Entity 打天下」是新人最典型的坏味道，会造成三个真实问题：
① 安全风险——前端可以提交 balance、isAdmin 这类敏感字段，如果直接绑定到 Entity 落库就出事（称为批量赋值漏洞）；
② 契约脆弱——数据库加一个字段、改一个名字，接口契约就被动改变了，前端可能因此崩溃；
③ 序列化问题——双向关联（订单 ↔ 用户）会导致 Jackson 无限递归，报 StackOverflowError；懒加载对象在事务外访问会抛 LazyInitializationException。
一句话结论：Entity 是「数据库的形状」，DTO 是「接口的形状」，两者的变化原因不同，必须解耦。

10.2 事务：@Transactional 的七个传播行为

传播行为语义典型场景
REQUIRED（默认）有事务就加入，没有就新建90% 的场景
REQUIRES_NEW总是新建独立事务，挂起外层事务记录日志、发送通知——即使主业务回滚，日志也要留下
NESTED嵌套子事务，子事务回滚不影响外层（靠 Savepoint）批量处理中「单条失败不影响其他条」
SUPPORTS有则加入，没有就以非事务方式执行只读查询
NOT_SUPPORTED以非事务方式执行，挂起当前事务调用不支持事务的外部接口
MANDATORY必须在事务中，否则抛异常强制约束调用方
NEVER必须不在事务中，否则抛异常极少使用
事务失效的六种场景（面试高频，务必背下来） ① 方法非 public（CGLIB 代理无法拦截）；
② 同类内部调用（this.method() 绕过代理）；
③ 异常被自己 catch 了没抛出（Spring 感知不到，不会回滚）；
④ 抛的是受检异常（默认只对 RuntimeException 和 Error 回滚，需配 rollbackFor = Exception.class）；
⑤ 类没有被 Spring 管理（自己 new 出来的对象）；
⑥ 数据库引擎不支持事务（MyISAM）。
记忆口诀：「不 public、自己调、被吞掉、受检抛、没托管、没引擎」。

10.3 事务内绝对不要做的三件事

❌ 在事务里做远程调用
  • RPC 超时可能几秒，期间数据库行锁一直被持有
  • 其他请求全部阻塞 → 连接池耗尽 → 雪崩
  • 且远程调用无法回滚，「本地回滚了但远程已执行」
❌ 在事务里发 MQ 消息
  • 消息已发出但事务回滚 → 下游收到脏数据
  • 事务先提交后发消息 → 发消息失败 → 下游丢事件
  • 正解：本地消息表 / 事务消息 / 发件箱模式
❌ 在事务里循环大量操作
  • 循环里逐条 update，事务极长
  • undo log 撑大、锁持有时间线性增长
  • 正解：批量 SQL，或拆成多个短事务
❌ 在事务里做耗时计算/文件 IO
  • 任何「不访问数据库但很慢」的事都是浪费锁持有时间
  • 原则：事务内只做数据库操作，且尽量短
口语模板（被问「长事务有什么危害」） 「长事务的危害有三层，而且是层层递进的： 第一层，它持有行锁时间长，其他请求等待，直接拉高 RT； 第二层，它占用数据库连接不归还，连接池被慢慢耗干，于是所有接口都开始排队， 这时表面上看是「服务整体变慢」，实际根因只是一个接口的事务太长； 第三层，它对 MySQL 内部也有伤害——undo log 无法及时清理，回滚段膨胀，MVCC 读需要遍历更长的版本链，连只读查询都会变慢。 所以我的原则是：事务内只做数据库操作，绝不包含远程调用、消息发送和耗时计算。」

10.4 数据访问：从连接池到索引

借连接
HikariCP→ SQL 解析→ 执行计划

关键点面试要点
连接池大小不是越大越好。经验公式：连接数 ≈ CPU核数 × 2 + 磁盘数。连接过多会导致数据库频繁上下文切换与锁竞争，反而更慢。而且连接数与线程池要匹配：线程数远大于连接数时，大量线程在抢连接，等于把排队从应用层搬到了数据库层
连接泄漏异常路径没归还连接 → 连接池逐渐耗尽 → 服务假死。排查手段：HikariCP 的泄漏检测（leakDetectionThreshold）、SHOW PROCESSLIST 看长时间 Sleep 的连接
索引B+ 树，矮胖、叶子成链。必答：聚簇索引（主键，存整行）vs 二级索引（存主键值，需要回表）、最左前缀、覆盖索引避免回表、索引失效场景（函数、隐式类型转换、前导模糊、OR、不符合最左前缀）
锁InnoDB 行锁加在索引上，没走索引的更新会升级为锁全表——这是高并发下最致命的性能陷阱。间隙锁（Gap Lock）用于防幻读，但也更容易死锁
MVCC通过 undo log 版本链 + ReadView 实现「读不加锁」，这是「可重复读」的实现基础。面试加分点：MVCC 只解决快照读，当前读（SELECT ... FOR UPDATE）仍然要加锁
慢查询EXPLAIN 看 type（要避免 ALL）、key（实际用的索引）、rows（扫描行数）、Extra（出现 Using filesort / Using temporary 就要警惕）

10.5 缓存：链路中最容易出错的一环

问题成因解法
穿透查询不存在的数据，缓存永远不命中，每次都打到数据库缓存空值（短 TTL）、布隆过滤器前置拦截、参数合法性校验
击穿单个热点 key 过期瞬间，大量并发请求同时打到数据库互斥锁（只让一个请求回源）、逻辑过期（不过期，异步更新）、热点数据永不过期

缓存一致性：标准答案应该这样组织 第一步，先承认不可能强一致。只要缓存和数据库是两个系统，就一定会有一致性窗口，目标是把窗口控制到业务可接受。
第二步，选策略。主流是 Cache Aside + 先更新库再删缓存。为什么是「删除」而不是「更新」？ 因为更新的值可能来自并发计算的旧快照，而删除是幂等的、更安全。
第三步，讲清极端场景。「先更新库再删缓存」在读请求恰好在此期间回填了旧值时会短暂不一致，所以引出 延迟双删（写完后延迟几百毫秒再删一次）或 订阅 binlog 异步删（更可靠）。
第四步，给兜底。关键数据设短 TTL 自动兜底，并保证业务读缓存时能容忍短暂旧值（如商品详情页）， 而强一致的场景（余额、库存扣减）必须直接读库，不走缓存。

10.6 异步与下游调用

消息队列的三种价值
  • 异步：下单后发积分、发通知不阻塞主流程
  • 解耦：订单服务不需要知道有几个下游
  • 削峰：秒杀流量先入队，按能力消费
  • 代价：一致性从「同步强一致」变成「最终一致」，必须处理丢失、重复、乱序
RPC 调用的四大配套
  • 超时：不设超时 = 线程永久阻塞
  • 重试：只对幂等操作重试，且要退避
  • 熔断：下游持续失败就快速失败，避免线程被拖住
  • 降级：返回兜底数据，保证整体可用
  • 核心认知：本地调用不会失败，远程调用一定会失败
「至少一次」与幂等：MQ 场景的必答组合 主流 MQ 保证的是 At Least Once（至少一次），意味着消息一定会重复。 所以消费端必须幂等。实现方式：① 业务唯一键 + 数据库唯一索引（最可靠，插入冲突即忽略）； ② Redis 记录已处理的消息 ID（要注意与业务操作在同一事务边界内，否则会丢）； ③ 状态机判断（订单已支付就不再处理）。 面试时主动说「Exactly Once 在分布式下是不可能的，工程上只能用『至少一次 + 幂等』来等价实现」——这句话的分量很重。
高频追问（先自测，再展开）
为什么连接池不是越大越好？
很多人直觉认为「连接多 = 并发高」，实际相反。数据库的瓶颈通常在CPU、磁盘 IO 和锁竞争上——连接多了，只会让更多请求同时争抢同一批资源，增加上下文切换与锁等待，吞吐不升反降。经典公式是 连接数 ≈ CPU核数 × 2 + 有效磁盘数。更重要的推论：如果 Tomcat 有 500 个线程，而连接池只有 50，那 450 个线程都在抢连接——把「应用层排队」变成了「数据库层排队」，故障排查时会更难定位。所以两者必须匹配，并通过压测找拐点。
乐观锁和悲观锁怎么选？
悲观锁（SELECT ... FOR UPDATE）：假设冲突一定发生，先锁住再操作。实现简单、正确性高，但吞吐低，且不适合长事务。适合写冲突激烈且必须串行的场景，如扣库存。
乐观锁（version 字段 + CAS 更新）：假设冲突很少，更新时校验版本，失败则重试。吞吐高，但冲突激烈时重试成本飙升，而且失败要由业务处理。
选择依据是「冲突概率」：冲突少用乐观锁，冲突多用悲观锁或改成队列串行化。补充：如果更新能写成「带条件的原子 SQL」（UPDATE stock = stock - 1 WHERE id=? AND stock >= 1），那就不需要显式加锁——这是最优雅的做法，利用数据库自身的原子性。
为什么 UPDATE 没走索引会锁全表？
因为 InnoDB 的行锁是加在索引记录上的，而不是加在「行」这个概念上。如果 WHERE 条件没有可用索引，存储引擎就必须扫描所有记录才能确定哪些行需要更新；在这种情况下，它会锁住扫描路径上经过的所有记录——效果等同于锁表。这是高并发下最危险的性能陷阱：一条漏了索引的 UPDATE 能让整个系统的写入排队。排查方法：SHOW ENGINE INNODB STATUS 看锁等待，或查 information_schema.INNODB_TRX。
接口 P99 突然从 50ms 涨到 3s，怎么排查？
按「先定位环节，再定位代码」的顺序：
① 看大盘：是所有接口慢，还是某一个接口慢？所有接口慢 → 怀疑基础设施（DB、Redis、网络、GC）；单个接口慢 → 看该接口的变更。
② 看资源：CPU（是不是 GC 时间占比高）、内存（有没有频繁 Full GC）、连接池（activeCount 是否打满）、线程池（队列是否堆积）。
③ 看依赖：是否有慢 SQL、下游 RPC 是否变慢（链路追踪直接看得到）。
④ 看代码：jstack 抓线程栈，把线程按状态分组统计——如果大量线程卡在同一个方法上，那就是元凶。
⑤ 看变更：最近有没有发版、有没有数据量突增、有没有定时任务重叠。
面试要点：一定要体现出「分层排除」的思路，而不是一上来就说「去看日志」。
什么是「无状态服务」？为什么它重要？
无状态指服务实例本身不保存任何与请求相关的状态，所有状态都外置到 Redis / DB。
为什么重要：① 可以任意扩缩容——新实例随时能接管任何请求；② 可以随意重启/发布——不丢数据；③ 可以故障转移——一台挂了请求转到别的机器没有任何影响。
反面案例：把用户会话存在应用内存里（本地 Session）、把上传文件的临时状态放在本地磁盘、在单例 Bean 里存 ThreadLocal 之外的可变成员变量。
一句话：云原生的前提是无状态。有状态的部分必须交给专门的中间件。
序列化为什么会影响接口性能？
三个层面：① CPU——JSON 序列化是纯 CPU 操作，大对象、深层嵌套、循环引用都会显著消耗 CPU，高并发下会成为瓶颈；② 体积——字段名重复、null 值、精度冗余（BigDecimal 全精度输出）都会放大响应体，直接增加传输时间；③ 内存——构造大 DTO 会产生大量临时对象，加剧 GC 压力。
优化手段：用 @JsonInclude(NON_NULL) 剔除空字段、分页与字段裁剪（GraphQL 或 fields 参数）、避免返回嵌套过深的聚合对象、必要时改用 Protobuf 等二进制协议。一个真实经验：一个返回 5MB JSON 的接口，改成分页 + 字段裁剪后，P99 从 2s 降到 200ms——瓶颈根本不在数据库。

11.2 序列化的常见坑（全栈交叉区，追问浓度高）

问题现象解法
Long 精度丢失后端 ID 是 1234567890123456789，前端拿到变成 ...800JS 的 Number 只能安全表示 2^53。后端必须把 Long 序列化成字符串（@JsonSerialize(using = ToStringSerializer.class) 或全局配置）。这是前后端联调最经典的翻车点
日期格式不统一有时是时间戳，有时是 2026-09-14T12:00:00.000+08:00，还有时差 8 小时全局配置统一格式与时区（spring.jackson.time-zone=GMT+8），推荐直接用 ISO-8601 或时间戳，并明确约定
null 字段一堆响应体里大量 "field": null，体积浪费严重@JsonInclude(NON_NULL)；但注意有些前端依赖字段存在，改之前要沟通
循环引用订单里有用户，用户里有订单列表 → StackOverflowError用 DTO 打破循环、@JsonIgnore、@JsonBackReference。根治方式是 DTO 隔离
懒加载异常JPA 场景下报 LazyInitializationException在事务内完成数据装配再转 DTO；不要在序列化阶段才触发懒加载
BigDecimal 全精度输出金额返回 19.9900000000000000001统一设 scale 与舍入模式，序列化时格式化
Long 精度丢失：一个能让联调卡半天的经典问题 Java 的 long 是 64 位，JS 的 Number 是双精度浮点，安全整数上限只有 2^53 - 1。 所以雪花算法生成的 19 位 ID 一定会失真——而且是「查得到但查不对」的诡异现象：前端拿 1234567890123456789 去请求， 实际发出去的是 1234567890123456800，后端查不到数据。 标准解法：后端序列化成字符串 + 前端按字符串处理。 顺带一提，这也是「为什么有些接口的 ID 是 string 类型」的原因——不是设计随意，而是被迫的。

11.3 响应头决定接口的「能力」

响应头作用配错的后果
Content-Type告诉浏览器怎么解析响应体配错会导致下载而非渲染，或中文乱码（缺 charset）
Content-Encoding声明压缩算法（gzip / br）与 Vary 不匹配会被 CDN 缓存污染
Cache-Control缓存策略接口误设为 public → 用户私有数据被 CDN 缓存并泄露给他人
ETag / Last-Modified协商缓存校验缺少则每次都全量传输
Set-Cookie下发 Cookie漏了 HttpOnly / Secure / SameSite → XSS 可直接窃取凭证
Access-Control-*跨域授权错误响应没带 CORS 头 → 前端只能看到「CORS 错误」，看不到真正的 500
Content-Length / Transfer-Encoding声明响应体长度流式响应（SSE、大文件）必须用 chunked，否则连接会被提前关闭
Cookie 的三个安全属性，一次说清 HttpOnly：禁止 JS 读取，防 XSS 窃取 token（这是最重要的一条）；
Secure：只在 HTTPS 下发送，防中间人嗅探；
SameSite：限制跨站携带，防 CSRF。Lax 是现代浏览器默认值。
实践建议：认证凭证放 HttpOnly + Secure + SameSite=Lax 的 Cookie，而不是 localStorage。 localStorage 里的 token 一旦页面有 XSS 就直接被拿走，而且无法被服务端限制。这也是「token 该放哪」这道题的标准答案。

11.4 压缩与传输优化

压缩算法压缩率适用
gzip中通用支持度最好，性价比高。一般能压到 20~30%
br（Brotli）高比 gzip 再小 15~20%，现代浏览器都支持，静态资源首选
zstd高 + 极快压缩与解压都很快，新项目值得考虑
不压缩—已压缩格式（图片、视频、zip）不要再压，纯浪费 CPU
一条安全红线：压缩比率不能太高 如果同时存在「攻击者可控的输入」和「敏感数据」并一起压缩，攻击者可以通过观察压缩后的长度变化推断出敏感内容—— 这就是 BREACH / CRIME 攻击。缓解手段：对包含敏感信息的响应禁用压缩，或把 CSRF token 与用户输入分开响应。 能主动提到这一点，说明你在安全上有真实认知。
高频追问（先自测，再展开）
统一响应包装 {code, message, data} 有什么争议？
它是实践与规范的权衡。好处：前端只需写一次拦截器就能统一处理错误、统一提示。争议有三点：
① 与 HTTP 语义重复——HTTP 状态码本就能表达成功/失败，再套一层业务码会让「HTTP 200 但业务失败」成为常态，监控与网关的熔断策略会失效（网关按 HTTP 状态码统计错误率，全是 200 就看不出故障）；
② 破坏 RESTful 的直观性；
③ 冗余（每次多几个字节）。
成熟做法：HTTP 状态码表达「协议层结果」，业务码表达「业务结果」，两者都保留。比如余额不足返回 HTTP 400 + 业务码 1001，而不是 HTTP 200 + 业务码 1001。
响应体太大怎么办？
按优先级：① 分页（最基础，但要避免深分页——LIMIT 1000000, 20 会扫描并丢弃百万行，应改用「基于游标/上次最大 ID」的方式）；
② 字段裁剪（列表接口不返回详情字段）；
③ 压缩（gzip/br）；
④ 流式返回（SSE / 分块，让首字节尽早到达，改善感知性能）；
⑤ 异步导出（超大结果走「提交任务 → 轮询/通知 → 下载文件」）。
注意：把 10 万条数据做成一个 JSON 返回，是最常见也最容易被面试官抓住的设计缺陷。
为什么网关的错误响应也要带 CORS 头？
因为浏览器判断跨域是否允许，看的是最终返回的那个响应的 CORS 头。如果请求因为鉴权失败被网关返回 401，而 401 响应里没有 Access-Control-Allow-Origin，浏览器就会把它当成跨域失败——前端控制台只会显示「CORS 错误」，完全看不到 401 这个真实原因。这会导致排查方向完全跑偏。所以 CORS 头必须在最外层（网关或统一的 Filter）无条件添加，甚至要早于鉴权执行。
服务器推送（SSE）和 WebSocket 在这个链路里有什么区别？
SSE 基于普通 HTTP，响应 Content-Type: text/event-stream，服务器持续写入、连接不断开，单向（服务端 → 客户端），浏览器原生支持 EventSource，会自动重连。WebSocket 通过 HTTP 的 Upgrade 头完成协议升级，之后就是全双工，但不再走 HTTP 语义。
选择依据：只需要服务端推（通知、大模型流式输出）用 SSE，简单且能复用鉴权与网关；需要双向实时（聊天、协同编辑、游戏）用 WebSocket。注意 SSE 受 HTTP/1.1 的 6 连接限制，HTTP/2 下没有这个问题。

阶段 ⑤ 浏览器渲染 接收响应、进程切换与导航提交

数据交棒的时刻：从网络进程移交给渲染进程

面试热度 ★★★★
一句话答案 网络进程收到响应后先看状态码：3xx 则按 Location 重新走一遍流程； 304 则直接用本地缓存 copy；200 则继续。 然后根据 Content-Type 决定去向——是 text/html 就交给渲染进程， 是二进制附件就走下载分支。 浏览器为这个站点分配一个渲染进程（受站点隔离约束）， 通过网络进程与渲染进程之间的 IPC 把响应体移交过去，这一动作叫 「提交导航」（Commit Navigation）。 至此，页面进入渲染管线。

一个容易被问到的细节：渲染进程是怎么选的？ 浏览器的策略是「按站点（Site）复用」： 同一站点的多个标签页会共用同一个渲染进程（省内存）； 不同站点则强制隔离（安全，即 Site Isolation）。 如果新 URL 与当前页面同站点，会直接复用当前渲染进程； 否则新建一个。 面试加分点：这也解释了「同站点的一个标签页崩了，另一个也白屏」这种现象。

12.3 缓存与重定向：两个容易讲错的地方

❌ 常见错误说法 「304 是从缓存重新发的请求」—— 方向错了。304 是浏览器发请求、服务端确认没变，服务端依然参与了，只是不返回响应体。 所以 304 不能省掉往返，只省响应体。
✅ 准确说法 强缓存命中根本不发请求（最快）； 协商缓存命中要发请求、返回 304（省响应体）。 两者的性能差异在于「有没有那次往返」。
重定向类型浏览器行为对链路的影响
301 / 308被强缓存下一次访问直接跳转，不请求原地址。配错极难回滚——用户浏览器会一直跳错
302 / 307不缓存每次都请求原地址再跳转，多一个往返
HTML meta refresh解析到才跳比 3xx 慢，且用户能感知到停顿，一般只做兜底
HTTPS 降级与重定向的成本 「http → https 重定向」会带来额外一个完整往返（DNS 可能已缓存，但 TCP + TLS 要重来）。 所以生产环境应尽量做到首次请求就是 https—— 手段是 HSTS（浏览器记住，后续直接用 https）和 HSTS Preload（内置列表，连第一次都跳）。 面试时把「重定向不是免费的」这句话说出来，很有说服力。
高频追问（先自测，再展开）
为什么接口返回了数据，页面却没更新？
可能的原因按概率排序：① 请求被后续导航取消（用户提前点了别的）；② 响应被浏览器拦截（CORS），服务端执行了但 JS 拿不到；③ 前端状态更新了但没触发渲染（未正确触发响应式，或改了对象的深层属性）；④ 渲染被长任务阻塞，画面还没刷新；⑤ 命中了强缓存返回了旧数据。排查方法：在 Network 面板看该请求的 Status 与 Size 列，能立刻区分「网络问题 / 缓存问题 / 前端问题」。
请求被取消（canceled）是什么原因？
① 页面导航：用户在请求返回前点击了链接，所有未完成的请求会被取消；② 组件卸载：SPA 中路由切换导致请求被中止（常见于未做清理的 fetch）；③ 重复请求：同一 URL 短时间内发出多个请求，浏览器可能取消部分并用缓存；④ 主动 abort：代码里用了 AbortController。关键影响：被取消的请求服务端可能已经执行完了——所以「用户点两次提交」这类场景必须在服务端做幂等。
为什么点击下载链接后页面不会跳转，但表单提交会？
因为浏览器在收到响应后根据 Content-Type 决定行为。如果服务器返回 Content-Type: application/octet-stream 或带 Content-Disposition: attachment，浏览器就不启动渲染流程，直接把响应体交给下载管理器。而表单提交的响应是 text/html，就会走渲染。推论：不要让后端接口在错误情况下意外返回二进制类型，否则浏览器会莫名其妙地弹出下载。另外，<a download> 属性可以强制触发下载，但跨域时该属性可能被忽略（安全限制）。
为什么刷新页面时弹出了「确定要重新提交表单」？
因为上一次导航是通过 POST 完成的，浏览器缓存了这个 POST 请求的上下文，刷新会重放该请求。浏览器为防误操作弹出确认框。标准的解决方案是 PRG 模式（Post-Redirect-Get）：POST 处理完成后返回一个 302 重定向到结果页，这样浏览器最后停在的是一个 GET 请求，刷新就不会重放 POST。这是「为什么表单提交后要用重定向」这个老问题的正解，也是幂等思想的经典应用。

四判断（状态码 / Content-Type / 安全头 / 是否当前导航）；一句关键：HTML 才渲染，其他都可能变成下载。

阶段 ⑤ 浏览器渲染 HTML 解析与 DOM 构建

把一堆字节变成一个树形结构；同时决定哪些资源会被发现和下载

面试热度 ★★★★★
一句话答案 HTML 解析器把字节流按编码解码成字符，再经词法分析（Tokenization）变成一个个 Token （开始标签、属性、文本、结束标签），然后由树构造器（Tree Construction）按 HTML 规范把它们组装成 DOM 树。 解析过程是流式的、边下边解析的，并带有大量容错处理（闭合缺失标签、修正错误嵌套）。 同时浏览器会启动预扫描器（Preload Scanner），在解析的同时提前发现并并行下载 CSS、JS、图片等外部资源。 关键阻塞规则：<script> 会阻塞 DOM 解析（除非加 async/defer）；<link rel=stylesheet> 不阻塞解析，但会阻塞渲染，且会阻塞其后脚本的执行。

「流式解析」是一个容易忽略但很重要的特性 浏览器不需要等 HTML 全部下载完才开始解析——收到多少就解析多少，边解析边构建 DOM，边发现资源边开始下载。 这就是「为什么把首屏关键内容放在 HTML 前面更利于首屏时间」的原因： 更大的好处不是「传得快」，而是「更早被发现、更早开始渲染」。 面试时可以用这句话收尾：「HTML 的解析是全链路上唯一可以『边传输边处理』的环节，所以资源顺序本身就是性能优化手段。」

HTML 规范里有一整套明确的错误处理算法，规定了遇到未闭合标签、错误嵌套、非法字符时该怎么修。 这是 HTML 与 XML 最本质的区别——XML 报错停机，HTML 尽力而为。

13.3 资源加载与阻塞规则（必背）

资源 / 标签阻塞 DOM 解析阻塞渲染说明
<script>（无属性）✅ 阻塞✅必须下载并执行完才继续解析。这是最影响首屏的阻塞
<script async>❌ 不阻塞可能阻塞下载完立刻执行，执行顺序不确定。适合无依赖的独立脚本（统计埋点）
<script defer>❌ 不阻塞❌ 不阻塞等 DOM 解析完、按顺序执行，在 DOMContentLoaded 之前。适合需要操作 DOM 的业务脚本
<link rel="stylesheet">❌ 不阻塞✅ 阻塞不阻塞 HTML 解析，但浏览器会等 CSSOM 就绪才开始渲染；同时它会阻塞其后 script 的执行（因为脚本可能读样式）

@import（CSS 内）❌✅ 严重阻塞必须串行下载（解析到才发起），是公认的反模式，用多个 <link> 替代
为什么业界共识是「CSS 放 head，JS 放 body 底部」 CSS 放 head：让样式尽早开始下载，避免「先渲染无样式内容再闪一下」（FOUC）。它阻塞渲染但不阻塞解析，代价可接受。
JS 放底部或加 defer：因为 <script> 会阻塞解析，放在 head 会让整个页面的 DOM 构建停下来等它。 更关键的是：JS 放底部时，DOM 已经构建完，脚本可以直接操作 DOM，不会出现「找不到元素」——这也是它成为惯例的另一个原因。
现代最佳实践：用 defer 放 head 里——既能更早被发现和下载（预扫描器立刻看到），又不阻塞解析，还保证顺序。这是比「放底部」更优的方案。

13.4 预扫描器：一个被低估的加速机制

HTML 解析器遇到 <script> 就必须停下等它执行，此时后续资源都发现不了。 为此浏览器启动了一个独立的 预扫描器（Preload Scanner）： 它快速扫一遍后面的 HTML 文本，把显而易见的资源（script、img、link、iframe 的 URL）提前发起下载， 不解析复杂的 DOM 结构，只做 URL 提取。

预扫描器的「盲区」—— 一个很实用的知识点 预扫描器只能识别 HTML 里静态写死的资源。 如果资源是通过 JS 动态创建的（document.createElement('script')）、 或 CSS 里引用的（background-image、@font-face）、 或 由 JS 拼接的路径，它一概发现不了——必须等 JS 执行到那一行才发起请求，白白浪费了宝贵时间。 这就是「关键资源用 <link rel="preload"> 显式声明」的价值：把发现的时机从「JS 执行后」提前到「HTML 解析时」。 字体（webfont）是最典型的受害者——它藏在 CSS 里，发现得最晚，所以常出现文字闪烁（FOIT）。

高频追问（先自测，再展开）
async 和 defer 的区别？一张嘴说清。
共同点：都不阻塞 HTML 解析（都是并行下载）。
区别在执行时机：
async：谁先下载完谁先执行，顺序不可控，可能在 DOM 构建完成之前就执行。适合无依赖的独立脚本（埋点、广告）。
defer：等 DOM 解析完成后按出现顺序依次执行，在 DOMContentLoaded 之前。适合有依赖关系的业务脚本。
一句话记忆：async 是「谁快谁上」，defer 是「排队按序」。
补充：defer 对模块脚本 type="module" 是默认行为——这一点很多人不知道。
为什么要把 script 放底部，而不是加 defer？
现在的答案是：加 defer 更好，且应该放在 <head>。原因：① 发现更早——预扫描器在 head 时就能看到它并立刻开始下载，放底部则要等 HTML 解析到那一行；② 同样不阻塞解析；③ 保证执行顺序。
但有一个例外：如果脚本非常小且需要尽早执行（比如渲染前的主题切换，避免白屏闪烁），应该内联在 head 里，而不是外链——因为外链还要一次往返。「关键代码内联、非关键代码 defer」是更精细的答案。
为什么 document.write() 是危险的？
因为在文档解析完成后调用 document.write() 会隐式清空整个文档（相当于 document.open()），页面内容全部消失。另外它还会阻塞解析器，且对异步脚本、动态插入的脚本行为不一致。现代替代方案：innerHTML、insertAdjacentHTML、DOM API。唯一还算合理的用途是「同步注入一段用于测量/兜底的脚本」，但即便如此也要慎用。面试看到「document.write」出现在性能优化题里，基本可以判定为扣分点。
CSS 阻塞渲染，但如果 CSS 加载失败怎么办？
浏览器会对样式表设置超时，超时后继续渲染（用默认样式），避免页面永远白屏。这正是「CSS 阻塞渲染」不至于造成灾难的原因。但要注意：如果 CSS 挂在很慢的域名上，用户会看到一段较长的白屏，所以样式表必须放在自己的主域名（避免额外 DNS/TCP）并尽量精简。另一个关键点：<link> 后面如果有同步脚本，脚本会等 CSS 下载完才执行——这是 CSS 阻塞「间接」影响解析的路径。
defer 脚本和 DOMContentLoaded 谁先执行？
defer 脚本先执行。规范规定：所有 defer 脚本在 DOM 解析完成后、DOMContentLoaded 触发之前按顺序执行完，然后才触发 DOMContentLoaded。实践意义：在 defer 脚本里绑定的事件处理器，一定会在 DOMContentLoaded 之前就位，所以不会错过事件。而 async 脚本的执行时机与这两个事件完全无关，可能在它们之前或之后——这就是 async 不能操作 DOM 的原因。

两个关键机制：流式解析（边下边解）、预扫描器（提前发现资源）。 三属性区分：无属性阻塞、async 谁快谁上、defer 排队按序。

阶段 ⑤ 浏览器渲染 CSS 解析、样式计算与渲染树

每个 DOM 节点到底该长什么样——这一步的计算量常被严重低估

面试热度 ★★★★★
一句话答案 CSS 文本被解析成 CSSOM 树，然后与 DOM 树结合，经历三步样式计算： ① 收集匹配规则（为每个节点找出所有命中的选择器，匹配是从右往左做的）； ② 层叠与继承（按权重、来源、顺序决出胜负，继承属性从父节点取值）； ③ 生成 ComputedStyle（把相对值、百分比、关键字解析成绝对值）。 最终 DOM + CSSOM 合成 渲染树（Render Tree）——只包含需要显示的节点， 所以 display:none 的元素不在其中。 核心认知：浏览器为了「流式渲染」必须先把 CSSOM 建完整，因为后面的规则可能覆盖前面的——这就是 CSS 阻塞渲染的根本原因。

14.1 为什么 CSSOM 必须完整才能渲染

HTML 可以边解析边构建 DOM 并开始渲染（因为 DOM 是树状、增量的）； 但 CSS 不行——它的规则是平铺的、后写的可能覆盖前写的。 如果你先拿前 100 行 CSS 去渲染，等后面 500 行到达时，之前算出的样式可能全部作废。

这是「CSS 阻塞渲染」的底层原因 渲染不能基于「部分 CSS」开始，否则必然闪烁。 这直接推导出实践结论：关键 CSS 应内联在 HTML 里（内联的样式随 HTML 一起到达，不需要额外往返， 所以能立刻参与渲染），非关键 CSS 用 media 查询或异步方式延后加载。 这样能把首屏时间显著提前——这就是「关键 CSS 优化」的原理，而不是玄学。

14.4 为什么选择器匹配是「从右往左」

这是样式计算里最常被追问的细节。以 .list li.item a 为例：

从左往右（不可行） 先找所有 .list，再在它们内部找 li.item，再找 a。
问题：在树还没遍历到叶子时，你无法确定这条规则最终会不会命中， 导致必须遍历大量无关分支，路径爆炸。
从右往左（浏览器实际做法） 先找所有 a 元素（从右端锚点出发，候选集小）， 然后逐级向上验证祖先是否满足 li.item、.list。
一旦某一级不满足就立即剪枝，效率高得多。
由此推导出的实用结论 因为匹配是从右往左的，所以：
① 右侧选择器越具体越好——用 .item 比用 * 或裸标签好得多；
② 避免在右侧使用通配符，如 .list * { }，它会让候选集变成所有元素；
③ 深层嵌套代价高，如 .a .b .c .d .e，每多一层就多一轮祖先验证；
④ :nth-child 等需要计算位置的选择器更贵，因为它要统计兄弟节点；
⑤ BEM 这类扁平命名之所以被推崇，除了可读性，也有性能原因——单类名选择器匹配成本最低。

高频追问（先自测，再展开）
CSS 中的 @import 为什么是反模式？
因为 @import 里的样式必须等父样式表下载并解析完，才能发现并开始下载子样式表——这是串行瀑布。假设 3 层嵌套，就变成 3 次串行往返，首屏延迟成倍增加。而多个 <link> 是并行的。此外 @import 也无法配合现代的构建工具做代码分割与按需加载。结论：永远用构建工具把 CSS 打包成一个 <link>，或者用构建期处理代替 @import。
「重排」和「重绘」有什么区别？
重排（Reflow / Layout）：几何属性变化（宽高、位置、字体、内外边距、增删节点）→ 必须重新计算布局，可能连带影响所有后代与兄弟节点，开销最大。
重绘（Repaint）：只影响外观不影响几何（颜色、背景、阴影）→ 跳过布局，直接重新绘制，开销较小。
合成（Composite）：只改 transform / opacity → 连绘制都不用，GPU 直接合成，最快。
必背的性能结论：动画优先用 transform 和 opacity；不要用 top/left/width/height 做动画。
什么是「布局抖动（Layout Thrashing）」？
在循环中交替进行「读取布局信息」和「修改样式」，例如： 
for (let i = 0; i < items.length; i++) {
  items[i].style.width = items[i].offsetWidth + 10 + 'px';  // 读→写→读→写…
}
每次读取 offsetWidth 都会强制浏览器立即完成一次布局计算（因为要给你准确值）， 于是循环 N 次就触发 N 次同步重排。解法：先批量读、再批量写（用两个循环分开）， 或用 requestAnimationFrame、FastDOM 这类批处理工具。 易被强制同步布局的属性：offsetTop/Left/Width/Height、scrollTop、clientWidth、getComputedStyle()、getBoundingClientRect()——记住这几个名字，面试可以直接报出来。
CSS 变量（自定义属性）会影响性能吗？
会，但要看用法。静态使用时基本无额外开销（样式计算阶段就解析完了）。但如果用 JS 在运行时频繁修改 CSS 变量，会导致所有使用该变量的元素重新计算样式，如果变量定义在 :root 上，那就是整棵树——开销可能很大。实践建议：频繁变化的动画值用 transform 直接改内联样式，而不是通过改 CSS 变量；把变量定义在尽可能小的作用域上。
为什么「样式表加载失败」不会导致页面永久白屏？
因为浏览器对样式表设置了超时保护，超时后会用默认样式继续渲染。但要注意两个衍生问题：① 如果样式表卡在慢域名上，用户会经历一段较长的「无样式内容闪现」（FOUC）；② 更隐蔽的是，如果 <link> 后面有同步脚本，脚本会一直等样式表下载完才执行——此时表现是「HTML 解析停顿」，而不是「样式没生效」，排查时容易找错方向。正确做法：<link> 自己放前面，脚本用 defer。

阶段 ⑤ 浏览器渲染 JavaScript 执行与事件循环

唯一能「打断」渲染管线的东西；也是长任务卡顿的元凶

面试热度 ★★★★★
一句话答案 JS 由 V8 引擎执行：源码先被解析成 AST，再编译成字节码由解释器 Ignition 执行； 运行中被判定为「热点」的函数会被 TurboFan 即时编译（JIT）成机器码优化执行； 一旦假设不成立则去优化回退到字节码。 执行遵循 事件循环：调用栈清空后，先执行所有微任务（Promise、MutationObserver）， 再进行一次渲染机会（requestAnimationFrame → 样式 → 布局 → 绘制 → 合成）， 然后取下一个宏任务（定时器、I/O、事件回调）。 核心：JS 与渲染共用主线程——长任务会直接阻塞渲染，让页面卡住。

15.1 V8 的执行流程与优化机制

源码→ 词法/语法分析
建 AST→ Ignition
解释执行字节码→ TurboFan
热点 JIT→ 机器码
三个提升性能的语言层面概念
  • 隐藏类（Hidden Class）：V8 给对象维护一个「形状」，形状相同的对象共享访问路径，属性访问更快
  • 内联缓存（Inline Cache）：记住上次访问的属性偏移，下次直接命中
  • 去优化（Deopt）：如果对象形状突变、类型不稳定，优化代码作废，性能显著下降
由此得出的实用规则
  • 对象初始化时把所有属性都声明出来（避免后续动态增删属性导致隐藏类变更）
  • 不要让数组混装不同类型（元素类型不稳定）
  • 热函数里保持参数类型稳定（避免多态调用）
  • 这些规则解释了「为什么同样的逻辑，写法不同性能差好几倍」

15.2 事件循环与渲染时机（最容易画错的一张图）

类别包含执行时机
宏任务setTimeout、setInterval、I/O、UI 事件回调、postMessage、MessageChannel每轮事件循环取一个执行
微任务Promise.then/catch/finally、queueMicrotask、MutationObserver每个宏任务结束后全部清空，且新增的微任务会在本轮继续执行完
渲染requestAnimationFrame → 样式计算 → 布局 → 绘制 → 合成不是每个宏任务后都渲染，由浏览器按帧率决定（一般 60Hz / 16.7ms 一次）
「微任务饥饿」—— 一个能体现深度的点 因为微任务队列必须在下一帧渲染前被完全清空，如果某个微任务不断产生新的微任务 （例如递归的 Promise.then、无限 queueMicrotask）， 事件循环会永远停在清空微任务这一步，渲染永远轮不到——表现为页面完全冻结。 对比：如果用 setTimeout 递归，至少每轮之间还有机会渲染（虽然会卡但不会死）。 面试时提到这一点，能明显区分于只会背「微任务优先于宏任务」的候选人。

15.3 长任务与性能：为什么 JS 会阻塞渲染

问题的本质
  • JS 执行、样式计算、布局、绘制全都在主线程上，是互斥的
  • 主线程被 JS 占住时，用户输入也无法响应（点击没反应）
  • 长任务 = 超过 50ms 的任务，Performance 面板会明确标记
解法（按落地成本排序）
  • 时间切片：把大任务切成小块，每块结束后让出主线程（React 18 的并发渲染就基于此）
  • 让出主线程：requestIdleCallback 做低优先级工作；scheduler.yield() 是更新的方案
  • 搬离主线程：Web Worker 做纯计算，主线程只负责渲染
  • 减少 JS 体积：代码分割、按需加载、tree-shaking——解析和执行大包本身就是长任务
requestAnimationFrame 与 setTimeout 的本质区别 requestAnimationFrame：回调在渲染之前执行，由浏览器按帧对齐，页面不可见时会暂停（省电）。 setTimeout(fn, 16)：只是「至少 16ms 后放入宏任务队列」，执行时机与渲染帧不对齐， 可能在一帧内执行多次或跳过，导致动画抖动。
结论：所有视觉动画相关的时间调度都必须用 requestAnimationFrame，没有任何例外。 补充一个常被问的：setTimeout(fn, 0) 不是立即执行，而是「尽快放入宏任务队列」，规范上有最小 4ms 的延迟（嵌套多层时）。
高频追问（先自测，再展开）
一个页面卡顿，怎么定位是 JS 还是渲染的问题？
用 Performance 面板录制一段操作，看火焰图的构成：
① 如果主线程被大块黄色的「Scripting」占满，说明是 JS 长任务——去看是哪个函数，通常是大循环、大数据的处理、或深拷贝；
② 如果是「Rendering」或「Painting」占比高，说明是布局抖动或过度绘制——去找强制同步布局的代码、或大量阴影/模糊效果；
③ 如果「Scripting」很碎但频繁，可能是高频事件回调（scroll/mousemove）没有节流；
④ 如果主线程很空但依然卡，考虑是不是合成层过多导致 GPU 压力，或者存在内存泄漏引发频繁 GC。
面试要点：一定要提「先分类，再定位」，而不是笼统地说「用性能工具看看」。
闭包为什么会造成内存泄漏？
闭包本身不是问题——它让内部函数能访问外层变量，是 JS 的核心能力。问题是当闭包的生命周期远超预期时：内部函数被长期持有（挂在全局对象、DOM 事件、定时器上），它引用到的外层变量（可能是一个巨大的对象）就永远无法回收。典型场景：① 定时器/事件监听没有清理（SPA 中组件卸载但监听还在）；② 缓存对象只增不减（自己实现的 Map 缓存没有淘汰策略）；③ 意外的全局变量。排查：Chrome Memory 面板做堆快照对比，看哪类对象在两次快照之间持续增长。这个思路和后端排查 Java 堆内存泄漏是完全一样的——「对比两次快照，找持续增长的对象」。
async/await 和 Promise 在事件循环里怎么排？
await 后面的代码相当于 Promise.then 的回调，属于微任务。所以：await asyncFn() 之后的语句会在本轮微任务队列中被调度，而不是立即同步执行。
关键差异：await 会暂停当前 async 函数的执行，但不会阻塞主线程——控制权交回事件循环，其他任务继续跑。
一个易错点：async 函数即使内部没有 await，返回值也会被包成 Promise，因此 .then 回调仍在微任务中执行——所以「async 函数一定比同步函数晚一拍」，这在做时序假设时要注意。
Web Worker 能解决所有长任务问题吗？
不能。限制有三：① 不能访问 DOM——所以「修改 DOM」这件事永远只能在主线程做，Worker 只能做纯计算并把结果 postMessage 回来；② 通信有成本——结构化克隆（structured clone）会复制数据，大对象传输本身就慢，需要用 Transferable Objects（如 ArrayBuffer）实现零拷贝转移；③ 有启动开销——Worker 创建和加载脚本需要时间，短任务用 Worker 反而更慢。
适用判断：单次计算耗时超过 50ms 且是纯 CPU 计算、数据可以转移的，才值得用 Worker。
「解析 1MB 的 JS 需要多久」——这类估算题怎么答？
面试官问这类题是想看你的量级感。可以参考的经验值：JS 的解析+编译成本大致是每 KB 约 0.1~0.3ms（中低端移动设备），所以 1MB 的 JS 大约需要 100~300ms 的纯解析时间——这还没算执行时间。而这 100~300ms 会完整阻塞主线程，直接体现为白屏或交互无响应。
由此得出的结论比数字更重要：① 首屏需要的 JS 应该控制在几百 KB 以内；② 用代码分割（code splitting）把非首屏代码延后；③ 压缩 + tree-shaking 后仍未达标的，要考虑替换依赖库。把这个「成本 → 措施」的链条说出来，比背数字更有价值。

阶段 ⑤ 浏览器渲染 布局 · 绘制 · 合成：像素上屏

排、绘、合——决定动画是否流畅的三个环节

面试热度 ★★★★★
一句话答案 渲染树 → 布局（Layout / Reflow）：计算每个节点的几何信息（位置与尺寸），输出布局树。 → 绘制（Paint）：按图层生成绘制指令列表（先画什么后画什么），栅格化成位图（Tiles）。 → 合成（Composite）：GPU 把各图层按正确的顺序叠合，最终上屏。 三层的优化手段完全不同：布局靠减少范围、绘制靠减少面积、合成靠善用图层——记住这个对应关系，性能问题就能按层归类。

16.1 三个阶段各自在算什么

阶段输入 → 输出触发条件开销
布局 Layout渲染树 → 每个节点的位置与尺寸几何属性变化：宽高、内外边距、位置、字体、增删节点、display 变化最大，可能牵连整个文档（回流）
绘制 Paint布局树 → 绘制指令 + 位图外观变化：颜色、背景、阴影、边框、圆角中，取决于绘制面积
合成 Composite图层 → 最终画面只改 transform / opacity，或图层顺序变化最小，可交给 GPU 并行
这就是「动画要用 transform 和 opacity」的全部原因 只有这两个属性的变化能跳过布局和绘制，直接进入合成阶段。 用 left/top 做位移动画 = 每帧触发布局；用 background-color 做动画 = 每帧触发绘制； 用 transform: translateX() = 只走合成。
面试时如果能补一句「这不是风格偏好，而是渲染管线的结构性差异」，说服力会强得多。

16.2 布局：开销最大的一步

布局范围的扩散
  • 改变一个元素的宽高，可能影响所有兄弟节点与后代
  • 绝对定位（position: absolute/fixed）的元素脱离文档流，改动它不会影响别人——所以动画元素应尽量脱离文档流
  • float、table 布局的回流代价更高
减少布局开销的手段
  • 动画元素用 position: absolute / fixed 脱离文档流
  • 用 transform 替代 top/left
  • contain: layout 告诉浏览器「这个子树的布局不影响外部」，把布局范围限制在子树内
  • content-visibility: auto：屏幕外内容跳过渲染，长列表性能利器

16.3 合成层：一个能显著提升性能也容易翻车的机制

浏览器会把页面划分成多个图层，每个图层独立栅格化后再由 GPU 合成。 图层内的变化不会影响其他图层，所以把动画元素提升为独立图层，就能让它的动画完全不影响页面其他部分。

提升为合成层的方式说明建议
will-change: transform显式告诉浏览器「这个元素会变化，请提前准备」首选方式，但要慎用——它会让图层一直存在，占内存
transform: translateZ(0)老式 hack，利用 3D 变换触发提升能用 will-change 就别用它
position: fixed固定定位元素天然独立成层副作用，不需要刻意用
opacity 动画、filter、video、canvas、iframe浏览器自动提升被动，注意它带来的内存开销
图层不是越多越好——「层爆炸」是真实事故 每个合成层都要占用显存（一个全屏图层在 1080p 下约 8MB，算上额外缓冲区可能是几十 MB）。 如果一个长列表的每个 item 都加了 will-change，几百个图层会瞬间吃光显存，导致页面崩溃或严重卡顿。
纪律：will-change 只加在「即将发生动画的少量元素」上，并且动画结束后应移除 （可通过 JS 动态添加/删除，或用 animationend 事件清理）。
排查：DevTools 的 Layers 面板可以看到所有图层数量与内存占用。

16.4 现代渲染管线的变化（加分项）

传统管线现代管线（Chrome RenderingNG）
Layout → Paint → CompositeLayout → Pre-paint → Paint → Commit → Tiling → Raster → Activate → Draw
绘制与合成耦合较紧绘制与合成解耦，合成线程可以独立工作，主线程被阻塞时滚动依然流畅
栅格化较粗分块（Tiling）+ 光栅化，只为可见区域和即将可见的区域栅格化
为什么「主线程卡住时页面还能滚动」 因为现代浏览器把合成与栅格化放到了独立线程。滚动、以及只涉及 transform/opacity 的动画， 不需要主线程参与，所以即使 JS 卡死，这些操作依然流畅。 但一旦滚动过程中需要重新计算布局（比如用了 position: sticky 或滚动监听里改了尺寸），就必须回到主线程，卡顿立刻出现。 这解释了「为什么滚动性能问题往往是布局问题」，是一个非常能体现理解深度的点。
高频追问（先自测，再展开）
为什么用 CSS 动画比 JS 动画流畅？
关键不在语言，而在执行线程与渲染阶段。CSS 动画（尤其是只涉及 transform/opacity 的）由合成线程驱动，不需要主线程参与，即使 JS 在忙也不会掉帧。JS 动画（setInterval 或 requestAnimationFrame 逐帧改样式）跑在主线程，会和页面其他 JS、样式计算争抢时间，一旦有长任务就会掉帧。
更细致的一点：如果 CSS 动画涉及 width/height/top/left，它依然要每帧走布局，优势就消失了。所以准确的说法是「合成层上的 CSS 动画最快」，而非「CSS 动画一定快」。
position: sticky 为什么有时会让滚动变卡？
因为 sticky 元素的定位依赖于滚动位置，滚动时浏览器需要不断重新计算它的位置。如果它所在的容器布局复杂，或者页面上有多个 sticky 元素，滚动就会频繁触发布局计算——而这些计算必须在主线程完成，无法交给合成线程，于是滚动卡顿。
缓解手段：① 给 sticky 元素的父容器加 contain: layout，限制布局影响范围；② 避免在 sticky 元素的祖先上使用复杂的布局（如深嵌套的 flex/grid）；③ 减少 sticky 元素数量。
什么是「过度绘制」？怎么排查？
指同一像素被重复绘制多次——比如多层重叠的半透明元素、大面积的阴影/模糊、被遮挡但仍被绘制的元素。每一次绘制都要消耗 GPU 与内存带宽。
排查：DevTools 的 Rendering 面板里打开「Paint flashing」（绿色高亮重绘区域）和「Layer borders」；优化：① 减少大面积 box-shadow 与 blur（它们非常昂贵）；② 被完全遮挡的元素用 content-visibility 或条件渲染移除；③ 避免不必要的 opacity 图层叠加。
虚拟列表为什么能优化长列表性能？
因为长列表的性能瓶颈其实是三重叠加的：① DOM 节点数（几万个节点本身占用大量内存）；② 布局计算（节点越多，布局时间越长，而且是全量计算）；③ 绘制面积（即使不可见，浏览器也可能需要处理这些节点）。
虚拟列表（窗口化）的核心是：只渲染视口内 + 少量缓冲区的节点，把 DOM 数量从「数据量」降到「视口容量」——通常从几万降到几十个。
代价与坑：① 无法用浏览器的原生「Ctrl+F 查找」与锚点定位（因为内容不存在）；② 滚动条高度需要手动撑起（用占位元素）；③ 高度不固定的 item 计算复杂，需要实测或估算；④ 快速滚动时可能出现白屏，需要缓冲区。面试时能说出这几个坑，说明你真正用过而不是只知道概念。
为什么「首屏不要用 JS 渲染关键内容」？
因为走 JS 渲染意味着：HTML 到达 → 解析 → 下载 JS → 解析 JS → 执行 JS → 发起数据请求 → 拿到数据 → 再渲染——这是一条串行且很长的链，其中任何一步慢都会推迟首屏。而直接由服务端返回 HTML（SSR/SSG），浏览器可以在 HTML 到达时立刻开始解析和渲染，首屏时间可以缩短一半以上。
更完整的分层答案：① SSG（构建期生成）适合内容不常变的页面；② SSR（每请求渲染）适合内容动态但对 SEO 与首屏有要求；③ 流式 SSR + 选择性水合是当前的最佳实践（先送出已就绪的部分，再逐步激活交互）；④ 骨架屏是最低成本的兜底——它不改变真实性能，但显著改善感知性能。
能讲出「真实性能」与「感知性能」的区别，是很强的加分点。

三种代价的优化方向：布局靠缩小范围、绘制靠减少面积、合成靠善用图层； 动画铁律：只用 transform 和 opacity。

阶段优化手段主要收益指标

17.3 三个最容易被忽略的「体验杀手」

① 图片未预留尺寸 → CLS 爆炸
  • 图片加载完成才知道尺寸，内容被推下去
  • 解法：显式写 width / height 或 aspect-ratio
  • 同理：广告位、动态插入的横幅必须预留空间
② 字体闪烁 → 文字跳动
  • 自定义字体下载慢，出现「不可见文字闪烁」（FOIT）或「无样式闪烁」（FOUT）
  • 解法：font-display: swap + 字体子集化 + preload
  • 中文全量字体动辄几 MB，子集化是最有效的手段
③ 首屏依赖的 JS 太大 → 白屏
  • JS 下载 → 解析 → 执行，全程阻塞
  • 解法：代码分割、路由懒加载、依赖替换（用轻量库）、SSR
  • 解析成本约每 KB 0.1~0.3ms，1MB 就是几百毫秒
④（附加）第三方脚本失控
  • 统计、客服、广告脚本往往在关键路径上同步加载
  • 解法：全部 async、延迟到首屏后加载、定期审计
  • 很多线上性能问题最后追溯到某个第三方 SDK
高频追问（先自测，再展开）
INP 和 FID 有什么区别？为什么 FID 被淘汰了？
FID（首次输入延迟）只测量「用户第一次交互到浏览器开始处理」的延迟，即输入延迟那一段，不包括事件处理与渲染的时间——所以它经常给出「良好」的乐观结果，即使页面实际上很卡。
INP（Interaction to Next Paint）测量的是从用户交互到下一次画面更新的完整时长，涵盖输入延迟 + 事件处理 + 呈现延迟，且取整个页面生命周期内（通常取 P98）的最差交互。
结论：INP 更贴近用户真实体感，也更难优化——因为它把「事件处理慢」和「渲染被阻塞」都算进来了。FID 在 2024 年被 INP 正式取代。
怎么判断一个性能问题来自「网络」还是「服务端」？
看 TTFB 的构成。用 curl 的 -w 格式化输出，或浏览器 Network 面板的 Timing 分解：
DNS / TCP / TLS 三段耗时 → 属于连接成本；
Request sent → Waiting（TTFB） → 这段包含「请求上行 + 服务端处理 + 首字节下行」，通常是服务端耗时；
Content Download → 属于响应体传输，与体积和带宽相关。
关键判断：如果 TTFB 占了大头，问题在服务端（缓存、SQL、下游调用）；如果连接三段占大头且每次都很高，说明连接没被复用（可能服务器主动关闭了连接，或跨域导致无法复用）。这个方法在现场排查时极其有效，而且成本最低。
「性能优化」做过哪些？怎么答才不像背答案？
面试官最反感的就是罗列「我用了 CDN、压缩、缓存」。有效回答应该遵循 「背景 → 度量 → 定位 → 手段 → 验证」五步：
① 背景：「我们一个列表页 P75 的 LCP 是 4.2 秒，超出良好阈值。」
② 度量：「接入 web-vitals 上报后，发现 TTFB 只占 400ms，大头在资源加载和渲染。」
③ 定位：「用 Performance 面板看，发现首屏依赖的一个工具库有 800KB，解析执行占了 1.2 秒，是 LCP 延迟的主因。」
④ 手段：「做了两件事：把该库改为按需引入（降到 120KB），并把首屏必要的 CSS 内联。」
⑤ 验证：「改完后 P75 LCP 从 4.2s 降到 1.9s，CLS 保持 0.02 未退化。」
哪怕数据是编的，这套结构本身就证明你懂工程方法。只报手段不提数据，反而是减分项。
如果只允许你做三件事来提升性能，你选哪三件？
这是一道判断题，考的是优先级意识。参考答案：
① 把缓存策略做对（HTML 协商缓存 + 静态资源内容哈希长缓存）。收益最大、成本最低，一次做对终身受益，直接让复访体验接近瞬时。
② 优化最慢的那个接口（前面提过：瓶颈通常在服务端）。先度量找出 P99 最差的接口，加缓存、补索引——一个慢 SQL 的优化收益可能超过所有前端优化之和。
③ 把首屏的 JS 砍掉一半（代码分割 + 依赖瘦身 + 必要内容 SSR）。直接改善 LCP 和 INP。
答题时一定要说明「选择依据是什么」——是「收益/成本比最高」，而不是「因为这是最佳实践」。

网络与协议

输入 URL 到页面展示，中间发生了什么？
六个阶段：浏览器发起（解析 URL、查缓存）→ 网络传输（DNS、TCP 握手、TLS 握手）→ 请求上行（HTTP 报文、CDN、负载均衡、网关）→ 服务端处理（内核 epoll → Tomcat → Filter → DispatcherServlet → Service → 数据库）→ 响应返回（序列化、压缩）→ 浏览器渲染（DOM、CSSOM、样式计算、JS 执行、布局、绘制、合成）。说完骨架等追问，不要主动展开细节。
为什么 TCP 握手是三次而不是两次？
因为要确认双向通道都可用，三次是最小次数。两次的话服务端无法确认「自己的 SYN+ACK 被客户端收到了」，可能为已废弃的连接分配资源。不是四次是因为服务端的 SYN 和 ACK 可以合并成一个报文（捎带确认）。
TIME_WAIT 有什么用？过多怎么办？
两个作用：① 确保最后一个 ACK 到达（丢了还能重发）；② 让本次连接的残余报文在网络中消散，避免污染新连接。时长 2MSL。过多说明本机是主动关闭方——先问「为什么连接不能复用」，再考虑 tcp_tw_reuse，绝不用已废弃的 tcp_tw_recycle。
HTTPS 握手过程？为什么混合加密？
ClientHello（随机数 + 套件 + SNI + key_share）→ ServerHello（选定套件 + key_share）+ 证书 + Finished → 客户端校验证书、算出会话密钥、发 Finished。TLS 1.3 只需 1 RTT。
混合加密的原因：非对称加密安全但慢，只用来协商密钥与验证身份；对称加密快，用来加密真正的数据。两者结合才兼顾安全与性能。
HTTP/1.1、2、3 的区别？
1.1 → 连接复用（keep-alive），但存在应用层队头阻塞；
2 → 二进制分帧 + 多路复用（彻底解决应用层队头阻塞）+ HPACK 头压缩，但仍有 TCP 层队头阻塞；
3 → 基于 QUIC（UDP），消除 TCP 层队头阻塞，1-RTT/0-RTT 握手，支持连接迁移。
强缓存和协商缓存有什么区别？
强缓存（Cache-Control: max-age）：不发请求，直接用本地副本，状态码 200 (from cache)。协商缓存（ETag/If-None-Match）：要发请求，服务端确认没变返回 304（省响应体但不省往返）。优先级：Cache-Control > Expires，ETag > Last-Modified。
DNS 用 UDP 还是 TCP？
默认 UDP 53：查询是一次问答、报文小、要求快，建连成本不划算。两种情况用 TCP：① 响应超过 512 字节且无 EDNS0 扩展；② 区域传送（主从同步）。加密方案 DoT 用 TCP 853、DoH 用 HTTPS 443。
同源策略的「源」由什么决定？
协议 + 域名 + 端口，三者完全相同才同源。路径和查询参数不参与，所以 CORS 无法按接口路径粒度做限制。注意 a.com 与 www.a.com、http 与 https 都算跨域。
CORS 报错怎么解决？
先明确请求其实发出去了、服务端也执行了，只是浏览器不给 JS 看结果。解决位置在服务端：返回 Access-Control-Allow-Origin（带凭证时不能是 *）；复杂请求要处理 OPTIONS 预检，且预检必须早于鉴权（预检不带凭证，被 401 拦掉跨域就永远过不去）；设 Max-Age 减少预检次数；错误响应也要带 CORS 头。
四层和七层负载均衡怎么选？
四层只看 IP+端口，性能极高（百万级 QPS），但不能解析内容；七层能看 URL/Header/Cookie，可做路由、改写、SSL 卸载、灰度，但性能较低。经典组合：LVS（四层）在最外层扛量 → Nginx（七层）做灵活路由 → 应用。

后端与框架

Spring MVC 处理一个请求的完整流程？
请求先过 Filter 链（Servlet 规范）→ 进入唯一的 DispatcherServlet → HandlerMapping 按 URL 找到 HandlerMethod → HandlerAdapter 驱动执行 → Interceptor.preHandle → 参数解析器绑定参数并校验 → 调用 Controller → Interceptor.postHandle → HttpMessageConverter 序列化成 JSON → 通过 Filter 链返回。异常由 HandlerExceptionResolver（@RestControllerAdvice）统一处理。
Filter、Interceptor、AOP 的区别？
Filter（Servlet 层，最外）：能拿到原始 request/response，不知道会进哪个方法；Interceptor（Spring MVC）：能拿到 Handler，知道要去哪个方法；AOP（Bean 方法级，最内）：能拿到参数、返回值、异常，作用于任意 Bean。一句话：Filter 管进没进门、Interceptor 管去哪个房间、AOP 管房间里干什么。
@Transactional 在哪些情况会失效？
六个：① 方法非 public；② 同类内部调用（this 调用绕过代理）；③ 异常被自己 catch 没抛出；④ 抛的是受检异常（默认只回滚 RuntimeException，需配 rollbackFor）；⑤ 类没被 Spring 管理（自己 new 的）；⑥ 数据库引擎不支持事务。
口诀：不 public、自己调、被吞掉、受检抛、没托管、没引擎。
缓存穿透、击穿、雪崩怎么区分和解决？
穿透：查不存在的数据，缓存永不命中 → 缓存空值 + 布隆过滤器；
击穿：单个热点 key 过期瞬间并发打库 → 互斥锁 / 逻辑过期；
雪崩：大批 key 同时过期或 Redis 宕机 → 过期时间加随机 + 多级缓存 + 高可用。
记忆：穿透是「查空」、击穿是「单点」、雪崩是「同时」。
缓存和数据库怎么保证一致性？
先承认无法强一致，目标是控制不一致窗口。主流方案是 Cache Aside + 先更新数据库再删除缓存（删除而非更新，因为删除幂等更安全）。极端场景用延迟双删或订阅 binlog 异步删。关键数据设短 TTL 兜底；强一致场景（余额、库存）直接读库不走缓存。
接口幂等怎么保证？
位置在 Service 层且依托数据库唯一约束。手段：① 唯一索引（最可靠）；② 去重表；③ Redis SETNX（快但有丢失风险，做前置拦截）；④ 状态机（状态只能单向流转，天然幂等）。关键细节：重复请求要返回与首次相同的结果，而不是报错。
为什么连接池不是越大越好？
因为数据库的瓶颈在 CPU、磁盘 IO 与锁竞争，连接多了只会增加上下文切换与锁等待。经验值 连接数 ≈ CPU核数 × 2 + 磁盘数。更重要的是：线程池远大于连接池时，大量线程在抢连接，等于把排队从应用层搬到了数据库层，故障更难定位。
MQ 的「至少一次」意味着什么？
意味着消息一定会重复，所以消费端必须幂等。Exactly Once 在分布式下不可能实现，工程上只能用「至少一次 + 幂等消费」来等价达成。这也是为什么说「引入 MQ 的本质是用最终一致性替换同步确定性」。
为什么 UPDATE 没走索引会锁全表？
因为 InnoDB 的行锁加在索引记录上，不是加在「行」上。没有可用索引时必须全表扫描才能确定目标行，扫描路径上经过的记录全被锁住，效果等同锁表。后果：高并发下一条漏索引的 UPDATE 能让整个系统写入排队。

前端渲染与性能

DOMContentLoaded 和 load 的区别？
DOMContentLoaded：DOM 树构建完成且 defer 脚本已执行（图片、样式可能还没好），大部分初始化业务代码应该在这里跑；load：所有资源（图片、字体、iframe）全部加载完成，用于需要精确测量的场景。
async 和 defer 的区别？
都不阻塞 HTML 解析。async：下载完立刻执行，顺序不可控（适合无依赖的埋点类脚本）；defer：等 DOM 解析完、按出现顺序执行，在 DOMContentLoaded 之前（适合业务脚本）。记忆：async 谁快谁上，defer 排队按序。
重排、重绘、合成的区别？动画怎么优化？
重排：几何变化，重新计算布局，代价最大；重绘：外观变化，跳过布局；合成：只改 transform/opacity，GPU 直接处理。
动画优化：只用 transform 和 opacity——它们能跳过布局与绘制，直接进入合成阶段。绝不用 top/left/width/height 做动画。
事件循环的顺序是什么？
调用栈清空 → 执行所有微任务（含新产生的）→ 渲染机会（rAF → 样式 → 布局 → 绘制 → 合成）→ 取下一个宏任务。
微任务：Promise.then、queueMicrotask、MutationObserver；宏任务：setTimeout、I/O、事件回调。关键：微任务不清空则永远不渲染——递归微任务会让页面彻底冻结。
长任务是什么？怎么优化？
执行时间超过 50ms 的任务，会推迟渲染、导致交互无响应。优化：① 时间切片（切成小块、让出主线程）；② 搬进 Web Worker（纯计算）；③ 减小 JS 体积（解析执行本身就是长任务）；④ requestIdleCallback 处理低优先级工作。
CLS 为什么重要？怎么降低？
CLS 衡量视觉稳定性——内容突然跳动会让用户误点，体验极差。降低手段：① 图片/视频显式声明宽高或 aspect-ratio；② 广告位、动态插入内容预留空间；③ 字体用 font-display: swap 并做子集化；④ 避免在已有内容上方插入 DOM。
为什么用 Long 类型的 ID 会出问题？
因为 JS 的 Number 是双精度浮点，安全整数上限只有 2^53-1，而雪花算法生成的 19 位 ID 超过这个范围，低位会被截断。表现为「查得到但查不对」。解法：后端序列化成字符串，前端按字符串处理。
Token 应该存在哪里？
HttpOnly + Secure + SameSite=Lax 的 Cookie。因为 localStorage 里的 token 一旦页面存在 XSS 就会被直接窃取，且服务端无法限制其使用；而 HttpOnly Cookie 禁止 JS 读取，能有效防 XSS 窃取，SameSite 还能防 CSRF。
页面白屏很久，你怎么排查？
按「先分类，再定位」的思路：
① Network 瀑布图看 TTFB——HTML 很久才回来就是服务端问题；
② 看关键资源（CSS/JS）的开始下载时间——很晚说明被阻塞资源卡住（同步 script、@import）；
③ Performance 火焰图看主线程有没有长任务占住；
④ 确认是不是首屏强依赖 JS 渲染（考虑 SSR / 骨架屏）。
核心：白屏 = 渲染被阻塞，要找「谁在阻塞」。
性能优化你优先做哪三件事？
① 把缓存策略做对（HTML 协商缓存 + 静态资源内容哈希长缓存）——收益最大、成本最低；② 优化最慢的那个接口——瓶颈通常服务端，一个慢 SQL 的优化收益可能超过所有前端优化之和；③ 砍掉首屏一半的 JS（代码分割 + 依赖瘦身）。并说明选择依据是「收益/成本比最高」，而非「最佳实践」。
第 ⑥ 章 · 陷阱

易错点与反问陷阱

面试官常在「你以为自己会」的地方下手。这一节列出的都是真实出现频率最高的表述错误。

十四个高频表述错误

❌ 错误表述✅ 正确表述
「304 是从缓存里重新下载的」304 是发了请求、服务端确认未变，只省响应体不省往返。「不发请求」的是强缓存
「no-cache 是不缓存」no-cache 是可以缓存但每次都要校验；不缓存是 no-store
「CORS 是服务端拒绝了我的请求」CORS 是浏览器行为，请求到达了、服务端可能已执行，只是浏览器不把结果给 JS
「HTTPS 就是 HTTP 加了一层加密」提供机密性、完整性、身份真实性三个保证，缺一不可
「epoll 是异步 IO」epoll 属于同步 IO（多路复用）——内核只通知「可读」，读数据还得应用自己做
「TCP 是可靠的所以不会丢数据」它保证的是失败会被发现，不是失败不会发生。业务层仍必须做幂等与重试
「三次握手是为了保证可靠传输」是为了双向确认收发能力；可靠传输靠的是序列号、确认、重传、窗口机制
「HTTPS 的 keep-alive 和 TCP keepalive 是一回事」完全不同：前者是应用层连接复用，后者是内核层存活探测
「DOMContentLoaded 就是页面加载完成」它只表示 DOM 构建完成，图片字体可能还没好，那是 load
「CSS 会阻塞 DOM 解析」CSS 不阻塞 HTML 解析，它阻塞渲染，并间接阻塞其后的脚本执行
「微任务比宏任务快」不是快慢问题，是优先级：每个宏任务结束后会清空全部微任务
「connection pool 越大并发越高」超过拐点后反而更慢——数据库是瓶颈，连接多只会增加上下文切换与锁竞争
「TIME_WAIT 是 TCP 缺陷，应该尽量消除」它是保障可靠关闭的必要机制，要优化的是「为什么连接不能复用」
「用了 MQ 系统就高可用高并发了」MQ 把复杂度从性能转移到了可靠性——重复、丢失、乱序、顺序性都要自己处理

面试官的五个「挖坑」追问，怎么接住

坑 1 · 「那你详细说说你说的这个……」
  • 这是深挖测试：你说出口的每个名词他都可以往下钻三层
  • 策略：只说自己能讲三层的东西。没把握的用「这块我了解原理但没深入实践过」带过
  • 禁忌：不懂装懂，然后被一路追问到崩
坑 2 · 「如果……会怎样？」
  • 考的是边界思维，不是知识点
  • 策略：先明确此时链路在哪一环出问题，再推导后果
  • 比如「DNS 挂了会怎样」→ 已建立的连接不受影响 → 只有新连接失败 → 这就是连接池存在的意义之一
坑 3 · 「你们线上是怎么做的？」
  • 考的是真实经验，编不了太久
  • 策略：讲清「背景 → 度量 → 定位 → 手段 → 验证」五步，哪怕只有一件小事
  • 禁忌：只报手段不提数据——那说明你只是执行者而非决策者
坑 4 · 「为什么不用 XX 方案？」
  • 考的是取舍意识，没有标准答案
  • 策略：先承认它合法，再说明在当前约束下为什么不选（团队规模、业务阶段、运维成本）
  • 加分表述：「如果团队规模到 X 人、QPS 到 Y，我会考虑切过去。」
坑 5 · 「微服务不是更好吗？」
  • 这是考察判断力的经典诱导
  • 策略：明确说「能单体就单体，真的疼了再拆」
  • 理由：微服务解决的是组织协作问题而非性能问题，代价是分布式复杂度全面上升
通用原则：先问清边界
  • 遇到开放式问题，先反问约束条件（量级？一致性要求？团队规模？）
  • 这本身就是成熟工程师的标志——没有约束就没有正确答案
  • 最危险的回答是「这个看情况」然后什么都不说

答题的三个层次（拿分结构）

第一层（30 秒）：给骨架

只讲六个阶段的名字与顺序，不展开任何细节。目的是让面试官看到你有全局观。这一层就决定了他是「继续聊」还是「换一题」。

第二层（2 分钟）：每阶段一个亮点

从每个阶段里挑一个最有价值的机制讲，比如 DNS 的「递归 vs 迭代」、TCP 的「为什么三次」、服务端的「DispatcherServlet 流程」、渲染的「布局/绘制/合成」。 关键：主动挑你最有把握的，而不是最难的——把面试官引到你熟悉的话题上。

第三层（等追问）：钻深

面试官会挑他感兴趣的追问。此时要纵向讲透，并且主动提一句「我们线上遇到过……」——一个真实案例的价值远超十段理论。

最后一条，也是最重要的一条 这道题不是为了考你背得全不全，而是考你能不能建立全局。 如果只背了流程却说不出「瓶颈通常在哪」「哪一层的优化收益最大」，那只是复述； 而如果你能在讲完后自然补一句「实际生产中，瓶颈通常在服务端耗时和渲染阻塞，DNS 和 TCP 的开销相对可控」—— 这一句话就把你从「背过」的候选人变成了「做过」的候选人。

术语速查表

按链路顺序排列。任何一条说不清，回到对应关卡复习。

URL / URI
统一资源定位符。六段：协议、主机、端口、路径、查询、片段。fragment 不发给服务端
百分号编码
把非 ASCII 与结构字符转成 %XX。 encodeURI 编码整条 URL，encodeURIComponent 编码参数值
站点隔离（Site Isolation）
不同站点使用独立渲染进程，实现安全与稳定性隔离
强缓存
不发请求直接用本地副本。由 Cache-Control / Expires 控制
协商缓存
发请求但服务端可返回 304 不传响应体。由 ETag / Last-Modified 控制
Service Worker
页面与网络之间的可编程代理，独立线程，必须 HTTPS，是 PWA 的基础
递归查询
客户端把问题交给本地 DNS，由它负责给出最终答案
迭代查询
本地 DNS 逐级询问根 / TLD / 权威服务器，每级只告诉下一步该问谁
GSLB
全局负载均衡，权威 DNS 按来源 IP 返回就近机房 IP，即「智能 DNS」
HTTPDNS
绕过运营商 Local DNS，直接通过 HTTPS 向自家 DNS 查询，防劫持、更精准
三次握手
SYN → SYN+ACK → ACK。目的是双向确认收发能力，成本 1 RTT
TIME_WAIT
主动关闭方在 2MSL 内的等待状态，确保最后 ACK 可达并让残余报文消散
SLOW START / 拥塞控制
慢启动、拥塞避免、快重传、快恢复四阶段；现代算法 CUBIC、BBR
SYN Flood
大量 SYN 不回 ACK，占满半连接队列。防护靠 syncookies
Accept Queue
内核完成握手后的全连接队列，应用 accept() 取走。溢出表现为连接超时
TLS
传输层安全协议，提供机密性、完整性、身份真实性。1.3 只需 1 RTT
前向安全
长期私钥泄露也不影响历史会话安全。ECDHE 每次临时生成密钥，TLS 1.3 强制要求
SNI
ClientHello 中的明文域名，用于一台服务器多证书选择。也是隐私缺口
ALPN
握手期协商应用层协议（h2 / http/1.1），省掉一次额外往返
OCSP Stapling
由服务器代取证书吊销状态并随握手一起发送，省掉客户端查询往返
CORS
跨域资源共享。简单请求直接发后校验；复杂请求先发 OPTIONS 预检
幂等性
同一请求执行多次，结果与执行一次相同。重试的前提条件
队头阻塞
同一连接上前一个请求慢会阻塞后面。1.1 有应用层队头阻塞，2 剩 TCP 层，3 彻底消除
QUIC
基于 UDP 的传输协议，合并 TCP + TLS 握手，支持 0-RTT 与连接迁移
反向代理
代表服务端的代理，隐藏后端拓扑。Nginx 是典型
epoll
Linux IO 多路复用。红黑树存 fd + 就绪链表，O(1) 获取就绪事件。属于同步 IO
Reactor 模型
事件驱动 IO 模型。Tomcat 单 Reactor 多线程，Netty 主从多线程
DispatcherServlet
Spring MVC 的前端控制器，负责调度 HandlerMapping / Adapter / 参数解析 / 返回值处理
AOP 代理
Spring 通过 JDK 动态代理或 CGLIB 织入切面。同类内部调用绕过代理导致失效
MVCC
多版本并发控制。靠 undo log 版本链 + ReadView 实现读不加锁，只作用于快照读
回表
二级索引查到主键后，再回聚簇索引取整行数据。覆盖索引可以避免
Cache Aside
缓存旁路模式：读时先查缓存、写时先更库再删缓存，是最主流的缓存一致性策略
DOM / CSSOM
HTML 解析出的文档树 / CSS 解析出的样式树。二者结合成渲染树
预扫描器
HTML 解析器旁的独立扫描线程，提前发现静态资源并下载。JS 动态创建的资源是它的盲区
样式层叠
按「来源与重要性 → 权重 → 书写顺序」决出最终样式。匹配是从右往左做的
渲染树
DOM + CSSOM 的产物，只包含需要显示的节点。display:none 不在其中
重排 / 重绘 / 合成
分别对应布局、绘制、合成三个阶段，开销依次降低
合成层
可独立栅格化的图层，变化不影响其他部分。过多会导致显存爆炸
长任务
执行超过 50ms 的任务，会阻塞渲染与交互响应
微任务 / 宏任务
微任务在每个宏任务结束后全部执行完；微任务不清空则永远不渲染
LCP / CLS / INP
Core Web Vitals 三指标，分别衡量加载速度、视觉稳定性、交互响应
TTFB
首字节时间，是区分「网络问题」与「服务端问题」的关键分界线
关键渲染路径
从 HTML 到首帧所必须经过的资源与步骤：HTML → DOM、CSS → CSSOM、合成渲染树 → 布局 → 绘制
