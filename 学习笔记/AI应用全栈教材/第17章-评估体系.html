第 17 章　评估体系
一次体检没有意义，一张长期跑的回归集才有

第 3、4 章做了一次体检。这一章把它变成一套能持续运行、能拦住退步、能支撑决策的体系。区别在自动化和门禁：体检是你主动去做的，体系是每次改动都会自动跑、跑不过就不许上线的。

本章学习目标
理解　为什么必须分三层测：单元、链路、端到端
掌握　模型裁判的校准方法，以及三种系统性偏差
掌握　上线门禁的设计：阈值、对比方式、失败处理
掌握　把生产数据回流成评估样本的三个来源
了解　评估体系的维护成本与腐化

17.1　三层评估，各管一段

端到端准确率是最容易测的，也是最没用的——它只告诉你「不行」，不告诉你「哪里不行」。所以要分层。

层测什么样本频率失败时
单元单个环节：分类准确、检索 recall、工具参数正确率、格式合法率20–50 条/环节每次改动直接定位到环节
链路两三个环节串起来：检索+生成、工具+组装50–100 条每天定位到接口
端到端完整用户场景，含前端交互100–200 条每次发布只作门禁，不作诊断

分层的价值在于成本与灵敏度。单元层几十条样本、几秒钟跑完，可以在每次改提示词时都跑；端到端要 200 条、几分钟、还可能涉及真人和界面，只能发布前跑。

例题 17-1　三层各自的指标与阈值
单元层（每次改动，< 30s）
  分类准确率　　　≥ 0.90
  检索 recall@5　 ≥ 0.85
  工具参数合法率　≥ 0.98
  JSON 解析成功率 ≥ 0.995

链路层（每天，< 3min）
  引用正确率　　　≥ 0.90
  越界率（幻觉）　≤ 0.02
  误拒率　　　　　≤ 0.08

端到端（每次发布，< 10min）
  任务准确率　　　≥ 基线 − 3 个点
  采纳率（离线模拟不可得）→ 用人工评分代替
  P95 延迟　　　　≤ 8s
「≥ 基线 − 3 个点」这个写法很重要：门禁不该是绝对值，而是「不许变差」。
绝对阈值会随着业务变化变得不合适（比如新增了难类别），而「相对基线」永远成立。

17.2　模型裁判：能省钱，但必须校准

端到端评估如果有 200 条开放式回答，人工判要 10 小时以上。模型裁判能压到 20 分钟，代价是引入偏差。

三种系统性偏差

偏差表现对策
同源偏好用 A 判 A 的输出，评分偏高裁判模型选不同族；或至少不同版本
长度偏好更长的回答得分更高，即使内容相同rubric 里明确「冗余扣分」；或按长度分组比较
位置偏好A/B 对比时前位胜率更高交换顺序各跑一次，取平均

校准：用 30 条人工标注对齐

校准的做法很朴素：人工标 30 条，让裁判模型也标这 30 条，算一致性。如果一致率低于 85%，说明 rubric 写得不够具体，要先改 rubric，而不是直接用。

例题 17-2　一个可用的 rubric
# 判「回答是否可用于客服场景」，输出 pass / fail / unsure

pass  需同时满足：
  1. 结论正确（与【知识】一致，无越界事实）
  2. 回应了客户的真实诉求（不是只回答字面问题）
  3. 不含未经知识支持的承诺（时限、金额、赔付）
  4. 长度 ≤ 120 字，无冗余客套

fail  满足任一：
  1. 事实与【知识】冲突，或出现【知识】中没有的具体数字/条款
  2. 未回应核心诉求
  3. 含有"一定""保证""肯定可以"等绝对化承诺
  4. 推诿（只让客户自己去看，未给可行下一步）

unsure  仅在【知识】本身存在冲突或缺失时使用
关键是把标准写成可判定的条件，而不是「是否专业」「是否友好」。
后者会让裁判模型退回自己的偏好，而它的偏好和你的业务不一致。

注意 unsure 这个出口。没有它，裁判模型会被迫在「对」和「错」之间选，而遇到模糊情况它会随机选一个，制造噪声。有了出口，这些样本会被单独拎出来，由人工处理——而它们往往恰好是最有价值的那批（暴露知识冲突或缺失）。

17.3　门禁：让退步无法上线

门禁的核心不是「跑测试」，而是「跑不过就不许上」这个机制真的被执行。多数团队有测试但没有门禁，因为它们被当成建议。

例题 17-3　门禁的四个判断
def gate(new, base, items):
    # ① 总体不许退步超过 3 个点
    if new.acc < base.acc - 0.03: return 'BLOCK: 总体退步'

    # ② 关键类别不许退步超过 5 个点（退款、赔付）
    for c in CRITICAL:
        if new.by_cat[c] < base.by_cat[c] - 0.05:
            return f'BLOCK: {c} 退步'

    # ③ 新增的「从对变错」不许超过 5 条
    regress = [i for i in items if i.was_ok and not i.now_ok]
    if len(regress) > 5: return 'BLOCK: 回归过多'

    # ④ 幻觉率不许上升
    if new.halluc > base.halluc + 0.005: return 'BLOCK: 幻觉上升'
    return 'PASS'
四条里第 ③ 条最关键，也最容易被漏。
只看总体，30 条改进 + 25 条退步 = 净 +5，看起来是进步；
但那 25 条退步里通常包含最不能错的场景（退款金额、时效承诺）。

「关键类别」这个概念要说清：它由错误代价决定，不由样本量决定。退款、赔付、时效承诺、隐私相关——这些类别的错误会造成真实损失，所以它们的阈值要更严（5 个点），而且必须单独看，不能被平均。

被 BLOCK 时怎么办

门禁的意义在于它会产生摩擦，而摩擦必须有人处理。三种处理方式，按顺序：

  1. 修。如果退步来自真实问题（新提示词丢了某个约束），修完再跑。
  2. 确认是标注错误。评估集也会错。如果某条样本的标注本身有问题，走「标注修正」流程：记录原因、双人确认、生成 v2 版本。但不能为了通过门禁而改标注——这个界限要写进流程。
  3. 豁免。如果退步是有意的权衡（牺牲某类换取另一类），需要产品和技术共同签字，并在发布说明里记下。豁免必须有记录，且要有期限（比如「观察两周，如投诉上升则回滚」）。

17.4　数据飞轮：三个免费来源

评估集最大的问题是会腐化：三个月后它不再代表真实分布（业务变了、客户变了、问题变了）。持续补充的成本很高，但有三个来源是免费的。

来源一：用户纠正（第 7 章的 edit_ops）

「改后插入」的编辑对是最干净的标注：它直接告诉你「模型写的」和「人想要的」差在哪。每周汇总一次，把出现频次最高的编辑对转成评估样本（before 作为输入，after 作为期望输出）。

来源二：低置信与拒答样本

被判为「不建议采用」的、以及模型自己拒答的样本，是模型最不确定的区域。这些样本人工标一遍，能直接暴露两类问题：系统性地缺少知识，或者系统性地缺少能力。

来源三：投诉与返工

客户投诉的工单、坐席返工的工单，是最有价值的负样本。它们代表真实损失。这类样本量不大（一个月可能几十条），但它们的权重应该更高——建议在评估集里单独成组，报告时单独列出。

例题 17-4　评估集的版本演进
v1（第 3 章）　　200 条，分层抽样，手工标注
v2（+1 月）　　 +40 条来自 edit_ops 高频编辑对
v3（+2 月）　　 +25 条来自低置信样本；标注 8 条错误已修正
v4（+3 月）　　 拆分：core 180 条（冻结，永不改动，用于跨月对比）
　　　　　　　　　　live 120 条（每季度轮换 1/3，跟踪分布漂移）

报告口径：core 上 84.2%（与上月 84.0% 可比）
　　　　　live 上 79.5%（与上月 81.0% 不可比，因为样本换了）
　　　　　投诉组 12 条中 7 条失败（单独列出，不进平均）
core / live 分开是关键设计：
core 保证纵向可比（同一批题，永远不变），live 保证横向代表（跟上真实分布）。
只有 core，你会脱离现实；只有 live，你无法判断「是变差了还是题变难了」。

17.5　体系本身也会腐化

评估体系跑起来之后，有三种腐化方式，都要定期检查：

  • 过拟合。团队反复在 core 上试，最终 core 的分数越来越高，而线上没变。检测方法：留一份 holdout（第 3 章），一个季度跑一次。如果 core 上升而 holdout 不动，说明过拟合了。
  • 标注漂移。三个月后新标的人对标准的理解和当初不同。检测方法：定期重标 30 条老样本，看和原始标注的一致率。低于 0.85 就要重新对齐。
  • 样本失效。业务变了，某些样本已经没有意义（比如「跨境税费」这个业务下线了）。检测方法：按类别统计失败率，长期 0 失败且业务已下线的类别应当移除。

这三项检查的成本大约是每季度半天，而它们能防止一个更糟的情况：你有一个看起来很专业的评估体系，但它测的东西和真实世界已经无关了。这比没有评估更危险，因为它给了你虚假的信心。

四个让评估体系失效的做法
  1. 门禁只是建议。「这次先上了，下次补」——一旦有过一次，门禁就永久失效了。
  2. 为了过门禁改标注。这等于把尺子改了去适应身高。改动必须走独立流程并留痕。
  3. 只看端到端。失败了不知道改哪，于是每次都是「全量重试一遍」，效率极低。
  4. core 和 live 混在一起报。你会得到一个既不可纵向比较、也不代表当下的数字。
本章小结
  • 三层评估：单元（每次改动）、链路（每天）、端到端（每次发布）。分层是为了定位，不是为了全面。
  • 阈值用「基线 − N 个点」而不是绝对值，因为绝对值会随业务变化失效。
  • 模型裁判三种偏差：同源、长度、位置。用 30 条人工标注校准，一致率 < 85% 先改 rubric。
  • 门禁四判：总体、关键类别、新增回归条数、幻觉率。第三条最容易被漏，也最重要。
  • 被 BLOCK 只能修 / 修标注（走流程）/ 豁免（签字 + 有期限），不能「下次补」。
  • 三个免费样本来源：编辑对、低置信与拒答、投诉返工。
  • core（冻结、纵向可比）与 live（轮换、跟随分布）分开维护、分开报告。
  • 体系会腐化：过拟合、标注漂移、样本失效。每季度半天检查。

本章综合习题

综合题一门禁显示「总体 +2 个点，但 17 条从对变错」。你会放行吗？给出你的判断过程和需要的额外信息。
答案

不会直接放行。总体 +2 掩盖了 17 条退步，而这 17 条的性质决定了一切。

需要的第一项信息：这 17 条落在哪些类别。

如果集中在「投诉建议」这类低风险类别（错了只是答得不够好），放行合理；如果落在退款、赔付、时效承诺上，即使只有 3 条也应当拦住——因为每一条都对应真实的钱或承诺。

需要的第二项信息：这 17 条是怎么错的。三种情况区别很大：

  • 变短了、漏了细节 → 可能是新版本更简洁，属于有意权衡，但要确认漏掉的不是关键信息。
  • 引用了错误条款 → 危险信号，说明改动影响了检索/组装，不是单纯的提示词调整。
  • 变成拒答了 → 说明新版本更保守。这在合规上可能是好事，但会拉低可用性，需要业务方确认。

需要的第三项信息：净 +2 是从哪来的。如果是「30 条改进 + 17 条退步」净 +13 条（约 +6 个点），那和「+2 个点」对不上——说明还有别的变化（比如某些样本从错变成另一种错，或者样本数不一致）。数字对不上时，先查数据，不要先解释。

我的实际决定会是：如果 17 条里有关键类别，先修；如果全在低风险类别且净改进稳定，可以放行但要记录，并在两周内观察「插入后全删」比例（第 8 章）是否上升——那是线上版的回归信号。

这道题的方法论：净值的正负不能作为放行依据，因为错误的代价不对称。+2 个点的收益可能是「多答对了几个无关紧要的问题」，而 17 条退步里只要有一条是「多承诺了一次赔付」，净值就是负的。

综合题二模型裁判和人工的一致率只有 78%。列出三种可能原因，以及你会先改哪一个。
答案

原因一：rubric 太抽象（最常见）。如果 rubric 写的是「回答是否专业、是否友好」，裁判模型只能按自己的偏好判，而它的偏好和你的业务标准不一致。先改这个。

改法：把每条标准写成可判定的条件。比如「专业」改成「不含口语词（啊、呢、吧）、不含夸张表述（超级、绝对）、使用完整句」。「友好」改成「开头有一句承接客户情绪的表述，且不超过一句」。

原因二：样本本身模糊。30 条里有 5–8 条连人都判不一致（第 3 章的 kappa 问题）。这种情况下，78% 已经是上限——不是裁判不行，是任务本身没有唯一答案。

验证：让两个人分别标这 30 条，算他们之间的一致率。如果也只有 80%，说明是样本问题，该做的是把这些样本移到 unsure 组或剔除，而不是调裁判。

原因三：裁判模型不理解业务术语。比如「无理由退货」和「质量问题退换」的区别，通用模型可能混淆，于是把正确答案判成错。

改法：在裁判的提示词里加一个小术语表（5–8 条），只解释容易混的概念。不要加太多——裁判的上下文越长，它对每条标准的注意力越弱。

我会先改哪一个：先做原因二的验证（成本 20 分钟，两个人标 30 条）。因为如果一致率上限就是 80%，改 rubric 是白费功夫。先确认「这个任务是否可判定」，再优化判定者——这个顺序和第 2 章「提示词的效果上限由任务是否可判定决定」是同一条道理。

补充一个判断：一致率不需要到 95%。85%–90% 就够用了，因为裁判的作用是「批量初筛」，不是「最终裁决」。把它当成一个高召回率的过滤器，人工只复核它判错的，整体效率仍然提升 10 倍。

综合题三设计一个「每周自动跑、结果发到群里」的评估方案。写出跑什么、怎么报、异常怎么触发。
答案

跑什么（三组，总耗时 < 15 分钟）：

① core 集 180 条（每周固定跑）：产出准确率、幻觉率、误拒率、P95 延迟。

② 本周新增的编辑对 30 条（从 edit_ops 抽）：用 before 作输入、after 作参考，看新版本能否复现人想要的写法。这一组测的是「有没有学到上周的反馈」。

③ 本周投诉工单里的 AI 相关样本（通常 5–15 条）：只报告不计算入总分，作为「真实损失」的证据。

怎么报（一条消息，四段）：

【AI 评估周报 10-26】
core 180 条：准确 84.2%（上周 84.0%）　幻觉 1.7%（1.7%）
  关键类别：退款 91%（持平）　时效 86%（−2）
  最差类别：发票重开 62%（15 条错 6）

编辑对 30 条：复现率 57%（上周 44%）
  高频未复现：退货→换新（9 次）

投诉样本 12 条：7 条与 AI 回答相关
  其中 3 条涉及「时效承诺」（见 thread）

结论：整体持平；时效类退步 2 点需关注；编辑对复现率上升说明改动有效。

异常怎么触发（三档）：

P1（立刻 @ 所有人）：关键类别下降 > 5 点，或幻觉率 > 3%。

P2（当天跟进）：总体下降 > 3 点，或某类别失败率 > 30% 且样本 ≥ 10。

P3（记录观察）：任何单项指标连续三周同方向变化（即使每周都在阈值内）——趋势比单点更重要。

三个设计要点：

① 报「最差类别」比报总分有用。总分不变时，某个类别可能已经崩了（发票重开 62%），而这才是下周要做的事。

② 编辑对那一组是「闭环验证」。没有它，你不知道团队根据用户反馈做的改动有没有效果——而这恰恰是最该被验证的事。

③ 投诉样本不进平均，但要出现在报告里。它是唯一带真实损失权重的信号，虽然量少、不具统计意义，但它的存在感能防止团队只看「84% 还不错」。
