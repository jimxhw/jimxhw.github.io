第 13 章　向量检索
模型不知道你的业务，你得把该知道的递给它

前三篇造出来的是一个「会说人话」的系统，但它不知道你的退货政策写在第几条。这一章开始补上这块：把企业知识变成模型能用的形式。这个领域叫 RAG（Retrieval-Augmented Generation，检索增强生成），而它的效果上限，80% 由检索质量决定，20% 才由生成决定。

本章学习目标
理解　关键词检索失效的三种典型情况
掌握　embedding 与相似度的正确用法，以及「归一化」为什么必须做
掌握　按条款切分而非按字数切分，以及父子块的用法
掌握　用 pgvector 建表、建索引、带过滤查询
掌握　用 recall@k 量化检索质量，以及混合检索的收益判断

13.1　关键词检索的三个失效

如果知识库只有几百条，用 SQL LIKE 就够了。失效从三个地方开始：

情况客户的说法知识库的写法关键词能匹配吗
同义「耳机一只没声音」「单侧无声属质量问题」不能
口语「我买的那个能退不」「商品支持七日无理由退货」不能
跨表达「钱什么时候到账」「退款将于 1–3 个工作日原路退回」不能

这三种的共同点是：字面不重合，语义重合。而向量检索解决的正是这件事——它把文本映射到一个高维空间，语义相近的文本距离更近。

但要注意，向量检索也有它自己的失效：精确匹配类的查询。「订单号 20260312008」这种，向量检索可能召回一堆「订单号 2026031xxxx」。所以真实系统里两者都要，第 13.5 节讲怎么合并。

13.2　embedding 与相似度

embedding 是一个把文本变成定长向量的函数。它的关键性质是：语义相近 → 向量夹角小。所以最常用的相似度是余弦相似度，取值 −1 到 1，越大越像。

例题 13-1　归一化为什么必须做
import numpy as np

def cos(a, b):
    return a @ b / (np.linalg.norm(a) * np.linalg.norm(b))

# 如果提前归一化，余弦就退化成点积，快一个数量级
def norm(v):
    return v / np.linalg.norm(v)

cos(norm(a), norm(b)) == norm(a) @ norm(b)     # True

# pgvector 里对应两种算子
# <=>  cosine distance = 1 - cos
# <#>  negative inner product（要求向量已归一化）
归一化的实际好处：索引效率更高（内积比余弦少一次除法）、避免零向量除法错误。
代价是必须保证入库和查询用同一个模型、同一个归一化方式，否则距离没有意义。

「同一个模型」这条规则听起来显然，但它是最常见的线上事故来源之一：换了 embedding 模型，只重建了一半索引，于是新旧向量混在一张表里。结果不是报错，是召回质量莫名下降 20%，而这种下降很难归因。

防法是：在表里存 model_name 和 dim 两列，查询时带上条件；换模型时新建一张表（或新建分区），重建完成再切换，绝不在原表上原地更新。

选模型：三个判断维度

维度怎么判断注意事项
语言中文为主必须选中文或多语模型很多英文模型在中文上退化明显，且不会报错
维度768 / 1024 / 1536 常见维度越高越贵（存储与计算都线性增长），收益递减
领域通用 vs 领域微调电商客服这类场景，通用模型通常够；法律医疗需要专门模型

不要用「跑分高」选模型。判断方法很实际：拿 30 条真实查询，人工标出「应该召回哪几条」，然后算每个模型的 recall@5。这个测试一小时能做完，比任何排行榜都准。

13.3　切分：按条款，不按字数

切分（chunking）是 RAG 里最被低估的一步。大多数人用的规则是「每 500 字切一块，重叠 50 字」，这个规则在小说上没问题，在业务文档上会持续制造错误。

例题 13-2　按字数切会切断什么
原文（售后政策）
第 4 条　耳机类商品签收后 7 天内可无理由退货，运费由买家承担。
第 5 条　质量问题 15 天内可退换，运费由卖家承担。判断依据为
        品牌售后检测报告；无报告时以开箱视频或照片为准。
第 6 条　定制类商品不适用无理由退货。

按 80 字切（块边界在「判断依据为」处）
块 A：第 4 条……第 5 条　质量问题 15 天内可退换，运费由卖家承担。判断依据为
块 B：品牌售后检测报告；无报告时以开箱视频或照片为准。第 6 条……

检索「质量问题怎么退」→ 命中块 A，得到「运费由卖家承担」但拿不到判断依据
检索「需要什么证明」→ 命中块 B，但没有「第 5 条」这个上下文，模型不知道这条在讲什么
问题的本质：条款是可独立引用的最小单位，而字数不是。
按字数切会把一条规则切成两半，两半单独看都不完整，而检索只能返回其中一块。

正确做法：三层切分

  1. 结构化切分：先按文档结构切（章 / 条 / 款 / 表格行）。如果文档有编号，就按编号切。这一步能解决 80% 的问题。
  2. 长度兜底：如果某个条款超过 800 字（比如一个长表格），再按句子切，但必须在块前加上「所属条款号」，让每个块自带上下文。
  3. 父子块：存两份——小块（用于检索，精准）和大块（用于生成，完整）。检索时用小块命中，返回给模型时用它的父块。

第三种做法解决了一个根本矛盾：检索要短（信息密度高，噪声少），生成要长（上下文完整，不断章取义）。两者不兼容，所以必须分开存。

例题 13-3　父子块的表结构
create table kb_chunk (
  id          bigserial primary key,
  doc_id      text not null,
  parent_id   bigint,                    -- 指向父块（null 表示自己是父块）
  clause_no   text,                      -- '售后政策v3.2 第5条'
  content     text not null,
  embedding   vector(1024),
  model_name  text not null,              -- 换模型时用于过滤
  policy_ver  text not null,              -- 政策版本
  effective_at date not null,             -- 生效日期
  is_active   boolean default true
);
三个元数据字段容易被省略，缺了都会出问题：
policy_ver 用于「政策改了，旧答案要失效」；effective_at 用于「按当时政策回答」；
is_active 用于「条款作废但不删除」（历史工单复盘需要）。

13.4　pgvector：建索引与带过滤查询

选 pgvector 而不是专用向量数据库，是一个工程判断：复用现有 PostgreSQL，少一个要运维的组件。在几百万条以内，它的性能完全够，而且它能和业务表 JOIN——这一点在需要按租户、按政策版本过滤时特别重要。

例题 13-4　HNSW 索引与带过滤的查询
-- 索引：HNSW，余弦距离
create index on kb_chunk
  using hnsw (embedding vector_cosine_ops)
  with (m = 16, ef_construction = 64);

-- 查询：先过滤再排序（过滤条件写在 WHERE 里）
select id, clause_no, content,
       1 - (embedding <=> $1) as score
from kb_chunk
where is_active
  and model_name = 'bge-m3'
  and policy_ver = $2
  and effective_at <= $3
order by embedding <=> $1
limit 8;
两个坑：
① m 和 ef_construction 越大越准但建索引越慢。16 / 64 是通用起点。
② 过滤 + 向量检索有冲突：HNSW 是先找近邻再过滤，如果过滤后剩下的很少，可能返回不足 k 条。
　　解法是调大 ef_search（会话级参数），或者用分区把过滤条件变成物理隔离。

第二个坑在真实业务里很容易踩到：如果你的知识库按政策版本分区，而查询要求 policy_ver='v3.2' 却只覆盖了 10% 的数据，向量索引会先在全部数据里找 8 个最近邻，然后过滤，结果可能只剩 1–2 条。

最干净的解法是按 policy_ver 做分区表，让每个版本有自己的索引。这样过滤在物理层面完成，不依赖 ef_search 调参。代价是查询时要动态指定分区——但这是路由层的事，不影响业务代码。

13.5　量化检索质量：recall@k

检索质量不能用「感觉召回得还行」来判断。有一个简单且够用的指标：recall@k——对于每条查询，人工标出「正确的知识条目」，看前 k 条里召回了几条。

例题 13-5　算 recall@5
测试集：50 条真实查询（从工单里抽，带人工标注的相关条款）

查询 1：应召回 {第4条, 第5条}　实际 top5 = {第4条, 第12条, ...}　→ 命中 1/2
查询 2：应召回 {第7条}　　　　　实际 top5 = {第7条, ...}　　　　　→ 命中 1/1
...
50 条平均：recall@5 = 0.72

解读：
  > 0.90　检索基本不是瓶颈，去优化生成
  0.75–0.90　还有空间，先查切分和 embedding
  < 0.75　检索是主瓶颈，改提示词无效（对应第 4 章归因树的 ② 层）
这个指标的价值在于它把「检索」和「生成」的功劳分开了。
没有它，你只知道「答错了」；有了它，你知道是「没找到」还是「找到了没用对」。

混合检索：什么时候值得做

混合检索 = 向量检索 + 关键词检索（BM25），两路结果融合。它的收益集中在两类查询上：

  • 含专有名词、型号、编号：「XR-200 的保修期」——向量可能召回「耳机保修」但不含型号。
  • 短查询：「能退吗」这三个字的向量信息量极低，向量检索表现不稳定；关键词反而能匹配到「退货」条款。

判断要不要做：先算 recall@5。如果已经 0.88 以上，混合检索的收益通常小于维护成本。如果在 0.7 左右，且错误里有大量「型号/编号类」查询，就值得做。

融合方式最简单的是 RRF（Reciprocal Rank Fusion），它不需要两路分数可比：

例题 13-6　RRF 融合
# score = Σ 1 / (k + rank)，k 通常取 60
def rrf(lists, k=60):
    score = defaultdict(float)
    for lst in lists:              # 每路一个排序列表
        for rank, doc_id in enumerate(lst, 1):
            score[doc_id] += 1 / (k + rank)
    return sorted(score, key=score.get, reverse=True)
RRF 只用到排名，不用分数。这是它最大的优点：
向量相似度（0–1）和 BM25 分数（0–几十）量纲完全不同，直接加权是错的，而 RRF 绕过了这个问题。
四个让召回质量悄悄下降的做法
  1. 换 embedding 模型但不重建全量索引。新旧向量混在一张表，不报错，只是变差。用 model_name 过滤 + 新建表切换。
  2. 按字数切条款。规则被切成两半，检索只能命中其中一半，模型断章取义。
  3. 查询向量没归一化，入库的归一化了。距离计算失去意义，返回结果接近随机。
  4. 只按向量检索就下结论「RAG 效果不好」。先算 recall@5，可能是检索问题，不是 RAG 本身不行。
本章小结
  • 关键词检索在同义、口语、跨表达三种情况下失效，向量检索补这块，但精确匹配仍要靠关键词。
  • 余弦要归一化；入库与查询必须同模型同归一化；换模型要新建表切换，不能原地更新。
  • 选 embedding 模型用 30 条真实查询算 recall@5，不看排行榜。
  • 按条款切，不按字数切；超长条款切完要带上条款号；检索用小块、生成用父块。
  • pgvector 的过滤与向量检索有冲突，最干净的解法是按版本分区。
  • recall@5 < 0.75 说明检索是主瓶颈，此时改提示词无效。
  • 混合检索用 RRF 融合（只用排名，不用分数），适合型号、编号、短查询。

本章综合习题

综合题一知识库上线后，坐席反馈「问退款政策，它答的是换货政策」。列出三种可能原因，并说明如何用 recall@5 判断责任在检索还是在生成。
答案

三种原因：

① 切分把两条政策放进了同一个块。如果第 4 条（退款）和第 5 条（换货）在同一个 500 字的块里，检索命中这个块，模型看到两段内容，选了错的那一段。这是最可能的原因。

② 两条政策的向量太接近。「7 天内可无理由退货」和「15 天内可退换」语义高度相似，如果知识库里还有一条「换货运费由卖家承担」，排序可能颠倒。

③ 政策版本混了。v3.1 的退款条款和 v3.2 的换货条款同时被召回。模型没有版本概念，它只会引用看起来相关的那条。

怎么判断责任：

对这批问题算 recall@5：如果正确条款（第 4 条）出现在 top5 里，说明检索没问题，是生成没用对（原因可能是块里混了条款、或提示词没要求引用编号）。如果正确条款根本没被召回，说明检索有问题（切分或向量）。

再做一步更精确的：注入对照——把第 4 条原文直接塞进提示词，看模型能否答对。能答对，就是检索问题；还是答错，就是判断层问题（第 4 章的错误归因树）。

为什么必须先判这一层：「答错政策」这个症状，三种原因的修法完全不同——改切分、改 embedding、加版本过滤。不区分就只能三个都试一遍，而每个都需要一天。一个 50 条的 recall@5 测试，半小时就能定位。

综合题二你要为一个 3,000 条的售后政策库设计切分方案。写出具体规则，并说明如何处理长表格和跨条款引用。
答案

规则（四层，按顺序执行）：

① 第一层：按编号切。政策库通常有「第 X 条」或用标题分节。以条款为最小单位，一条一块。这一层能覆盖 90% 的内容，且保证每个块可独立引用。

② 第二层：每个块前加「上下文头」。格式是「《售后政策 v3.2》第 5 条（质量问题退换）」。这个头会被一起向量化。这一条极其重要——因为条款正文里常常没有「售后」「退货」这些词（比如「质量问题 15 天内可退换」不含「售后」），但客户的问题里一定有。

③ 第三层：超过 800 字的条款拆成子块，并建父子关系。子块用于检索，父块用于生成。子块开头也带上下文头 + 「（第 1/3 部分）」。

④ 第四层：长表格按行切，每行带表头。比如运费表，每行是「品类 + 情形 + 承担方」，切出来必须是完整的一行且包含表头信息，不能只切半行。

跨条款引用怎么处理：原文里如果出现「按第 6 条执行」，不要把它展开成正文（会重复且容易过期），而是在块的元数据里加一个 refs 字段 ['第6条']。检索时如果命中了含 refs 的块，把被引用的块一起取出来作为附加上下文。

为什么不用重叠（overlap）：重叠是为「切断了句子」设计的补丁。按条款切不会切断句子，所以不需要重叠。加了重叠反而会让相邻条款的内容出现在同一个块里——那正是综合题一里「答错政策」的原因。

一个验收标准：随机抽 30 个块，让一个不了解业务的人读，问他「这一条讲的是什么情况适用」。如果他能答对，说明块是自包含的；如果他说「不知道在说什么」，说明上下文头不够或切分有问题。

综合题三recall@5 只有 0.68。列出你的改进顺序（不超过五步），并说明每一步的预期收益和验证方式。
答案

五步，按「成本低、收益大」排：

① 看失败的 32% 是什么类型（0 成本，半天）。把没召回的那些查询逐条看，分类：是切分问题（正确条款被切断了）、是词汇问题（客户说法和条款用词完全不同）、还是精确匹配问题（型号、编号）。这一步决定后面几步的优先级，不能跳过。

② 改切分 + 加上下文头（1–2 天，预期 +8~15 个点）。如果 ① 里「切分问题」占比最高（通常如此），这一步收益最大。验证方式：重跑同一份 50 条测试集，看 recall@5 的变化。

③ 换 embedding 模型（半天，预期 +3~10 个点）。用同一份测试集对比 2–3 个候选模型。注意必须全量重建索引，不能混。如果 ① 里主要是「词汇问题」，这一步收益明显；如果是「切分问题」，收益很小。

④ 加混合检索（1–2 天，预期 +5~12 个点）。针对 ① 里「精确匹配问题」的部分。用 RRF 融合，不需要调权重。验证时要分层看：含型号/编号的查询提升多少，纯自然语言查询有没有变差。

⑤ 加 rerank（1 天，预期 +3~8 个点）。用交叉编码器（cross-encoder）对 top20 重排。它比向量检索准但慢，所以只对少量候选做。这一层对「语义接近但答案不同」的情况特别有效——比如退款 vs 换货。

为什么这个顺序：①②③ 是「修数据」，④⑤ 是「加组件」。数据没修好就加组件，会把问题埋得更深——比如切分错了，加 rerank 只是让错误的块排得更靠前。而且每加一个组件，就多一个需要调参和监控的东西。

一个反向提醒：如果做完 ①–⑤ 仍不到 0.85，要考虑的是「这个知识库本身是否回答了这些问题」。有些查询在知识库里真的没有答案，那不是检索的问题，是知识覆盖的问题——而这类情况应该被识别出来并走拒答（第 2 章），而不是靠调检索硬凑。
