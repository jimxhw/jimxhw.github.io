第三篇 · 服务
第 10 章　异步与并发
一个请求等 8 秒，一百个请求就是 800 秒

AI 服务有一个和传统接口完全不同的特征：几乎全部时间都在等。等模型返回、等工具接口、等数据库。这类「等待占 95%」的服务，一旦用同步写法，并发能力会退化到 1——不是慢一点，是根本上不去。这一章讲清楚为什么，以及怎么写对。

本章学习目标
理解　I/O 密集型服务里，线程数不是并发能力的上限，等待方式才是
掌握　async/await 的正确写法，以及最常见的三个「假异步」错误
掌握　超时、重试、退避、熔断四件套的配置顺序
掌握　流式接口的并发模型：长连接占用与并发上限的关系
了解　什么任务不该同步做，而应该进队列

10.1　等 8 秒的真实代价

一个 AI 摘要请求 8 秒，其中模型推理占 7.6 秒，本地处理占 0.4 秒。这个比例决定了它必须异步。

先看同步版本会发生什么。假设用 4 个 worker 进程，每个进程一次处理一个请求：

例题 10-1　并发能力的算术
同步（4 worker × 1 并发）：
  吞吐 = 4 / 8s = 0.5 请求/秒
  60 个坐席，每人每 3 分钟用一次 → 0.33 请求/秒
  看起来够用，但只要有 5 个人同时点：
  第 5 个人要等 8s，第 6 个等 16s → P95 直接爆炸

异步（4 worker × 每进程 50 并发）：
  吞吐上限 ≈ 200 / 8s = 25 请求/秒
  实际瓶颈变成上游配额，而不再是本地进程
关键不是「快 50 倍」这个数字，是瓶颈位置变了：
同步时瓶颈是你的进程数，异步时瓶颈是上游配额——后者才是应该被管理和优化的地方。

为什么同步版本只能 1 并发？因为线程在等 I/O 时是被挂起的，但它占着栈和它所在的执行单元。要更多并发就只能加线程，而线程有成本（约 1MB 栈、上下文切换），到几百个就开始互相拖累。

异步模型换了一种做法：等的时候把执行权交出去，同一个线程去处理别的请求，等结果回来再接着执行。一个线程可以同时持有上千个「等待中」的请求，因为它们不占执行权，只占一点内存。

10.2　三个「假异步」

写完 async def 不等于异步。有三种写法会把事件循环堵住，效果和同步一样，甚至更差（因为你还以为它是异步的）。

错误一：在 async 函数里调用同步的库

例题 10-2　阻塞调用堵住整个循环
# ✗ requests 是同步库，这一行会把事件循环卡住 8 秒
async def call_llm(prompt):
    r = requests.post(URL, json={...}, timeout=60)
    return r.json()

# ✓ 换成异步客户端
async def call_llm(prompt):
    async with httpx.AsyncClient(timeout=60) as c:
        r = await c.post(URL, json={...})
        return r.json()

# ✓ 如果只能用同步库，丢到线程池
await asyncio.to_thread(requests.post, URL, json={...}, timeout=60)
危害在于它不报错。表面上一切正常，只是并发上不去，P95 随人数线性上升。
检测方法：日志里打 asyncio.all_tasks() 的数量，如果并发请求很多但任务数一直是 1，就是这个原因。

错误二：在 async 函数里做重计算

Markdown 转 HTML、PDF 解析、大 JSON 序列化、加密——这些是 CPU 密集的，await 救不了它们。它们必须放到进程池（ProcessPoolExecutor）或独立服务里，因为 Python 的 GIL 让线程池对 CPU 任务无效。

经验判断：单次超过 50ms 的纯计算，就不要放在请求路径上。

错误三：以为 asyncio.gather 会自动限流

例题 10-3　并发上限必须显式加
# ✗ 200 个请求同时发出去 → 上游 429，全部失败
results = await asyncio.gather(*[call_llm(x) for x in items])

# ✓ 用信号量限流
SEM = asyncio.Semaphore(16)

async def guarded(x):
    async with SEM:
        return await call_llm(x)

results = await asyncio.gather(*[guarded(x) for x in items])
gather 只负责「一起等」，不负责「限速」。
200 个同时打出去，通常的结果是 180 个 429、20 个成功，总耗时反而比限流更长。

10.3　流式接口的并发模型

流式请求有一个特殊性质：它的连接生命周期很长。一次普通请求 0.2 秒，一条流 9 秒，相差 45 倍。这意味着并发连接数会以同样倍数堆积。

算一下真实的占用：60 个坐席，平均每 3 分钟触发一次，每次 9 秒。按照利特尔法则（Little's Law），平均并发 = 到达率 × 驻留时间 = 0.33 × 9 ≈ 3 个并发连接。这个数字很小，看起来完全不用担心。

但峰值不是平均值。真实分布是「上班前 10 分钟集中使用」，那 10 分钟里可能有 40 个人同时触发，于是瞬时 40 个并发连接。

环节默认上限超限后的表现
浏览器同域连接数6（HTTP/1.1）后续请求排队，界面表现为「点了没反应」
Nginx / 网关常见 1024一般不是瓶颈，但 proxy_read_timeout 默认 60s 会掐断长流
应用 worker看你设的并发上限排队，或直接 429
上游模型配额按账号的 RPM/TPM429，且会连带影响其他功能

第一行经常被忽略：HTTP/1.1 下浏览器对同一域名只开 6 个连接。如果你的页面同时有 6 个流式请求（比如打开一个有 6 个面板的看板），第 7 个会被浏览器排队，而排队是不发出去的——服务端看不到，日志里也没有，用户只看到「没反应」。解决办法是 HTTP/2（多路复用）或把流分配到不同子域。

流式的并发上限要单独设

普通请求和流式请求不能共用一个并发池。原因：一个流占 9 秒，如果流把池占满，普通请求（比如「加载工单详情」）就全部排队，整个页面卡住。

做法是分两个信号量：SEM_STREAM=20、SEM_FAST=100，并且流式超限时的行为是快速失败并告知，而不是排队。因为排队 9 秒的流对用户毫无意义——他早就放弃了。

10.4　超时、重试、退避、熔断

四件套有严格的配置顺序，顺序错了会互相打架。

第一步：给每层设超时，且内层小于外层。

例题 10-4　超时预算的分层
用户可接受的总时长　　　　　　　　　　30s
  前端 fetch 超时　　　　　　　　　　 28s   # 略小于总预算
    服务端请求处理上限　　　　　　　　 25s
      上游模型连接超时　　　　　　　　  5s   # 建连不该慢
      上游模型首字超时　　　　　　　　 12s
      上游模型总超时　　　　　　　　　 22s
      工具接口超时　　　　　　　　　　  3s   # 内部接口，应该很快
核心规则：内层超时必须小于外层。
如果内层 30s、外层 25s，外层先超时放弃，但内层的请求还在跑——你既拿不到结果，又在付费。

第二步：只对可重试的错误重试。429、502、503、连接超时可重试；400、401、403、内容审核拒绝不可重试。这个判断必须显式写，不能「失败就重试三次」——对 400 重试三次只是把一次错误放大成三次。

第三步：退避要带抖动。

例题 10-5　指数退避 + 抖动
import random, asyncio

async def with_retry(fn, max_try=3, base=0.8):
    for i in range(max_try):
        try:
            return await fn()
        except Retryable as e:
            if i == max_try - 1:
                raise
            # 指数 + 全抖动：0 ~ base*2^i 之间随机
            await asyncio.sleep(random.uniform(0, base * 2 ** i))
不加抖动会形成重试风暴：所有失败请求在同一时刻重试，
上游刚要恢复又被压垮，然后集体再等一轮。抖动把重试摊平到整个区间。

第四步：熔断。当连续失败率超过阈值（比如 20 次里失败 10 次），直接快速失败一段时间，不再请求上游。理由是：上游已经不行了，继续请求只会让它更不行，而你的用户还得等满超时。

熔断的三个状态：关闭（正常）、打开（快速失败）、半开（放几个请求试探）。半开这一步不能省——没有它，恢复后无法自动回到正常状态。

四件套的顺序是超时 → 重试 → 退避 → 熔断，因为它们的作用域是嵌套的：超时限制单次，重试包住单次，退避在重试之间，熔断包住所有重试。

10.5　什么不该同步做

有一条判断标准很好用：如果用户不需要在这一次交互里看到结果，就不要在请求路径上做。

任务该不该同步理由
生成回复建议同步（流式）用户正在等
工单自动分类异步队列结果用于路由，不需要立刻显示
批量重算历史摘要异步队列 + 进度条分钟级，跑完通知即可
评估集跑批离线任务不是线上路径
向量化知识文档异步队列文档更新后 1 分钟内可检索即可

把「工单自动分类」从同步改异步，会带来一个额外的收益：可以重试。同步请求失败了，用户看到红字，你要他再点一次；异步任务失败了，队列会自动重试，用户无感。这是异步最容易被忽略的价值——它不只是为了快，更是为了「失败可以被消化」。

但异步也有代价，必须提前设计两件事：

  1. 幂等：同一个工单被投递两次，不能产生两条分类、两次通知。用 ticket_id + task_type 做去重键。
  2. 可观测：队列积压了多少、最老的任务等了多久。没有这两个数，异步系统挂了你是最后一个知道的。
四个会拖垮服务的写法
  1. async 里调同步 SDK。不报错，只是并发退化成 1——最难查的一类性能问题。
  2. gather 不限流。一次打 200 个，换来 180 个 429，总耗时比串行还长。
  3. 外层超时小于内层。外层放弃后内层还在跑，钱照花，结果没人要。
  4. 流式和普通请求共用并发池。一条长流能把整页的其他接口拖死。
本章小结
  • AI 服务 95% 时间在等，同步写法把并发压到 1，瓶颈错误地落在进程数上。
  • 三个假异步：同步库、重计算、gather 不限流。第一种最隐蔽，靠 all_tasks() 数量检测。
  • 流式连接生命周期长 45 倍，并发上限要单独设，超限应快速失败而不是排队。
  • HTTP/1.1 同域 6 连接是隐形上限，界面「点了没反应」可能卡在浏览器而不是服务端。
  • 超时分层：内层必须小于外层；只对可重试错误重试；退避必须带抖动；熔断要有半开态。
  • 不需要用户当场看到结果的任务进队列，它带来的是「失败可被消化」，不只是快。

本章综合习题

综合题一服务上线后，1 个用户时 P95 是 9 秒，20 个用户时 P95 变成 90 秒。你的代码全是 async def。最可能的原因是什么？给出两个验证方法。
答案

最可能的原因：async 函数里调用了同步阻塞的东西。90 秒 ≈ 9 秒 × 10，这个「线性叠加」的形状是典型特征——请求在串行执行，20 个请求排成 10 批。如果瓶颈是上游配额，通常表现为部分 429 而不是整齐的倍数增长。

最常见的三处：requests 而不是 httpx.AsyncClient；同步的数据库驱动（psycopg2）；同步的文件读写或 time.sleep。

验证一（最快）：在请求处理中途打印 len(asyncio.all_tasks())。如果并发 20 个请求时这个数一直是 1–2，说明事件循环里确实只有一个任务在跑，其余都在等——确认阻塞。

验证二（定位到具体行）：用 py-spy dump --pid <pid> 在压力下抓两次栈。如果两次都停在同一个同步调用的内部（而不是 epoll_wait），那一行就是元凶。py-spy 不需要改代码，也不需要重启，是排查这类问题最有效的工具。

为什么不用「加 worker」解决：加 worker 只是把 90 秒变成 45 秒，成本翻倍而根因还在。先确认是不是阻塞，再谈扩容——顺序反了，你会为一个代码问题持续付服务器费用。

综合题二上游模型服务开始不稳定，随机 20% 请求超时。你有超时、重试、退避、熔断四个手段。给出你的配置方案和理由。
答案

配置方案：

首字超时      12s     总超时  22s     （前端 28s，留余量）
重试次数      2 次（共 3 次尝试），仅对超时和 503
退避          0.8s / 1.6s，全抖动
熔断          滑动窗口 60s 内失败率 > 50% 且样本 ≥ 20 → 打开
              打开 30s → 半开，放 3 个请求试探，全成功才关闭
单请求总预算  28s（超过则直接放弃，不再重试）

四条理由：

① 20% 失败率下，重试 2 次能把成功率提到 1 − 0.2³ = 99.2%。这是重试唯一真正有效的场景：独立随机失败。如果失败是相关的（同一个上游全挂），重试毫无用处，这就是为什么必须配熔断。

② 总预算必须封顶。3 次尝试 × 22 秒最坏情况是 66 秒，前端早就断了，而服务端还在烧钱。所以要有「单请求总预算 28 秒」，超了就直接返回失败——这个预算要显式实现，不能指望超时自己叠加。

③ 熔断的样本门槛不能低。如果窗口里只有 3 个请求、失败 2 个，失败率 67%，但不该熔断——样本太少，噪声太大。这就是 样本 ≥ 20 这个条件的意义。

④ 半开只放 3 个。放太多会在上游刚恢复时又把它压垮；放 1 个又可能因为偶然失败而重新打开。3 个是经验值，全成功才关闭。

一个容易漏的补充：熔断打开期间，接口应该返回什么？不能返回 500，应该返回 503 + code: UPSTREAM_UNAVAILABLE + hint: 预计 30 秒后恢复，并让前端显示「暂时不可用，可手动刷新」而不是「出错了」。熔断是保护措施，不该表现成故障。

综合题三为什么「工单自动分类」更适合异步队列而不是同步接口？如果改成异步，你需要额外设计哪三样东西？
答案

为什么异步：

① 结果不被当场消费。分类结果用于把工单路由到正确的技能组，发生在工单创建后的几秒内，坐席不需要盯着它。同步做等于让用户为一个他看不见的结果等待。

② 失败可以重试。同步失败只能让用户重试（他不会），异步失败队列会自动重试 3 次，最终进死信队列。

③ 可以削峰。工单创建有突发（比如群发通知后集中回复），同步会把峰值直接压到模型配额上，异步可以排队消化。

④ 省一次往返。同步要等 1–2 秒，这 1–2 秒会占住一个并发位；异步只是投递一条消息，几毫秒。

必须额外设计的三样：

① 幂等键。ticket_id + task_type 做去重。否则同一条工单被投递两次（重试、或前端重复提交），会产生两条分类记录，甚至两次通知。

② 死信队列与告警。重试 3 次仍失败的任务进死信，并且要有告警。没有死信队列的异步系统，失败任务是静默消失的——用户以为分类了，实际没有，工单一直挂在「未分类」里。

③ 状态回写与超时兜底。工单上要有一个 classify_status 字段（pending / done / failed）。并且要有一个定时任务扫描「pending 超过 5 分钟」的工单，重新投递或降级为人工分类。这一条是为了防止消息丢失导致工单永久卡住。

这道题的一般形式：把任何同步任务改异步，都要同时回答「重复怎么办、失败怎么办、卡住怎么办」三个问题。三个都答上来，才算设计完。
