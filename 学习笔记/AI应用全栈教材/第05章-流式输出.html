第 5 章　流式输出
它解决的从来不是速度问题，是等待的问题

第一篇建立了尺子，也拿到了第一份数字。从这一章开始进入你的主场：界面。流式输出是 AI 交互里最容易被低成本实现、又最容易被做坏的一层。多数团队只加了 stream: true 就以为做完了，然后在真实使用中遇到卡顿、乱码、半截代码块、反复闪烁——这些问题没有一个出在模型侧。

本章学习目标
理解　为什么「总耗时相同、首字更早」的实现体感快得多
掌握　SSE 的解析循环，包括中文被拆包时的处理
掌握　增量渲染的三个坑：半截语法、重排抖动、代码块未闭合
掌握　中断、重试与降级：如何让流式失败不像崩溃
了解　为什么密钥绝不能出现在浏览器里

5.1　8 秒的两种过法

场景

客服工作台的右侧有一个「会话摘要」面板。改造之前，坐席点「生成摘要」，按钮变成转圈，8 秒后整段摘要一次性出现。改造之后，文字以每秒约 200 字的速度吐出来，2 秒内出现第一个字，9 秒才全部完成。

总耗时变长了 1 秒。但两周后的埋点数据显示：改造前面板的日均打开次数 43 次，改造后 210 次；摘要采纳率从 24% 升到 39%。

有个坐席在访谈里说了一句很关键的话：「以前我不知道它在干什么，我会去点别的，回来就忘了要干什么了。」

这段访谈解释了流式的真实作用。它不是在「让用户少等」，因为总时间没有减少；它是把一段没有信息的等待，换成一段有信息的等待。人忍受不确定的能力很差，忍受确定的进展的能力很好——同样 8 秒，转圈是前者，逐字输出是后者。

有三个数字值得记住，它们是设计流式的依据：

时间点用户的状态设计含义
0–1 秒注意力还在上一个动作上不需要任何反馈，加骨架屏反而显得闪
1–3 秒开始怀疑是不是没点上必须有可见变化（按钮态、光标的第一个字）
> 5 秒无变化判定为卡住，开始重复点击重复点击会带来并发请求，这是后续第 6 章要处理的问题

由此得到一个具体的设计规则：首字时间（TTFT）比总耗时重要得多，应当作为独立的性能指标来优化。把 TTFT 从 4 秒降到 1.5 秒，即使总耗时不变，体感提升也远大于把总耗时从 9 秒降到 7 秒。

5.2　SSE：一条长连接上的分帧

流式传输的事实标准是 SSE（Server-Sent Events）。它的好处是纯 HTTP、无需协议升级、能穿过大多数代理。代价是单向（只能服务端推）、文本协议（二进制要编解码）、以及没有内置的重连语义——断了就是断了。

数据格式极简，每一帧是 data: 加内容加两个换行。但实际使用中有三个陷阱，全部出在「网络会把字节流切成任意大小」这件事上。

例题 5-1　浏览器侧的正确读法
const res = await fetch('/api/summarize', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ ticketId }),
  signal: controller.signal,          // 用于中断
});

const reader = res.body.getReader();
const dec = new TextDecoder('utf-8');
let buf = '';

while (true) {
  const { done, value } = await reader.read();
  if (done) break;

  // stream:true 让不完整的 UTF-8 字节留在 decoder 内部
  buf += dec.decode(value, { stream: true });

  // 只按完整帧切分，剩下的留在 buf
  let idx;
  while ((idx = buf.indexOf('\n\n')) >= 0) {
    const frame = buf.slice(0, idx);
    buf = buf.slice(idx + 2);
    if (frame.startsWith('data: ')) {
      const payload = frame.slice(6);
      if (payload === '[DONE]') return;
      onDelta(JSON.parse(payload).text);
    }
  }
}
两个必须有的东西：decoder 的 stream 选项，以及跨帧的缓冲区。
少了第一个：一个中文字在 UTF-8 里占 3 字节，被切成 2+1 时两个都不合法，输出乱码。
少了第二个：一帧可能被切成两次到达，JSON.parse 直接抛错——这是流式最常见的线上故障。

乱码这个坑特别值得强调，因为它在英文环境里几乎不会出现，而在中文业务里必然出现。表现是：大部分内容正常，偶尔蹦出一个 �，或者某句话的头两个字母不见了。日志里看不出来，只有肉眼看界面能发现，而它通常出现在快速滚动时。

还有一个更隐蔽的问题：服务端也用了缓冲区。即使你的代码是逐块 write，前面的 Nginx、负载均衡、甚至某些运行时的默认行为，都可能把小块攒成大块再发出去。这时你会发现「流式」变成了每 2 秒来一大段。

例题 5-2　让流真的流起来
# 服务端（FastAPI）：三个 header 缺一不可
return StreamingResponse(
    gen(),
    media_type='text/event-stream',
    headers={
        'Cache-Control': 'no-cache, no-transform',   # no-transform 禁止代理压缩改写
        'X-Accel-Buffering': 'no',                  # 关掉 Nginx 的缓冲
        'Connection': 'keep-alive',
    },
)
如果上线后发现「还是一大段一大段地来」，先检查这三行，再检查 CDN 有没有开压缩。
这类问题在本地开发环境 100% 不会出现，因为本地没有反向代理。

5.3　增量渲染：三个必须处理的半截状态

拿到增量文本之后，多数人做的第一件事是 setState(prev => prev + delta)。这在纯文本上没问题，但 AI 的输出几乎总是 Markdown——而 Markdown 的语法是跨越字符的，流式到达时会出现大量「语法未闭合」的中间状态。

坑一：半截语法导致渲染跳变

假设模型正在输出一个加粗的词。到达的字节序列依次是：这是 → **重 → **重要** → 的。在第二个时刻，界面上会先出现两个字面星号 **重，然后突然变成加粗的「重要」。

用户的感受是「文字在跳」。每次格式切换都会引起一次重排，一段 300 字的回复里可能跳十几次。

处理方式有两种，按成本排序：

  • 简单方案：流式期间用纯文本渲染，结束后再切到 Markdown。实现成本几乎为零，代价是最后有一次整体重绘——如果回复长，这次重绘很明显。
  • 更好方案：只对「已闭合」的片段做 Markdown 解析，未闭合的尾部按纯文本输出。也就是把文本切成「安全前缀 + 不稳定尾部」，只渲染前缀。
例题 5-3　安全前缀切分
function splitSafe(text) {
  // 未闭合的行内标记：** __ ` ~~ 以及链接的 [
  const inline = ['**', '__', '`', '~~'];
  for (const m of inline) {
    const n = text.split(m).length - 1;
    if (n % 2 === 1) {                    // 奇数个 → 最后一个未闭合
      const i = text.lastIndexOf(m);
      return [text.slice(0, i), text.slice(i)];
    }
  }
  // 未闭合的代码块：``` 计数为奇数
  const fences = (text.match(/```/g) || []).length;
  if (fences % 2 === 1) {
    const i = text.lastIndexOf('```');
    return [text.slice(0, i), text.slice(i)];
  }
  return [text, ''];
}
稳定前缀交给 Markdown 渲染器，尾部当纯文本。
代价是尾部那一小段会短暂丢失格式，但因为它是「正在被写出来」的地方，用户反而觉得自然。

坑二：每次都全量重渲染

每来一个 delta 就整段重新解析 Markdown 并替换 DOM，在 300 字以内还行，超过 800 字就会开始掉帧。原因是 Markdown 解析是 O(n)，而 delta 有几百个，总复杂度是 O(n²)。

两个改法，都不复杂：

  1. 按块增量：以空行为界，把文本切成块，已经结束的块解析一次后缓存起来（用块内容的哈希做 key），只重算最后一块。
  2. 按时间节流：不是每个 delta 都渲染，而是每 16–50ms 合并一次。人眼分辨不出 20ms 的差异，但渲染次数能降一个数量级。

节流的阈值有讲究。低于 16ms 没有意义（还不如一帧），高于 100ms 会看出「一段一段跳」。40ms 左右是舒服的区间：视觉上连续，渲染压力降到 1/25。

坑三：滚动位置被抢走

内容在增长，容器高度在变。如果容器是「自动滚到底」，用户在生成过程中向上滚动查看前面的内容，会被强行拽回底部。这是 AI 产品里抱怨最多的问题之一。

规则很简单，但必须显式实现：只有用户本来就贴在底部时，才自动跟随。

例题 5-4　跟随与脱离
const NEAR = 48;   // px，容差
let stick = true;

box.addEventListener('scroll', () => {
  const gap = box.scrollHeight - box.scrollTop - box.clientHeight;
  stick = gap < NEAR;         // 用户滚上去了 → 停止跟随
}, { passive: true });

function onDelta(t) {
  append(t);
  if (stick) box.scrollTop = box.scrollHeight;
}
再加一个细节体验会好很多：脱离了跟随之后，右下角浮出「回到最新」按钮，点击后 stick = true 并滚到底。
这一条不需要任何额外状态机，但用户会明确感觉到「它听我的」。

5.4　中断、失败与降级

流式最容易被忽略的是失败路径，因为它「大部分时候是好用的」。而线上真正影响信任的就是那 3% 的失败：请求发出去了、字吐了一半、连接断了。用户看到的是半句话，而他不知道这半句话能不能用。

中断要做两件事，缺一不可

用户点「停止生成」时，前端的 controller.abort() 只断开了浏览器到你的服务；服务端到模型的请求可能还在跑，继续消耗 token。正确做法是前端 abort 后，服务端要能感知连接关闭并主动取消上游请求。

例题 5-5　服务端的取消传播
async def gen():
    try:
        stream = await cli.chat.completions.create(..., stream=True)
        async for chunk in stream:
            if await request.is_disconnected():   # 客户端已断开
                await stream.close()
                return
            yield 'data: %s\n\n' % json.dumps({'text': chunk.delta})
    except asyncio.CancelledError:
        raise                       # 不要吞掉，否则连接无法正确关闭
不做这件事的代价在账单上：一个坐席打断 5 次、每次浪费 1,200 token，每天 200 人就是 120 万 token/天 的纯浪费。
而且这些请求会占着并发配额，让别人的首字时间变长。

第二件事是界面上的交代。半截内容不能就这么留在那里。合理的处理是：在半截文本后追加一行浅色的状态提示「已停止 · 内容不完整」，并保留一个「重新生成」的入口。不要清空已生成的内容——那会让用户觉得白等了，而实际上那半段往往是有用的。

断线与重试

网络断了，重试是最自然的想法，但流式的重试有一个特殊问题：你不能从断点续传。模型是无状态的，它不知道上次写到哪。所以重试只能整体重来，而整体重来意味着用户会看到开头重复一遍。

可接受的做法有三种，按体验排序：

做法体验适用
清空重来差，但清晰刚开始就断了（< 10% 内容）
保留旧内容，新内容另起一块并标注「重新生成」中，会有点重复感断在中间
用已生成的内容作为前缀，让模型「接着写」好，但可能语义重复长文，且断在明显的位置

第三种听起来最聪明，实际上要慎用：模型看到「已有的半段」会倾向重复刚说过的内容，尤其在段落中间。如果要用，提示词里必须写清「以下内容已经生成，请直接续写，不要重复前文」，并且接受偶尔的重复。

降级：流式失败后自动退回非流式

有一个成本很低但很少有人做的策略：首字超时 6 秒仍未收到第一帧时，自动中止并以非流式重试一次。

理由是这样：首字慢通常意味着上游排队或网络抖动，这时继续等下去大概率还是慢；而非流式请求走的是同一条链路，但只需一次往返，反而可能在 3 秒内拿到完整结果。用户看到的是「等了 6 秒，然后整段出现」，体验不算好，但比「等了 40 秒什么都没有」强得多。

这个策略要配一个指标：降级率。如果降级率超过 5%，说明链路有系统性问题，应该去查上游而不是继续优化前端。

5.5　密钥不能出现在浏览器里

这一节短，但它是整本书里最不能妥协的一条。

很多教程的示例代码是直接在浏览器里 new OpenAI({ apiKey: 'sk-...' })。这个写法在演示里完全可用，因为浏览器确实能调通那个接口。但它等于把你的密钥公开发布了：任何人打开开发者工具就能拿到，然后以你的名义消费，账单记在你头上。

除了密钥，还有三件只有服务端才能做的事：

  • 审计：谁在什么时候问了什么。合规要求留痕时，前端直连无法留。
  • 脱敏：请求出网前把手机号、身份证替换掉。前端做也能做，但用户可以绕过前端。
  • 限额：按人、按部门、按功能限流。前端做不到，因为它可被篡改。

所以标准架构只有一个形状：浏览器 →（你的服务，做鉴权/脱敏/限流/审计）→ 模型。你的服务在这里是一个薄代理，但它承担的正是那些「必须可信」的职责。

流式实现的四个红线
  1. 密钥进前端：等于公开。哪怕只用于内部系统，也会出现在截图和录屏里。
  2. 不做跨帧缓冲：迟早会遇到半截 JSON 导致解析失败，而且只在弱网时出现，测试环境复现不了。
  3. 不做取消传播：用户每次打断都在花你的钱，且占用并发。
  4. 不处理半截 Markdown：界面会持续跳动，用户会认为「这个功能很粗糙」，而实际上只是渲染问题。
本章小结
  • 流式解决的是「等待有没有信息」，不是「快不快」。优化目标是 TTFT，不是总耗时。
  • SSE 解析必须有两样东西：TextDecoder 的 stream:true，以及跨帧缓冲。
  • 服务端要发 no-transform / X-Accel-Buffering: no，否则代理会把流攒成大块。
  • 增量渲染的三个坑：半截 Markdown、全量重解析、滚动被抢。三者都有低成本解法。
  • 中断要做取消传播；断线不能续传，只能重来或续写；首字超时可降级为非流式。
  • 密钥、审计、脱敏、限额——四件事决定了你必须有一个服务端代理。

本章综合习题

综合题一上线后运营反馈「有些字显示成方块」。你在本地和测试环境都复现不了。最可能的原因是什么？给出两个验证方法。
答案

最可能的原因：UTF-8 多字节字符被分包截断，且解码时用了 dec.decode(value) 而没有 { stream: true }。一个中文字占 3 字节，很可能被切在 1+2 或 2+1 的位置。没有 stream 选项时，TextDecoder 会把不完整的字节序列替换成 U+FFFD（显示为 � 或方块），并且这个替换是不可逆的——后续字节到达时，前面那两个字节已经丢了。

为什么本地复现不了：本地环回网络的 MTU 和分包方式与线上不同，服务端一次 write 往往正好是完整字符边界。加上本地通常没有反向代理，流不会被二次切分。

验证方法一（最直接）：在 dec.decode 前打印 value.byteLength 和 value 的首尾字节。如果看到长度不是 3 的倍数、且首字节落在 0xE4–0xE9（中文三字节的首字节）区间，基本可以确认。

验证方法二（不改代码）：用浏览器开发者工具的网络面板，把「流」响应导出，按字节查看。搜索 EF BF BD（U+FFFD 的 UTF-8 编码），如果出现，说明解码丢字节。

补充一个低成本防御：把所有流式文本在服务端做一次 encode/decode 往返测试，用一段纯中文长文本，按 1–7 字节随机切块喂给解析函数，断言输出与原文完全一致。这类测试能覆盖掉一整类只有在弱网才出现的 bug。

综合题二你要决定「工单自动分类」这个功能要不要做成流式。给出判断过程和结论。
答案

判断过程三步：

① 输出是给人读的，还是给程序消费的？分类结果是 JSON，交给下游路由逻辑，人不读。这是第一条否决理由——流式的前提是「有人在等着读」。

② 中间状态有没有意义？流式只有在「部分结果也有价值」时才成立。摘要的前两句有用，因为坐席可以先读着；而分类的半个 JSON 没有任何价值，解析不了就不能用。

③ 总耗时落在哪个区间？如果分类调用只需 0.8 秒，加流式纯属增加复杂度，而且首帧和完整结果几乎同时到达，用户不会感知到差别。

结论：不做流式。但要做另一件事——把这段等待藏起来。分类应该在工单创建时异步触发，结果回写到工单字段，坐席打开工单时分类已经在了。这是「消除等待」而不是「优化等待」，成本更低、体验更好。

这道题的真正考点是：流式是一个局部优化，而很多场景的正确答案是把等待挪到用户看不见的地方（预计算、异步、缓存）。当你发现自己在为一个 1 秒的操作设计流式时，先问一句「这个操作能不能不发生在他面前」。

综合题三用户点了「停止生成」，界面上应该发生哪四件事？
答案

① 前端中断连接：controller.abort()，并把按钮状态从「停止」切回「发送」。

② 服务端感知断开并取消上游：这是唯一能真正省下 token 的一步。只做 ① 的话，钱照花、并发照占。

③ 保留已生成内容，并标注不完整：在后面加一行浅色状态「已停止 · 内容不完整」。不要清空——清空会让用户觉得前面的等待被作废了。同时把「重新生成」和「继续」两个入口都留着，因为用户停止的原因不同：有时是嫌慢，有时是发现方向错了。

④ 记录一次埋点：记 stop_at_token（在第几个 token 停止）和 stop_reason（手动 / 超时 / 断线）。这个数据非常有用：如果大量停止发生在 50 token 以内，说明首句就没抓住需求；如果集中发生在 300 token 左右，说明输出太长，该压短；如果 stop_reason 里断线占比高，那是基础设施问题。

多数团队只做 ① 和 ③，所以既没省钱也说不清用户为什么不用。第 ④ 条是本章最便宜的一个改进：加一行埋点，下次讨论「要不要缩短输出」时就有证据了。
