在写第一行代码之前，先分清你要造的是哪一种东西

这一章不写复杂的代码。它要解决的是更前置的问题：同样叫「接入了大模型」，为什么有的系统上线后被大量使用，有的三个月后就无人问津？答案不在模型，在于你造的是哪一类东西，以及你是否按那一类的要求去造它。

本章学习目标
理解　AI 应用的三类形态，以及它们在信任成本上的本质差别
掌握　用 token 估算一次调用的成本，并能算出多轮对话的真实开销
掌握　用结构化输出约束模型，使它的返回值可以被程序直接消费
了解　成本优化的正确顺序，以及为什么它不能从换模型开始

1.1　三类 AI 应用：问答、辅助、代理

场景

某公司的客服部门在 2026 年春天上线了一个 AI 问答机器人。技术方案没有问题：接了当时最好的模型，灌了三百页产品文档，还做了知识库检索。上线时演示效果很好，领导当场表扬。

三个月后，后台数据显示日均调用 47 次。而客服团队有 40 个坐席，每天处理约 800 个工单。

复盘时发现一个细节：这 47 次里，有 31 次来自同一个新人。她之所以在用，是因为她刚入职，很多政策不熟。老坐席几乎不用，因为「查文档比问它还快，而且它有时候说错，我还得自己核对一遍」。

这个故事里没有技术故障。系统能用，回答大体准确，成本也不高。它失败的原因在更早的地方：做的人没有区分「问答」和「辅助」是两种不同的东西，用造问答的思路造了一个本该是辅助的产品。

三类形态

按「模型输出之后发生什么」来划分，AI 应用只有三类：

第一类，问答（Q&A）。用户提出一个问题，模型给出回答，用户自己判断要不要信。模型输出之后的下一步是人阅读。客服知识库问答、内部政策查询都属于这一类。

第二类，辅助（Copilot）。模型提出一个草稿或建议，人决定采纳还是修改。模型输出之后的下一步是人在草稿上操作。会话摘要、回复建议、工单分类建议属于这一类。

第三类，代理（Agent）。模型决定做什么，并直接执行。模型输出之后的下一步是系统动作。自动查订单、自动改地址、自动发起退款属于这一类。

图 1-1　三类形态的递进关系。从左到右，模型的决定权在增加，而工程约束的严格程度必须以更快的速度增加。

为什么这个区分很重要

因为三者的难度来源完全不同，而很多人误以为它们只是同一个东西的不同复杂度。

问答的难度是「答得准」。这个问题可以通过检索、提示词、模型选型来改善，属于技术问题。

辅助的难度是「比人自己做更省力」。注意这一条：它和准确率有关，但不只是准确率问题。一个准确率 90% 的回复建议，如果坐席每次都要花 5 秒读完再花 5 秒判断对不对，而她自己写只要 8 秒，那这个功能在她的账上是亏的。这就是前面那个故事里老坐席不用系统的真实原因——不是它错得多，是它没有跨过「省力」这条线。

代理的难度是「可控、可回滚」。因为没人拦着它了，所以任何一次错误都是系统的错误，不是人的错误。这要求它必须能审计（事后知道它做了什么）、能回滚（做错了能改回来）、有边界（知道什么绝对不能碰）。

例题 1-1　给客服平台的五个功能分类
// 判断标准只有一个：模型输出之后，下一步是什么？

1. 坐席问「七天无理由的起算时间是从哪天开始？」
   → 模型输出 → 坐席阅读 → 问答

2. 坐席点「生成摘要」，模型给出一段通话摘要
   → 模型输出 → 坐席编辑后填入工单 → 辅助

3. 模型自动给新工单打上分类标签并分派到技能组
   → 模型输出 → 系统直接分派 → 代理

4. 客户提问后，模型给出三条候选回复，坐席点其中一条发送
   → 模型输出 → 坐席选择后发出 → 辅助

5. 模型查询订单状态并直接告诉客户
   → 模型输出 → 系统调用接口并回复客户 → 代理
观察：第 3 和第 5 看起来都是「自动回复」，但第 3 错了会导致工单进错组、延误处理，第 5 错了只是答错一句话。同属代理类，风险等级仍不同——这提示分类之后还要再评一次风险。

一个常见的误判

做完这个分类，很多人会想：既然代理最有价值，那就直接做代理。

这是一个成本极高的判断错误。原因不是技术难度，而是代理类应用需要的信任是逐步建立的。你的组织对它没有信任记录，一旦第一次上线就出现一次错误操作，这个项目会被直接叫停，而这时候你还没有机会证明别的东西。

在实践中更稳妥的路径是：先用问答证明「它说得对」，再用辅助证明「它有用」，最后才用代理证明「它可以被托付」。这三步对应三种完全不同的验收方式：问答验收准确率，辅助验收采纳率，代理验收自动闭环率与事故率。

本章后面所有的技术内容，都以「辅助」这一类的标准来要求。这是你的主战场：它足够复杂，能体现工程能力；又足够安全，不会因为一次错误就前功尽弃。

练习 1-1　三类形态的判断

1-1①把下面四个功能归类，并写出每个功能「模型输出之后的下一步」。
答案
  • 坐席问「七天无理由从哪天起算」→ 坐席自己阅读，再决定怎么回客户 → 问答
  • 模型生成通话摘要 → 坐席编辑后填入工单 → 辅助
  • 模型给出三条候选回复 → 坐席点其中一条发出 → 辅助
  • 模型查完订单状态并直接回复客户 → 系统发出，没有人经手 → 代理

检验方法只有一个：问「模型说完这句话之后，是人的眼睛在看，还是人的手在改，还是机器自己动了」。三种回答分别对应三类形态。

1-1②「模型自动给工单打标签，打完后坐席可以改」——这属于哪一类？依据是什么？
答案：属于代理，不是辅助

依据不是「人能不能改」，而是默认路径走哪边。人不去动它就直接流入下游，说明决定权已经在系统手里，标注「可修改」只是给了一个事后纠错的机会，不改变它的形态。反过来，如果必须先点「确认」标签才生效，人才是决定者，那是辅助。

这个区分不是文字游戏。代理类要承担「错了是系统的错」的全部责任，所以它必须额外具备审计、可回滚和边界限制；而辅助类只要保证「人看得懂、改得快」就够了。把一个代理当成辅助来建，是后面事故最常见的起因。

1-1③对你自己系统的三个 AI 功能做同样的分类，并回答：有没有哪个你原本以为是辅助，仔细看默认路径后其实是代理？
参考要点

这类题的答案因人而异，但判断时需要避开两种常见误判：

  • 把「自动填充」当辅助。如果填充后人不改就直接提交，它是代理。
  • 把「人工抽检」当辅助。抽检是在事后，不改变默认路径，仍然是代理。

按经验，一个系统里被误判成辅助的代理通常不少。每找出一个，就等于找到一个还没做审计和回滚的地方。

1.2　token 与上下文窗口：模型真正的成本单位

场景

一个客服 AI 助手上线第一个月，账单是 3400 元，完全在预算内。第二个月账单 11800 元。第三个月 27000 元。

用量确实在涨——从日均 400 次调用涨到 900 次，翻了一倍多。但账单涨了近八倍。团队一开始怀疑被刷了，查了日志，没有异常请求，每次调用的内容也都很正常。

真正的原因藏在一个没人注意的地方：为了让机器人「更懂上下文」，产品经理要求它记住整个会话。而客服的会话长度分布极不均匀——多数两三轮就结束，少数投诉工单能聊到二十几轮。

token 是什么

大模型不按「字」计费，按 token。token 是模型处理文本的最小单位，它可以是一个字、一个词、一个词的一部分，甚至一个标点。

对中文来说，一个汉字大约对应 0.6 到 1 个 token，具体取决于分词器。一个粗略的估算是：1000 个汉字约等于 700 到 1000 个 token。英文反而更省：一个英文单词通常不到 1.5 个 token。

这件事只在一个场景下重要：当你需要估算成本或者判断会不会超长的时候。它是个工程常数，不必精确，但不能不知道。

上下文窗口的两个性质

性质一：窗口有上限。 每个模型有一个最大 token 数，输入加输出不能超过它。常见的是 32K、128K、200K 几档。

性质二：窗口不是内存，它是每次请求都要重新付费的。 这一条是本节的核心，也是最容易被误解的地方。

很多人把上下文窗口理解成「模型的记忆容量」，于是自然地认为：既然它能记住 128K，那把整个知识库塞进去就行了。

但机制上不是这样。模型是无状态的。它不记得你上一次说了什么。所谓「多轮对话」，实际上是每一轮都把你之前说过的所有内容重新发一遍。

多轮对话的成本是平方级增长

假设每一轮的消息平均 R 个 token。第 N 轮请求时，模型需要收到前面所有轮次的内容，所以第 N 轮的输入是 N×R。

那么 N 轮对话的总消耗是：

R + 2R + 3R + … + N×R = R × N(N+1)/2

而如果按「每轮独立」的直觉去算，会是 N×R。两者之比是 (N+1)/2。

也就是说，十轮对话的真实开销是直觉估算的 5.5 倍，二十轮是 10.5 倍。

图 1-2　每一轮请求都要重发此前全部内容。十轮累计消耗 11000 token，而不是直觉上的 2000 token。
例题 1-2　算一次真实的多轮对话开销
# 假设：每轮用户输入 100 token，模型回复 100 token，共 10 轮
# 单价格：输入 2 元 / 百万 token，输出 8 元 / 百万 token

R = 200                    # 每轮新增 200 token（用户 100 + 回复 100）
total_in = total_out = 0

for n in range(1, 11):
    total_in  += n * R            # 输入 = 前面所有轮 + 本轮
    total_out += R * 0.5          # 输出只有本轮

cost = total_in/1e6*2 + total_out/1e6*8
print(f"输入 {total_in} token，输出 {total_out} token")
print(f"单次会话成本 {cost:.4f} 元")
输入 11000 token，输出 1000 token
单次会话成本 0.0300 元

观察：如果按「每轮独立」的直觉算，输入只有 1000 token，成本 0.0100 元。真实开销是直觉的 3 倍。按日均 900 次会话算，一个月的差额是 540 元——这还没算长尾的二十几轮投诉工单。

这对客服场景意味着什么

客服会话的长度分布是极不均匀的：绝大多数两三轮结束，少数投诉能拖到二十轮以上。如果你的策略是「带上全部历史」，那么成本会被那一小撮长会话主导。

三个可用的做法，从简单到复杂：

  1. 滑动窗口。只保留最近 K 轮。简单有效，代价是丢失早期上下文。对客服场景通常够用，因为客服的问题大多是局部的。
  2. 摘要压缩。超过窗口时，把早期对话压缩成一段摘要保留。多一次模型调用，但能保住长程信息。
  3. 结构化状态。不保存原始对话，只保存提炼出的关键槽位（订单号、诉求、已确认的事实）。这是最省也最可控的做法，但需要你先定义清楚业务里有哪些槽位。

第三种做法在后文的 Agent 编排里会再次出现，并且会变成整个系统的主干。这里只需先建立一个意识：发给模型的东西应该是你精心选择的，而不是全部历史。

三个容易误判的地方
  1. 把上下文窗口当内存。窗口大只意味着「一次能塞更多」，不意味着「记得更久」。每次请求都是独立的，状态需要你自己维护。
  2. 认为窗口大就一定更好。长上下文存在「中段遗忘」现象：放在输入中间部分的信息，被模型利用的概率明显低于开头和结尾。所以把 200 页文档塞进去，效果往往不如检索出最相关的 3 段。
  3. 用字数直接当 token 数。中文、英文、代码、数字的 token 密度差别很大。写预算脚本时要调用分词器实测，不要拿字数乘一个系数了事。

练习 1-2　算多轮对话的真实开销

1-2①把例题 1-2 的轮数从 10 改成 20，成本变成多少倍？轮数翻倍，成本为什么不是翻倍？
答案

输入 = 200 × (1+2+…+20) = 200 × 210 = 42,000 token；输出 = 100 × 20 = 1,000 token。

成本 = 42000 × 2/10⁶ + 1000 × 8/10⁶ = 0.084 + 0.008 = 0.100 元，是 10 轮（0.030 元）的 3.3 倍。

原因：轮数 N 只让「每一轮的长度」线性变长，而累计是求和，所以总量按 N² 增长。工程量级上记住一个数：轮数翻倍，输入成本约涨 4 倍（这里没到 4 倍，是因为输出的固定部分摊薄了比值）。

1-2②改用滑动窗口，只保留最近 5 轮，同一个 10 轮会话的成本降多少？这个降幅说明了什么？
答案

第 1–5 轮输入仍是 200/400/600/800/1000，第 6–10 轮固定为 1000。输入合计 = 3000 + 5000 = 8,000 token（原 11,000，降 27%）。

成本 = 8000 × 2/10⁶ + 1000 × 8/10⁶ = 0.024 元，比原来省 20%。

值得注意的是：输入降了 27%，总成本只降 20%，因为输出是固定 1000 token 且单价是输入的 4 倍，占了大头。这说明单靠裁剪历史救不了成本——真正的大头要看输出这一侧。

1-2③统计你系统真实的会话长度分布（至少 200 个样本），判断成本主要来自哪一段。
参考结论

客服场景的典型形状是：中位数只有 2–3 轮，但均值被 5% 左右的长会话拉到 8 轮以上。按平方增长算，那 5% 的长会话通常贡献一半以上的 token 消耗。

如果统计结果印证了这一点，正确的动作不是「整体优化」，而是给长会话单独设计策略（超 N 轮切摘要或结构化状态），中短会话保持原样。对分布的长尾做定点处理，比全局调参省得多。

1.3　第一个调用：非流式与流式

这一节要把一个最小的可用调用写出来。它很短，但里面有几个参数如果不理解，后面所有内容都会走偏。

请求的结构

几乎所有主流模型服务的调用接口都是同一个形态：你发一个 messages 数组，模型返回一条消息。messages 里每一项都有 role 和 content。role 有三种：

  • system：设定模型的身份和规则，通常放在最前面，且只有一条
  • user：用户的输入
  • assistant：模型之前的回复（用于多轮时回填历史）

「多轮对话」在协议层就是把之前的 user 和 assistant 消息原样拼进数组。这就是上一节成本问题的来源——它在协议层是显式的。

非流式与流式

同样的请求，可以要求一次性返回完整结果，也可以要求逐块返回。前者叫非流式，后者叫流式。

例题 1-3　两种调用方式
# 非流式：等全部生成完，一次性拿到
resp = client.chat.completions.create(
    model="your-model",
    messages=[
        {"role": "system", "content": "你是客服助理，只回答政策问题。"},
        {"role": "user",   "content": "七天无理由从哪天起算？"},
    ],
    temperature=0.2,
)
print(resp.choices[0].message.content)

# 流式：边生成边返回
stream = client.chat.completions.create(
    model="your-model",
    messages=[...],          # 同上
    temperature=0.2,
    stream=True,
)
for chunk in stream:
    delta = chunk.choices[0].delta.content
    if delta:
        print(delta, end="", flush=True)
观察：非流式的返回值里是完整的 message.content；流式每次拿到的是 delta.content，可能为空字符串，也可能只是一个字。必须判空。

两个容易被忽略的参数：

temperature（温度）控制输出的随机性。取值 0 到 1（有的模型到 2）。做客服这类需要稳定、可复现的输出时，应该压低到 0.1 到 0.3。调高它会让你后面做的评估失去意义——同一道题两次跑出不同结果，你无法判断改动有没有效果。

max_tokens 限制输出长度。不设的话，模型可能在你不希望的时候长篇大论，而输出通常比输入贵两到四倍。客服摘要这类任务，设一个明确上限是最省钱的优化。

什么时候用流式

判断标准不是「越长越好」，而是你能不能接受用户在这段时间里什么都不看到。

场景推荐理由
生成给用户读的长文本（摘要、回复建议）流式人在等待时会怀疑系统卡死，流式把等待变成「正在生成」
生成给程序解析的结构化数据非流式程序要的是完整 JSON，中间状态无意义反而增加解析复杂度
短输出（少于 30 字）非流式流式的连接开销和代码复杂度不值得
批量离线处理（跑评估集）非流式无人观看，流式只增加复杂度
流式的三个特殊问题
  1. 错误可能发生在流的中间。非流式的失败通常是「一开始就失败」，你可以干净地重试。流式可能已经吐了 300 字然后断掉，这时候用户已经读了部分内容，清空重来会让体验更差。正确做法是保留已生成内容，标注「生成中断」并允许续写。
  2. 重试不一定是安全的。如果流式输出已经被部分消费，重试意味着重新计费一次完整生成。要区分「可安全重试」和「需要人工确认」的情况。
  3. 超时设置要分两段。非流式只有一个总超时；流式需要「首字超时」和「总超时」两个，否则一个卡在中间的连接会一直挂着，占住连接池。

练习 1-3　流式与非流式

1-3①把 temperature 分别设为 0 和 1，同一个问题各跑 5 次，记录差异。这个实验说明什么？
答案

temperature=0 时，5 次输出基本逐字相同（少数情况下因服务端的批处理差异有细微波动）；temperature=1 时，5 次输出的措辞、结构、长度都会有明显差别，个别次会出现不同的结论倾向。

结论有两个：一是评估必须锁定低温，否则你改了提示词后看到的分数变化里，混着采样噪声，无法归因。二是「同一道题跑两次结果不同」不是模型的缺陷，是参数设定的后果——需要稳定复现的场合（分类、抽取、评估），就把温度压到 0–0.3；需要发散创意的场合才调高。

1-3②给流式调用加上「首字超时 5 秒、总超时 30 秒」的双重控制，超时后优雅中断。
答案要点

关键不是两个 timeout 参数，而是两个分别在不同时刻判定的计时器，因为普通的请求超时只能控制连接建立和整体时长，管不到「连接正常但迟迟不出字」这种卡在中间的状态。

t0 = time.time()
first_at, buf = None, []

# 每个 chunk 到达时依次检查两条
if first_at is None and time.time() - t0 > 5:
    raise TimeoutError("首字超时")      # 从没出过字 → 可直接失败重试
if time.time() - t0 > 30:
    raise TimeoutError("总超时")        # 已出部分字 → 保留 buf，标记「生成中断」

退出后必须区分这两种情况：首字超时时一个字都没吐，可以安全重试；总超时时已经有部分内容，直接丢弃重来会浪费一次完整计费，也会让用户看到内容突然消失。正确做法是保留已生成部分，标「生成中断」并允许续写。

1-3③下面四个环节，各应选流式还是非流式：①工单自动分类 ②会话摘要给坐席看 ③批量跑评估集 ④生成 20 字以内的客服话术。
答案
  • ① 工单分类 —— 非流式。输出是给程序解析的结构化数据，中间状态无意义，流式反而增加解析复杂度。
  • ② 会话摘要 —— 流式。它是给人读的长文本，流式把「怀疑卡死」变成「正在生成」。
  • ③ 批量评估 —— 非流式。无人观看，流式只增加代码复杂度和连接占用。
  • ④ 短话术 —— 非流式。输出太短，流式的连接开销和复杂度不值得。

判断标准始终是同一句话：你能不能接受人在等待期间什么都看不到。能接受就非流式，不能接受才上流式——流式是有成本的，不是默认更优。

1.4　结构化输出：为什么必须约束格式

场景

一个工单自动分类功能上线两周后，监控报错。日志里是一行：Unexpected token '，' in JSON at position 42。

原因是提示词里写了「请以 JSON 格式返回」，模型大部分时候确实返回了 JSON，但偶尔会在前面加一句「好的，分类结果如下：」，或者在 JSON 外面套一个 markdown 代码块。解析器一遇到这些就崩。

负责人一开始的反应是「加一句更强的指令，要求它只返回 JSON」。改完之后错误率从 3% 降到 0.8%，但还是会偶发。三个月里一共有十一次线上失败，全部发生在客户催促、单量最大的时候。

自然语言不能直接进程序

模型输出的是文本，而程序需要的是结构。这中间必须有一次转换，而转换是否可靠，取决于你用哪种方式约束它。

有三种约束方式，可靠性依次递增：

图 1-3　三种约束方式。提示词约束依赖模型配合，schema 约束由服务端强制。

为什么提示词约束不可靠？因为它是「请求」而不是「约束」。你在提示词里写「只返回 JSON」，模型把它理解为一个意图，而模型的输出是在概率分布上采样得到的——绝大多数时候它会照做，但你没有任何机制保证这一点。所谓「加一句更强的指令能把错误率降下来」，本质上是提高了采样落在这个意图上的概率，不是消除了失败可能。

而 schema 约束是服务端在生成过程中强制的：它限制了模型只能输出符合给定结构的 token 序列，而不是事后再检查。这两者在机制上不同，所以可靠性的差别不是量的差别，是质的差别。

例题 1-4　用 schema 约束工单分类的输出
# 约束的目标：返回一个分类和一个置信度，分类必须在给定的枚举值里

schema = {
    "type": "object",
    "properties": {
        "category": {
            "type": "string",
            "enum": ["退款售后", "物流查询", "产品咨询", "投诉", "其他"]
        },
        "confidence": {"type": "number"},
        "reason": {"type": "string", "maxLength": 50}
    },
    "required": ["category", "confidence"]
}

resp = client.chat.completions.create(
    model="your-model",
    messages=[
        {"role": "system", "content": "你是客服工单分类器。"},
        {"role": "user",   "content": ticket_text},
    ],
    response_format={"type": "json_schema", "json_schema": schema},
    temperature=0,
)

result = json.loads(resp.choices[0].message.content)
# 即使 schema 生效，业务校验仍然必须做
assert result["category"] in schema["properties"]["category"]["enum"]
assert 0 <= result["confidence"] <= 1
观察：schema 保证了「category 一定是五个值之一」「confidence 一定是数字」，但不保证逻辑正确——一个物流问题完全可能被分到「退款售后」，格式完全合法。格式合法与内容正确是两个独立的问题。

格式正确不等于内容正确

这是本节最需要记住的一句。结构化输出解决的是「能不能解析」，不解决「对不对」。

用了 schema 之后，你的程序不会再因为解析失败而崩，但错误的内容会安静地通过，进入下游流程——而这类错误比崩溃更危险，因为崩溃会报警，错误的内容不会。

所以在工程上，结构化输出必须配两层校验：

  • 格式校验：字段是否存在、类型是否正确、枚举是否合法。这层由 schema 和一次 assert 完成。
  • 业务校验：这个值在业务上说得通吗？比如「分类为退款，但工单里没有任何订单号」，这是业务上不成立的组合。
结构化输出的三个坑
  1. 把 schema 当成正确性保证。schema 只约束形状。一个字段齐全、类型正确、逻辑全错的结果，schema 检查完全放行。
  2. 嵌套太深。三层以上的嵌套结构，模型出错的概率明显上升，而且出错时更难定位。能扁平化就扁平化。
  3. 忘了留「无法判断」的出口。如果枚举里没有「无法判断」或「其他」，模型在遇到超纲输入时会被迫选一个最接近的——这会制造出看起来有结论、实际是硬猜的结果。这个出口必须留，并且在后续逻辑里特殊处理。

练习 1-4　结构化输出与校验

1-4①把例题 1-4 的 enum 里去掉「其他」，然后输入一条超纲工单（比如「你们公司的发票抬头能改成集团统一抬头吗」），它会输出什么？这个结果说明什么？
答案

它不会报错，也不会返回空。它会被强行塞进最接近的一类——大概率是「产品咨询」或「退款售后」，而且 confidence 往往还给得不低。整条输出格式完全合法，schema 全部通过。

这揭示了一个容易被忽略的事实：枚举里没有出口，模型就没有「不知道」这个选项，它只能把不确定翻译成一个确定的答案。对下游来说，这条「硬猜」的结果和一条真正准确的结果长得一模一样，没有任何字段能区分。

所以「其他」或「无法判断」这个出口不是可选项，而是必须项；而且下游必须对它特殊处理（转人工或进待审队列），不能和正常分类走同一条路。

1-4②给上面这个 schema 加一条业务校验：「如果 category 是退款售后，则必须能定位到订单号或金额」。写出校验代码，并说明校验失败时应该怎么处理。
答案 
import re

def check_business(r, ticket_text):
    if r["category"] == "退款售后":
        blob = r.get("reason", "") + " " + ticket_text
        if not re.search(r"(订单号|订单|￥|元|\d{8,})", blob):
            return False, "判为退款但无订单号/金额线索"
    return True, ""

处理方式的关键是不要直接丢弃，也不要直接放行。丢弃会损失一条真实工单；放行会把错误传到下游。正确做法是降级为待人工确认，并把这批记录单独存起来——它们恰好是最好的改进素材，能直接告诉你模型在哪些输入上系统性判断错误。

还有一点：这条校验之所以必要，是因为它检查的东西 schema 原理上无法表达。schema 只能约束「字段是什么形状」，跨字段的业务合理性（分类与证据是否匹配）必须由你自己写。

1-4③把 confidence 从连续数值改成三档枚举（高/中/低），利弊各是什么？
答案

利：

  • 模型自报的连续数值是没有校准的，0.87 和 0.83 之间并不存在真实差别，给出这种精度是虚假的。
  • 分档更容易写分流规则：低 → 必须人工确认，高 → 可自动执行。用连续值反而要拍一个阈值。
  • 三档时模型更倾向于说「低」，会提高它对不确定性的坦白度。

弊：

  • 丢失区分度，两条都是「中」的工单无法排序。
  • 档位的含义仍然由模型自己理解，它说的「高」不一定是真的准。

结论：分档更适合工程落地，但要真正把它用起来，必须用自己的评估集实测每一档的实际准确率。实测出来「高」档只有 72% 准，就不能拿它当自动执行的依据。信模型自报的数值不行，信自己测出来的数字才行——这一步是把「置信度」从装饰字段变成可决策字段的唯一办法。

1.5　成本模型与预算意识

场景

预算超支之后，负责人的第一反应是换一个更便宜的模型。换完效果确实便宜了一半，但坐席反馈「变笨了」，采纳率从 61% 掉到 43%。

后来做了一次分析：如果先做另外三件事——给高频问题加缓存、把知识库全塞改成检索三段、给摘要设置 max_tokens——成本能降 62%，而且完全不损失质量。换模型这件事，其实是最后才该做的。

成本公式

一次调用的成本由三项构成：

成本 = 输入 token × 输入单价 + 输出 token × 输出单价

两个定价上的事实：

  • 输出通常比输入贵两到四倍。所以「让它少说一点」往往比「让它少读一点」更省钱。
  • 单价是分模型档位的，差距可达几十倍。同一个厂商的旗舰模型和轻量模型，单价可能相差 20 倍以上。

把它们拼成一个可算的式子：

月成本 = 日均调用量 × 30 × (输入 token × 输入单价 + 输出 token × 输出单价)

例题 1-5　算一个 40 坐席系统的月成本
# 场景：40 坐席，人均日调用 12 次，即日均 480 次
# 单次：输入 3000 token（含检索到的知识片段），输出 400 token
# 单价：输入 2 元/百万，输出 8 元/百万

calls_per_day = 40 * 12
in_tok, out_tok = 3000, 400
p_in, p_out = 2/1e6, 8/1e6

per_call = in_tok*p_in + out_tok*p_out
monthly  = calls_per_day * 30 * per_call

print(f"单次 {per_call:.5f} 元 → 月成本 {monthly:.0f} 元")

# 三个不损失质量的优化，按顺序叠加
m1 = monthly * 0.55   # 缓存命中 45%（高频问题重复率）
m2 = m1 * 0.70        # 输入从 3000 降到 1200（检索代替全塞）
m3 = m2 * 0.85        # 输出限长 250 token
print(f"优化后 {m3:.0f} 元，降幅 {(1-m3/monthly)*100:.0f}%")
单次 0.00920 元 → 月成本 132 元
优化后 43 元，降幅 67%

观察：这个例子的绝对金额很小，因为它只有 480 次/天。真实的客服系统往往单次输入上万 token（长会话 + 多段检索），月成本会到一个需要认真管理的量级。

优化的正确顺序

成本优化有四层，顺序不能颠倒，因为前三层不损失质量，第四层损失质量。

顺序手段典型降幅对质量的影响
1减少不必要的调用：缓存、去重、合并请求30–60%无（命中缓存的请求本来答案就一样）
2缩短输入：检索代替全塞、压缩历史20–40%通常无，甚至更好（长上下文有中段遗忘）
3缩短输出：设 max_tokens、约束格式10–25%无（只要上限设置合理）
4换更小的模型50–90%有，且可能显著

为什么顺序不能反？因为前两层动的是「不必要的浪费」，第四层动的是「能力」。先砍能力会让系统变差，而变得差的系统会失去用户，失去用户之后成本自然降下来了——但那是失败，不是优化。

一个实践建议：在还没有做前三层优化之前，不要开始讨论「换哪个模型更便宜」。这个讨论会让你把注意力放在最不该动的地方。
三个算漏的地方
  1. 只算输入不算输出。输出单价是输入的 2–4 倍，而在摘要、建议这类任务里输出占比不低。漏掉输出会低估 30% 以上。
  2. 忽略重试成本。失败重试是双倍计费。如果失败率 5%，实际成本比理论值高 5%–10%（取决于重试策略）。
  3. 忽略开发与评估成本。跑评估集、调试提示词、做对比实验，这些也都走 API。在你的窗口期内，这部分可能占总消耗的 20%–40%。做预算时要单列一项。

练习 1-5　成本估算与优化顺序

1-5①沿用例题 1-5 的参数，假设缓存命中率不是 45% 而是 20%，优化后的月成本变成多少？这个数字取决于什么？
答案

未优化月成本 132 元。命中率 20% 意味着 80% 的请求要真实调用：

132 × 0.80 × 0.70 × 0.85 ≈ 63 元，比原来的 43 元高出 46%。
作为极端对照，如果命中率为 0，则是 132 × 0.70 × 0.85 ≈ 79 元。

命中率不是可以随便假设的参数，它取决于业务问题分布的集中度。政策类问题（「七天无理由怎么算」「运费谁承担」）重复率极高，八成请求能命中；个性化投诉、异常订单几乎不重复，命中率接近 0。所以正确的做法是从真实日志里统计两个数：完全相同问题的占比，和语义相同但表述不同的问题占比。后者要靠向量相似度去重，比字符串匹配能多捞回一截。

1-5②在例题 1-5 已经做完三层优化的基础上，还要求「不损失质量」再降 30%，你会动哪里？
答案

不能简单再压前三层——它们已经接近各自的极限，而且边际收益在快速衰减。真正有效的是两条新的路径：

① 分级路由。不是笼统地「换小模型」（那是第 4 层，会损质量），而是按请求难度分流：查订单、查物流、格式化这类任务，小模型的表现和大模型没有区别，可以走小模型；只有涉及多轮推理、政策判断的请求才交给大模型。实测下来，客服场景里这类简单请求通常占一半以上，整体成本能降 30–50%，而抽检质量基本不变。

关键区别在于：整体换模型是无差别降级，分级路由是精准降级。前者把 10% 的难题也一起降了，后者只降那些本来就不需要大脑的题。

② prompt 缓存。那段几百上千 token 的系统提示词和知识片段，每次请求都在重发。多数厂商对重复前缀有折扣计价，命中后这部分可省一半以上。这部分完全不损质量，属于纯粹的遗漏。

1-5③统计你系统最近一个月的 token 消耗构成（输入 / 输出 / 评估调试），判断哪一部分最值得动。
参考结论

客服类系统的典型占比大约是：输入 60–75%，输出 20–30%，评估调试 5–15%。如果你的数字落在这个区间，说明异常不在这里，问题在输入侧的结构。

把输入再拆一层，通常会看到：系统提示词与规则说明占 20–40%，检索到的知识片段占 30–50%，对话历史占 15–35%。排名第一的优化点几乎总是「每次都重发的固定内容」——它单次看不多，但乘以调用量就是最大的一块，而且它恰恰是最容易通过缓存或前置判断消掉的。

反过来，如果发现评估调试占比超过 30%，这不算浪费，反而说明你在做正确的事；但它会让你的月度预算估算严重偏低，做预算时必须单列这一项。

本章小结
  • AI 应用按「模型输出之后发生什么」分为三类：问答、辅助、代理。三者的难度来源不同——问答难在准确，辅助难在省力，代理难在可控可回滚。
  • 不要从代理起步。信任是逐步建立的，先用问答证明说得对，再用辅助证明有用，最后才用代理证明可托付。
  • 成本按 token 计，输入与输出分开计价，输出贵 2–4 倍。
  • 模型无状态，多轮对话在协议层是每次重发全部历史，因此成本按平方增长，十轮是直觉估算的 5.5 倍。
  • 流式解决的是感知问题不是速度问题。但流式有独立的错误处理、超时、重试语义，不能直接套用非流式的方案。
  • 要用程序消费模型输出，必须用 schema 约束，而提示词约束只是概率上的改善。
  • 格式正确不等于内容正确。 schema 保证能解析，业务校验保证说得通，两者都要有。
  • 成本优化顺序不可颠倒：减少调用 → 缩短输入 → 缩短输出 → 最后才换模型。前三层不损失质量。

本章综合习题

下面两题需要用上本章全部五节的内容。先自己做，再对照答案——尤其第二小题的数字，务必自己算一遍。

综合题一你手上有一个客服会话摘要功能：单次输入 6000 token（包含全部历史对话），输出 500 token，日均 400 次，用的是单价较高的模型。目前采纳率 24%，月成本约 900 元。
（1）它属于哪一类形态？（2）只做「缩短输入」这一层优化，成本降到多少？（3）采纳率低和成本高，有没有可能是同一个原因？
答案

（1）辅助类。模型输出摘要，坐席编辑后填入工单，决定权仍在人手上。但要注意一个信号：采纳率 24% 意味着它没跨过辅助类的真正门槛——「比人自己做更省力」。它「能生成」，但坐席算下来还不如自己写，这正是 1.1 那个故事的同一形态。

（2）先反推单价。月调用 400 × 30 = 12,000 次，900 ÷ 12,000 = 0.075 元/次。设输出单价是输入的 4 倍，则 6000p + 500×4p = 8000p = 0.075，得输入约 9.4 元/百万、输出约 37.5 元/百万。

假设「最近 5 轮 + 关键槽位」把输入从 6000 压到 2000 token：
输入 0.0188 元 + 输出 0.0188 元 ≈ 0.0375 元/次，月成本约 450 元，降 50%。

注意这个 50% 恰好是一半，原因很直接：输入少了三分之二，而输出一分未动。这也说明继续在输入上动刀的收益上限就是 50%，再往上必须处理输出。

（3）很可能同因，而且这是本章最值得带走的一个判断。

输入里塞着全部历史，其中大部分和「要总结什么」无关。这些冗余内容带来两个后果：一是直接推高成本；二是长上下文存在中段遗忘，模型会漏掉被埋在中间的关键诉求，摘要于是变成「什么都说了一点、什么都没说准」。坐席读到的摘要不在点子上，就得自己重写——采纳率自然低。

所以正确的第一步不是「优化提示词让它写得更好」，而是把「要总结什么」显式定义成几个槽位（客户诉求、已确认事实、待办动作、情绪风险），只喂相关信息。这一改动同时打中成本和采纳率两个指标。这也是后面第 12 章讲结构化状态时要展开的主线。

综合题二为「工单自动分类」设计完整方案：（1）输出 schema，含分类、置信度、以及「无法判断」的出口；（2）两条格式校验和两条业务校验；（3）上线后用哪些指标验收。
答案

（1）schema

{
  "category":   enum ["退款售后","物流查询","产品咨询","投诉","无法判断"],
  "confidence": enum ["高","中","低"],
  "evidence":   string, maxLength 80,   // 原文中支撑判断的关键句
  "required":   ["category", "confidence"]
}

三个设计要点：分类必须互斥且穷尽；confidence 用三档而非连续值（理由见练习 1-4③）；evidence 不是装饰字段，它是后面做业务校验和人工复核的唯一抓手——没有它，复核员只能重读整张工单。

（2）校验

格式校验：① category 必须落在五个枚举值内；② confidence 必须是三档之一且 evidence 不超过 80 字。

业务校验：① category 为「退款售后」时，工单文本或 evidence 里必须能定位到订单号或金额，否则不仅分类可疑，还意味着这条工单本身信息不全；② category 为「无法判断」时，禁止进入自动分派，必须落入人工待审队列——这条校验的价值不在于拦住错误，而在于给系统一个诚实的出口。

（3）验收指标（三个一起看，缺一不可）

  • 分类准确率：上线前用 200 条人工标注的工单实测，作为基线。低于 85% 不建议自动分派。
  • 人工纠正率：上线后坐席改标签的比例。它比离线准确率更真实，因为含了「边界模糊」和「业务口径变化」的影响。
  • 「无法判断」的触发率：这个数字两头都有问题。持续低于 3% 说明模型在硬猜（枚举出口形同虚设）；持续高于 20% 说明分类体系或提示词没覆盖真实业务。合理区间通常在 5–12%。

只报准确率是不够的：一个把所有长尾都硬塞进已知类别的模型，准确率可能还不错，但它在做的是「假装知道」。能诚实说「不知道」的系统，才是能长期上线的系统。
