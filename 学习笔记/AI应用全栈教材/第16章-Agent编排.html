第 16 章　Agent 编排
「让模型自己决定下一步」，是能力也是风险

第 15 章给了模型工具，但没说谁决定「什么时候用哪个」。这个决定权放在哪，就是编排的全部内容。这一章的核心主张可能和你在别处读到的不一样：大多数被叫做「Agent」的东西，其实应该是状态机；真正的自由规划只适合很窄的场景，而且必须配上严格的终止条件。

本章学习目标
理解　三种编排形态的边界：固定流程、状态机、自由规划
掌握　判断一个场景该用哪种形态的三个问题
掌握　手写一个可用的状态机编排（含工具调用与确认）
掌握　死循环的四种形态与终止条件设计
了解　风险分级与人工确认节点的位置

16.1　先问：真的需要 Agent 吗

业内的「Agent」这个词已经膨胀到失去定义。本书用它指一件具体的事：由模型自主决定调用哪个工具、调几次、什么时候停。这个能力很强，但它有三个代价：不可预测、难评估、贵。

所以先问三个问题，只要有一个答案是「否」，就不该用自主编排：

问题答案是「否」意味着该用什么
① 步骤数量是否不固定？步骤固定（查订单→判断→回答）固定流程，甚至一个提示词就够
② 下一步是否依赖上一步的内容，而不只是结果？只是数据传递，判断逻辑确定状态机（分支写死）
③ 错误是否可以承受并被发现？错了不可挽回，或很难发现状态机 + 人工确认

举个具体的对照。客服场景里 90% 的需求长这样：

  • 「订单到哪了」→ 查订单 → 回答。一步，固定。
  • 「我要退款」→ 查订单 → 判断是否满足条件 → 满足则确认后执行 → 回答。四步，固定。
  • 「我这耳机左耳没声音，买了 5 天，能退吗，顺便看看有没有别的颜色可以换」→ 这是一个复合诉求：判断退款条件 + 查库存 + 可能还要改单。步骤数不定，且下一步依赖上一步结果。这才是 Agent 的场景。

第三种的共同特征是：客户一次说了多件事，而这几件事之间有依赖。用固定流程做，你要穷举所有组合（退款+换货、退款+查物流、换货+查库存……），组合数爆炸；用 Agent，模型自己排顺序。

一个实用的判断标准：如果你的流程图能画完，就不要用 Agent。画不完（因为分支取决于语义而不是数据），才考虑自主编排。而「画不完」这种情况，在客服场景里大概占 10%。

16.2　四种形态，从确定到自由

图 16-1　四种形态：控制力递减、灵活度与成本递增

第四种「自由规划」在图里被画成黄色，是有意的。它的问题不是「不好用」，而是在它出错时你很难解释为什么——同样的输入，它这次调了两个工具，下次调了三个，你无法预先知道，也无法在测试里覆盖。

所以实践中的正确做法是嵌套：外层是状态机（保证主流程可控），内层某一个状态是「自由规划」（处理复合诉求）。这样即使内层跑偏，外层也能兜住——超时、超步数、需要确认时就打断。

16.3　手写一个状态机

下面这段代码是整个第四篇的核心。它不长，但包含了编排需要的全部要素：状态、转移、工具、确认、终止。

例题 16-1　一个可用的编排循环
from enum import Enum

class S(Enum):
    UNDERSTAND = 'understand'      # 判断客户要做什么
    PLAN       = 'plan'            # 选下一步
    ACT        = 'act'             # 调工具
    CONFIRM    = 'confirm'         # 等人工确认
    ANSWER     = 'answer'          # 组织最终回答
    ABORT      = 'abort'           # 终止（超步数/超时/异常）

async def run(ticket, ctx, budget=6):
    st, steps, trace = S.UNDERSTAND, 0, []
    while st not in (S.ANSWER, S.ABORT):
        steps += 1
        if steps > budget:                       # 终止条件一：步数
            st = S.ABORT; break

        if st is S.UNDERSTAND:
            ctx.intent = await classify(ticket)
            st = S.ABORT if ctx.intent is None else S.PLAN

        elif st is S.PLAN:
            step = await plan_next(ctx)                # 模型决定下一步
            if step.kind == 'tool':
                ctx.next_tool = step; st = S.ACT
            elif step.kind == 'confirm':
                ctx.next_tool = step; st = S.CONFIRM
            else:
                st = S.ANSWER

        elif st is S.ACT:
            res = await execute(ctx.next_tool, ctx)      # 第 15 章的三层校验
            trace.append((ctx.next_tool, res))
            ctx.observe(res)
            st = S.PLAN                                  # 回到规划

        elif st is S.CONFIRM:
            ok = await wait_confirm(ctx)               # 不超时，见第 6 章
            st = S.ACT if ok else S.ANSWER

    return await answer(ctx, trace) if st is S.ANSWER else handoff(ctx)
三个设计点：
① ACT 之后一定回到 PLAN，不直接跳到 ANSWER——因为工具结果可能引出下一步。
② ABORT 不是错误，是一种正常出口，它走 handoff（转人工），而不是抛异常。
③ budget=6 是硬约束，和模型无关——即使模型想继续，也不让它继续。

第 ② 点值得展开。「转人工」是 Agent 最重要的能力，而它经常被实现成异常路径。如果超步数时抛一个异常，用户体验是「系统出错了」；如果走 handoff，用户体验是「这个问题有点复杂，我帮你转给同事」——同样的技术事实，完全不同的感受。

而且 handoff 必须带上上下文：客户说了什么、已经查了什么、卡在哪一步。没有这些，接手的人工坐席要从头问一遍，客户会重复描述——这是最伤体验的环节。

16.4　确认节点放在哪

判断标准只有一条：这一步的后果，是否可以由发起人在事后完全承担。

动作后果可逆吗影响范围是否需要确认
查订单、查物流无后果无不需要
生成回复草稿可逆（不发送就没影响）无不需要（发送前有一次确认）
改地址、加备注可逆（30 分钟内）单个订单需要
发短信/通知客户不可逆客户感知需要，且要展示文案全文
退款不可逆资金需要 + 额度判断
批量操作不可逆多单需要 + 二次确认（输入数量）

「发短信」这一行容易被低估。它技术上只是调一个接口，但一旦发出去就无法收回，而客户会把它当作正式承诺。所以它必须确认，而且确认卡片上要显示完整文案——不是「发送通知」，而是「向 138****5678 发送：『您的订单已…』」。

批量操作那一行的「二次确认」也有讲究：不要用「确定要执行吗」这种确认，它会被无脑点掉。要用输入数量的方式：「请输入要退款的订单数（共 37 单）」。这个动作无法被肌肉记忆完成，必须真的看一眼。

16.5　死循环的四种形态

自主编排最现实的工程问题不是「答得不好」，是「停不下来」。四种形态，每一种都需要独立的防护：

形态一：同一个工具反复调，参数不变

模型没读懂返回结果，于是再调一次。防护是检查重复：如果 (tool_name, args_hash) 在本次会话里出现过，第二次就直接返回「这个查询已经做过了，结果是 …」，不再执行。

形态二：两个工具互相触发

查订单发现地址异常 → 查地址服务 → 地址服务提示「请先确认订单状态」→ 又查订单。这种循环的周期是 2，重复检测抓不到（因为参数略有不同）。防护是步数上限 + 状态访问计数：同一个工具被调用超过 3 次就终止。

形态三：模型不断「再确认一下」

每一步都调一个查询工具，永远不进入 ANSWER。这在模型不确定时很常见。防护是预算递减 + 强制收敛：步数用掉 2/3 时，在提示词里加一句「你必须在剩余 N 步内给出答案，信息不足就说明不足」。

形态四：确认节点被反复触发

模型每次都请求同一个写操作，用户每次都拒绝，模型再请求。防护是拒绝即终止：一次拒绝之后，这个工具在本次会话里被禁用，并直接走 ANSWER。

例题 16-2　四道闸一起上
GUARDS = {
  'max_steps': 6,              # 总步数
  'max_same_tool': 3,          # 同一工具最多调 3 次
  'dedup': True,               # (tool, args_hash) 去重
  'deny_blocks_tool': True,     # 拒绝后禁用该工具
  'wall_clock_s': 45,          # 总时长（含等待工具）
}
五个参数里 wall_clock_s 最容易被忘，但它防的是最坏情况：
每个工具都 3 秒超时、调了 6 次、中间还等了两次确认——总时长可能到 60 秒，用户早就走了。

还有一件事：所有触发终止的情况都要记日志，并带上「终止原因」。原因分布本身就是最有价值的调优依据——如果 60% 的终止是「超步数」，说明任务对你的模型太难，应该拆小；如果 40% 是「同工具重复」，说明某个工具的描述或返回格式有问题。

四个编排上的错误决定
  1. 能用流程图画的场景用了自由规划。得到的是不可测试、不可解释、成本更高的系统，而收益接近零。
  2. 终止时抛异常而不是转人工。技术上是同一个结果，体验上差一个量级，而且用户会重复描述问题。
  3. 只设步数上限，不设时长上限。步数到 6 但每步 8 秒，总时长 48 秒，用户早走了。
  4. 批量操作只做「确定吗」的确认。会被肌肉记忆点掉，要改成输入数量。
本章小结
  • Agent 的三个代价：不可预测、难评估、贵。三个问题里有一个「否」就不该用。
  • 判断标准：流程图能画完 → 不用 Agent；画不完（分支取决于语义）→ 才用。
  • 四种形态：单一提示词 60%、固定流程 25%、状态机 12%、自由规划 3%。
  • 正确做法是嵌套：外层状态机兜底，内层某个状态做自由规划。
  • 状态机三要点：ACT 后必回 PLAN、ABORT 是正常出口走转人工、budget 与模型无关。
  • 确认节点看「后果能否事后完全承担」；批量操作用输入数量而非「确定吗」。
  • 死循环四种形态，四道闸一起上：步数、同工具次数、参数去重、拒绝即禁用、总时长。
  • 终止原因要记日志，它的分布直接告诉你下一步该改什么。

本章综合习题

综合题一给出三个客服场景，分别说明该用固定流程、状态机、自由规划，并写出判断依据。
答案

场景 A：客户要退款（固定流程）。

步骤恒定：查订单 → 判断是否满足退款条件（7 天无理由 / 15 天质量问题）→ 计算金额 → 确认 → 执行 → 告知时效。六步，没有分支能改变顺序，只有「是否满足条件」这一个二元分支，而它是数据判断不是语义判断。

依据：流程图能完整画出，且分支由字段决定（签收日期、商品类别），不由模型判断。用自由规划只会带来「有时多查一次」的浪费和不可预测性。

场景 B：客户说「耳机坏了，想退，但我想先看看能不能换别的颜色」（状态机）。

这里有两个诉求，顺序不定（先退还是先看颜色），而且「能不能换」取决于库存和是否在换货期内。分支可以枚举：可换货 → 查库存 → 有货 → 换货 / 无货 → 退款，不可换货 → 退款。

依据：路径依赖客户回答，但所有路径可枚举（大概 5–6 条）。用状态机既能覆盖，又能在每条路径上做明确的校验和确认。

场景 C：客户说「我上周买的耳机左耳没声音，你们说可以退，但我朋友说他退了三个月才到账，你帮我看看我这单到底怎么回事，还有我另一单也一直没发货」（自由规划）。

这是复合诉求：既有一个具体问题（左耳无声）、一个质疑（退款时效）、还有一个独立问题（另一单未发货）。步骤数不定——可能要查两三张订单、查退款流水、查物流，而且下一步取决于上一步查到什么（如果发现退款已到账，就不用查流水了）。

依据：穷举组合不现实，且顺序需要根据中间结果调整。但即使这样，它也应当嵌在一个状态机里：外层控制步数、控制写操作必须确认、控制超时转人工。

三个场景的共同规律：判据不是「难不难」，而是「路径是否可枚举」。难的但可枚举 → 状态机；简单的但组合爆炸 → 自由规划。

综合题二你的 Agent 在生产上偶发「卡住 40 秒后返回一句无关的回答」。列出四个可能原因和对应的防护。
答案

原因一：工具超时后模型继续尝试。某个工具卡了 10 秒超时，模型不死心又调了两次，最后步数耗尽走了兜底回答。
防护：工具超时返回时带 retryable: false 和明确的 hint（「该查询暂时不可用，请直接告知客户稍后重试」），禁止模型重试。关键是把「不可重试」明确告诉模型，否则它会自己判断「再试一次也许行」。

原因二：确认节点等待时间长。模型请求了写操作，坐席在忙没点，等了 30 秒后超时，走了兜底。
防护：确认不该有 40 秒超时（第 6 章说过不允许超时）。正确做法是把它挂起并转入待办，同时立刻给用户一个「已提交，待确认」的回复，而不是让整个会话卡住。

原因三：模型在 PLAN 状态反复犹豫。它每一步都想「再确认一下」，调了 4–5 个查询工具，最后预算耗尽。
防护：预算递减提示（「你还剩 2 步，必须给出答案」）+ 同工具次数上限。并且记录「每个会话的工具调用序列」，看是否有固定的犹豫模式。

原因四：上下文过长导致模型忽略了已有信息。前面查到的结果在上下文中间，被「中间遗忘」了，于是它重新查一遍——这既慢又贵，最后还可能给出与已查结果矛盾的答案。
防护：把已获得的关键事实结构化地重述在每轮提示词末尾（「已查到：订单 20260312008 已发货，物流单号 SF123」），而不是指望模型从历史消息里翻。这一步成本很低，效果很明显。

为什么必须先分类：四种原因的修法完全不同（改工具错误信息 / 改确认流程 / 改预算策略 / 改上下文组织）。而它们的症状都是「慢 + 答非所问」。区分方法是看日志里的状态序列——如果能看到「ACT 出现了 5 次」，就是原因三；如果「CONFIRM 停留了 30 秒」，就是原因二。这就是为什么要记录状态转移，而不只记录最终结果。

综合题三设计一个「批量退款」的确认流程，要求既不会误操作，又不会因为流程太重而没人用。
答案

核心设计：分层确认 + 可预演 + 可中断。

① 预演（Dry run）。Agent 先输出一张表：将要退款的 37 单、每单金额、总计金额、以及被排除的 5 单及原因（已退款 / 超期 / 金额异常）。这一步不执行任何操作，只是一次「模拟」。

排除项必须显示，因为它是用户判断「这个批量是否符合预期」的最重要依据。只显示「将退款 37 单」而不显示「排除了哪 5 单」，用户无法确认逻辑是否正确。

② 分级确认。按总金额分三档：< 500 元 单次确认；500–5000 元 确认 + 输入总金额；> 5000 元 需主管审批（转审批流，Agent 只负责准备材料）。

输入总金额而不是「点确定」，是因为它无法被肌肉记忆完成——你要看着表格把 3,847 输进去，这个过程会强迫你核对。

③ 分批执行 + 可中断。不要一次性提交 37 单，而是每批 5 单，每批完成后显示进度（「已完成 15/37，已退 1,240 元」），并提供「暂停」按钮。

这个设计解决了一个真实痛点：如果第 3 单就发现异常，用户可以停下来，而不是等 37 单全部跑完再想办法撤回。而且它给了用户「我随时能停」的安全感，这直接影响他敢不敢用这个功能。

④ 失败处理要具体。某一单失败不能中断整个批次，但必须汇总展示：「32 单成功，3 单失败：T…001（余额不足）、T…018（订单状态异常）、T…025（超权限）」，每单带可执行的处理建议。

⑤ 完整回执。执行完成后生成一份可下载的回执，包含每单的订单号、金额、时间、操作人、确认人。这份回执是财务对账和事后审计的唯一凭据。

为什么这样设计不算「重」：整个流程里用户只做三件事——看预演表、输入总金额、点执行。加起来不到 30 秒，而它替代的是「37 次手工操作」。

关键的取舍：预演和分批是「增加系统复杂度」换取「用户的操作确定性」；分级确认是「增加一次交互」换取「风险与金额匹配」。三者都不是为了防 AI，而是为了让用户敢用——这是所有高风险自动化功能的真正门槛。
