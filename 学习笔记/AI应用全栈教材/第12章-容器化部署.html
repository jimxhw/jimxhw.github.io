第三篇 · 服务
第 12 章　容器化部署
「在我机器上是好的」这句话，从此不再成立

前十一章的代码都在一个终端里跑。这一章把它放进容器、放到一台别人也能访问的机器上，并解决一个 AI 服务特有的难题：怎么在不切断用户长连接的前提下发布新版本。

本章学习目标
掌握　写一个结构正确的 Dockerfile（多阶段、非 root、有健康检查）
掌握　配置与密钥的注入方式，以及为什么不能打进镜像
理解　流式服务的优雅退出：为什么普通 docker stop 会截断回答
掌握　健康检查的两个端点（存活 / 就绪）的区别
了解　上线清单与回滚判断标准

12.1　一个能用的 Dockerfile

例题 12-1　多阶段构建
# ---------- 构建阶段 ----------
FROM python:3.12-slim AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ---------- 运行阶段 ----------
FROM python:3.12-slim
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
COPY --from=build /install /usr/local

# 非 root 用户
RUN useradd -m -u 10001 app
WORKDIR /app
COPY --chown=app:app . .
USER app

EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --start-period=15s --retries=3 \
  CMD python -c "import urllib.request,sys; \
      sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:8000/healthz',timeout=2).status==200 else 1)"

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", \
     "--proxy-headers", "--forwarded-allow-ips=*"]
四个关键点：多阶段（编译工具不进最终镜像）、非 root（被攻破时损失最小）、
PYTHONUNBUFFERED=1（否则日志会被缓冲，出问题时看不到最后几行）、
start-period（启动要加载模型和连接池，给 15 秒宽限，否则会被健康检查误杀）。

PYTHONUNBUFFERED 这一行值得单独说。它看起来只是日志细节，实际上是很常见的排查障碍：容器崩溃时，最后几行日志通常就在缓冲区里，随进程一起消失了。而最后几行恰好是「为什么崩」的唯一线索。

多阶段构建的效果也很直接：单阶段镜像往往 1.2GB（带 gcc、头文件、pip 缓存），多阶段通常 200–300MB。镜像小的好处不只是拉取快——它是每次扩容、每次回滚的时间。在需要快速回滚的场合，从 3 分钟降到 20 秒是有意义的差别。

12.2　配置与密钥不能进镜像

镜像一旦构建，里面的每一层都可以被 docker history 看到，包括被后续层删除的文件。把密钥写进 Dockerfile，即使下一行删掉，它仍然在镜像历史里，任何拿到镜像的人都能取出来。

做法是否可取说明
写在 Dockerfile 的 ENV 里不可进镜像层，可被导出
COPY .env 再删除不可历史层里还在
运行时 -e 传入勉强会出现在 docker inspect 和进程环境里
挂载文件 / 密钥管理服务推荐运行时注入，不进镜像，便于轮换

还有一个实战细节：配置缺失必须让容器启动失败。如果服务能带着空密钥启动，它会正常响应 /healthz，看起来部署成功，但所有业务请求都失败。这种「健康但不工作」的状态，比直接崩溃难查得多。第 9 章的启动校验就是为这件事准备的。

12.3　优雅退出：流式服务的特殊难题

发布新版本时，容器要停掉。默认行为是发 SIGTERM，等 10 秒，然后 SIGKILL 强杀。对一个 0.2 秒的普通接口，这没问题；对一条正在输出第 300 个字的流，它会在用户眼前断掉。

用户看到的是「回答说到一半消失了」，而且刷新后也找不回来——因为那次生成已经丢了。这类问题在发布日集中出现，但很少有人把它和发布联系起来。

图 12-1　优雅退出：三步顺序不能颠倒

应用侧的实现要点：

例题 12-2　捕获 SIGTERM，等在途请求
import asyncio, signal
from contextlib import asynccontextmanager

inflight = 0
stopping = False

@asynccontextmanager
async def lifespan(app):
    loop = asyncio.get_running_loop()
    def on_term():
        global stopping
        stopping = True          # /readyz 立刻开始返回 503
    loop.add_signal_handler(signal.SIGTERM, on_term)
    yield
    # 关停阶段：给在途请求最多 60 秒
    for _ in range(120):
        if inflight == 0:
            break
        await asyncio.sleep(0.5)
stopping 这个标志的关键作用：让就绪检查先失败，把新流量挡在外面，
而监听端口仍然开着，好让在途的流跑完。「不接新的」和「不服务旧的」是两件事。

12.4　两个健康检查端点

一个 /healthz 是不够的，因为「活着」和「能干活」是两件事。

端点回答的问题失败时的动作检查什么
/healthz（存活）进程还活着吗重启容器只检查进程本身，不查任何外部依赖
/readyz（就绪）能接流量吗摘除流量，不重启数据库连通、配置齐全、未在关停

把外部依赖写进存活检查（/healthz）是一个常见但严重的错误：数据库抖动 → /healthz 失败 → 编排系统重启全部容器 → 重启后仍然连不上 → 循环重启 → 一次数据库抖动变成全站不可用。

规则很简单：存活检查只能检查自己，就绪检查才能检查依赖。依赖挂了应该摘流量（等它恢复），而不是杀进程（它没做错什么）。

就绪检查还有一个细节：它应该有缓存。如果每个请求都去 ping 一次数据库，检查本身会变成负载。通常的做法是每 5 秒刷新一次状态，检查端点只读缓存值。

12.5　上线清单与回滚

发布 AI 功能比发布普通功能多两件事：模型和提示词也有版本，以及质量可能悄悄退化。所以清单要覆盖这三层。

例题 12-3　上线清单（可打印）
□ 代码版本：commit ______　镜像 digest ______
□ 提示词版本：p___（与代码同级管理，不是热改）
□ 模型版本：______（记录到请求日志，便于归因）
□ 评估：holdout 集准确率 ___%（基线 ___%，下降 >3 点则不上）
□ 索引：知识库版本 ______，重建完成时间 ______
□ 配置：新增环境变量 ______，已在目标环境设置
□ 容量：预估峰值并发 ___，当前并发上限 ___
□ 回滚：上一版镜像 digest ______，回滚命令 ______
□ 观察窗口：发布后 30 分钟盯 4 个指标（错误率/429/TTFT P95/采纳率）
两行最容易被跳过：提示词版本 和 索引版本。
「代码回滚了但提示词没回滚」会造成一个很难解释的状态：行为还是新的，代码是旧的。

回滚的判断标准要提前定，不能临场讨论。建议三条硬指标，任一触发就回滚：

  1. 错误率超过基线 2 倍，持续 5 分钟。
  2. TTFT P95 超过 8 秒，持续 5 分钟（用户已经开始放弃）。
  3. 采纳率下降超过 30%，持续 30 分钟（说明内容变差了，而这不会报错）。

第三条最容易被忽略，因为它是「沉默的退化」：接口 200、延迟正常、没有异常日志，但内容质量掉了。没有采纳率这个业务指标，你只能等用户投诉。

还有一条经验：回滚要演练。发布前真的回滚一次到上一版，确认命令可用、镜像还在、数据兼容。很多团队的回滚方案从未被执行过，等到真需要时才发现「上一版镜像被清理了」。

四个部署期的高频故障
  1. grace period 用默认 10 秒。长流被截断，表现为「发布日回答总是说一半」。
  2. 存活检查查数据库。一次抖动触发全量重启，把小故障放大成全站事故。
  3. 密钥打进镜像。docker history 可导出，且轮换密钥时必须重新构建。
  4. 提示词热改没版本。出问题时无法复现，因为「当时的提示词」已经不存在了。
本章小结
  • Dockerfile 四要点：多阶段、非 root、PYTHONUNBUFFERED、健康检查带 start-period。
  • 镜像小不是洁癖，它是扩容和回滚的时间。
  • 密钥只能运行时注入；配置缺失必须启动失败，不能「健康但不工作」。
  • 流式服务要延长 stop_grace_period，捕获 SIGTERM，并让就绪检查先失败。
  • 退出顺序：网关下线 → 等待刷新 → SIGTERM → 停止接新、等在途 → 退出。顺序错就会有发布日 502。
  • 存活只查自己，就绪才查依赖。混用会把小故障放大成全站事故。
  • 上线清单要覆盖代码、提示词、模型、索引四层版本；回滚标准提前定，且要演练。

本章综合习题

综合题一每次发布新版本，都有用户反馈「AI 回答说到一半就没了」。平时没有这个问题。给出三个可能原因和验证方法。
答案

原因一：容器 grace period 太短（默认 10 秒）。一条流 9 秒，加上建连和排队，很容易超过 10 秒，于是被 SIGKILL。
验证：看被截断的请求，其持续时间是否集中在 9.5–10.5 秒之间。如果是，就是这个原因——这个「整齐的 10 秒」是决定性证据。

原因二：退出顺序错，网关还在转发。容器已收到 SIGTERM 并停止接收，但网关的注册还没刷新，新请求打到它身上 → 502 或空响应。
验证：统计截断请求的时间分布。如果集中在发布开始后的 0–15 秒内（而不是发布全程），说明是切换窗口问题，不是 grace period。同时查网关日志有没有 502。

原因三：多副本滚动更新时，旧副本被摘除但连接没有 drain。负载均衡把连接关掉了，而应用侧还在往里写。
验证：在服务端记录「写入时连接已断」的次数（写 yield 时捕获 BrokenPipeError / ClientDisconnect）。这个数字在发布期间上升就是它。

三者的修法完全不同：改 stop_grace_period、改退出顺序、改负载均衡的 drain 配置。而它们的症状一模一样——所以必须靠时间分布来区分，不能靠猜。这也是为什么第 9 章强调每个请求要有 trace_id：没有它，你连「哪些请求被截断了」都统计不出来。

综合题二为什么存活检查不能查数据库？如果已经这么写了，怎么安全地改过来？
答案

为什么不能：存活检查失败会触发重启容器。如果它检查数据库，那么数据库一抖动，所有容器同时健康检查失败、同时被重启。重启期间服务完全不可用，而数据库那边的小抖动本该只是「慢一点」。

更糟的是循环：容器重启需要 15–30 秒（加载依赖、建连接池），这段时间里它仍然连不上数据库，于是下次检查又失败，又被重启。一次 5 秒的数据库抖动，会变成 10 分钟的完全不可用。

核心区别是：存活检查判断的是「进程是否陷入死锁或崩溃」，这类问题只能用重启解决；依赖不可用不属于这类问题，它应该表现为「暂时不接流量」，等依赖恢复后自动回来。

安全改造的三步：

① 先加就绪检查，不改存活检查。让 /readyz 承担依赖检查，并从网关/编排配置里启用它。观察一周，确认摘流量机制工作正常。

② 把存活检查改成只查进程。最简单的实现是返回一个常量 {"ok": true}——它只证明「事件循环还能响应请求」。这一步要在低峰期做。

③ 观察重启次数。改造后容器重启次数应该降到接近 0（除了真实崩溃）。如果还有周期性重启，说明有别的东西在导致进程退出，需要单独查。

一个额外收益：改完之后，你的服务在数据库维护窗口内可以「优雅降级」——返回 503 提示而不是整个不可用。这是可用性上的实质提升，而不只是配置更规范。

综合题三你要发布一版新提示词。写出你的发布与回滚方案，要求能回答「如果质量变差了，多久能发现、多久能恢复」。
答案

发布方式：提示词按版本号管理，与代码同一套发布流程，不做热改。

准备
  p13 写入配置中心，状态 draft（不被读取）
  用 holdout 60 条跑一次：准确率 ___%（基线 84%，门槛 81%）
发布
  灰度：按 agent_id 哈希 10% → 30% → 100%，每档观察 2 小时
  请求日志带 prompt_ver，指标可按版本切分
观察（4 个指标）
  ① 准确率代理：人工抽检 20 条/小时
  ② 净采纳率（实时埋点）
  ③ 「插入后全删」比例
  ④ 转人工率
回滚
  配置中心把 p13 状态改为 disabled，p12 立刻生效（无需重启）
  预计恢复时间：< 1 分钟
  数据：已产生的 p13 输出保留，标记版本，用于事后分析

「多久能发现」：准确率这种指标有滞后，靠抽检最快也要 1 小时。但「插入后全删」比例是实时信号——它不需要人工判断，只要用户行为变化就能看出来。经验上质量下降 5 个点，这个比例会在 20 分钟内明显上升。所以把它作为主告警指标，能发现得最快。

「多久能恢复」：关键是提示词不打包进镜像。如果提示词在镜像里，回滚要走一次完整发布（构建 + 推送 + 滚动更新），最快 10 分钟；如果放在配置中心且支持热切换，回滚是秒级。这一个设计决定，把 MTTR 从 10 分钟降到 1 分钟。

为什么灰度按人而不按请求：按请求灰度会让同一个坐席今天用新版明天用旧版，他的反馈无法归因，而且行为会被两版混淆。按人固定分组，才能得到干净的分组对比。这是第 8 章「学习效应」的直接应用。
