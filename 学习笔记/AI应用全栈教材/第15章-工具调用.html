第 15 章　工具调用
这是「会聊天」和「能办事」之间的那一步

RAG 让模型能引用知识，但它仍然只是「说」。工具调用（function calling / tool use）让它能「做」：查订单、改地址、发短信、建工单。这是本书里技术含量最集中、也最能区分候选人的一章——因为它同时需要前端（确认界面）、后端（接口设计）和模型侧（描述与错误处理）三种能力，而大多数候选人只有其中一种。

本章学习目标
理解　工具调用的本质：模型只产出参数，不执行任何东西
掌握　把工具描述写成提示词：名称、说明、参数、边界
掌握　四件工程必备：参数校验、幂等、超时、权限
掌握　错误信息的设计：让模型能自我纠正
了解　为什么必须从只读工具开始，以及风险分级

15.1　它到底发生了什么

先说清一件事，因为它经常被误解：模型不会执行任何代码。它的全部工作是「输出一段 JSON，描述它想调用哪个工具、参数是什么」。真正执行的是你的代码。

一次工具调用是四步循环：

图 15-1　四步循环：模型只产出参数，执行永远在你的代码里

这个认识有几个直接推论，都很实用：

  • 「模型误操作」是可以完全避免的。因为执行权在你手里。你在执行前做校验、做权限判断、做人工确认，它就不可能误操作。
  • 模型能「编造」参数。它可能返回一个不存在的订单号、一个格式正确的假金额。所以校验是必需的，不是可选的。
  • 工具调用的质量，一半取决于描述写得清不清楚。模型只能根据 description 判断「什么时候该用这个工具」，写不清楚它就会用错或用漏。

15.2　工具描述就是提示词

很多人把工具定义当作接口文档来写，结果模型频繁用错。原因是模型不做「阅读理解」，它做的是「模式匹配」——描述里的每个词都在参与「这个工具适合什么场景」的判断。

例题 15-1　同一个工具的两种描述
✗ 接口文档式
{
  "name": "get_order",
  "description": "获取订单信息",
  "parameters": {"order_id": {"type": "string", "description": "订单号"}}
}

✓ 决策导向式
{
  "name": "get_order_status",
  "description": "查询订单的当前状态，包括物流进度、是否已发货、是否可修改地址。
                  当客户询问『到哪了』『发货了吗』『能不能改地址』『什么时候到』时使用。
                  不要用它查退款进度（用 get_refund_status），不要用它查商品库存（用 check_stock）。",
  "parameters": {
    "order_id": {
      "type": "string",
      "description": "11 位订单号，形如 T20260312008。若客户只给了后 4 位，
                      先调用 search_order_by_suffix 换取完整订单号。"
    }
  }
}
四类信息缺一不可：做什么（不只是名字）、什么时候用（客户的原话）、
什么时候不要用（最容易被省略，但对区分相似工具至关重要）、参数怎么得到（包括前置步骤）。

「什么时候不要用」这一条的价值经常被低估。客服场景里天然存在大量相似工具：查订单状态、查退款进度、查物流轨迹、查售后单。它们对模型来说都是「查东西」，如果不写清边界，它会随机选一个，然后你得到一个语义正确但字段全错的结果。

还有一个更细的技巧：在参数描述里写「怎么获得这个参数」。上面那个例子里，「若客户只给了后 4 位，先调用 search_order_by_suffix」这一句，把两个工具串成了一条路径。没有它，模型会拿着「2008」去查，然后得到空结果，再回头问客户——多一轮交互。

参数设计的三条规则

  1. 参数越少越好。5 个参数以上的工具，模型填错的概率显著上升。如果确实需要很多参数，拆成两个工具（先查后改）。
  2. 用枚举，不用自由字符串。「改地址的原因」如果写成 string，模型会编；写成 enum: ["填错", "搬家", "改公司地址"]，它只能选。
  3. 必填项要真的必填。不要用「可选参数 + 默认值」来表达业务约束，因为模型不理解默认值——它会以为可以不填，然后得到错误结果。

15.3　四件必须做的事

一、参数校验：不信模型给的任何东西

模型返回的参数必须当作不可信输入处理，和用户表单提交是一个级别。原因很直接：它可能编造，可能格式错，可能超出业务范围。

例题 15-2　执行前的三道检查
async def execute(name, args, agent):
    # ① 结构校验（类型、枚举、长度）
    fn = TOOLS.get(name)
    if not fn: return err('UNKNOWN_TOOL', '没有这个工具')
    try:
        args = fn.schema.model_validate(args)      # pydantic
    except ValidationError as e:
        return err('BAD_ARGS', str(e))     # 让模型自己改

    # ② 业务校验（这里才是防事故的地方）
    if fn.is_write and not agent.can_write(args.order_id):
        return err('FORBIDDEN', '该订单不在你的负责范围')
    if fn.is_write and not await confirmed(args.idempotency_key):
        return err('NEED_CONFIRM', '需坐席确认后才能执行')

    # ③ 超时保护
    return await asyncio.wait_for(fn.call(args), timeout=3)
三层的分工：①保证参数能用，②保证操作该做，③保证不卡住。
只做 ① 是不够的——一个格式完全正确的 order_id，可能属于别的客户。

二、幂等：模型可能重复调用

两个原因会导致重复：模型在一次回复里返回两个一样的 tool_calls；或者执行超时后编排层重试。对「查订单」无所谓，对「退款」是灾难。

做法是给每个写操作带一个幂等键，由编排层生成（不是模型生成——它会编），在执行侧做去重：

# 幂等键 = trace_id + tool_name + 关键参数哈希
key = f'{trace_id}:refund:{order_id}:{amount}'
if await cache.get(key):
    return cache.get(key)          # 返回上次的结果，不重复执行
result = await do_refund(...)
await cache.set(key, result, ttl=3600)

这里有一个细节：缓存的是「结果」，不是「已执行」这个标记。如果只标记已执行而不返回结果，重试的调用会拿到空，模型会以为失败了再试一次。

三、超时：没有超时的工具会拖垮整个编排

工具调用的链路是：模型 → 你的代码 → 内部接口。内部接口如果卡住 30 秒，整个对话就卡 30 秒，用户以为死了。建议阈值 3 秒，超过就返回「查询超时」让模型决定下一步（通常是告知客户稍后）。

四、权限：工具级 + 数据级

工具级是「这个坐席能不能用这个工具」（比如普通坐席不能用「批量退款」）；数据级是「这个工具能不能操作这条数据」（比如只能操作自己负责的订单）。两者都要，缺一个就有漏洞。

15.4　从只读工具开始

工具按风险分三级，接入顺序应当严格按这个顺序：

级别例子风险接入条件
只读查订单、查物流、查库存、查工单历史低（错了只是信息不对）可直接上，用日志监控准确率
低风险写改地址、加备注、发短信通知中（可撤销或影响有限）必须有确认界面 + 撤销入口
高风险写退款、改价、改权限、批量操作高（涉资金或权限）必须双人确认或主管审批 + 额度上限 + 完整审计

为什么必须从只读开始，有三个理由，第二个最重要：

  1. 它能把「模型能不能正确填参数」这个问题先解决掉。参数填不对的模型，做写操作就是灾难；而只读工具的错误代价接近零，可以在真实流量里跑一周看准确率。
  2. 它能积累「哪些查询最常见」的数据。这些数据会告诉你第二个工具该做什么——而闭门设计出来的工具顺序往往是错的。
  3. 它能让坐席先建立信任。一个「查得又快又准」的工具，会让坐席愿意接受后面的「帮我把地址改了」。反过来，第一个上线的工具如果是改地址，一次错误就会让整个 AI 功能被关掉。

只读工具本身也有很高的价值，这一点常被低估。查订单这件事，坐席平均要切 3 个系统、花 40 秒。把它变成一句话就能拿到，单次节省 40 秒，一天 100 单就是 1.1 小时。这个数字足以让技术负责人批准整个项目，而它不需要任何写操作。

15.5　错误信息要让模型看得懂

工具返回的错误，接收方是模型，不是人。所以它需要的不是「友好」，是「可据以决策」。

例题 15-3　三种错误写法
✗ 只给状态码
{"error": 500}
→ 模型不知道怎么办，通常会重试同一个调用，或者编一个答案

✗ 只给人看的话术
{"error": "系统开小差了，请稍后再试"}
→ 模型会转述这句话，客户什么也没得到

✓ 可据以决策的结构
{
  "ok": false,
  "code": "ORDER_NOT_FOUND",
  "message": "订单号 20260312008 不存在（可能是 20260312080）",
  "retryable": false,
  "hint": "请向客户确认完整订单号，或调用 search_order_by_phone 用手机号查"
}
→ 模型能选：问客户 / 换工具 / 停止
三个字段决定模型的行为：
code 决定它能识别错误类型；retryable 决定要不要重试；hint 决定下一步做什么。
少了 retryable，模型会对 400 类错误重试三次，浪费三轮交互。

有一个反直觉的建议：在 message 里给出可能的正确值。上面那个例子里，「可能是 20260312080」这一句，能让模型主动问客户「您是不是想说 …080」。这种能力在不给提示的情况下是不会出现的，而它显著提升了一次解决率。

但要小心不要过度提示：不要在有权限风险的地方给出候选值。比如「手机号 138****5678 对应的客户是李婷」这种，等于向无权查看的人泄漏了信息。提示只在「同一客户内部」成立时才给。

四个工具调用的红线
  1. 不校验就执行。模型给的参数等同于用户输入，必须过 schema + 业务校验。
  2. 写操作没有幂等键。一次重试就是一次重复退款，而这类错误事后很难对齐。
  3. 写操作没有确认界面。第 7 章说过，责任必须归人。而且确认界面是最便宜的防错手段。
  4. 工具描述只写「做什么」，不写「什么时候不用」。相似工具会互相误用，而错误往往是字段级正确、语义级错误，很难发现。
本章小结
  • 模型只产出参数，不执行任何东西。执行权在你的代码里，所以「误操作」在架构上可以完全避免。
  • 工具描述是提示词：写清做什么、什么时候用、什么时候不要用、参数怎么获得。
  • 参数设计三规则：越少越好、用枚举、必填就真必填。
  • 执行前三层检查：结构（能不能用）、业务（该不该做）、超时（会不会卡）。
  • 写操作必须有幂等键，且缓存「结果」而不是「已执行」标记。
  • 风险三级：只读 → 低风险写 → 高风险写。必须按顺序接入，只读的价值已经足够立项。
  • 错误信息给模型看：code / message / retryable / hint，四个字段决定它的下一步。

本章综合习题

综合题一模型频繁在客户问「退款到哪了」时调用「查订单状态」，而不是「查退款进度」。列出三种修法，按成本从低到高排序，并说明各自的局限。
答案

修法一：改描述里的「什么时候不要用」（成本最低，10 分钟）。

在 get_order_status 的描述里加一句「不要用它查退款进度（用 get_refund_status）」；同时在 get_refund_status 的描述里加「当客户问『钱什么时候到账』『退款到哪了』『什么时候退回来』时使用」。

局限：如果两个工具的核心词汇高度重叠（都有「订单」「状态」），模型仍可能混。而且描述越长，模型对每句话的权重越低。

修法二：合并工具，用参数区分（成本中，半天）。

把两个工具合成一个 get_order_info(type: enum["status", "refund", "logistics"])。模型只需要判断「查订单的哪方面」，不需要在相似的工具间选择。

局限：合并后单次返回的数据更多，可能带来额外延迟；而且 type 选错的后果和工具选错类似，只是概率低一些。适用条件是「这些查询底层是同一个系统的不同视图」——如果不是，合并会制造一个巨大的接口。

修法三：路由前置，不让模型选（成本高，1–2 天）。

在调用模型之前，用规则或小模型判断意图（「退款进度」类关键词 → 直接调 get_refund_status），把工具选择从模型侧移到编排侧。

局限：规则路由会漏掉口语化表达，而且它把「灵活性」换成了「确定性」——遇到规则没覆盖的意图时表现更差。更适合的场景是「工具很多（> 10 个）且模型选择准确率长期上不去」。

为什么这个顺序：先试成本最低的，因为它经常就够用了。描述的问题在实践中占多数，而它的修复不需要动架构。不要一上来就做路由——那会把一个提示词问题固化成一个需要长期维护的规则系统。

综合题二设计一个「修改收货地址」工具的完整定义和执行逻辑。要求考虑：参数、校验、确认、幂等、错误处理。
答案

工具定义：

{
  "name": "update_shipping_address",
  "description": "修改未发货订单的收货地址。仅当客户明确要求修改地址、
                  且订单状态为「未发货」时使用。已发货订单不能用此工具，
                  应告知客户联系承运商。",
  "parameters": {
    "order_id":   {"type": "string", "description": "11 位订单号"},
    "new_address": {"type": "string", "description": "完整新地址，含省市区与详细地址。
                    必须由客户提供，不得由你推断或补全。"},
    "reason":     {"type": "string", "enum": ["填错", "搬家", "改公司地址", "其他"]}
  }
}

执行逻辑（六步）：

① 结构校验：order_id 匹配 ^T\d{11}$；new_address 长度 10–120；reason 在枚举内。不通过返回 BAD_ARGS + 具体字段错误。

② 业务校验：订单存在、属于当前坐席的负责范围、状态为「未发货」。任一不满足返回对应 code（NOT_FOUND / FORBIDDEN / ALREADY_SHIPPED），且 retryable: false。

③ 地址合法性：调地址服务校验省市区是否匹配、是否在配送范围。这一步经常被省略，而它在真实业务里能拦掉 5%–10% 的错误地址。

④ 生成确认单：返回 NEED_CONFIRM 和确认卡片的内容（原地址、新地址、订单号、金额、可否撤销）。此时不执行任何修改。

⑤ 确认后执行：带幂等键 trace_id + order_id + hash(new_address)。执行前检查幂等缓存；执行后写缓存（含结果）。

⑥ 记录审计：谁、什么时候、改了什么、原值是什么、确认人是谁。审计记录要能支持「三个月后客户投诉地址错了」的复盘。

错误处理的关键细节：ALREADY_SHIPPED 的 hint 要写「订单已于 X 日发货，建议告知客户联系承运商修改，承运商电话可以从 get_logistics 获取」。这样模型能直接给出下一步，而不是干巴巴地说「不能改」。

为什么第 ④ 步单独成一步而不合并进 ⑤：因为它对应的是人机边界，而不是一个技术步骤。把它做成独立的状态（第 6 章的 confirm），才能保证「不允许超时」「必须留痕」「界面能渲染」这三件事都有地方承载。

综合题三老板说「直接让 AI 自动退款，效率最高」。你会怎么回应？给出一个既能推进又不失控的方案。
答案

先说清风险的具体形态，不要泛泛说「有风险」：

「自动退款有三个具体的失控方式：① 模型编造订单号或金额，退给了错误的人；② 条件判断错——客户说的情况不满足退款条件，但模型判成满足；③ 重复执行——重试机制导致同一单退两次。这三个都不会报错，只会体现在财务对账上，而那时已经过去一个月。」

再给一个分层方案，把「全自动」拆成可验证的台阶：

第一阶（2 周）：只读 + 建议。AI 判断是否满足退款条件，输出「建议退款 / 不建议」+ 依据条款，由人执行。这一步测的是判断准确率——用 200 条历史工单做评估集，要求 ≥ 95% 才能进下一阶。

第二阶（1 个月）：小额自动 + 大额确认。设一个额度上限（比如 50 元以下自动），以上必须确认。同时加三道护栏：单日单人累计上限、同一订单只能自动一次、每笔自动退款都进「当日复核清单」由主管抽检 10%。

第三阶：逐步放开额度。用前两阶的数据算「自动退款的事故率」和「人工复核的驳回率」。驳回率是核心指标——它直接反映模型的判断质量。低于 1% 才考虑提高额度。

然后给一个可量化的验收标准：

「第一阶结束时我给你三个数字：判断准确率、平均处理时长下降多少、以及有多少笔是『AI 建议退但人判断不退』。如果第三个数字超过 5%，说明它比人激进，不能自动。」

为什么这样回应有效：

① 它没有拒绝，而是给出了路径——老板要的是效率，这个方案能到，只是分三步。

② 它把「风险」翻译成了具体的、可被验证的场景（编造、判错、重复），而不是抽象担忧。

③ 它给了一个客观的放行条件（准确率 ≥ 95%、驳回率 < 1%），而不是「我觉得还不行」。这让讨论从「谁更保守」变成「数据到了没有」。

这道题真正考的是：在「技术判断」和「业务诉求」之间，能不能给出一个双方都能接受的中间路径。这是 AI 全栈岗位和纯开发岗位最大的差别——后者只需要说「做不到」，前者需要说「这样能做到一部分，代价是什么」。
