第三篇 · 服务
第 9 章　从脚本到服务
脚本只要跑通就行，服务要对每一次失败负责

前两篇所有代码都可以写在一个 main.py 里，用命令行跑。这一章开始变化：当它要给 60 个坐席同时用、要能被别人调用、要在出错时不崩溃，它就必须变成一个服务。这个转变的难点不在框架，而在你要开始为「别人怎么用它」负责。

本章学习目标
理解　脚本与服务的四个本质差别
掌握　用 FastAPI 写出一个结构正确的服务（路由 / 模型 / 依赖 / 异常）
掌握　输入校验与错误码设计：让调用方知道该怎么办
掌握　鉴权与租户隔离：知道是谁在调，且只给他该看的
了解　配置与密钥的管理方式

9.1　脚本能跑，为什么不叫服务

场景

一个「会话摘要」功能最初是一个脚本：读一个 JSON 文件，调模型，写一个 JSON 文件。前端同学用 Node 起了个临时的转发接口，把文件读出来返回给页面。三个人用，跑了两周，很好。

推广到全组 60 人之后，一周内出了五件事：

① 两个人同时点，第二个人拿到的是第一个人的摘要（临时接口把结果写在同一个文件里）。
② 有人传了一个 4 万字的工单，请求跑了 90 秒，前端超时，但后端还在跑，又跑了三次。
③ 有人传了一个空的工单号，脚本报 KeyError，整个进程退出，所有人 503。
④ 密钥写在脚本第 12 行，被截图发到了项目群里。
⑤ 有人问「这个功能昨天用过多少次」，没人答得上来。

五件事对应五个缺失，而它们正好构成「服务」的定义：

事件缺失的东西服务里对应的概念
① 结果串了请求间无隔离无共享可变状态；每个请求独立上下文
② 超时后还在跑没有超时与取消超时预算 + 取消传播
③ 一个坏请求打挂全部没有输入校验与异常边界Schema 校验 + 全局异常处理
④ 密钥泄露配置与代码混在一起环境变量 / 密钥管理
⑤ 说不清用量没有结构化日志每次请求一条可聚合的记录

第一个问题特别值得说，因为它的形态很隐蔽：用文件或全局变量做「临时缓存」，在单用户场景下完全正常，多人时就变成数据串号。修法不是加锁，而是根本不要在请求之间共享可变状态——需要缓存就用带 key 的缓存，key 里必须包含所有影响结果的输入。

9.2　一个结构正确的服务

下面这个骨架只有 40 行，但它的分层是对的。后面所有章节都会在这个骨架上加东西。

例题 9-1　最小可用服务
from fastapi import FastAPI, Depends, HTTPException
from pydantic import BaseModel, Field
from typing import Annotated

app = FastAPI()

# ---------- 1. 输入契约 ----------
class SummarizeReq(BaseModel):
    ticket_id: str = Field(pattern=r'^T\d{11}$')
    transcript: str = Field(min_length=10, max_length=60000)
    max_chars:  int = Field(default=120, ge=40, le=400)

# ---------- 2. 身份（依赖注入） ----------
async def current_agent(authorization: str = Header(...)):
    agent = verify_token(authorization)          # 见 9.4
    if not agent:
        raise HTTPException(401, 'token 无效')
    return agent

# ---------- 3. 路由只做编排 ----------
@app.post('/api/summarize')
async def summarize(req: SummarizeReq, agent: Annotated[dict, Depends(current_agent)]):
    if not await can_access(agent, req.ticket_id):
        raise HTTPException(403, '无权访问该工单')
    return await do_summarize(req, agent)
三段各自的职责：契约（能进来的数据长什么样）、身份（谁在调）、编排（做什么）。
路由里不应该有一行业务逻辑——它只负责把这三件事串起来。

三个细节值得单独讲。

Field 上的约束不是装饰。max_length=60000 直接挡住了「4 万字工单」导致的 90 秒请求；pattern 挡住了空工单号导致的 KeyError。这两条约束把第 9.1 节的事件 ② 和 ③ 从「线上故障」变成了「400 响应」，代价是两行代码。

身份用依赖注入，不用中间件。因为业务代码需要知道是谁在调（不只是「有没有权限」）。用依赖注入，agent 会直接出现在函数签名里，忘不了；用中间件，身份藏在 request.state 里，早晚有人忘。

路由不写业务逻辑。这条规矩的价值在第 13 章之后会显现：当你需要把「摘要」改成「带检索的摘要」，或者加一层缓存，改动应该只发生在 do_summarize 里，而不是在路由里。路由一旦掺了逻辑，测试就必须起 HTTP 服务才能跑。

9.3　错误码：让调用方知道下一步

初学者常犯的错是「出错就 500」。500 的含义是「服务有 bug」，调用方唯一能做的就是重试或报警。但真实错误分五类，每类的应对完全不同：

状态码含义调用方应该做什么典型场景
400你的请求不合法改请求，重试无意义字段缺失、格式错、超长
401身份不明刷新 token 后重试一次token 过期
403身份明确但无权不要重试，换人跨租户访问
429太频繁按 Retry-After 退避配额用尽、并发超限
503依赖不可用退避重试，可能要多等上游模型超时、数据库连不上

关键区别在 400 和 503：前者重试一万次也没用，后者等一会儿就好了。把 400 报成 500，会导致调用方疯狂重试，把一次小问题放大成雪崩。

响应体也要有结构。别只返回一句中文：

例题 9-2　错误响应体
{
  "code": "TRANSCRIPT_TOO_LONG",
  "message": "对话长度 82,340 字，超过上限 60,000 字",
  "field": "transcript",
  "hint": "请只提交最近 30 轮，或先降级为分段摘要",
  "trace_id": "tr_9f21a8"
}
四个字段各有用处：
code 给程序判断（可枚举，可 i18n）；message 给人看且带具体数值；
hint 给下一步动作（这一条最容易被忽略，也最有用）；trace_id 让排查能对上日志。

hint 这一项值得坚持。它把「报错」变成了「引导」——调用方（可能是不熟悉这个服务的同事）看到 hint 就知道该怎么改，而不是去问你。一个带 hint 的错误响应，能省掉一次群里的对话。

9.4　鉴权与租户隔离

「谁在调」有两个层次，很多实现只做了第一层。

第一层：身份可信。token 有效、签名正确、未过期。这一层决定「你是不是我们的坐席」。

第二层：数据可见。这个坐席能不能看这张工单。这一层决定「你能看到什么」。

只做第一层会导致一个很常见的漏洞：任何坐席都能通过改 ticket_id 读到任意工单的摘要，而摘要里可能包含其他客户的手机号、地址、订单信息。这个漏洞在内部系统里经常被忽略，因为「都是同事」，但它同时也是合规问题。

例题 9-3　把可见性做成查询的一部分
# ✗ 先查数据，再判断权限（两处容易漏）
ticket = db.get(ticket_id)
if ticket.owner != agent['id']:
    raise HTTPException(403)

# ✓ 把权限条件写进查询（不可能漏）
ticket = db.get(ticket_id, tenant_id=agent['tenant'])   # 租户隔离
if ticket is None or ticket.owner != agent['id']:
    raise HTTPException(404)            # 注意：返回 404 而不是 403
两个要点：
① 租户条件写进 SQL，而不是查出来再过滤——后者一旦有人新增查询就会漏。
② 无权访问返回 404 而不是 403：403 等于告诉对方「这个工单存在，只是你看不到」，这本身就是信息泄漏。

返回 404 这个细节有争议——有人认为 403 更利于排查。判断标准是系统是否跨租户：同一公司内部用 403 便于协作；SaaS 多租户场景必须 404，因为「存在性」本身是敏感信息。

还有一件经常被漏的事：日志里不要记完整请求。排查需要的是 trace_id、agent_id、ticket_id、耗时、token 数、是否成功，不需要对话原文。原文进日志等于把 PII 复制了一份到日志系统，而日志系统的权限通常比业务库松得多。

9.5　配置与密钥

三条规矩，没有例外：

  1. 密钥不进代码库。包括「只是内部测试用的」。一旦进过 Git，即使后来删掉，它也在历史里。
  2. 配置从环境读，且启动时校验。缺失的配置应该在启动时直接崩，而不是在第一个请求时抛 NoneType。
  3. 不同环境用不同密钥。开发环境的调用打到生产账号上，是很多「账单异常」的真正原因。
例题 9-4　启动即校验的配置
from pydantic_settings import BaseSettings

class Cfg(BaseSettings):
    llm_api_key: str
    llm_base_url: str = 'https://api.example.com/v1'
    db_url: str
    max_concurrency: int = 16
    env: str = 'dev'

    class Config:
        env_file = '.env'

cfg = Cfg()          # 缺字段会在这里直接抛错，服务起不来
assert cfg.env != 'prod' or cfg.llm_api_key.startswith('sk-prod-')
启动失败远好于带病运行。
最后那行 assert 看着多余，但它挡住了一类真实事故：把测试密钥配到了生产环境，然后所有请求 401，而报错信息指向「模型不可用」。
上线前必须过的五关
  1. 每个入参都有约束。长度上限、格式、枚举。没有约束的字符串字段，早晚会有人传 4 万字。
  2. 每个外部调用都有超时。没有超时的调用，在上游卡住时会耗尽你的连接池。
  3. 每个请求都有 trace_id。且它出现在响应体、日志、以及上游请求的 header 里，三者能对上。
  4. 每条错误都有 code 和 hint。让调用方能自己解决 80% 的问题。
  5. 密钥只在环境变量里。用 grep 在仓库里搜一遍 sk-，结果必须是 0。
本章小结
  • 脚本与服务的差别不是框架，是「请求间隔离、超时取消、输入校验、配置分离、可观测」五件事。
  • 不要在请求之间共享可变状态；缓存必须带包含全部输入的 key。
  • 结构分三段：契约（Pydantic 约束）、身份（依赖注入）、编排（路由只串联）。
  • 错误分五类：400 改请求、401 换 token、403 换人、429 退避、503 等一会儿。别把 400 报成 500。
  • 错误体要有 code / message / hint / trace_id，hint 决定调用方能否自助。
  • 鉴权两层：身份可信 + 数据可见。租户条件写进查询，跨租户无权返回 404。
  • 配置从环境读并在启动时校验；缺配置要崩在启动，不要崩在第一个请求。

本章综合习题

综合题一有人报告「偶尔会拿到别人的摘要」。列出四种可能原因，并给每一种一个能在十分钟内完成的验证方法。
答案

原因一：用文件或全局变量做缓存，key 不完整。
验证：在返回前打印 id(result) 或缓存 key。如果两个不同 ticket_id 的请求拿到同一个对象/同一个 key，确认。十分钟够。

原因二：前端请求没有绑定工单，切换后面板复用。
验证：在响应体里加 ticket_id 字段，前端渲染前断言它等于当前工单。不等就丢弃并记一条日志。上线一天看日志有没有触发——这是最快的二分法，能直接排除或确认前端责任。

原因三：连接池或 session 复用出错。比如把 requests.Session 或数据库游标放在全局，多线程下互相覆盖。
验证：在服务端把并发从 1 调到 32，用同一个 ticket_id 打 200 次，检查响应里的 agent_id 是否始终一致。并发升高后出现不一致，就是共享状态问题。

原因四：流式响应的取消传播没做对。用户中断后，残留的生成器继续往旧连接写，而连接被复用了。
验证：日志里记 trace_id 和连接 id。如果同一个连接上出现两个 trace_id，就是这一类。

这类 bug 的方法论：不要靠读代码找。先在响应里加一个「归属标识」并断言，用生产流量跑一天。用数据把可能性从四个减到一个，比四个人各读一遍代码快得多。

综合题二为什么「无权访问」在很多场景下应该返回 404 而不是 403？如果团队坚持用 403，你会怎么处理？
答案

理由：403 泄漏了「存在性」。「403 无权访问」这句话的完整含义是「这个资源存在，但你不能看」。在多租户系统里，攻击者可以用 403 和 404 的差异做枚举：逐个试 ticket_id，凡是返回 403 的就说明该工单真实存在，返回 404 的说明不存在。这个差异足以让他摸清你的业务量、客户分布，甚至推断出 ID 生成规则。

如果团队坚持用 403，可以做三件事：

① 加频率限制。按账号限制「404/403 类响应」的速率，比如每分钟超过 30 次就 429。这让枚举变慢，但不根除。

② 加检测与告警。统计每个账号的「越权尝试率」，异常时告警并临时冻结。这比限制速率更有效，因为它针对行为而不是数量。

③ 区分「跨租户」和「同租户无权」。跨租户一律 404（这是安全边界），同租户内保留 403（便于协作排查）。这个折中通常是团队最能接受的。

这道题真正的考点是：错误码不只是给人看的提示，它是一种信息通道。每多返回一点信息，就多一分被利用的可能。设计错误码时，除了问「调用方需要知道什么」，还要问「不该让谁知道什么」。

综合题三写出你对一个「AI 摘要」接口做上线前检查的清单（不超过 8 条），每条都要能在 5 分钟内验证。
答案

八条，按验证成本从低到高：

  1. 传一个空 body，应返回 422/400 且带 code，不能 500。（curl -X POST 一次）
  2. 传 transcript 为 100,000 字，应返回 400 且 hint 说明上限。（一行脚本生成）
  3. 不带 Authorization 头，应返回 401；带过期 token，应返回 401 而非 500。
  4. 用 A 的 token 请求 B 的 ticket_id，应返回 403 或 404，不能返回内容。
  5. 在仓库根目录 grep -r "sk-" .，结果为空。
  6. 把上游域名指向一个不可达地址，应返回 503 且带 trace_id，且在超时时间内返回（不能挂 90 秒）。
  7. 连打 50 次并发，检查是否有请求拿到别人的结果（比对响应里的 ticket_id 与请求一致）。
  8. 看一条日志，确认包含 trace_id / agent_id / ticket_id / latency / tokens / ok，且不包含对话原文。

为什么这八条：它们覆盖了第 9.1 节那五个事故的全部根因，且每一条都能在一个终端里完成。第 6 条最容易被跳过——很多人只在正常路径上测过，而「上游挂了会怎样」是上线后第一个会遇到的情况。

一个额外建议：把这八条写成一个 shell 脚本 smoke.sh，每次发布前跑一遍。它不需要成为 CI 的一部分（虽然更好），但至少要有一个固定入口，让「上线前检查」不依赖某个人记得。
