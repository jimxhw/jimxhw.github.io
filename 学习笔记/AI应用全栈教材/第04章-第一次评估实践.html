第 4 章　第一次评估实践
用一下午拿到一个数字，并用它终结所有争论

第 3 章做出了尺子，这一章用它量一次。目标很小但很具体：给你的客服系统现有的 AI 能力，跑一次可复现的体检，产出一份别人能引用、也能反驳的报告。这件事的成本大约是一个下午，而它带来的位置变化，比读十篇论文都大。

本章学习目标
理解　人工、规则、模型裁判三种评估范式各自的适用边界
掌握　把「答得好不好」翻译成四个可计算的指标
掌握　写一个并发跑批脚本，把结果落成可分析的表格
掌握　用错误归因树定位问题在哪一层，而不是笼统地说「效果不好」
了解　那份三页体检报告该写什么、不该写什么

4.1　三种范式，别混着用

评估一个 AI 功能，手段只有三种。它们不是互相替代的关系，成本、可信度、适用场景都不同。

范式怎么做成本适合致命弱点
人工评估人逐条判断对错高，约 3–5 分钟/条开放式生成、语气、可用性不可重复，人会疲劳、标准会漂移
规则评估用代码判：格式、字段、关键词、数值一致极低，几乎免费结构化输出、有明确规则的场景只能判「格式对」，判不了「内容对」
模型裁判让另一个模型按评分标准判中，约为成本 1/10开放式生成的大规模初筛有系统性偏好，且和被测模型可能同源

实践中的正确组合是三层串联，而不是选一个：

  1. 规则先筛：JSON 能不能解析、字段齐不齐、分类是否在枚举内、引用的条款号是否真的出现在知识里。这一层能拦掉 20%–40% 的错误，成本接近零。
  2. 模型再判：对通过规则层的样本，让裁判模型按 rubric 判「是否回答了客户诉求」「是否有编造」。这一层把 200 条的处理成本从 15 小时压到 20 分钟。
  3. 人工只判两批：模型裁判判「错」的（确认是不是真错），以及随机抽 10% 判「对」的（确认裁判没有放水）。

第三层的第二句容易被忽略：如果只复核「判错」的，你永远发现不了裁判在放水。抽 10% 被判「对」的样本人工看一眼，是唯一的校准手段。经验上，未经校准的模型裁判会放过 5%–15% 的实质错误——它倾向于认为「说得通」就是「说得对」，而这两件事在业务里差得很远。

一个必须说清的偏见
  1. 同源偏好。用 A 模型裁判 A 模型的输出，评分会系统性偏高，因为它的措辞习惯和自己一致。条件允许时，裁判模型应当与被测模型不同族。
  2. 长度偏好。裁判模型普遍偏爱更长的回答，即使内容相同。控制方法是 rubrics 里明确「简洁得满分，冗余扣分」，或直接对不同长度分组比较。
  3. 位置偏好。做 A/B 对比时，放在前位的答案胜率更高。必须交换顺序各跑一次。

4.2　把「答得好不好」翻译成四个数

业务方说的「效果不好」，落到指标上是四件不同的事。分开算，才能分别修。

指标一：任务准确率

对分类、抽取这类有唯一答案的任务，就是 判对条数 / 总条数。定义的关键在于「判对」的粒度：字段全对才算对，还是主字段对就算对？

建议两个都算，并分开报。严格准确率（所有字段完全一致）和主字段准确率（核心字段一致）。前者反映工程质量，后者反映业务可用性。两者差距大，说明错误集中在次要字段上，那类错误通常可以靠后处理修掉，不必动模型。

指标二：幻觉率

定义要窄，否则算不准。可用的定义是：回答中出现了知识库里不存在、且无法从对话推出的具体事实（条款、时限、金额、承诺）。

注意「具体」这个词。含糊的表达（「一般几天内」）虽然不好，但不构成幻觉；「7 天内可退」如果知识里写的是 15 天，就是幻觉。这个区分让幻觉率可以被规则部分自动化：把回答里的数字、条款号抽出来，和知识原文做匹配。

指标三：拒答率与误拒率

这两个必须成对看。拒答率是「该答却拒了」的比例，反映可用性；误答率是「该拒却答了」的比例，反映风险。只看一个必然被优化到极端：只追求不幻觉，模型会变成什么都拒；只追求都回答，它会开始编。

指标四：延迟与成本

不要报平均值。报 P50 / P95 / P99，以及分段的 token 成本。原因是体验由长尾决定：P50 是 1.2 秒、P95 是 9 秒的系统，坐席记住的是那 5% 的卡顿。

例题 4-1　四个指标的落表口径
样本：200 条（dev 140 / holdout 60），golden_v1 @ 8f3c1a90b7e2

准确率
  strict_acc   = 所有字段与 label 完全一致            # 工程口径
  primary_acc  = 主字段一致即可                      # 业务口径

幻觉
  halluc_rate  = 含「知识外具体事实」的条数 / 应回答条数

拒答
  over_refuse  = 应回答却输出转交语的条数 / 应回答条数
  under_refuse = 应拒答却给出具体结论的条数 / 应拒答条数

性能
  ttft_p50 / ttft_p95        # 首字时间，秒
  total_p95                  # 总耗时，秒
  cost_per_call              # 单次均值，元
报告里这七个数字一起出现，才构成一次完整的体检。
只报 strict_acc，是「模型评测」；七个一起报，才是「系统评估」。

4.3　跑一次：脚本的结构

体检脚本不长，但结构必须对。顺序是：读集子 → 并发调用 → 落原始响应 → 事后评分。这四步要分开，因为调用很贵、评分很便宜、改评分标准很常见。把响应先存下来，之后改判分逻辑就不用重跑模型。

例题 4-2　一次可复现的体检
import asyncio, json, time, pandas as pd
from openai import AsyncOpenAI

cli = AsyncOpenAI()
SEM = asyncio.Semaphore(8)          # 并发上限，别把配额打爆

async def one(row):
    async with SEM:
        t0 = time.perf_counter()
        r = await cli.chat.completions.create(
            model='MODEL', temperature=0,
            messages=[{'role': 'system', 'content': SYS},
                      {'role': 'user', 'content': row.content}],
        )
        return dict(
            sample_id=row.sample_id,
            raw=r.choices[0].message.content,
            latency=time.perf_counter() - t0,
            in_tok=r.usage.prompt_tokens,
            out_tok=r.usage.completion_tokens,
        )

async def main():
    df = pd.read_csv('golden_v1.csv')
    rows = await asyncio.gather(*[one(r) for r in df.itertuples()])
    pd.DataFrame(rows).to_csv('run_v1_raw.csv', index=False)

asyncio.run(main())
关键点：先存 raw，再评分。
评分逻辑会改十几次（口径、边界、例外），每改一次都重跑 200 次调用，是纯浪费。
temperature=0 也不是为了「稳定」这个说法，是为了让两次运行之间的差异主要来自你改的东西。

并发上限设 8 是有意的，不是随手填的。太低（比如串行）会让 200 条跑 20 分钟，你就不愿意多跑；太高会被限流，触发重试，反而更慢，而且延迟数据会被重试污染，P95 直接失真。8–16 是大多数 API 的舒适区，具体看你的配额。

还有一件事要记住：把 run_v1_raw.csv 保存下来。它是「某个版本在某个时刻的表现」的唯一证据。三个月后有人问「当时为什么会这样」，只有这份原始响应能回答。它也是后面做回归对比的基线。

4.4　读懂结果：错误在哪一层

跑完之后你手里有一个准确率，比如 71%。这个数字本身没有行动价值——它只告诉你「不够好」。有价值的是把 29% 的错误分到几个格子里，因为不同的格子对应完全不同的修法。

图 4-1　错误归因树：先判格式与检索，再判判断与表达

这张图里最重要的一句话是「唯一该改提示词的一层是 ③」。但现实中，团队遇到效果不好时的第一反应几乎总是改提示词，因为那是唯一不用理解系统的动作。22 条检索失败被当成提示词问题时，你会观察到一种典型现象：每次改提示词，都有一批样本变好、另一批变差，净值原地踏步。看到这个模式，就该去查检索，而不是继续改提示词。

一个判 ② 的具体手法

检索层的错误最难判，因为它需要你同时看「该给什么」和「实际给了什么」。有一个便宜的做法：把正确知识片段的第一句，人工塞进提示词，再跑一次这些样本。

如果准确率从 71% 跳到 90%，说明模型本身有能力答对，问题在检索。如果只到 74%，说明知识给对了它也用不好，问题是判断层。这一次对照实验的信息量，比调十版提示词都大，成本是一次跑批。

4.5　那份三页报告

体检的价值不在你知道了什么，在别人能引用什么。所以必须写下来，而且要短——三页，多了没人看。

第一页：结论与口径

开头三段话，不要铺垫：

  1. 一句话结论：「现有 AI 回答在 200 条真实工单上，主字段准确率 71%，其中 38% 的错误来自知识检索，不是生成。」
  2. 测量口径：样本来源、时间窗、条数、数据集指纹、模型版本、运行日期。这一段是让别人能反驳你的关键，缺了它，数字就变成宣传。
  3. 一句话限制：「本次只测了单轮问答，未覆盖多轮追问与工具调用。」主动写限制，比被别人指出来的代价小得多。

第二页：分布，不是均值

一页放三张东西：按类别的准确率条形图（带样本数）、混淆矩阵里最主要的三个混淆对、错误归因的饼图或堆叠条。这一页的作用是让人看见「均值掩盖了什么」。

举一个真实的效果：某团队报「整体 84%，可以上线」。加上按类别的条形图后发现，「发票重开」这一类 15 条全错——因为这个类别在训练示例里从未出现过。而发票重开每月有 400 单，全部要人工重做。84% 和「某个高频小类全错」可以同时成立，而后者才是真正要修的。

第三页：三个可执行建议

每条建议都要带预期收益和成本，写成可以被否决的形式：

  • 「把知识切分从 800 字改成按条款切分，预计修掉 22 条检索错误中的 12–15 条，工作量 2 天。」
  • 「给发票类补 3 个示例并加一个独立分类分支，预计该类从 0/15 提到 12/15，工作量半天。」
  • 「对置信度低的样本改为强制转交，预计误答减少但转人工上升约 6%，需要业务方确认能否接受。」

第三条特意写了代价，这是有意设计的。一份只讲收益的报告会被当成推销；一份写了代价的报告才会被当成分析。而且第三条实际上把决策权交回给了业务方，这在组织里是更安全的姿态。

报告里不要做的三件事
  1. 不要用「业界平均 92%」做对照。没有可比口径的平均值，只是给读者制造焦虑，同时暴露你不懂口径。
  2. 不要只给一个总分。总分无法指导行动。如果篇幅只够放一个数字，那就放「错误最多的那一类错了几条」。
  3. 不要在没有 holdout 的情况下承诺「优化到 90%」。你在 dev 上能到 90%，上线后大概率回到 82%。承诺兑现不了，比不承诺更伤信任。
本章小结
  • 三种范式串联使用：规则先筛、模型裁判中筛、人工只判两批（判错的 + 10% 判对的）。
  • 四个指标成对看：准确率看分布、幻觉率定义要窄、拒答率与误答率必须同时报、延迟报 P95 不报均值。
  • 脚本顺序：调用与评分分离，先存 raw 再评分；并发 8–16；temperature=0。
  • 错误归因顺序不能颠倒：格式 → 检索 → 判断 → 表达。只有第三层该改提示词。
  • 判检索层最便宜的手法：人工把正确知识塞进提示词重跑一次，看能跳到多少。
  • 报告三页：结论与口径、分布而非均值、三个带代价的建议。

本章综合习题

综合题一体检结果：strict_acc 71%，primary_acc 88%。这两个数的 17 个点差距说明什么？你会先修哪一边？
答案

17 个点的差距说明错误几乎都落在次要字段上。主字段（类别、结论）基本正确，但附加字段（置信度、依据引用、二级标签、时间戳格式）经常错或缺。

先修次要字段，不要碰模型。理由是成本结构完全不同：次要字段的错误通常可以用后处理修掉——缺字段就补默认值、格式错就重新规范化、置信度越界就截断。这些都是几行代码的事，不需要重跑模型，也不会引入新风险。

而改模型去提高 strict_acc 有两个代价：一是可能把已经对的 88% 弄坏（主字段的稳定性通常比次要字段脆弱）；二是即使提到 80%，你付出的调优时间足够把后处理做到 95%。

但有一个例外必须查：如果某个次要字段是下游依赖的（比如「是否需要人工复核」这个布尔值），那它的错误不叫次要错误，它会直接影响流程。这种情况下要先看这个字段单独的准确率，而不是看整体 strict_acc。

综合题二你怀疑问题在检索层。给出一个成本最低的验证实验，并说明如何解读两种结果。
答案

实验：正确知识注入对照（knowledge-injection ablation）。

步骤：① 从 200 条里挑出所有判错的样本（比如 58 条）；② 人工为每条写出「理想知识片段」（可以从原文复制，不必改写）；③ 把这些片段直接拼进提示词，替换原来的检索结果；④ 重跑，只看这 58 条的新结果。

解读 A：错误从 58 降到 12（准确率跳到约 94%）。模型有能力答对，瓶颈在检索。此时应该动切分、索引、混合检索、query 改写，一个字都不要改提示词。

解读 B：错误从 58 只降到 46。知识给对了它也用不对。这是判断层问题，可能是任务定义不清、示例误导、或者需要拆成两步（先判断适用条款，再组织语言）。此时改提示词、加示例、拆任务才有意义。

解读 C：错误反而增加到 61。这个结果最有信息量——说明你注入的知识格式和模型习惯的格式不一致（比如原文有大量表格、编号混乱），或者知识变长后淹没了关键句。这类情况提示的是「上下文组装方式」有问题，而不是检索或提示词。

成本：一次 58 条的跑批，加上人工写 58 条理想片段（约两小时）。这两个小时通常能省掉两周的无效调优。

综合题三你要向技术负责人汇报。他只有五分钟，且已经听过三次「AI 效果不错」。写出你的开场三句话。
答案

参考版本：

「我用 200 条真实工单测了现在的回答功能，主字段准确率 71%，这个数字和上线时演示的效果差距不小。

错误里 38% 出在知识检索——该给的条款没给到，模型只能靠猜；这部分改提示词没用，需要动切分和索引。剩下 31% 是判断错误，知识给对了但没用对。

我建议先花两天修检索，预计能把这 71% 提到 82% 左右；如果两周内到不了 85%，说明这条路的天花板比预想低，那时候再讨论要不要换方案。」

为什么这三句有效：

① 第一句给的是可反驳的数字，不是感受。它同时隐含了「之前的演示不可靠」，但没有指责任何人。

② 第二句做了归因，把问题定位到具体层次，并明确排除了一个常见动作（改提示词）。这句话的作用是建立你的判断力，而不只是报告事实。

③ 第三句给的是带时间点和退出条件的承诺。「两周到不了 85% 就换方案」这一句尤其重要——它让你不必为结果兜底，只为一个可检验的路径负责。

反过来看常见的错误开场：「我们现在 AI 已经能回答大部分客户问题了，效果还不错，接下来想优化一下准确率。」——这句话没有数字、没有归因、没有承诺，五分钟会变成一次寒暄。
