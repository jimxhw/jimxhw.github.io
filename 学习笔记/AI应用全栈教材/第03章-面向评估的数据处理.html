你没法在没有尺子的情况下改进任何东西

第 2 章末尾那个「通过率从 84% 到 87%」的问题，答案取决于你手里有多少条样本、这些样本是怎么选出来的。这一章讲的就是这件事：把业务里随手可得的对话记录，变成一份能反复使用、结论站得住的评估数据集。它是全书中唯一一章「几乎没有代码」的章节，却是后面所有章节的地基。

3.1　没有尺子的六周

场景

2025 年底，一家电商公司的客服系统上线了「工单自动分类」。做法很直接：把工单标题和描述发给模型，要求它从 12 个类别里选一个，字段名写死，格式稳定。

上线第一周，运营反馈「分得挺准」。第二周开始有人说「售后类的老是分错」。第三周，开发改了一版提示词，加了 8 个类别说明和 3 个示例，自己试了十几条，觉得明显变好，就发了。

第四周，售后组说「现在更乱了」。开发再改，再加示例。到第六周，提示词已经 1400 字，谁都说不清它比第一版好还是差。项目经理问了一句：「现在的准确率是多少？」会议室安静了几秒——没有人知道。他们有过六次「改进」，但没有一次留下过数字。

这件事的核心不是提示词写得不好，而是他们在没有测量工具的情况下做了六次改动。每一次改动的依据都是「试了十几条，感觉变好了」，而十几条样本在 12 分类任务上的分辨率接近于零：随机猜测的准确率是 8.3%，一个「感觉不错」的版本可能是 62%，也可能是 71%，这十几条根本分不出来。

更麻烦的是第三周那次改动。他们把 8 个类别说明和 3 个示例加进提示词，直觉上这是「给模型更多信息」，但那 3 个示例全部来自售后类——因为提出问题的就是售后组。于是模型学到了一个隐含先验：售后类的样本在训练分布里被过度代表，遇到模棱两可的工单会倾向判成售后。这个偏移在「试十几条」的检验里看不出来，因为试的也多半是售后工单。

评估集的作用不是打分，是让改动可比较。没有固定评估集时，每次改动前后测的其实是不同的东西：不同的样本、不同的心情、不同的记忆。这样的比较必然得出「感觉变好了」这种无法证伪的结论。

由此得出一条优先级：在写第二版提示词之前，先把尺子做出来。这把尺子的成本比大多数人想的低——一个下午，200 条样本，一张三列的表格。它能省掉的返工是以周计的。

3.2　抽样：200 条怎么选

假设你手上有 5,000 条已解决的历史工单。最自然的做法是随机抽 200 条，但这个做法会踩三个坑。

坑一：随机抽样会让长尾消失

5,000 条工单里，退款售后可能占 40%，物流查询占 25%，而「发票重开」「跨境税费」「企业月结」这些加起来不到 3%。随机抽 200 条，前三类各能抽到几十条，后几类可能一条都没有。

但长尾恰恰是最容易出错的地方。原因很朴素：模型的错误集中在它见得少的模式上，而你的业务价值往往也集中在长尾上——退款是标准流程，跨境税费才是需要人工判断的部分。评估集如果漏掉长尾，你会得到一个漂亮但无意义的 92%。

做法是分层抽样（stratified sampling）：先按类别分组，每类至少保证 15 条，剩下的名额按业务占比分配。这样既保留了「整体准确率」的可解释性，又保证了每一类的估计有足够样本。

坑二：只抽「已解决」的工单会高估表现

已解决的工单是幸存者。那些客户直接骂人挂断、坐席放弃、升级到主管的会话，往往不在「已解决」这个状态里。而它们才是模型最容易答错的。

所以抽样前先确认状态字段的取值，把「已解决」「已关闭」「升级」「超时未响应」「客户放弃」都算进池子，按真实比例抽。如果你的评估集只包含顺利的对话，它评估的就不是你的系统，而是你的运气。

坑三：时间窗口太窄会锁死在一个版本上

2026 年 3 月公司改了一次退货政策（7 天无理由改成 15 天），如果评估集全部取自 2 月的工单，那它测的是旧政策下的回答。模型在新政策下答得对不对，这套集子看不出来。

合理的窗口是最近 3 个月，且跨过至少一次业务规则变更。跨变更是有意的：它让评估集天生包含「政策刚改，模型还在引用旧条款」这类真实错误，而这正是最危险的一类错误。

图 3-1　分层抽样：长尾保底 15 条，其余按业务占比分配

一个可以照着写的抽样脚本

例题 3-1　分层抽样（pandas）
import pandas as pd

df = pd.read_sql(SQL, conn)          # 5,000 条，含 category / status / created_at
df = df[df.content.str.len() > 20]      # 去掉空壳

# 长尾兜底：先给每类 15 条，再按剩余名额的占比分配
FLOOR, TOTAL = 15, 200
cats = df.category.value_counts()
long_tail = [c for c in cats.index if cats[c] <= 60]

parts, used = [], 0
for c in long_tail:
    g = df[df.category == c].sample(min(FLOOR, len(df[df.category == c])), random_state=7)
    parts.append(g); used += len(g)

rest = df[~df.category.isin(long_tail)]
quota = (TOTAL - used) * rest.category.value_counts(normalize=True)
for c, n in quota.items():
    parts.append(rest[rest.category == c].sample(max(8, round(n)), random_state=7))

sample = pd.concat(parts).drop_duplicates('ticket_id')
sample['label'] = ''       # 留空，等人工标注
sample.to_csv('golden_v1.csv', index=False)
print(len(sample), sample.label.isna().sum())
输出：203 条，其中 203 条待标注。
多出的 3 条来自 max(8, …) 的取整保护——宁可多几条，不要某一类少于 8 条。

脚本里两个细节值得注意。random_state=7 不是为了结果好看，是为了可复现：三个月后别人跑同一个脚本，抽到的必须是同一批工单，否则「上次那套集子」这句话就不成立。

drop_duplicates('ticket_id') 也是必需的。客服系统里同一张工单常有多条记录（每次状态变更一条），直接抽会把同一张工单抽进集子好几次，人为放大它的权重。这类重复在数据里非常隐蔽，抽取时不去重，你会在评估时得到「某类准确率突然变好」，实际只是那几条重复样本被改对了。

3.3　标注：让标准可以被别人复用

拿到 200 条工单之后，要把「正确答案」填进 label 列。这一步看起来体力活，实际上是整章最容易出错的地方，因为你心里那把尺子别人看不见。

先定标签体系，不要边标边想

常见做法是「标着标着发现少了一类，就加一个」。这会导致前 100 条按 12 类标、后 100 条按 14 类标，两段数据不可比，集子报错。

正确做法是先拿 20 条试标，把遇到的边界情况记下来，定死标签后再标全量。定标签时守住三条规则：

  • 互斥：每条样本只能落在一个类别里。做不到互斥，就说明类别定义里有重叠（比如「退款」和「售后」在很多公司是同一件事）。
  • 穷尽：必须有一个「无法判断」出口，且它也是一个合法标签。没有出口的标签体系，会逼标注人硬塞，制造出一批噪声标签。
  • 可操作：每个类别的定义要写成「看到什么现象就归到这一类」，而不是「这一类是什么意思」。前者能执行，后者只能讨论。
例题 3-2　标签表的两列写法
✗ 只能讨论的写法
退款售后：与退款、退货、售后相关的工单。

✓ 可以执行的写法
退款售后：
  出现「退款 / 退货 / 换货 / 补发 / 赔偿」任一诉求 → 归此类
  即使同时在问物流，只要核心诉求是钱或货的处置 → 归此类
  仅在询问进度、且未提出处置诉求 → 归物流查询
  同时涉及两类且无法判断主诉求 → 归「无法判断」
差别在于：第二种写法里每一句都能被另一个人拿去判断。
第一种写法在遇到「我要退款，顺便问下快递到哪了」时会引发争论，而这种工单占真实数据的 15% 以上。

双人标注与 kappa：检验标准是否可传递

如果你一个人标完 200 条，你会得到一个数字，但你不知道这个数字是「模型的表现」还是「你的偏好的稳定性」。区分方法很便宜：让另一个人独立标 50 条，然后算一致性。

不要用「一致率」这个指标。两个人各标 50 条，即使完全随机猜，在类别分布不均时也能得到 40% 以上的「一致率」。要用 Cohen's kappa，它扣掉了「随机也能对上」的那部分：

例题 3-3　算一次 kappa
kappa = (p_o - p_e) / (1 - p_e)

p_o = 实际一致率                    # 两人标的一样的比例
p_e = 随机情况下的期望一致率         # Σ(每人各类占比之积)

例：50 条，两人一致 41 条 → p_o = 0.82
    甲：售后 60% / 物流 25% / 其他 15%
    乙：售后 55% / 物流 30% / 其他 15%
    p_e = .60*.55 + .25*.30 + .15*.15 = .33 + .075 + .0225 = .4275

kappa = (0.82 - 0.4275) / (1 - 0.4275) = 0.3925 / 0.5725 ≈ 0.69
0.69 属于「中等偏上一致」。可以直接用的经验阈值：
< 0.6　标签定义有问题，先修定义，不要标全量
0.6 – 0.8　可用，但边界样本会有争议，结论要留余地
> 0.8　定义足够清楚，可以当基准集用

kappa 低的时候，最常听到的回应是「那个人不熟悉业务」。这句话通常是错的。一个熟悉业务的人标不出和你一致的结果，说明你的标准只存在于你的头脑里，而这恰好是最该修的东西——因为模型比新人更不熟悉业务，它看到的和新人一样模糊。

实操上有一步很划算：把不一致的 9 条拿出来逐条讨论，通常会发现其中 4–5 条是同一类边界问题。修掉这个边界，kappa 会从 0.69 跳到 0.85 以上，而花的时间不到一小时。

3.4　脱敏、截断、冻结

数据集一旦要离开生产库、进入开发环境或者发给外部（模型 API），有三个工程动作必须做。它们的顺序不能颠倒。

第一，脱敏：在抽出来的那一刻就做

客服对话里必然有手机号、身份证号、地址、订单号、银行卡后四位。这些东西一旦进了 CSV，就会跟着出现在日志、Git 仓库、截图、以及你发给模型的请求里。

做法是可逆替换，而不是删除：

例题 3-4　保结构脱敏
import re

RULES = [
    (r'1[3-9]\d{9}',                    'PHONE'),      # 手机号
    (r'\d{17}[\dXx]',                  'IDCARD'),     # 身份证
    (r'\b\d{16,19}\b',                  'BANKCARD'),   # 银行卡
    (r'[\u4e00-\u9fa5]{2,4}(省|市|区|路|街|号)', 'ADDR'),
]

def mask(text, keep_order=True):
    buf = {}
    for pat, tag in RULES:
        def rep(m):
            key = '<%s_%d>' % (tag, buf.setdefault(tag, 0) + 1)
            buf[tag] = buf.get(tag, 0) + 1
            return key
        text = re.sub(pat, rep, text)
    return text

mask('我手机 13812345678，订单 20260312008，要求退到尾号 6222 的卡')
# '我手机 <PHONE_1>，订单 20260312008，要求退到尾号 6222 的卡'
为什么保留占位符而不是删掉：
① 模型需要知道「这里原本有个号码」，否则会把句子理解成事实缺失
② 同一条对话里两个不同号码能被区分，多轮指代才成立
③ 占位符稳定，不改变 token 数太多，评估结论可比

注意订单号我没有替换。这是有意的取舍：订单号在推理链路里是必要信息（查物流、查退款都要用它），而它本身不构成个人身份标识——除非它能反查到人。如果你的订单号可以直接对应客户，那就必须替换，并把映射表放在独立的有权限的存储里。

脱敏的检查方法不是看代码，是搜结果。抽完之后跑一遍正则，在 CSV 里搜手机号模式、身份证模式，命中数必须是 0。这个检查要写进脚本，每次重新抽样都跑，不能靠人记得。

第二，截断：控制单条的 token 预算

真实工单的对话长度分布是长尾的。大部分 5—10 轮，少数能到 200 轮。一条 200 轮的会话可能有 30,000 token，它会让评估脚本的成本和延迟都失控，而且这类超长会话的答案往往依赖中段信息，截断后连人也没法判断对错。

处理方式分两步：先统计分布，再定规则。假设你统计出来 P50 是 640 token、P90 是 2,100、P99 是 9,400，那么合理的规则是：

区间处理理由
≤ 3,000 token（约 95%）原样保留覆盖绝大多数场景，不引入额外变量
> 3,000 token保留首 2 轮 + 末 8 轮，中间标注「已省略 N 轮」开头是诉求，结尾是结论，中间多为来回确认
无法截断的（如长表格附件）单独放一组，不计入总体指标，单独报告它测的是另一个能力，混在一起会污染结论

「单独一组」这个做法值得记住。当一类样本需要特殊处理才能评估时，正确做法是把它隔离出来单独报告，而不是想办法塞进平均值。塞进去的结果是平均值被拉低，但你不知道是模型不行还是你的预处理不行。

第三，冻结：让数据集不再变化

这是最容易被忽略、代价最大的一步。评估集做好之后，会有人出于好意持续「补充几条典型样本」。三个月后你发现，1 月报的 78% 和 4 月报的 85% 没法比——因为集子变了，题目变简单了。

冻结的意思是三件事同时固定：

  1. 内容固定：文件命名带版本号 golden_v1.csv，改动只能新建 v2，不能原地编辑。
  2. 指纹固定：算一个哈希写进文件名或 README，任何人拿到文件都能验证是不是同一份。
  3. 用途固定：v1 只用于评估，绝不拿去调提示词、挑示例。一旦用它调过，它就不再是考题，而是练习题。
例题 3-5　给数据集算指纹
import hashlib, pandas as pd

df = pd.read_csv('golden_v1.csv').sort_values('sample_id')
payload = df[['sample_id', 'content', 'label']].to_csv(index=False)
digest = hashlib.sha256(payload.encode()).hexdigest()[:12]
print(digest)                      # 例如 8f3c1a90b7e2
# 报告里写：评估集 golden_v1 @ 8f3c1a90b7e2，203 条
只看指纹不看版本号，是因为版本号会被人改，哈希不会。
报告里带上这个 12 位串，任何人都能确认「这次 85% 和上次 78% 是在同一份题上跑的」。

3.5　泄漏：最常见的三种自欺

数据集干净、冻结、算过 kappa，仍然可能得出虚高的结论。原因是信息泄漏：评估时用了模型在「学习」阶段见过的东西。

第一种：示例就来自评估集

从 200 条里挑 3 条当少样本示例，然后用这 200 条评估。这三条必然全对，而且模型会向这三条的风格靠拢，使邻近样本也变容易。正确做法是从评估集之外另抽示例，或者至少把这 3 条从评估集里剔除。

第二种：同一张工单的多个副本分居两侧

客服系统里同一客户同一问题常开多张工单。如果一张在示例里、一张在评估集里，模型等于见过答案。抽样时按 customer_id + 问题指纹 去重，而不是按 ticket_id。

第三种：评估集和调参集是同一份

这是最普遍的一种，也是最难自我察觉的。你反复在 200 条上试了 30 版提示词，选出最好的那版，报出它的 87%。这个 87% 不是这一版的真实水平，是「30 版里的最大值」，它天然高于期望值——你在做选择，而选择会挑中噪声的高点。

解决办法不是「不要调参」，而是分出一份不动的留出集（holdout）：

集合条数用途使用频率
开发集 dev140调提示词、挑示例、看错误随便用，每天跑
留出集 holdout60只在决定上线前跑一次一个版本只跑一次

留出集的数字通常比开发集低 3—8 个百分点。这个落差不是退步，是虚高的部分被拿掉了。第一次见到这个落差的人会很难受，但它才是你上线后真实会遇到的水平。

三个必须现在就建立的习惯
  1. 任何数字旁边都写清「在哪个集子上、多少条」。「准确率 87%」是没有信息量的；「87%，dev 140 条 @8f3c1a」才是一句可以被检验的话。
  2. 不要用留出集做日常调试。跑超过三次，它就变成了开发集，而你不会得到第二次机会。
  3. 数据集和代码一起进版本库，但不进公开仓库。CSV 里有真实对话，即使脱敏过也不该公开。
本章小结
  • 评估集的作用是让改动可比较。没有它，「变好了」是一句无法证伪的话。
  • 抽样必须分层，且长尾每类至少 15 条；只抽「已解决」会系统性高估。
  • 标签要互斥、穷尽、可操作；kappa 低于 0.6 时先修定义，不要标全量。
  • 脱敏做可逆替换而不是删除；截断按分布定规则；冻结靠版本号加哈希。
  • 三种泄漏最常见：示例来自评估集、工单副本分居两侧、开发集当测试集。
  • 分 dev / holdout 两份，holdout 一个版本只跑一次——这是唯一能挡住「选择偏差」的机制。

本章综合习题

综合题一你的评估集 200 条，模型分对了 168 条。产品经理问「准确率 84%，能不能上线」。你需要补充哪三个数字，才能回答这个问题？
答案

① 分错的那 32 条，错在哪些类别。84% 可能是「12 类里 11 类接近 100%，剩一类几乎全错」。如果那一类是退款（涉及赔付），84% 是不可上线的；如果那一类是「其他咨询」，84% 完全可上线。总体准确率对分布不敏感，而这恰恰是它最大的问题。

② 错误的方向性。把退款错判成物流，和把物流错判成退款，后果完全不同：前者导致该赔的没赔（客户投诉），后者导致不该赔的赔了（资金损失）。混淆矩阵的非对角线上，每个格子的代价不相等，所以「准确率」这个指标天生不适合有非对称代价的任务。

③ 这 84% 是在 dev 还是 holdout 上。如果是 dev，且你已经在这 200 条上试过 20 版提示词，那真实水平大概率在 76%–81%。如果 holdout 也是 84%，这个数字才可信。

补一句：还可以问「上线后错误的代价由谁承担」。分类错了，是坐席多改一下，还是自动流转到错误队列、客户等了三小时？同一个准确率，在不同的人机分工下，价值差一个量级。

综合题二你和同事双标 50 条，一致 41 条，kappa 算出 0.69。同事提议「再标 200 条，样本多了 kappa 就会上去」。这个说法对吗？
答案

不对，方向错了。kappa 衡量的是「标注标准的一致性」，它是一个比率型指标，不是估计量。增加样本量会让 kappa 的置信区间变窄——也就是让你更确信它是 0.69，而不是把它推向 0.85。

kappa 低的根因只有两个：标准不清，或者任务本身模糊。前者可以修（把边界规则写清楚），后者不该硬修——如果连两个熟悉业务的人都判不了一致，那就说明这条样本本来就该归到「无法判断」，或者这个任务不适合做自动分类。

正确做法：把那 9 条不一致的样本逐条讨论，找出它们是否属于同一类边界争议。经验上，9 条里通常有 4—6 条源于同一个规则缺口。补上这条规则，重标那 9 条，kappa 会明显上升。如果补完还是 0.7 以下，那要考虑的是「这个分类维度是否成立」，而不是继续加样本。

这道题的考点是一个更普遍的错误：把「样本量不足」当成所有统计问题的万能解释。样本量影响的是估计精度，不影响被测对象本身的性质。

综合题三设计一份标注表（写出列名和每列的作用），要求它既能支持「模型准确率」的计算，又能支持后续「错误归因分析」。
答案

八列，前四列是必需，后四列是为了归因：

列名作用
sample_id稳定主键，与工单号解耦（脱敏后不能再用工单号）
content脱敏后的输入，冻结不改
label人工标注的正确答案，计算准确率的依据
label_note一句话说明「为什么是这个标签」，用于边界争议复盘
difficulty易 / 中 / 难，人工判断。用于分层看表现，避免难题拉低均值后误判整体退化
need_context布尔。判断这条是否需要外部信息（订单状态、库存）才能答对。若为真而系统没有该信息，错误不该算模型的
expected_refusal布尔。这条是否应该拒答。单独统计，因为「该拒答却答了」是幻觉，「该答却拒了」是可用性问题，两者方向相反
annotator标注人。用于算 kappa、以及发现某个人的标注系统性偏移

为什么后四列重要：没有 difficulty，你无法区分「模型退步」和「这版集子恰好难题多」；没有 need_context，你会把「系统缺数据」记成「模型幻觉」，然后去改提示词，改一个月也没用；没有 expected_refusal，幻觉率和拒答率会互相抵消——一个既爱编又爱拒的模型，在单一准确率上可能看起来正常。

label_note 是性价比最高的一列。三个月后回看，你会忘了当时为什么这么标，而这一列是唯一能还原判断过程的东西。
