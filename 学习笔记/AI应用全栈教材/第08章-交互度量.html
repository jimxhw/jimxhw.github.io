第 8 章　交互度量
没有埋点，你所有的界面决策都只是审美

第 7 章说采纳率比准确率更重要。这一章解决「怎么把它算对」。这件事的难点不在埋点技术，而在定义：同一个「采纳率」，在不同的口径下可以差三倍，而选错口径会让你优化错方向——通常是把界面改得更容易点，而不是更有用。

本章学习目标
理解　为什么「曝光」和「触发」必须分开统计
掌握　设计一张能支撑漏斗与归因的事件表
掌握　采纳率的四种定义，以及各自会导致什么错误行为
掌握　A/B 的样本量估算与两个常见陷阱
了解　把前端体验指标（TTFT、输入延迟）纳入同一套度量

8.1　一张事件表，支撑所有问题

埋点最常见的失败不是漏埋，而是埋了一堆无法关联的点：有「点击生成」的次数，有「采纳」的次数，但两者不在同一个会话 id 下，于是没法算转化率。等到要用时才发现，只能重埋，而重埋意味着再等两周的数据。

避免这个问题的办法是先想清要回答哪些问题，再倒推字段。对 AI 辅助类功能，问题只有五个：

  1. 有多少人看到了这个功能？（曝光）
  2. 看到了之后有多少人用？（触发率）
  3. 用了之后有多少人接受？（采纳率）
  4. 接受了之后是否更快、更好？（业务效果）
  5. 不用的人卡在哪？（流失点）

五个问题对应五个事件，一条 trace_id 串起来：

例题 8-1　事件表的核心字段
show      { trace_id, agent_id, ticket_id, panel, ts }
trigger   { trace_id, trigger_type: auto|manual|shortcut, input_len, ts }
render    { trace_id, ttft_ms, first_token_ms, total_ms,
            out_len, seg_count, conf_tier: ok|check|reject }
action    { trace_id, seg_idx, kind: insert|edit|ignore|regen|close,
            edit_ops: [], ts }
send      { trace_id, final_len, edited_ratio, ts }        # 真正发出去了

# 关联键：trace_id（一次生成） + ticket_id（业务上下文）
# 归因键：agent_id（人） + prompt_ver（版本） + model（模型）
五个事件里，send 最容易被漏掉，而它是最重要的。
没有 send，「插入」就等于「采纳」——但插入之后坐席可能又全删了重写。只有 send 能证明内容真的被发出去了。

trigger_type 这个字段值得单说。自动触发（打开工单就生成）和手动触发（点按钮）的用户意图完全不同：自动触发的采纳率天然更低（因为大部分工单不需要），但它覆盖的场景更广。把两者混在一起算，会得到一个既不能反映意愿也不能反映覆盖率的数字。

8.2　采纳率：四种定义，四种后果

定义分子 / 分母数值会导致的错误行为
A 点击率插入次数 / 曝光次数最高把面板做得更显眼、按钮更大，而不是更有用
B 接受率插入次数 / 生成次数中高默认生成更短更笼统的内容，因为容易全盘接受
C 净采纳率发送时含 AI 内容的次数 / 生成次数中相对健康，但仍会奖励「短而无害」
D 省力率1 − (发送文本与建议的编辑距离 / 发送文本长度)低这个指标不奖励「不采纳」，需要和其他指标一起看

四种定义里，C 是最适合做主线指标的，因为它以「真的发出去了」为准，能过滤掉「插入后又全删」这种虚假采纳。D 更适合做质量指标——它衡量「AI 帮我省了多少字」，即使采纳率不高，只要每次能省 40% 的输入量，价值就存在。

A 和 B 的共同问题是分子太容易作弊。把「插入」按钮做得更大、把建议默认展开、把「忽略」藏起来，A 会明显上升，而业务效果不变。这是古德哈特定律的典型场景：一旦某个指标成为目标，它就不再是好的指标。

例题 8-2　算一次真实的口径差异
某月数据：
  曝光（打开工单且面板可见）　　18,400 次
  生成（实际产生建议）　　　　　 4,200 次
  插入（点了某个片段）　　　　　 3,100 次
  发送（最终发出的回复含 AI 内容）2,050 次

A 点击率 = 3100 / 18400 = 16.8%
B 接受率 = 3100 / 4200  = 73.8%
C 净采纳率 = 2050 / 4200 = 48.8%

报告里如果只写 B，会得到「采纳率 74%，效果很好」的结论；
而 C 说明有一半的生成没有被用上，且其中 1,050 次是「插入了又删掉」。
这 1,050 次「插入后删掉」是最有价值的一批数据。
它说明用户先信了，然后发现不对——比从一开始就不信更伤信任。
应当单独看这批样本的 conf_tier 分布：如果集中在 ok 档，说明分档判错了，这是可以立刻修的。

8.3　从采纳率到人效

采纳率是过程指标，业务方关心的是结果指标。三个可以直接算的：

指标定义AI 影响的方向
AHT（平均处理时长）工单从接起到关闭的时长下降，但注意包含「等待客户回复」的时间，应只算坐席活跃时长
FCR（首次解决率）同一问题 7 天内未再开的比例上升（答得准的间接效果），也可能下降（答得快但答错）
转人工率AI 会话转给人工的比例取决于场景：辅助坐席时无意义，自助服务时是关键

AHT 有一个常见误算：把「客户不回消息」的时间也算进去。正确做法是只累计坐席有操作的时间段（打开工单 → 最后编辑 → 关闭）。否则一个客户隔夜回复的工单会把 AHT 拉到 12 小时，而 AI 的影响被彻底稀释。

更实际的做法是算「单均坐席操作次数」——查了几次订单、切了几次系统、复制粘贴了几次。这个指标对 AI 的改进极其敏感，而且不受客户行为干扰。它也是最能说明价值的一句话：「AI 上线后，每单平均少切 2.3 次系统」。

8.4　A/B：两个必须避开的陷阱

灰度对比是唯一能证明因果的方法，但 AI 功能的 A/B 有两个特殊问题。

陷阱一：学习效应会污染对照组

坐席是同一批人。今天用 A 版，明天用 B 版，他会带着前一天的印象。更麻烦的是互相学习：坐席之间会交流「那个 AI 挺好用的」，于是对照组的人也开始更认真地看建议。这会让两组的差异被压缩，你得到「没有显著差异」的错误结论。

可行的办法：按人分组而不是按时间分组（同一批人固定用同一版，持续两周以上），并接受「组间人员能力差异」这个噪声——用前两周的基线数据做协变量校正。

陷阱二：辛普森悖论

这是最容易得出错误结论的地方。举一个真实形态的例子：

例题 8-3　分组合并后方向反转
旧版：简单工单 800 单，采纳 640（80%）
      复杂工单 200 单，采纳  60（30%）
      合计 1000 单，采纳 700（70%）

新版：简单工单 200 单，采纳 170（85%）
      复杂工单 800 单，采纳 280（35%）
      合计 1000 单，采纳 450（45%）

结论看上去：新版大幅退步（70% → 45%）
实际情况：两类工单都变好了（80→85，30→35）
原因是新版上线后，很多原本不触发 AI 的复杂工单开始触发了，
导致样本结构从「简单 8 : 复杂 2」变成「简单 2 : 复杂 8」。
整体数字的下降，来自构成变化，不是效果变化。

避免方法很固定：永远看分层数据，不看合并数据。至少按「工单复杂度」和「渠道」两层拆开，确认每一层方向一致，再谈整体。

样本量：算一次就不想再猜了

要检测两个比例的差异（比如 48% vs 52%），每组所需样本量近似为：

例题 8-4　样本量估算
n ≈ 16 × p(1−p) / Δ²

p = 0.50（保守取最坏情况）　Δ = 0.04（想检测 4 个点的差异）

n ≈ 16 × 0.25 / 0.0016 = 2,500 / 组

若日均有 700 次生成，两组各需 2,500 → 约 7 天
若只想检测 10 个点的差异：n ≈ 400 / 组 → 约 1.2 天
这个式子解释了一件事：想检测的差异越小，需要的样本量急剧增加（Δ 减半，n 变成 4 倍）。
所以「我们跑了三天，提升了 2 个点」这种结论，通常只是噪声。

8.5　把体验指标放进同一张表

界面改动往往不影响正确率，只影响体验，所以需要一组独立的指标。三个够用：

  • TTFT（首字时间）P50 / P95：第 5 章说过，它比总耗时更影响体感。上线流式之后这个数应该显著下降，如果没有，说明流式没生效（多半是代理缓冲）。
  • 输入延迟：坐席按键到字符出现的延迟。它在生成过程中最容易恶化，因为主线程被渲染占用。可以用 event.timestamp 到下一次绘制的时间近似。
  • 中断率：生成过程中被停止的比例。它高说明内容方向不对或太长，是最直接的「用户体验差」信号。

这三个指标和业务指标放在同一张周报里，会形成一种很有用的对照：如果采纳率下降而 TTFT 上升，那不是模型问题，是性能问题。没有这张表，团队会先去改提示词。

四个会让数据失去意义的细节
  1. 曝光定义含糊。「面板渲染了」和「面板在视口内且用户停留超过 1 秒」是两个完全不同的分母。后者才叫曝光。
  2. 没有排除内部账号。测试账号、演示账号的用法和真实坐席完全不同，它们会系统性拉高或拉低所有指标。
  3. 不记录版本。没有 prompt_ver 和 model 字段，指标变化时无法归因，只能猜。
  4. 把「插入」当「采纳」。第 8.2 节那 1,050 次「插入后删掉」会让指标虚高近 20 个点。
本章小结
  • 先定要回答的五个问题，再倒推字段；trace_id 串起曝光到发送。
  • 「发送」事件最容易被漏，而它是唯一能证明内容真被用了的证据。
  • 采纳率有四种口径：点击率、接受率、净采纳率、省力率。主线用净采纳率，质量用省力率。
  • 「插入后删掉」是最伤信任的一批数据，要单独看它的置信度分档分布。
  • 人效看 AHT、FCR，但更灵敏的是「单均坐席操作次数」。
  • A/B 两个陷阱：学习效应（按人分组）、辛普森悖论（永远看分层）。
  • 样本量 n ≈ 16p(1−p)/Δ²，想检测 4 个点需要 2,500/组。
  • TTFT、输入延迟、中断率要和业务指标同表，才能区分「模型问题」和「性能问题」。

本章综合习题

综合题一数据：曝光 12,000，生成 3,000，插入 2,400，发送含 AI 内容 1,500，插入后全删 600。算出三个口径，并指出最该优先修的问题。
答案

三个口径：

点击率 = 2400 / 12000 = 20.0%
接受率 = 2400 / 3000 = 80.0%
净采纳率 = 1500 / 3000 = 50.0%

最该优先修的问题：600 次「插入后全删」。它占插入量的 25%，而且它比「不插入」严重得多——用户先相信了，读了之后发现不能用，然后全部删掉重写。这个过程浪费的时间比一开始就自己写更长，而且会训练出「先插入再检查」的坏习惯，最终变成「干脆不用」。

怎么查：

① 看这 600 次的 conf_tier 分布。如果 70% 是 ok（可直接用），说明分档判错了——这些本该标成「需核对」，系统给了错误的安全信号。

② 看它们的 out_len 分布。如果集中在 150 字以上，是长度问题：用户以为能用，插入后发现太长，删到一半干脆全删。

③ 看 edit_ops 的高频项。如果反复出现同一个替换（比如「退货」→「换新」），那是知识层面的概念混淆，不是界面问题。

反过来说，80% 的接受率本身并不值得高兴。它只说明「点了插入的人大部分没立刻反悔」，而分母（3,000 次生成）相对 12,000 次曝光只有 25%——真正的瓶颈可能在「为什么四分之三的曝光没有产生生成」，也就是触发环节。这两个问题要分开修。

综合题二新版上线后整体采纳率从 70% 掉到 45%，但产品经理说「新版应该更好」。你会怎么查？给出不超过三步的流程。
答案

第一步：看样本结构有没有变。统计新旧两版的「工单复杂度分布」和「触发类型分布」（自动 / 手动）。如果新版的自动触发占比大幅上升，或者复杂工单占比上升，那就是构成变化，不是效果变化。这一步能在五分钟内确认是不是辛普森悖论。

第二步：分层看。按「复杂度 × 触发类型」切成 4 格，每格比较新旧两版的采纳率。如果每一格都持平或变好，而合计变差，就确认了：整体数字的下降完全来自结构变化，新版确实更好。

第三步：如果某几格真的变差，看那一格的 edit_ops 和 conf_tier。分档判错、长度变化、还是内容方向偏了，这三者的修法完全不同。

结论怎么写：不要写「采纳率下降 25 个点但其实是好事」——这句话没人信。要写：「新版在两类工单上分别提升 5 和 5 个点；整体数字下降是因为自动触发占比从 30% 升到 78%，而自动触发的基线采纳率本来就只有 20%。剔除结构影响后，新版优于旧版。」

这个案例的一般教训：当产品的覆盖策略变化时，任何以「每次生成」为分母的指标都会失真。分子分母的定义必须随产品形态一起更新，否则指标会从「测量工具」变成「误导工具」。

综合题三你要在一个 60 人坐席的团队里验证「片段化采纳」是否比「整段采纳」更好。设计实验，说明分组方式、指标、时长和预期陷阱。
答案

分组：按人随机分两组，各 30 人，固定两周不改组。不按时间分组（会引入学习效应），不按工单分组（同一个人两种界面会混乱）。分组前先记录两周基线（采纳率、AHT、单均操作次数），用于校正组间能力差异。

指标（三层，缺一不可）：

主指标：净采纳率（发送含 AI 内容 / 生成次数）。这是实验要验证的东西。

副指标：省力率（1 − 编辑距离/最终长度）。片段化如果只是让人「更容易点」，主指标会升而省力率不变——那就说明它带来的是虚假繁荣。

护栏指标：AHT、FCR、以及「插入后全删」的比例。片段化有可能降低采纳门槛，从而引入更多低质量内容，表现为 FCR 下降。

时长与样本量：若日均生成 700 次、两组各 350 次/天，检测 4 个点差异需 2,500/组，约 7 天；考虑到学习效应需要稳定期，取 14 天。

三个预期陷阱：

① 指标被定义污染。片段化后「插入」的次数天然变多（一段变三片），如果指标是「插入次数」，实验必然显示成功。所以主指标必须用「发送含 AI 内容」，它不受片段数影响。

② 操作负担转移。片段化让每次采纳需要点三次而不是一次，可能让重度用户反感。所以要单独看「重度用户（日均触发 > 20 次）」子集，这一组的方向可能相反。

③ 组间交流。60 人在同一个办公区，一周后控制组会看到实验组的界面。对策是在实验期不做全员培训、不发公告，并在分析时记录「控制组是否主动询问过新界面」——如果超过 20%，结论要打折。
