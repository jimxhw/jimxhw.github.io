第 11 章　缓存与成本
先算清钱花在哪，再谈优化

AI 服务的成本结构和传统后端完全不同：它按 token 计费，而 token 随「上下文长度」线性增长、随「对话轮数」平方增长。这意味着同一条业务逻辑，写法不同成本能差五倍。这一章讲三件事：钱花在哪、三种缓存各解决什么问题、以及一个必须避开的降本陷阱。

本章学习目标
理解　成本的四层结构，以及为什么要按这个顺序优化
掌握　前缀缓存、结果缓存、语义缓存各自适用与不适用的场景
掌握　缓存键的设计规则：漏一个字段就会串数据
掌握　分级路由：按难度分配模型，而不是整体降级
了解　成本归因与预算控制的做法

11.1　先算清钱花在哪

降本最常见的错误是「先换便宜模型」。在多数系统里，这一招的收益排在第四位，而且有质量代价。正确的顺序是按「影响倍数 × 实施成本」排：

图 11-1　成本优化的四层：先消除浪费，再动结构，最后才动模型

第一层「消除无用调用」的收益经常被低估。有两个高频来源：

  • 自动触发但无人看。打开工单就生成摘要，但数据显示只有 40% 的工单会看。改成「点击才生成」能直接砍掉 60% 的调用——代价是首字延迟，但第 5 章说过，TTFT 1.8 秒是可以接受的。
  • 重复请求。用户连点、页面刷新、组件重复挂载。这些在日志里表现为同一 ticket_id 在 2 秒内多次相同请求。加一层请求去重（相同 key 的并发请求合并成一个）能省 10%–20%。

11.2　三种缓存，别混着用

类型命中条件省钱方式风险
前缀缓存（provider 侧）请求开头字节完全一致命中的部分按更低单价计费，延迟也更低几乎无风险；但要求静态内容在最前
结果缓存（自己实现）全部输入完全一致命中时完全不调模型输入里含时间戳就会失效；数据更新后可能返回旧结论
语义缓存输入向量相似度 > 阈值命中时完全不调模型危险：语义相近不等于答案相同

前缀缓存：唯一「没有理由不做」的一项

规则只有一条：静态内容放最前，动态内容放最后。第 2 章已经讲过它的成本影响，这里补一个实现细节——要让前缀真的稳定，需要做到三点：

  1. 系统提示词里不能有时间戳、用户名、会话 id。任何每次变化的东西都会让前缀失效。
  2. 不要把「当前时间」拼在第一位。如果业务确实需要当前时间，放到用户消息末尾。
  3. 系统提示词不要动态拼装。如果按坐席等级拼不同的规则，那就把「等级」做成参数放在末尾，而不是改变前缀结构。

检查方法很直接：在日志里记下每次请求的 prompt 前 512 个字符的哈希。如果同一个功能的前缀哈希在不断变化，说明缓存一直在失效，而你很可能以为它在工作。

结果缓存：钱省得最多，也最容易出错

结果缓存适合「同一输入反复出现」的场景。客服系统里有两类特别适合：

  • 高频标准问题：「怎么开票」「发票丢了怎么办」这类，答案固定，一天被问几百次。
  • 幂等查询：「这个订单的物流状态」，5 分钟内重复问同一个订单，答案一样。

关键是缓存键要包含所有影响结果的输入。下面这个例子是真实事故的形状：

例题 11-1　缓存键漏字段
# ✗ 只用了问题文本
key = md5(question)
# 「我的订单到哪了」→ 所有客户的这个问题的答案被互相覆盖

# ✓ 包含所有影响输出的因子
key = md5('|'.join([
    question.strip().lower(),
    order_id or '-',          # 业务上下文
    policy_ver,                    # 政策版本（改了政策必须失效）
    prompt_ver,                    # 提示词版本
    model,                         # 模型版本
    tenant_id,                     # 租户
]))
六个字段缺一不可。最容易被漏的是 policy_ver 和 tenant_id。
前者导致「政策改了，用户还在收到旧答案」；后者是跨租户数据泄漏，属于事故级别。

还有一个常被忽略的条件：缓存应该有 TTL，而且 TTL 要和数据的更新频率匹配。物流状态 5 分钟、政策条款 1 小时、通用话术 24 小时。全都设 24 小时是偷懒，而它会导致「明明已经改好了，怎么还这样」这类无法复现的投诉。

语义缓存：看起来很美，通常是陷阱

语义缓存的逻辑是：如果新问题和某个缓存问题「意思相近」，就直接返回那个答案。问题在于——意思相近的问题，答案经常相反。

例题 11-2　相似度 0.96 的两个问题
Q1：耳机买了 5 天，能退吗？
Q2：耳机买了 15 天，能退吗？

embedding 余弦相似度：0.96

Q1 答案：可以，7 天无理由期内，运费买家承担。
Q2 答案：不能无理由退；若为质量问题，15 天内可换。
只差一个数字，相似度极高，答案完全不同。
语义缓存对「实体相同、条件不同」的问题几乎必然出错，而客服场景里这类问题占大多数。

如果非要用，必须加两个限制：① 只对「不含数字、日期、金额、订单号」的问题启用（用正则先筛）；② 阈值要高且要抽检（每周抽 50 条命中样本人工看，错误率超过 2% 就关掉）。

坦白说，在客服这种「条件依赖强」的场景里，语义缓存的收益通常小于风险。更稳的替代是：先用规则把高频标准问题识别出来（关键词 + 模板），命中就走固定答案，不命中就走模型。这不是缓存，效果更好，也不会错。

11.3　分级路由：不是换模型，是分配

「整体换便宜模型」是一个典型的错误优化，因为它无差别降级：把 90% 本来不需要大模型能力的请求降了（好），也把 10% 真正难的请求降了（坏），而那 10% 恰好是最影响信任的部分。

正确做法是先分级，再分配：

例题 11-3　两段式路由
def route(req):
    # 第一段：规则分流（免费、可解释）
    if is_template_hit(req):        # 标准问题，走固定答案
        return 'template'
    if req.knowledge_hits >= 2 and not req.has_conflict:
        return 'small'             # 知识明确，小模型够用
    if req.amount or req.needs_tool:
        return 'large'             # 涉及钱或要办事，必须大模型
    return 'medium'

# 第二段：小模型先答，置信度低才升级（级联）
ans = call('small', req)
if ans.conf_tier != 'ok':
    ans = call('large', req)        # 只对不确定的升级
两段的区别：第一段按「问题属性」分配，第二段按「模型自评」升级。
第二段的成本优势很大：如果 60% 的请求小模型能给出 ok，那 60% 的钱就省下来了，
而剩下 40% 用的仍是大模型——质量损失只发生在小模型自信但答错的那些，需要靠评估量化。

级联有一个必须测的东西：小模型「自信地答错」的比例。这个比例决定了级联的安全边界。测法很简单：拿 200 条评估集，跑小模型，看 conf_tier='ok' 的那些样本里有多少是错的。如果超过 5%，说明小模型的自评不可信，级联不能用。

11.4　成本归因：按功能、按人、按租户

没有归因就没法管。三条维度够用：

维度能回答的问题实现
按功能钱花在摘要还是分类上？请求带 feature 标签
按人有没有人在异常高频使用？带 agent_id
按租户哪个客户在亏钱？带 tenant_id

按人这一维经常发现意外：某个坐席一天调用 800 次，是平均值的 20 倍。原因可能是他的工作流不同（只处理复杂工单），也可能是他在刷按钮。这两种情况的处理完全不同，而只看总量你永远发现不了。

预算控制建议做成两道闸：软限（达到 80% 时告警给负责人，不阻断）和硬限（达到 100% 时降级为模板回答或直接返回「本功能今日额度已用完」）。只有软限会在某天突然爆掉；只有硬限会让业务在月中突然不可用。两道闸同时有，才有可预期性。

四个成本陷阱
  1. 把时间戳放在系统提示词第一行。前缀缓存全部失效，而你很可能以为它在工作。用前缀哈希验证。
  2. 缓存键漏了 tenant_id。这不是省钱问题，是数据泄漏事故。
  3. 用语义缓存处理带数字的问题。相似度 0.96 的两个问题，答案可能完全相反。
  4. 整体换小模型当降本。省下的钱通常会在两个月内以「质量投诉」的形式还回去。
本章小结
  • 四层结构：消除无用调用 → 缩短输入 → 缓存 → 分级路由。前三层不损质量，第四层损。
  • 前缀缓存没有理由不做：静态在前、动态在后，且要用前缀哈希验证它真的在命中。
  • 结果缓存的键必须包含：输入、业务上下文、政策版本、提示词版本、模型、租户。
  • 语义缓存对「条件不同」的问题必然出错，客服场景通常不该用。
  • 分级路由 ≠ 换模型。两段式：规则分流 + 小模型自评升级，并测「自信地答错」的比例。
  • 归因三维度：功能、人、租户。按人能看到 20 倍的异常用量。
  • 预算两道闸：80% 告警、100% 降级。只有一道都会出问题。

本章综合习题

综合题一你接手一个 AI 功能，月成本 3,000 元。列出你的排查顺序（不超过六步），说明每一步能发现什么问题。
答案

六步，按「不花钱就能查」到「要改代码」排：

① 看输入/输出 token 比例。如果输入是输出的 20 倍以上，说明上下文太长。「缩短输入」的空间很大。正常比例在 5–10 倍之间。

② 看前缀哈希的稳定性。取 100 条请求，算每条 prompt 前 512 字符的哈希，统计有多少个不同值。如果接近 100，说明前缀缓存完全没生效——这一项通常能省 20%–40%，而且零质量损失。

③ 看同一 ticket_id 的重复请求率。2 秒内相同请求出现多次，说明有连点或重复挂载。加请求合并能省 10%–20%。

④ 看自动触发 vs 手动触发，以及各自的「查看率」。如果自动触发占 80% 但只有 30% 被查看，改成手动或按条件触发，直接砍掉一半调用。

⑤ 看按功能的成本分布。经常发现某个「实验性功能」占了 40% 成本而只有 3% 使用量——那是没人维护的遗留代码，直接下掉。

⑥ 最后才看模型分配。统计各模型的调用占比与平均输出长度，判断哪些请求其实不需要大模型。

为什么不先换模型：①②③ 加起来通常能省 50% 以上且不损失质量，而换模型能省 40% 但会损失质量。先做零损失的部分，剩下的问题可能自己就消失了。很多团队反过来做，结果是「省了钱、质量差了、然后加回来、回到原点」。

综合题二设计一个「高频标准问题」的缓存方案，要求既能省钱又不产生错误答案。写出识别方式、缓存策略和失效条件。
答案

识别方式（不用语义相似度）：

从历史数据里统计出现频次最高的 100 个「问题模板」，为每个模板定义：一组必含关键词、一组排除关键词、以及一个标准答案（人工审核过的）。

模板：开票咨询
  必含：发票 / 开票 / 专票 / 普票
  排除：退 / 换 / 投诉 / 投诉
  答案：标准话术 v3（含「电子发票 1 个工作日发送至邮箱」等）
  答案版本：invoice_faq_v3

匹配时用「全含必含词 且 不含排除词」，命中即返回固定答案。用规则而不是向量，是因为规则可解释、可审计、可被业务方修改。

缓存策略：不要把它做成「缓存」，做成「模板库」。区别在于：缓存是命中率优化的产物，模板库是经过人工审核的标准答案集合。前者的错误无法追溯，后者的每一条都有负责人。

失效条件（三个，缺一不可）：

① 政策版本变化。模板里引用条款的，绑 policy_ver；政策更新时自动把相关模板标记为「待复核」，复核前不出。

② 答案被业务方修订。每次修订生成新版本，旧版本保留用于回溯「当时为什么这么答」。

③ 命中率异常。如果某个模板的命中量突然翻了 3 倍，说明排除词不够（可能混进了新场景），自动降级为走模型并告警。

为什么不用语义缓存：第 11.2 节的例子已经说明，语义相似度无法区分「买了 5 天」和「买了 15 天」。而模板方案里，「15 天」会因为不含完整的模板特征、或者因为答案需要条件判断，而不会命中模板——它的安全边界来自「保守匹配」，而不是来自「相似度阈值」。

综合题三老板要求「下个月成本降一半，质量不能降」。你会怎么回应？给出一个具体的方案框架。
答案

先给一个诚实的框架，而不是承诺。

「降一半在不损质量的前提下，可行性取决于三件事，我需要三天做一次测量才能回答。现在能说的是：有 50%–60% 的空间来自不损质量的部分，剩下的要靠分级路由，而分级路由需要先测一个数字。」

方案框架（四步）：

① 零损失部分（预计 −30%~45%）：修前缀缓存（静态在前）、合并重复请求、把自动触发改成条件触发。三项都不改变任何一次输出的内容，只是减少调用次数。

② 分级路由（预计 −20%~35%）：先测「小模型自信地答错率」。低于 5% 才做级联；高于 5% 就只能按规则分流（模板 + 简单问答走小模型），收益会小一些。

③ 质量护栏：用 200 条评估集做 A/B，主指标是准确率，护栏是「驳回率」（人工复核判错的样本占比）。护栏恶化超过 2 个点就回滚。

④ 无法避免的代价要提前说：如果 ①② 只能到 −40%，剩下的 10% 必须来自某处——要么接受更长的 TTFT（降低并发、合并批处理），要么接受某些场景质量下降，要么减少功能范围。这三者选一个，由业务方决定，不由技术方替他决定。

为什么这样回应：直接答应「可以」会在两周后变成「质量怎么差了」；直接说「不可能」会显得不专业。把需求拆成「确定能做到的」和「需要决策的」，是技术负责人最需要的能力。而 ①② 加起来通常已经接近目标，所以这个回应在多数情况下也能兑现。
