第 6 章　生成中的状态管理
用三个布尔量拼出来的东西，最后一定会出现不可能的状态

第 5 章解决了「怎么把字显示出来」，这一章解决「这些字处在什么阶段」。听上去像个前端细节，实际上它是 AI 界面最容易出错、也最容易被面试官追问的一层：一次生成要经历排队、连接、流式、等待工具、等待人确认、结束、失败，而失败还能分成十几种。用 loading / error / data 三个变量描述它，必然会出现「显示加载中，但内容已经出来了」这种无法解释的界面。

本章学习目标
理解　为什么 AI 交互的状态必须用有限状态机描述
掌握　画出一次生成的完整状态转移，并处理非法转移
掌握　解决竞态：迟到的旧响应覆盖新请求
掌握　乐观更新与回滚在流式场景下的正确写法
了解　超长会话的渲染性能优化手法

6.1　三个布尔量的失败

场景

工作台的 AI 面板最初用三个变量管理状态：loading、error、text。上线两周后，测试提了四个 bug，看上去互不相关：

① 生成到一半时切换工单，新工单的面板里出现了上一个工单的摘要后半段。

② 点了两次「生成」，第一条的结尾和第二条的开头粘在一起。

③ 显示「生成中」，但内容已经完整出现了，转圈还在转。

④ 请求失败后点重试，转圈转了 30 秒才报错，而这 30 秒里后端其实已经返回了失败。

修的时候发现，这四个 bug 的根因是同一个：三个变量可以组合出 8 种状态，其中 5 种是不该存在的，比如 loading=true, text='完整内容'，或者 error='超时', text='正在增长中'。没有人写代码去制造这些状态，是并发和异步回调自然产生的。

这不是前端的特殊问题，而是一个通用规律：用 n 个独立布尔量描述一个本质上互斥的过程，会得到 2ⁿ 种组合，其中大部分语义非法。而 UI 只能渲染，它不会拒绝非法状态，于是它会如实渲染出一个荒谬的界面。

解法是把状态收敛成一个枚举，并明确画出转移。枚举的取值不需要多，够用就行，本书的场景是七个：

状态含义界面上应显示
idle还没开始空态 + 生成按钮
connecting已发出，未收到第一帧按钮 loading，内容区一个浅色光标
streaming正在收字内容增长 + 「停止」按钮
tool_wait模型调了工具，等结果「正在查询订单…」这类具名进度
confirm等人工确认一个写操作确认卡片（做什么、影响谁、能否撤回）
done正常结束完整内容 + 采纳/编辑/重生成
error失败，且带失败类型分类错误提示 + 可重试的动作

注意 error 只有一个状态，但它必须携带一个失败类型字段。「失败」这个词对用户没有信息量；「网络断了，已生成的内容保留」「模型拒绝了这个请求」「配额用完了，请联系管理员」才是三种完全不同的处境，需要三种不同的按钮。

6.2　画出转移，然后拒绝非法转移

图 6-1　七个状态与允许的转移：实线自动、虚线需人工、红色可恢复

这张图里有两处设计决定值得单独说。

第一，confirm 不允许超时。其他状态都可以因为超时而中断，唯独等待人工确认的写操作不行。如果 60 秒没人点就自动取消，会出现「坐席去接了个电话，回来发现改地址的请求已经被悄悄取消」——而更糟的是相反的版本：超时自动执行。这两种都不该发生。正确做法是它一直等着，同时在别处（比如工单列表）提示「有 1 个待确认操作」。

第二，done 可以回退到 streaming。这在纯文本场景里没意义，但一旦有了工具调用就有意义了：模型可能已经输出「好的，我帮你查一下」，然后才发起工具调用；工具返回后它继续输出。如果不允许这条回退，就会出现「已完成」之后又冒出文字的情况，用户会以为界面错乱。所以状态机里 done → streaming 是合法的，只是要保证 done 的判定条件是「上游明确发来了结束标记」，而不是「一段时间没收到新字」。

写成一个 reducer，而不是散落的 if

例题 6-1　状态机的最小实现
const NEXT = {
  idle:       ['connecting'],
  connecting: ['streaming', 'error', 'idle'],
  streaming:  ['tool_wait', 'confirm', 'done', 'error', 'idle'],
  tool_wait:  ['streaming', 'error'],
  confirm:    ['streaming', 'done'],      // 不接受超时
  done:       ['streaming', 'idle'],        // 工具后继续输出
  error:      ['connecting', 'idle'],
};

function reducer(st, ev) {
  const to = ev.type === 'ERR' ? 'error' : ev.to;
  if (!NEXT[st.phase].includes(to)) {
    console.warn('非法转移', st.phase, '→', to, ev);   // 不静默
    return st;
  }
  return { ...st, phase: to, ...(ev.patch || {}) };
}
关键不是这张表，是 非法转移要被记录而不是被忽略。
线上出现的怪状态，几乎都能在 console 里找到一条「非法转移」记录，而这比事后猜要快得多。

注意 error 只能回到 connecting 或 idle，不能直接回 streaming。因为重试是重新发起一次请求，不是「继续上一次」——第 5 章说过，模型无状态，断点无法续传。把这条限制写进转移表，可以避免一类很隐蔽的 bug：重试后把旧内容当新内容继续追加。

6.3　竞态：迟到的旧响应用新请求的位置

这是 AI 界面里最高频的 bug，没有之一。它的形态是这样的：

  1. 用户点了「生成摘要」，请求 A 发出。
  2. 等了 3 秒，用户以为没点上，又点了一次，请求 B 发出。
  3. 请求 B 先回（因为服务端排队恰好更快），界面显示 B 的内容。
  4. 2 秒后 A 的第一帧到达，界面开始往 B 的内容后面追加 A 的字。

结果是两段内容混在一起，而且没有人能解释它为什么混。

标准解法是给每次请求一个序号（或 AbortController），并在写状态前检查「我还是不是最新的那个」：

例题 6-2　请求代际检查
const gen = useRef(0);

async function run(input) {
  const my = ++gen.current;              // 本次请求的代号
  abortRef.current?.abort();              // 顺手取消上一次
  const ac = new AbortController();
  abortRef.current = ac;

  for await (const delta of stream(input, ac.signal)) {
    if (my !== gen.current) return;         // 已被更新的请求取代，丢弃
    setText(t => t + delta);
  }
  if (my === gen.current) setPhase('done');
}
两道防线：abort 旧的（省资源）+ 代际检查（防竞态）。
只做 abort 是不够的——abort 是异步生效的，在它生效前仍可能有帧到达。

还有一个同类的场景：切换工单。第 6.1 节那个 bug ① 就是它。用户在看工单 A 的摘要，中途点了工单 B。如果生成逻辑绑定在「面板」而不是「工单」上，A 的剩余内容会写进 B 的面板。

处理方式和上面一致，但检查条件要换成「当前工单 id 是否仍是发起时的那个」。这类 bug 的共同点是异步回调里持有了过期的上下文，而修法永远是在回调里重新确认上下文，而不是相信发起时的假设。

6.4　乐观更新在流式下的特殊性

普通表单的乐观更新很简单：先更新界面，失败就回滚。流式场景多了一层麻烦：内容是持续增长的，回滚点什么？

举一个具体例子：坐席点了「用这条建议回复客户」。界面上这条建议立刻被标记为「已采纳」（乐观），同时发请求给后端记录采纳、并把内容填入回复框。如果请求失败，状态要退回「未采纳」。

问题出在失败的时候：这期间 AI 可能已经生成了下一段内容，回复框里用户可能已经开始编辑。此时回滚不能简单地「撤销」，否则会把用户的手动编辑一起抹掉。

失败时机错误做法正确做法
内容未被编辑弹窗报错，让用户重试静默回滚标记 + 角标提示「未记录，点此重试」
用户已开始编辑回滚内容只回滚「采纳标记」，内容保留（用户已经改了，内容归属已变）
生成仍在进行整体重置面板只改这一条的标记，不动生成流

由此得出一条原则：乐观更新的回滚范围，应当等于「这次操作实际改变了什么」，而不是「这个组件应该是什么样」。后者会导致大面积重置，用户会觉得自己做的事被系统抹掉了。

另一个相关的问题是乐观更新的可见性。如果一切顺利，用户不需要知道发生了什么；但一旦失败，必须有一个不打断操作的提示。所以好的做法是「乐观更新 + 弱提示 + 可重试入口」，而不是「乐观更新 + 失败弹窗」。弹窗会打断，而不提示会让用户以为记录成功了。

6.5　长会话的渲染代价

客服的会话动辄上百轮，而 AI 面板往往嵌在同一个页面里。当对话记录超过 200 条消息时，几个性能问题会同时出现：首屏卡、滚动掉帧、输入框延迟。

有三个手法，按投入产出排序：

一、把「增长中的那一条」和「已结束的」分开

已结束的消息内容不变，可以整块 memo 化，永不重算；只有正在生成的那一条需要每帧更新。很多实现把整个消息列表放在同一个 state 里，每来一个 delta 就重建整个数组，于是 200 条消息全部重新 diff。这一条改动通常能消掉 80% 的卡顿。

二、虚拟滚动，但只对长列表

超过 100 条时启用虚拟滚动。麻烦在于动态高度：AI 消息的高度在生成过程中持续变化，虚拟滚动需要测量。成熟的库（如 TanStack Virtual）支持动态测量，但要注意一个细节：正在生成的那一条不要参与虚拟化，让它渲染在滚动容器末尾之外，否则每一帧的高度变化都会触发测量和重排。

三、输入框优先级最高

坐席在生成过程中仍要打字。如果渲染阻塞了主线程，输入会明显延迟——这是最影响体感的问题，因为它发生在「用户在主动操作」的时候。

两个手段：把渲染更新放进 startTransition（React）或用 requestIdleCallback 调度；以及给输入框用非受控组件（defaultValue + ref），让它不参与 React 的渲染循环。后者不够优雅，但在长列表场景下效果显著。

四个会导致「界面看起来不专业」的细节
  1. 生成中允许发送新请求，但不做代际检查。内容会混。这是最伤信任的一类 bug，因为它让用户无法信任任何一段输出。
  2. 「生成中」用整屏遮罩。坐席无法同时看工单、打字、查历史。AI 面板必须是并行的，不能是模态的。
  3. 错误只显示「请求失败」。用户不知道是网络、配额、还是内容被拒。三种情况的下一步动作完全不同。
  4. 切换工单时不清理状态。上一单的内容会残留，而残留的内容会被误当成当前工单的信息使用，这在业务上是有风险的。
本章小结
  • n 个布尔量会组合出 2ⁿ 种状态，其中大多语义非法；用枚举 + 转移表替代。
  • 七个状态够用：idle / connecting / streaming / tool_wait / confirm / done / error。error 必须带类型。
  • confirm 不允许超时；done 允许回退到 streaming（工具调用后继续输出）。
  • 非法转移要记录，不要静默忽略——它是线上怪状态最快的定位线索。
  • 竞态要用「abort 旧的 + 代际检查」双保险；切换上下文时要在回调里重新确认，而不是相信发起时的假设。
  • 乐观更新的回滚范围 = 这次操作实际改变了什么，不是整个组件重置。
  • 长会话优化顺序：分离生成中的那一条 → 虚拟滚动 → 输入框去阻塞。

本章综合习题

综合题一用户投诉「AI 答到一半，突然变成了另一个客户的内容」。列出三种可能的原因，并说明如何从埋点上区分它们。
答案

原因一：切换工单后未清理/未校验上下文。生成流仍绑定在旧工单，写入了新工单的面板。
区分方法：埋点里同时记 ticket_id_at_start 和 ticket_id_at_write。两者不一致且发生了写入，就是这一类。

原因二：并发请求的响应交错。两次点击产生两个流，都往同一个缓冲区追加。
区分方法：记 gen_id（请求代号）。如果同一个面板的文本片段来自两个不同的 gen_id，就是这一类。

原因三：服务端串了会话。更少见但更严重——服务端用了共享的全局变量，或者连接池复用时把 A 的流写进了 B 的连接。
区分方法：服务端在每一帧里带上 trace_id，客户端记录收到的 trace_id 序列。如果同一个 gen_id 内出现了两个 trace_id，问题在服务端，前端再改也没用。

为什么必须区分：这三种原因分属前端状态管理、前端并发控制、后端隔离。不区分就只能靠猜，而猜错方向的代价是「改了三天，投诉照旧」。能用一个字段区分三个假设，是埋点设计最核心的价值。

综合题二为什么 confirm 状态不允许超时取消？如果业务方坚持要「60 秒无操作自动关闭」，你会怎么设计？
答案

不允许超时的理由：超时只有两种处理方式，都不可接受。自动取消会造成「坐席接了个电话，回来发现操作被悄悄丢弃」，而用户以为已经生效；自动执行则是更严重的问题——一个「给客户退 200 元」的确认，在没人点的情况下自己执行了，这已经不只是体验问题。

如果业务坚持要自动关闭，正确的设计是：

① 关闭 ≠ 执行，也 ≠ 取消，而是「挂起」。状态从 confirm 转到一个 pending（不在主流程里，但在待办列表中可见），UI 上卡片收起，但操作没有消失。

② 挂起要有归属。挂起项进入「我的待确认」列表，并按过期时间排序。这样它不会因为界面关闭而丢失，而是转移到一个更合适的地方等待。

③ 真正的过期要有明确的失效条件。比如「超过 24 小时自动失效，并通知发起人」——关键是有失效，且有通知，而不是静默消失。24 小时这个量级是合适的，因为「60 秒」对人的工作节奏来说太短，而业务上真正有意义的时效是「同一班次内」或「当天内」。

④ 高风险操作不允许挂起。涉及金额、权限变更、批量操作的确认，超时后必须显式失效并记录，不能转入待办——因为待办列表会被忽略，而忽略一个已经部分生效的操作是危险的。

这道题的通用形式：当有人要求给一个「必须有人确认」的流程加超时，正确的回应不是拒绝，而是把「超时」重新定义为状态转移，而不是结果。

综合题三你的对话面板在 300 条消息时输入框明显卡顿，但 CPU 占用不高。给出最可能的两个原因和验证方法。
答案

原因一：每次 delta 都重建整个消息数组，导致全列表 diff。300 条消息的 diff 本身不慢，但配合 Markdown 重新解析就慢了。CPU 不高是因为它是突发的短时占用，平均下来不明显，而输入延迟恰好撞在那些突发时刻上。

验证：在 React DevTools 的 Profiler 里录一段「生成中打字」的操作，看每次 commit 的耗时和涉及的组件数。如果每次提交有 300+ 组件重渲染，就确认了。这是最直接的证据，不需要猜。

原因二：输入框是受控组件，且它的 value 存在与消息列表同一个 context 里。每次 delta 更新 context，输入框所在的组件树也跟着重渲染，光标位置和输入法状态被重置。表现是「打字时偶尔掉字」或「中文输入法候选框错位」——后者在中文场景特别常见，也特别容易被误判成浏览器 bug。

验证：把输入框的 value 临时改成非受控（defaultValue + ref），如果卡顿消失，就确认了。这是五分钟就能做完的对照实验。

为什么先查这两个而不是「上虚拟滚动」：虚拟滚动解决的是「渲染太多 DOM」，而这两个问题的根因是「不必要的重渲染」。前者是治标，后者是治本。在没定位到根因前引入虚拟滚动，通常会把问题变得更复杂——因为动态高度的测量本身又成了新的性能瓶颈。
