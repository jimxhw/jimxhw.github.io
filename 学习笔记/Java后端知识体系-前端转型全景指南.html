00先想清楚这三件事

在学任何技术之前，先把心智模型从「前端」切换到「后端」。你有前端底子，这不是从零开始， 而是换一个视角看同一套系统。以下三件事想通了，后面所有知识点都会变得自然。

一、后端的核心是「数据」，不是「界面」

前端的核心是视图与交互：状态怎么流转、用户看到什么、动效是否流畅。 后端的核心是数据的正确性：这条数据从哪来、存到哪去、中途出错了怎么办、两个人同时改怎么办。 前端渲染错了，刷新一下就好；后端数据写错了，可能是一笔真实的钱、一个真实的订单，且往往不可逆。

所以后端的第一性问题永远是：这份数据在多线程、多进程、多机、网络随时会断的前提下，如何保持一致与正确。

二、后端的一切都是「请求—响应」，只不过服务对象不只是浏览器

你熟悉 axios.get('/api/user')。在后端，你站到了管道的另一端：你得处理并发的成千上万个这样的请求， 每个请求消耗线程、内存、数据库连接；你得决定它超时多久、失败重试几次、限流多少 QPS。

而且请求你的不只是浏览器 —— 还有其它后端服务（RPC）、消息队列投递的消息、定时任务、第三方回调。 「接口」这个词的内涵因此从「给前端用的」扩展为「服务之间互相调用的契约」。

三、后端能力的三个台阶，对应薪资的三个档

第一档：能把功能写出来 —— 会 Spring Boot、会 CRUD、会连数据库。这是「能干活」。

第二档：能把功能写对 —— 懂事务边界、懂并发安全、懂索引与慢查询、懂异常与日志规范。这是「不挖坑」。

第三档：能把系统撑住 —— 懂缓存与消息队列的取舍、懂限流熔断降级、懂部署与容量、能判断什么时候该拆服务。 这是「能被信任去负责一个系统」。

本指南的结构，就是按这三个台阶铺的：0~3 章对应第一档，4 章与 7 章对应第二档，5~6 章对应第三档。

01前端 → 后端 心智映射表

你已有的前端知识不是包袱，是脚手架。大多数后端概念在你脑子里都能找到对应物， 差异恰恰是最需要留意的地方。下面这张表建议反复看，每学一个新概念，先去表里找它的「前端孪生兄弟」。

你熟悉的前端对应的后端概念关键差异（最容易踩的坑）
React 组件树 / 依赖注入容器Spring IoC 容器都是「声明依赖、由框架装配」。但后端 Bean 默认单例，全局共享一份实例 —— 所以任何成员变量都是并发共享的，这是前端转后端最经典的第一个坑。
Redux Store / Pinia数据库Store 是内存、进程重启即丢失、几乎无并发。数据库是持久化、多进程并发访问、有事务和锁。前者的「状态管理」是同步问题，后者的「状态管理」是一致性问题。
JS 事件循环（单线程异步）线程池（多线程并发）前端天然无需锁，因为只有一个线程。后端的线程池同时跑 N 个请求，竞态条件、可见性、原子性成为日常问题 —— 这是后端最陡的一级台阶。
Hooks 的 useEffect 依赖Spring AOP 切面都是「在不改主体逻辑的前提下，环绕插入增强」。前端是函数式包装，后端是动态代理 + 方法拦截。
axios 发请求Spring MVC 处理请求你从「发请求的人」变成「接请求的人」。URL 路由、参数绑定、序列化、状态码，全部由你定义。
package.json / npmpom.xml / Maven、build.gradle / Gradle都是依赖管理。但 Java 生态有传递依赖版本冲突地狱（同一个库被三个依赖引入三个版本），Maven 的 dependencyManagement 就是为此而生。
TypeScript 类型定义Java 静态类型 + 泛型 + 接口TS 类型编译后擦除；Java 类型运行时依然存在（反射），所以能靠类型做序列化、做 ORM 映射、做依赖注入。这是后端框架能存在的根基。
前端路由 / Vite ProxyAPI 网关 / Nginx 反向代理网关是流量的统一入口：鉴权、限流、日志、路由转发都在这一层做，业务代码里不再关心。
Chrome DevTools日志 + 指标监控 + 链路追踪后端没有「看得见的运行时」。日志是后端唯一的 DevTools，写不好日志等于蒙着眼睛开车。
打包产物部署到 VercelDocker 镜像 + K8s 调度前端部署产物是无状态静态文件，随便重启。后端是有状态进程：要管内存、端口、连接池、优雅停机、多实例水平扩展。
CORS 跨域报错同源策略的另一侧前端时代你在报错的一侧，后端你要在解决的一侧配置允许来源。
localStorage 缓存Redis 分布式缓存localStorage 是「用户设备的、单一用户的」；Redis 是「服务端共享的、所有用户的」，还带过期策略、淘汰策略、持久化 —— 它是一个独立的数据系统。
乐观更新 / 本地状态回滚数据库事务前端的「回滚」是重渲染；后端的回滚是物理撤销已写入的数据，涉及日志（undo log）与隔离级别。
Web Worker / 分片计算消息队列 + 异步任务都是为了「不阻塞主流程」。后端把它做成了独立中间件，还能跨机器、能削峰、能重放。
怎么用这张表 学到一个新概念时，先问自己两个问题：
  • 「它在前端对应什么？」 —— 快速建立直觉，降低陌生感。
  • 「它对应物的差异在哪？」 —— 差异处就是后端真正的难度所在，把注意力压在这些地方。

0宏观地图：六层一纵模型

这是整份文档最重要的一章。先看全图，再看细节。 后端不是一个「技术点的集合」，而是一个分层的系统：每一层只解决一类问题， 层与层之间有明确的职责边界和调用方向。你之后学的每一个框架、每一个中间件，都能在这张图上找到自己的位置。

图 0-1　Java 后端六层一纵模型：层内解决一类问题，跨层通过明确契约协作

每一层到底在干什么

L2
Web 与框架层 —— 系统的「门面」
把网络上的字节流翻译成方法调用，把返回值翻译回字节流。你的业务代码只写「收到请求 → 做什么 → 返回什么」，至于 TCP 怎么收包、HTTP 怎么解析、线程怎么分配，全由这一层扛住。
HTTP 协议 · Servlet 规范 · Tomcat / Netty · Spring IoC / AOP · Spring Boot · Spring MVC · RESTful 设计 · 参数校验与全局异常
L1
工程与构建层 —— 系统的「施工脚手架」
一个人写 demo 不需要它，十个人写一年就必须有它。它定义项目长什么样、依赖怎么管、代码怎么编译打包、质量怎么守门。前端的 package.json + ESLint + GitHub Actions 大体就是这一层。
Maven / Gradle（依赖与生命周期）· Git 分支模型 · JUnit / Mockito（单测）· SLF4J + Logback（日志）· 代码规范与静态扫描
L0
语言与运行时层 —— 一切的地基
这一层决定你写出代码的下限。语法不会可以查，但「为什么这个循环慢 100 倍」「为什么加了 synchronized 还是出问题」「为什么服务跑几天就 OOM」，答案全在这一层。它是区分「会写 Java」和「懂 Java」的分水岭。
语法与面向对象 · 集合框架（List/Map/Set 的选型）· 泛型与类型系统 · 并发编程（线程池 / JUC / 锁 / 内存模型）· JVM（内存结构 / 类加载 / GC）· Java 版本演进
纵
非功能与架构能力 —— 贯穿所有层的「内功」
它不是某一层，而是渗透在每一层里的判断力。同一段业务代码，有人写成能用的，有人写成三年后还能改的，差别就在这一层。技术上它最难被量化，面试与晋升却几乎只看它。
分层与职责边界 · 设计模式落地 · 高可用设计（冗余 / 隔离 / 降级）· 安全（认证授权 / OWASP）· 性能优化方法论 · 领域建模 · 技术选型思维
L3
数据层 —— 系统的「心脏」
后端所有复杂度的源头都在这里。业务逻辑写得笨一点顶多难看，数据层写错了就是事故。这一层的核心命题是：如何在并发、故障、数据量增长的前提下，保证数据正确且访问够快。
JDBC 与连接池（HikariCP）· ORM 思想（MyBatis vs JPA）· MySQL 架构与存储引擎 · 索引与 B+ 树 · 事务与隔离级别 · 锁与 MVCC · 慢 SQL 与执行计划 · 分库分表与读写分离 · NoSQL 定位
L4
中间件与分布式层 —— 从单机到集群的跨越
单机思路很朴素：一个进程 + 一个数据库。但当流量涨十倍、数据涨百倍、可用性要求 99.99% 时，你必须引入外部系统来分担压力、解耦流程、协调多台机器。这一层是后端与前端差异最大、也是薪资增长最快的一段。
Redis 缓存（穿透/击穿/雪崩）· 消息队列（Kafka / RocketMQ）· RPC（Dubbo / gRPC）· 注册与配置中心（Nacos）· API 网关 · 限流熔断降级 · 分布式事务 · 分布式锁 · 分布式 ID · 微服务 vs 单体
L5
部署与运维层 —— 让代码真正跑在生产环境
代码在你本机能跑，和生产上稳定运行，中间隔着一整个 L5。生产环境会暴露一切你在本地看不到的问题：内存泄漏、连接池打满、磁盘写满、依赖的服务挂了。DevOps 不是运维的专利，现代后端要为自己的服务在生产的表现负责。
Linux 常用命令 · Docker 镜像与容器 · K8s 编排 · Nginx 反向代理与负载均衡 · CI/CD 流水线 · 可观测性三件套（日志 / 指标 / 链路追踪）· 安全加固 · 压测与容量评估

串联：一次「提交订单」请求的完整旅程

上面是静态的结构图。真正让知识体系长进脑子里的方式，是跟着一个真实请求走一遍。 下面 16 个步骤，每一步都标注了它属于哪一层、涉及哪些知识点。你会发现：所有零散的技术点， 其实都是同一个请求在不同阶段需要的东西。反复读这个小节，直到你能自己在白纸上画出这条链路。

1
用户在浏览器点击「提交订单」调用方
对后端而言，这一刻什么都不存在，只有一条还没到达的 HTTP 请求在路上。
2
DNS 解析域名 → 请求打到 Nginx / 网关L5L4
生产环境几乎不会让请求直接进应用。Nginx 做 TLS 卸载、静态资源、负载均衡；网关做统一的鉴权、限流、灰度路由。这一层是流量的总闸门。
3
网关校验 Token、检查 QPS、路由到订单服务L4
涉及：JWT / OAuth2 认证授权、令牌桶限流算法。如果这里拦住，请求根本见不到业务代码 —— 非功能性防护要放在业务之前。
4
请求抵达 Spring Boot 应用，Tomcat 从线程池取一个线程L2L0
关键认知：Tomcat 默认 200 个线程，意味着最多同时处理 200 个请求，第 201 个要排队。为什么你的接口一慢，整个服务就雪崩？答案就在这一行。背后是 L0 的线程池原理。
5
Filter 链 → Interceptor → DispatcherServlet 分发到 ControllerL2
这就是 Spring MVC 的核心流程。Filter 属于 Servlet 规范（更底层，连 Spring 的 Bean 都能拦），Interceptor 属于 Spring MVC（能拿到 Handler 信息）。日志埋点、鉴权、跨域处理通常挂在这里。
6
JSON 反序列化 + 参数校验，包装成 DTO 对象L2
前端传来的是字符串，这里变成有类型的 Java 对象，并按注解规则校验（必填、长度、范围）。校验不通过就抛异常 —— 于是引出下一步。
7
全局异常处理器兜底，返回统一格式的错误响应L2纵
后端必须保证：任何异常都不会把堆栈信息裸露给前端，也绝不让进程崩掉。统一响应结构（code / message / data）是团队规范的基础。
8
Controller 调 Service —— 分层架构的边界纵L2
Controller 只负责「接待」：解析参数、调用、返回。业务逻辑一律在 Service，数据访问一律在 DAO/Mapper。分层不是形式主义，是为了让每一层的测试、复用、替换成为可能。
9
Service 开启事务，划定「要么全成功要么全失败」的边界L3
事务边界画在哪里，是后端最见功力的设计决策之一。画小了数据不一致，画大了锁表影响并发。这里涉及事务传播行为、隔离级别、@Transactional 失效场景。
10
先查 Redis 缓存，未命中才查 MySQLL4L3
缓存的意义是用内存换数据库压力，通常能挡掉 90% 以上的读请求。代价是引入一致性难题：缓存和数据库谁先更新？不一致窗口能接受多久？缓存穿透、击穿、雪崩怎么防？
11
MyBatis 生成 SQL → 走索引 → 从连接池借一个数据库连接L3
两条关键约束：① SQL 走不走索引，性能差几百倍；② 连接池是稀有资源（几十个），借不出来的请求会一直等，最终拖垮整个服务。慢 SQL 是线上事故的头号元凶。
12
扣减库存需要防并发 —— 数据库行锁不够，上分布式锁L3L4
这是一个服务部署了 8 个实例的场景：本地 synchronized 锁只能锁住自己进程，必须用 Redis 或 ZooKeeper 做跨进程的互斥。「单机锁」到「分布式锁」的跨越，是分布式思维的起点。
13
写入订单与库存，同时发一条消息给 MQ 通知下游L3L4
发消息的目的是解耦与削峰：发短信、加积分、通知仓配这些事不该拖慢下单主流程，扔进消息队列异步做。但随之而来的新问题是：消息发送和数据库事务不在一个 atomic 范围内 —— 这就是「分布式事务」要解决的。
14
提交事务 → 释放锁 → 释放连接 → 结果序列化成 JSONL3L2
注意顺序：事务提交、锁释放、连接归还，任何一个环节顺序错误都可能造成严重后果（例如先释放锁再提交事务，会导致并发读到旧数据）。
15
记录日志、上报指标、链路追踪记录整条链路耗时L5纵
用户看到的是「下单成功」，运维看到的是「P99 耗时 380ms，其中 SQL 占 240ms」。可观测性是把「玄学故障」变成「可定位问题」的唯一手段。
16
响应经网关返回浏览器，前端渲染成功提示L2
闭环。整条链路上任何一环出问题，用户看到的都是「失败了」—— 而你要有能力判断，问题出在哪一环。
这条链路的价值 它把「后端」这个抽象概念变成了一个可以逐步定位的具体过程。以后每学一个新知识点，你都可以问自己： 它插在这条链路的哪一步？没有它，那一步会变成什么样？ 能答上来，就说明你真的理解了，而不只是记住了名词。

为什么按这个顺序学：依赖关系决定路线

六层不是并列的，它们有硬依赖。跳过前置去学后面的，只能背概念、抄配置，一遇到问题就抓瞎。 下面说明了本指南的推荐顺序，以及每个前置为什么不可跳过。

阶段学习内容为什么必须在这个位置
1Java 语法 + 面向对象 + 集合不解释。但要注意：JVM / GC 放到这一阶段结尾，因为理解了内存结构，后面才能理解「为什么方法里不要创建大对象」这类实践建议。
2Maven + Git + 写出可运行的程序现代 Java 项目没有「裸写 main 方法」的玩法。不会 Maven 就无法引入任何第三方库，也就无法写第二行有用代码。
3HTTP + Servlet + Tomcat + Spring 核心这是最关键的认知跳板。要理解 Spring Boot 为什么这么设计，你必须先知道「没有它的时候，Servlet 写起来多痛苦」。跳过 Servlet 直接学 Boot，你永远只会「照抄注解」。
4Spring Boot + MVC + 完成第一个 CRUD 接口到这里你就能写出「能跑的功能」了 —— 第一个台阶跨上去了。此时你的代码是「能运行但不合格」的。
5JDBC → MyBatis → MySQL（索引 / 事务 / 锁）绝不能跳 SQL 直接上 ORM。ORM 会把 SQL 藏起来，但慢查询、死锁、索引失效这些问题全都由 SQL 决定。只学 ORM 的人，永远查不出线上性能问题。
6并发编程 + JVM 深入放在这里而非开头：因为你此时已经写过一个多线程 Web 服务，知道「单例 Bean 被多个线程同时调用」是什么场景，学并发才有具体的问题锚点。没有锚点学并发，只会背出「volatile 保证可见性」这种无意义的话。
7Redis + 消息队列前置是「你已经遇到了性能瓶颈和耦合问题」。先体会没有缓存的痛，才知道缓存解决什么、又引入什么新问题。
8Docker + CI/CD + 可观测性让服务真正跑起来。这一步会逼你回头补 Linux 和网络知识，学习动力最强。
9微服务 + 分布式（注册中心 / 网关 / 分布式事务）务必最后学。微服务是在单体撑不住时的优化手段，不是起点。没写过单体的人直接上微服务，做出来的是「分布式单体」—— 比单体还糟。
一句话总结这个顺序 先能跑（语言+工程），再能对外服务（框架），然后能存对数据（数据库），接着能扛住并发（并发+JVM+缓存），最后能撑住系统（分布式+运维）。 每一步都建立在前一步「你已经痛过」的基础上。

1语言与运行时层（L0）

这一层不产出任何「功能」，它决定的是你写出代码的质量下限。 把一个功能做出来，L1~L5 的知识就够；但把功能写得高效、安全、可维护，必须靠 L0。 对于有前端基础的人来说，Java 语法本身一周就能过完 —— 真正的门槛是并发和JVM， 因为前端语言在设计上帮你去掉了这两个维度的问题，后端语言把它们原原本本还给了你。

1.1Java 语言与面向对象L0 · 基础
角色语法层面的入场券。它不解决任何业务问题，但没有它连问题都表达不出来。
它是什么 / 解决什么

Java 是一门静态强类型、编译成字节码、运行在虚拟机上的面向对象语言。核心特征是「先声明类型，后编译，运行期类型信息仍然保留」—— 最后这一点是后面所有框架（Spring、MyBatis、Jackson）能存在的技术前提。

前端视角

TypeScript 是它的近亲，但有三处关键差别：① TS 类型编译后被擦除，Java 类型在运行时通过反射依然可读；② Java 没有「函数是一等公民」，方法必须挂在类上（Java 8 后用函数式接口 + Lambda 变相支持）；③ Java 没有闭包逃逸、没有 undefined，所有引用默认是 null，空指针是后端最高频的线上异常。

在体系中的位置

它是 L1~L5 全部内容的表达语言。你后面学的每一个注解、每一层抽象、每一种设计模式，最终都要落回这里：类、接口、继承、组合、多态。前端转后端最容易犯的错是把类当「命名空间」用，而不是当「职责边界」用。

最容易踩的坑 误把 Java 当 TS 写。典型表现：一个类塞 800 行、把所有东西都写成 static 工具方法、用继承去复用代码而不是表达「is-a」关系。后端代码活得更久、改动更频繁、协作人数更多，可维护性的权重远高于前端。
判断你是否掌握
  • 能说清「接口」和「抽象类」在什么场景下分别该用哪个，以及为什么
  • 理解 Java 的 equals 与 hashCode 契约，以及为什么重写一个必须重写另一个
  • 知道为什么 Java 里大量使用「组合优于继承」，并能在代码里看出来
1.2集合框架：List / Map / Set 的选型能力L0 · 高频
角色后端的日常工具。业务代码里 80% 的数据处理都在和集合打交道，而集合选型错误是最隐蔽的性能杀手。
它解决什么问题

程序需要组织多个对象：要按顺序放（List）、要按 key 查（Map）、要去重（Set）。Java 把它们抽象成三套接口，各自有多个实现，不同实现在不同操作上的复杂度差一个数量级。

ArrayList 随机访问 O(1) 但中间插入 O(n)；LinkedList 插入 O(1) 但随机访问 O(n)；HashMap 查找平均 O(1) 但要考虑哈希冲突与扩容；ConcurrentHashMap 才是在多线程下的正确选择。

前端视角

JS 只有 Array 和 Map/Set，引擎帮你把实现细节藏了。Java 把选择权交给你，也就把责任交给了你。

一个前端很熟悉的坑在这里会重演：你在 React 里知道「不要用 index 当 key」「不要在大列表上做 O(n²) 查找」。后端一样 —— 在 List 里做 contains 判断是 O(n)，循环里套一层就变成 O(n²)，1 万条数据就会让接口超时，而换成 Set 立刻降到 O(1)。

在体系中的位置

向上支撑 L3 数据层（ORM 查询结果就是 List、缓存批量取回要用 Map 组装）和 L4 中间件（本地缓存、去重、聚合统计）。 它是「数据在内存中的形态」，也是你和数据库之间的转运层。

最容易踩的坑 ① 并发共享。普通 ArrayList、HashMap 都不是线程安全的。Spring 的 Bean 默认单例，一旦你把集合写成成员变量，多个请求线程同时写就会出现数据错乱甚至死循环（HashMap 并发扩容成环）。
② 扩容代价。HashMap 扩容要重新哈希全部元素，ArrayList 扩容要拷贝整个数组。能预估容量时直接给初始容量，是成本最低的优化之一。
判断你是否掌握
  • 拿到一个需求，能立刻判断「这里该用 List 还是 Map 还是 Set」，而不是默认 ArrayList
  • 能解释 HashMap 在什么条件下会退化成 O(n)，以及 Java 8 引入了什么来缓解
  • 知道什么情况下必须换成 ConcurrentHashMap 或 CopyOnWriteArrayList
  • 知道迭代中删除元素为什么容易抛 ConcurrentModificationException
1.3泛型与类型系统L0 · 基础
角色把「运行时的类型错误」提前到「编译期的类型错误」。是 Java 代码安全性与可读性的主要来源。
它解决什么问题

没有泛型时，集合只能存 Object，取出来必须强转，而强转错误只在运行时才炸。泛型让「容器里装的是什么类型」成为类型声明的一部分，编译器帮你挡住所有错误用法。

更深一层：泛型 + 注解 + 反射，是 Spring 能靠类型自动装配依赖、Jackson 能靠类型反序列化 JSON、MyBatis 能靠类型映射结果集的技术基础。

前端视角

和 TS 泛型几乎同构，你会有天然的熟悉感 —— <T extends Foo>、通配符 ? 对 TS 用户来说不难理解。

但有一个 Java 独有的反直觉点：类型擦除。Java 泛型只在编译期有效，编译后 List<String> 和 List<Integer> 是同一个类，所以你不能写 new T()、不能判断 obj instanceof List<String>。TS 用户同样经历类型擦除，这一点能无缝迁移认知。

在体系中的位置

它是框架与反射的地基。学习 Spring 时你会遇到 ResolvableType、学习 MyBatis 时会遇到 TypeHandler —— 这些看起来高级的东西，本质都是在处理「泛型信息在运行时部分丢失」这个问题的对策。不理解泛型，这些源码永远读不懂。

最容易踩的坑 以为泛型能防住所有类型问题。擦除意味着：通过反射依然能往 List<String> 里塞进 Integer（所谓「泛型擦除漏洞」）。这不是让你去利用它，而是提醒你 —— 泛型是编译期契约，不是运行时保证。
判断你是否掌握
  • 能说清「类型擦除」意味着什么，以及它会带来哪些限制
  • 看得懂 <? extends T> 与 <? super T> 的使用场景差异
  • 知道为什么框架代码里到处都是泛型，而业务代码里很少用
1.4异常体系与错误处理哲学L0 · 高频
角色后端程序的「错误表达方式」。它不是一个语法点，而是一套工程纪律 —— 一个团队的异常处理水平，直接反映其代码水平。
它解决什么问题

程序一定会在某个环节失败：参数不合法、数据库连不上、下游服务超时。异常机制让「失败」变成一种可以被显式传递、捕获、转换的信息，而不是让程序静默地继续跑下去产生错误数据。

Java 把异常分成两类：受检异常（编译期强制处理，代表「可预期且调用方应该处理」）与非受检异常（RuntimeException，代表「编程错误或不该在这里处理的故障」）。

前端视角

前端 try/catch 通常只为了不让页面白屏，Promise 的 reject 常常被忽略也没人发现。后端的异常处理要求完全不同：每一次捕获都必须有明确意图 —— 是重试、是降级、是转换为业务错误码、还是真的可以吞掉。

一个非常实用的类比：后端的全局异常处理器，就像前端最外层的 ErrorBoundary —— 兜底，绝不让异常穿透到用户可见层。

在体系中的位置

向下被 L0 各类 API 抛出，向上被 L2 的全局异常处理器统一收口，横向被 L5 的日志系统记录、被监控系统告警。异常是贯穿所有层的信息流。

最容易踩的坑 ① 空捕获：catch(Exception e){} 然后什么都不做 —— 这是线上事故的温床，故障发生了但没有任何痕迹。
② 用异常控制流程：把「用户不存在」这种正常业务分支做成异常抛出，性能差且语义错。
③ 吞掉或改写原始异常：捕获底层异常后抛出新的异常却不带上 cause，导致排障时丢失最关键的第一现场信息。
判断你是否掌握
  • 能说清「受检异常」为什么在现代 Java 实践中逐渐被弃用（如 Spring 全面使用 RuntimeException）
  • 能设计一套团队的异常规范：业务异常怎么分类、错误码怎么定义、怎么落到日志
  • 能在 code review 中指出所有「不当捕获」的代码并说明理由
1.5并发编程：线程、线程池与锁L0 · 分水岭
角色后端知识体系中最陡的一级台阶，也是前后端思维差异最大的一块。它决定了你是否真正理解「服务端」这三个字。
它解决什么问题

Web 服务器必须同时服务成千上万个请求，而 CPU 核心只有几个 —— 必须用多线程把 IO 等待时间利用起来。于是产生了前端世界里完全不需要面对的问题：

  • 原子性：两个线程同时给库存减 1，结果只减了 1 次
  • 可见性：A 线程改了标志位，B 线程永远看不到
  • 有序性：编译器与 CPU 重排序导致代码实际执行顺序与书写顺序不符

线程池则是「线程的复用与治理」：预先创建、限制上限、排队等待、拒绝策略。不治理线程，服务迟早被线程拖垮。

前端视角

JS 是单线程 + 事件循环，你在前端写下的每一行代码都天然是线程安全的。所以你从未建立过「竞态条件」的直觉 —— 这是转后端最需要重建的一块。

可以把线程池理解成「多个 JS 运行时同时跑同一份代码，共享同一批内存变量」。一旦这么想，你就会立刻明白为什么 count++ 不再安全、为什么单例 Bean 的成员变量如此危险。

在体系中的位置

它是竖着切穿所有层的主题：L2 的 Tomcat 线程池与 Spring 单例 Bean、L3 的数据库连接池与行锁、L4 的分布式锁与 MQ 消费并发、L5 的线程 dump 与 CPU 飙高排查 —— 全都建立在并发认知之上。

不懂并发，你在后端只能写「能跑的代码」，写不出「能上线的代码」。

最容易踩的坑 ① 把共享可变状态放在单例 Bean 里。这是前端转后端最高频、最致命的事故源 —— 本地测试单人操作完全正常，上线后出现「A 用户看到 B 用户数据」。
② 自己 new Thread()。不受控的线程创建会耗尽系统资源，必须走线程池。
③ 以为加了锁就万事大吉。锁的粒度、范围、顺序都会带来新问题：死锁、锁竞争导致的吞吐骤降、锁与事务嵌套导致的长时间持锁。
判断你是否掌握
  • 能说清线程池的核心线程数 / 最大线程数 / 队列 / 拒绝策略四要素如何共同决定行为，以及队列选错会发生什么
  • 能解释 volatile 和 synchronized 分别解决三大特性里的哪几个
  • 看到一段业务代码，能立刻指出其中所有存在线程安全风险的地方
  • 知道线上 CPU 100% 时，用什么工具（线程栈）定位到具体哪一行代码
1.6JVM：内存结构、类加载与垃圾回收L0 · 深水区
角色代码的「物理世界」。它解释了所有性能现象与线上诡异故障的最终原因。
它解决什么问题

Java 的承诺是「一次编写，到处运行」，代价是代码不直接跑在机器上，而是跑在一个虚拟机上。这带来三个必须理解的机制：

  • 内存结构：堆（对象）、栈（局部变量）、方法区（类元信息）、程序计数器。所有「内存溢出」问题都要先问「哪个区域溢出」。
  • 类加载：类的生命周期、双亲委派模型。这是理解「热部署」和「版本冲突」的钥匙。
  • 垃圾回收：不再被引用的对象被自动回收。GC 算法与分代设计直接决定服务的延迟与吞吐。
前端视角

其实你非常熟悉这几个概念 —— V8 也是带 GC 的运行时，浏览器也会内存泄漏，Chrome DevTools 的 Memory 面板就是前端版的 JVM 分析工具。

区别在于：前端的泄漏通常是「某个闭包被意外长期持有」，页面刷新就清零；后端的泄漏是持续累积的，服务不能重启着解决，几天后必然 OOM 崩溃。所以后端必须真的懂内存模型，而不是靠重启。

在体系中的位置

它是 L5 可观测性的主要调查对象：堆内存曲线、GC 频率与停顿时间、线程数 —— 这三条曲线是判断服务健康状况的体温计。它也是连面试官最爱追问的深水区：因为只有读过 JVM，才知道很多「最佳实践」背后的真实原因。

最容易踩的坑 背参数而不理解原理。很多人能背出「新生代用复制算法、老年代用标记整理」，却说不出「为什么大对象要直接进老年代」「为什么频繁 Full GC 通常意味着内存泄漏而不是内存不够」。
另一个常见误区：以为调大 -Xmx 能解决所有内存问题 —— 大多数时候它只是把崩溃时间往后推。
判断你是否掌握
  • 能画出 JVM 运行时数据区，并说出哪些区域线程共享、哪些线程私有
  • 能解释一次 Full GC 前后发生了什么，以及为什么它会导致接口「卡住几秒」
  • 拿到一份 OOM 堆转储文件，知道该用什么工具、从哪里开始查
  • 能说明「双亲委派」是什么，以及为什么需要打破它（Tomcat 与热部署场景）
1.7Java 版本演进：8 / 11 / 17 / 21 意味着什么L0 · 常识
角色语言能力的分界线。它决定你能用哪些语法、能不能享受新 GC 带来的性能红利，也是一条硬性的工程约束。
它解决什么问题

Java 9 之后改为每半年一个版本的快速迭代，同时用 LTS（长期支持版本）给企业提供稳定的升级锚点。当前的 LTS 是 8 / 11 / 17 / 21。

Java 8 是事实上的行业基线（Lambda、Stream、函数式接口、新的日期时间 API），至今仍有大量存量系统在用。Java 17 是当前新项目的主流选择（Records、文本块、密封类、强封装 JDK 内部 API）。Java 21 带来虚拟线程，是对「高并发 IO」这件事的范式级改变。

前端视角

类似 Node 的版本策略与 TC39 提案节奏 —— 语言在持续演进，但生产环境必须保守。前端用不用可选链是风格问题；后端选 Java 8 还是 17 是架构决策，因为它牵扯整个依赖生态、运维基线、甚至第三方中间件客户端是否兼容。

在体系中的位置

它是整个体系的地基版本号：L2 的 Spring Boot 3.x 要求 Java 17+，因此你的 Java 版本选择倒推决定了你能用哪个 Spring 版本、哪些中间件客户端版本。这是一条真实的、经常卡住项目的约束链。

最容易踩的坑 学习时直接上手 Java 21 + Spring Boot 3，然后在公司遇到 Spring Boot 2.x + Java 8 的老项目就完全懵了。 建议学习路径：以 Java 17 为目标掌握新特性，同时了解 Java 8 的语法基线，因为存量项目仍是市场主流。
判断你是否掌握
  • 能说出 Lambda 与 Stream 解决了什么问题（相对匿名内部类与手写 for 循环）
  • 知道 Stream 是惰性求值，以及为什么不要在 Stream 里做重 IO 操作
  • 了解虚拟线程和普通线程的本质区别，以及它主要解决什么场景的问题

2工程与构建层（L1）

这一层最容易被前端低估，因为你的 npm 生态已经把大部分工作标准化到「开箱即用」了。 但 Java 生态的历史包袱更重、企业级约束更多，这一层是团队协作效率与代码质量的实际守门人。 好消息是：你原本的工程化与 CI/CD 经验在这里可以快速平移，需要补的主要是 Java 特有的依赖模型。

2.1Maven / Gradle：依赖管理与构建生命周期L1 · 基础设施
角色项目的「骨架 + 供应链」。它定义项目结构、管理全部第三方依赖、控制从编译到打包的每一个环节。
它解决什么问题

Java 项目一旦超过三行代码就要用第三方库，而库又依赖别的库。Maven 解决四件事：

  • 统一项目结构：src/main/java、src/test/java、src/main/resources —— 换任何项目都能立刻找到代码
  • 依赖声明与自动下载：写一行 <dependency>，相关 jar 全部从仓库拉下来
  • 传递依赖与版本仲裁：A 依赖 B 依赖 C，Maven 自动处理，也自动制造「版本冲突地狱」
  • 标准化构建流程：compile → test → package → install → deploy，一条命令跑完全流程
前端视角

pom.xml ≈ package.json，本地仓库 ≈ node_modules，Maven 中央仓库 ≈ npm registry，生命周期阶段 ≈ npm scripts。

最大的差异在传递依赖的处理方式：npm 允许依赖树里同名包存在多个版本（各用各的），而 Java 的类路径是扁平的 —— 同一个类的多个版本只能留一个。这就是为什么后端会遭遇「NoSuchMethodError」这种诡异报错：编译时用的是 1.2 版，运行时类路径里被换成了 1.0 版。

在体系中的位置

它是所有其它层的前提 —— 没有 Maven/Gradle，Spring、MyBatis、Redis 客户端你一个都引不进来。 在企业里它还是发布流程的入口：CI 流水线的第一步永远是「执行构建」。

最容易踩的坑 ① 版本冲突排查困难。需要掌握「依赖树」的查看方式与 dependencyManagement / exclusions 的用法，这是后端必备技能。
② 不看 scope 乱写依赖（compile / provided / runtime / test）。比如把只在测试用的库打成 compile，会污染运行时类路径。
③ 用 IDE 的「自动导入」掩盖问题，团队里换台机器就构建失败 —— 说明项目结构或仓库配置有隐性问题。
判断你是否掌握
  • 能说清 Maven 的生命周期阶段有哪些，以及 package 和 install 的区别
  • 遇到 NoSuchMethodError / ClassNotFoundException 时，第一反应是去看依赖树
  • 知道多模块项目（parent / child）是怎么组织依赖继承的
  • 知道为什么企业内网通常要自建私服（Nexus），它解决什么问题
2.2Git 与团队协作规范L1 · 协作
角色多人协作的秩序来源。技术上你已经会 Git，但在后端团队里，它还承载着「发布节奏」与「责任追溯」的职责。
它解决什么问题

多人在同一份代码上并行开发、互不阻塞、还能随时发布其中一部分 —— 这需要分支模型 + 代码评审 + 发布流程三者配合。常见的有 Git Flow、GitHub Flow、主干开发 + 特性开关等。

后端还有一个前端不那么强调的点：提交历史即事故档案。出故障时，第一时间就是看最近合入的提交 —— 所以提交信息规范、变更范围小、一个提交只做一件事，是职业习惯而不是洁癖。

前端视角

日常操作完全一致（pull / commit / push / rebase / cherry-pick）。差异主要在发布纪律：

前端发布失误用户刷新一下可能就好了，或者回滚静态资源即可；后端发布涉及数据库变更与数据状态。一个错误的 DDL 或数据迁移脚本，回滚的难度可能是灾难级的 —— 所以后端对「变更可控」和「向后兼容」的要求严格得多。

在体系中的位置

它连接 L1 内部（触发 CI 构建）与 L5 部署（流水线的触发源）。同时它是非功能性能力的载体：代码评审是团队知识传递与技术把关的主要场合。

最容易踩的坑 把数据库变更当成代码变更来对待。「改个字段类型，回滚一下就行」—— 数据可能已经丢失或转换不可逆。 后端必须遵守的原则是：DDL 与数据迁移要有独立的、可审查的、灰度执行的流程，且优先做「新增字段」而非「修改/删除字段」。
判断你是否掌握
  • 能设计一个适合你团队规模的分支模型，并解释为什么不用另一种
  • 知道什么是「向后兼容的接口变更」，以及为什么要先上线新接口再下线旧接口
  • 了解数据库变更的常见上线策略（新增字段 → 双写 → 迁移数据 → 下线旧字段）
2.3单元测试：JUnit / Mockito / 测试策略L1 · 质量
角色代码的「安全网」。它是让「重构」这件事成为可能的前提 —— 没有测试的代码，改动只能靠祈祷。
它解决什么问题

后端代码的行为大量依赖外部状态（数据库、缓存、下游接口），无法像前端一样「改一下页面刷新看效果」。测试是这个反馈闭环的唯一替代品。

后端测试通常分三层：单元测试（测一个方法，外部依赖全部 mock，极快）、集成测试（起 Spring 容器 + 真实数据库/容器化依赖，验证装配与 SQL 正确）、端到端测试（真实调接口，验证整条链路）。

前端视角

你熟悉的 Jest / Vitest 在设计哲学上完全对应：Mockito 之于后端 ≈ jest.mock 之于前端，@SpringBootTest ≈ 起了一套完整运行环境。

一个可以复用的判断：「测试金字塔」的配比原则在前端后端是一样的 —— 底层单元测试多而快，上层集成测试少而慢。但后端普遍更强调「集成测试」，因为很多 bug 恰恰藏在 SQL、事务、序列化这些「跨组件」的地方，单测覆盖不到。

在体系中的位置

它在 L1 内部与 CI/CD 紧密耦合（流水线的质量门禁），同时是理解 L2 框架内部机制的最好方式 —— 想真正搞懂 Spring 的事务与代理，写一个测试去观察 @Transactional 在什么情况下失效，比读十篇文章都有效。

最容易踩的坑 ① 为了覆盖率写测试。测了 getter/setter 把覆盖率刷到 80%，核心业务逻辑一行没覆盖。
② 测试依赖执行顺序或外部真实数据，导致「单独跑能过，一起跑就挂」—— 这是团队里最消耗信任的问题。
③ 不测边界。空集合、null、超大值、并发调用、事务回滚 —— 后端 bug 高度集中在这些地方。
判断你是否掌握
  • 能说清什么该写单测、什么该写集成测试、什么干脆不测
  • 知道为什么 @Transactional 加在测试方法上能自动回滚数据
  • 能用测试复现一个 bug，再修复它（而不是手动改数据试来试去）
2.4日志体系：SLF4J + LogbackL1 · 排查生命线
角色后端的 DevTools。在生产环境里，日志是你唯一能「看到」程序内部发生了什么的手段。
它解决什么问题

服务跑在你看不到的服务器上。当用户说「下单失败了」，你必须能回答：这个请求进来了吗？走到哪一步？报了什么错？带着什么参数？耗时多少？

SLF4J 是门面（接口层），Logback / Log4j2 是实现。这层抽象让代码只依赖接口，可以随时替换日志实现 —— 这是 Java 生态「面向接口编程」思想的典型应用。

前端视角

前端 console.log 后关掉页面就没了。后端日志是可持久化、可检索、可告警的结构化数据。

更应该建立的认知是：日志的分级（ERROR/WARN/INFO/DEBUG）是一种运行时的流量控制手段。生产环境开 DEBUG 会让磁盘几小时写满、并把真正的错误淹没在噪音里；线上出问题时临时提升某个包到 DEBUG 级别，是常用的排障手法。

在体系中的位置

它是 L5 可观测性三件套（日志 / 指标 / 链路追踪）里最基础的一件。在微服务架构下还会升级为「集中式日志」（ELK / Loki），因为服务有几十个实例，不能逐个登录看。

最容易踩的坑 ① 用字符串拼接打日志而不是占位符 —— 即使该级别不输出，拼接也已经执行，白白浪费性能。
② 循环里打日志。一万次循环打一万行，磁盘和日志系统一起爆炸。
③ 日志里打印敏感信息。手机号、身份证、密码、Token、完整请求体 —— 这是实打实的数据安全事故，不是风格问题。
④ 关键路径无日志或日志无上下文。出问题时只知道「失败了」，不知道是哪个用户、哪个订单、哪次调用。
判断你是否掌握
  • 能说清「什么时候该打什么级别」的团队约定，并能说服别人遵守
  • 知道什么是 traceId，以及它如何在分布式环境下把一次请求的日志串起来
  • 能给一个接口设计出「出问题后 30 秒内定位原因」所需的日志埋点
2.5代码规范与静态检查L1 · 团队纪律
角色把「个人品味」变成「团队标准」。它的价值在项目第 6 个月、第 5 个人加入时才真正显现。
它解决什么问题

后端的生命周期通常比前端长得多（五到十年的系统很常见），维护成本主要由「可读性」决定。规范工具把命名、格式、分层约束、空值处理等固化成机器可校验的规则，在提交或构建阶段就拦住问题。

常见工具：阿里巴巴 Java 开发手册（P3C）、Checkstyle、SpotBugs、SonarQube（还能扫出安全漏洞与重复代码）。

前端视角

完全对应 ESLint + Prettier + husky 的组合，你会有强烈的熟悉感，迁移成本几乎为零。

差异在于：Java 的规范里有相当一部分是「正确性问题」而非「风格问题」。例如「必须用 equals 比较包装类型」「禁止在 foreach 里 remove」「集合初始化必须指定容量」—— 这些不是审美偏好，写错了会出 bug。

在体系中的位置

它是 L1 与纵向能力（代码质量）的结合点。在 CI 流水线中作为质量门禁存在，同时也是新人最快了解团队技术水准的入口。

最容易踩的坑 把规范当成教条去背。正确姿势是「知其所以然」：为什么 Integer a == 128 是 false 而 == 100 是 true？因为包装类缓存只覆盖 -128~127。理解了这个，你才会真正记住「包装类型必须用 equals」，而不是死记硬背。
判断你是否掌握
  • 能说出至少五个「Java 里看起来没问题但实际会出 bug」的常见写法
  • 知道为什么空集合应该返回 Collections.emptyList() 而不是 null
  • 能在 CI 中配置一套最小可用的质量门禁

3Web 与框架层（L2）

这一层是你从「调接口的人」变成「提供接口的人」的转折点，也是整个后端体系里最像「前端框架」的一层 —— Spring 的 IoC 之于后端，就像 React 的组件树之于前端：都是「声明依赖、由框架装配」。 但要注意：一定要先理解 Servlet，再学 Spring Boot，否则你只会用注解，不会用框架。

3.1HTTP 协议：从使用方到服务方L2 · 通信基础
角色前后端之间的唯一契约。你做前端时只关心「怎么发」，现在要关心「怎么正确、安全、高效地收和回」。
它解决什么问题

HTTP 定义了请求与响应的格式规范。作为服务端，你需要理解的是这些此前被 axios 帮你处理掉的部分：

  • 方法语义：GET 应幂等且无副作用，POST 创建，PUT 全量更新，PATCH 局部更新，DELETE 删除 —— 语义用错会导致前端缓存、重试、网关策略全部失效
  • 状态码：2xx 成功、3xx 重定向、4xx 客户端错误（参数错、未认证、无权限）、5xx 服务端错误。区分 4xx 和 5xx 是排障的基本功
  • Header：Content-Type、Authorization、Cookie、缓存控制、跨域相关头
  • 幂等性：为什么「网络超时后重试」对 GET 安全、对 POST 危险 —— 这直接引出分布式系统的重试与去重设计
前端视角

你已经知道这些概念，但站在了另一边。举一个典型场景：前端抱怨「接口 500 了」，后端要能立刻判断这是「服务出了故障」还是「用户传了非法参数被误判成服务错误」。该是 400 的返回了 500，会让整个监控系统失真 —— 报警里全是「服务端错误」，其实全是脏数据。

在体系中的位置

向下被 L2 的框架解析、向上是 L4 网关与 RPC 的基础（网关的限流、鉴权全部作用在 HTTP 层）。 它还是 L5 排查问题的第一现场：线上问题第一步永远是看请求状态码、响应时间、请求头是否正确透传。

最容易踩的坑 ① 用 200 包一切错误。所有接口都返回 200，再用 body 里的 code 表示成败 —— 这让网关、监控、CDN、日志系统全部无法正确判断服务健康度。
② 不区分幂等操作。把「创建订单」写成 GET，结果被浏览器预取或网关重试执行了两次。
③ 忽略超时设置。HTTP 客户端默认可能永不超时，一个慢下游能把你的线程池全部占满 —— 这是最经典的雪崩成因。
判断你是否掌握
  • 能设计一套规范的响应结构，并说清它与 HTTP 状态码的分工
  • 能解释为什么「超时 + 重试」机制必须配合幂等设计一起考虑
  • 知道 GET 与 POST 在缓存、书签、日志、代理行为上的实际差异
3.2Servlet 与 Tomcat：理解框架之前必须知道的事L2 · 认知跳板
角色Java Web 的底层规范。它本身已经很老旧，但不理解它，你对 Spring MVC 的理解就永远停留在「照抄注解」的层面。
它解决什么问题

裸写 Java 处理 HTTP 是很痛苦的：要自己监听端口、解析报文、管理线程、处理连接。Servlet 规范把这些标准化了：

  • Servlet 容器（Tomcat / Jetty / Undertow）负责网络通信、线程分配、生命周期管理
  • Servlet 是容器里的一个组件，只需要实现 service(request, response)，专注业务处理
  • Filter 是 Servlet 规范提供的横切扩展点，在请求进入 Servlet 前后插入逻辑

一个 Servlet 实例会被多个线程并发调用 —— 这就是 1.5 节讲的并发问题在 Web 场景下的具体落地。

前端视角

可以理解为「Web 服务器的最小可插拔单元」，类似前端的中间件（Express / Koa 的 middleware）。

但有一个关键区别值得反复琢磨：Node 的中间件是函数式链式调用，天然无状态；Servlet 是对象，对象就有成员变量，成员变量就会被多线程共享。这个差别，直接导致了「单例 Bean 成员变量事故」这一类高频问题。

在体系中的位置

它是 Spring MVC 的运行底座。Spring MVC 的 DispatcherServlet 本身就是一个 Servlet —— 也就是说， 整个 Spring Web 世界是挂在一个 Servlet 上的。懂了这一句，你就能理解为什么过滤器（Filter）属于容器层、 拦截器（Interceptor）属于 Spring 层，以及两者为什么执行顺序不同。

最容易踩的坑 跳过 Servlet 直接学 Spring Boot。后果是：看到 @WebFilter 和 HandlerInterceptor 分不清哪个是哪个；遇到 Tomcat 线程数、连接数、maxConnections 参数无从下手；不理解为什么有些超时是容器层的、有些是框架层的。
判断你是否掌握
  • 能说清一次请求在 Tomcat 内部的流转：连接 → 线程 → Filter → Servlet
  • 能解释 Tomcat 的线程池配置如何影响服务的最大并发能力
  • 知道 Filter 和 Interceptor 的执行时机差异，以及各自适合放什么逻辑
3.3Spring IoC：控制反转与依赖注入L2 · 框架之魂
角色Spring 的核心与地基。整个 Spring 生态（MVC、事务、AOP、Boot）全部构建在 IoC 容器之上。不理解它，后面所有注解都是黑魔法。
它解决什么问题

在没有 IoC 的时代，对象的创建和依赖装配由业务代码自己负责，结果是：

  • 要用的对象到处 new，依赖关系散落各处，改一处牵动全身
  • 无法统一管理生命周期（单例复用、销毁清理）
  • 无法在不改代码的前提下替换实现、插入增强 —— 也就是无法做测试、无法做 AOP

IoC 把「创建和装配对象」的控制权从业务代码反转给了框架：你在类上声明「我需要什么」，容器负责在启动时把所有对象建好、按依赖关系串起来、并在需要时注入给你。

前端视角

这是最容易被前端理解的一层。React 的 Context / Provider 树、Vue 的 provide/inject、Angular 的 DI 系统，本质都是同一件事：把依赖交给容器管理，组件只声明它需要什么。

你早就有这个直觉了：为什么你的组件不自己 new 一个 API client？因为它应该来自上下文 / 注入。后端只是把这件事推广到整个应用。

在体系中的位置

它是承上启下的枢纽：向上让 L2 的 MVC、事务、AOP 能织入业务代码；向下依赖 L0 的反射与代理机制。 它还塑造了后端最重要的一条架构纪律 —— 由容器管理的对象才有生命周期，才应该被复用；其余对象随用随建。

最容易踩的坑 ① 不理解「单例」的后果。Spring Bean 默认单例，意味着一个实例服务所有请求。往里面写成员变量 = 往全局变量里写用户数据。
② 循环依赖。A 依赖 B、B 依赖 A，容器启动时报错。这通常不是技术问题而是设计问题：说明两个类的职责边界没有划清。
③ 滥用 @Autowired 字段注入。它让依赖隐式、无法用 final 保证不可变、脱离容器就无法实例化（测试变难）。现代实践推荐构造器注入。
判断你是否掌握
  • 能说清 Bean 的作用域（singleton / prototype / request / session）分别适合什么场景
  • 能解释「Bean 的生命周期」大致经历了哪些阶段，以及初始化钩子有什么用
  • 知道构造器注入相比字段注入的三个具体优势
  • 看到一段代码能判断「这个对象是容器管理的还是自己 new 的」，以及区别是什么
3.4Spring AOP：面向切面编程L2 · 能力倍增器
角色让「与业务无关的横切关注点」从业务代码里消失。事务、日志、鉴权、缓存、限流 —— 你在 Spring 里用的这些能力，全部是 AOP 实现的。
它解决什么问题

有一类逻辑不属于任何单个业务，但几乎每个业务都要用：开事务、记日志、校验权限、统计耗时。如果把这些写进每个方法，业务代码会被淹没，而且改一次要改一百处。

AOP 的做法是：把这些逻辑定义成「切面」，并声明「在什么时机、对哪些方法生效」。业务代码保持纯净，增强由容器在调用时动态织入。

Spring AOP 的实现方式是动态代理：容器给你的 Bean 其实是代理对象，调用先进入代理，代理执行增强逻辑，再调用真实方法。

前端视角

你在前端用过类似的东西：高阶函数 / 装饰器 / 中间件（withAuth(withLogging(Component))），Redux 的 middleware 链，React 的 HOC。

更贴切的类比是 Proxy / 拦截器式的「环绕增强」。而动态代理的本质，你在前端其实也见过 —— Proxy 对象包装了目标对象，读写都会被拦截。Spring AOP 就是「服务端版的 Proxy 包装」。

在体系中的位置

它是 Spring 的横向能力挂载机制。理解了 AOP，你就明白了：为什么加一个 @Transactional 就能有事务、加一个 @Cacheable 就能有缓存、加一个 @Async 就能异步执行 —— 也就能理解它们各自失效的各种场景。

可以说：Spring 的「好用」，一半来自 IoC，一半来自 AOP。

最容易踩的坑 ① 同类内部调用导致 AOP 失效。这是后端最经典的面试题与生产事故：A 方法调用同类 B 方法，B 上的 @Transactional 不生效 —— 因为调用没经过代理对象。理解「代理」的本质，这个坑就再也不会踩。
② 切面顺序混乱。多个切面叠加时，谁先谁后有确定规则，顺序错了可能导致「事务还没开日志就记了」这类逻辑错误。
③ 在切面里做重活。切面作用在所有匹配的方法上，一个耗时的日志切面能拖慢半个系统。
判断你是否掌握
  • 能解释「为什么同类方法内部调用会使事务/缓存/异步注解失效」，以及如何规避
  • 能说清 JDK 动态代理与 CGLIB 代理的区别，以及为什么有时候必须用后者
  • 拿到一个横切需求，能判断它该用 AOP 还是用 Filter/Interceptor
3.5Spring MVC：一个请求是怎么被处理的L2 · 核心流程
角色把你的 Java 方法暴露成 HTTP 接口。它是后端最日常的一层，也是理解后续所有 Web 相关问题的地图。

图 3-1　Spring MVC 请求处理流程：容器层 → 框架层 → 业务层，再原路返回

它解决什么问题

把「HTTP 请求」和「Java 方法调用」之间的映射关系自动化：URL 对方法、参数对形参、返回值对响应体。你只需要声明映射，剩下的解析、绑定、校验、序列化全部由框架完成。

它还提供了几个关键扩展点：Interceptor（Spring 层的横切）、ArgumentResolver（自定义参数解析，比如从 Token 里取出当前用户）、HttpMessageConverter（序列化策略）。

前端视角

你写前端路由 path: '/user/:id' 时，是在声明「这个 URL 交给哪个组件」。Spring MVC 的 @RequestMapping 是同一件事，只是「组件」变成了「方法」。

更贴切的类比是 axios 的请求拦截器 + 响应拦截器：Interceptor 就是后端版的请求/响应拦截器，只是它跑在服务端。

在体系中的位置

它坐在 Tomcat 之上、业务代码之下，是请求进入业务逻辑的最后一站。这里也是最合适放「接口层通用能力」的地方：统一响应包装、参数校验、日志埋点、当前用户注入。

最容易踩的坑 把业务逻辑写进 Controller。Controller 应该只有三行：接参数、调 Service、返回。一旦开始写 if/else、写数据库操作，分层就破了。
另一个高频坑：不清楚 Filter / Interceptor / AOP 三者的区别与顺序，导致「为什么我这个鉴权拦截器拿不到登录用户」「为什么跨域配置没生效」这类问题反复出现。
判断你是否掌握
  • 能不看资料画出这条流程图，并标注每一层能放什么逻辑
  • 能说清 Filter / Interceptor / AOP 三者的执行顺序与适用场景
  • 知道请求体（RequestBody）为什么只能读一次，以及怎么解决需要重复读取的问题
3.6Spring Boot：约定优于配置L2 · 生产力
角色把 Spring 从「配置地狱」里救出来的工程化方案。它不引入新能力，只消除样板代码。
它解决什么问题

早年用 Spring 要写大量 XML / 配置类：数据源、事务管理器、MVC 组件、JSON 转换器，一个不漏。而其中 90% 的配置在所有项目里都一模一样。

Spring Boot 做三件事：

  • 起步依赖：引一个 spring-boot-starter-web，需要的十几个库自动带齐且版本互相兼容
  • 自动配置：根据类路径上有什么、你配了什么，自动决定要创建哪些 Bean
  • 内嵌容器：Tomcat 打进 jar 包里，直接 java -jar 就能起服务，不再需要单独部署 war 包
前端视角

几乎完美对应 Vite / Next.js 的「零配置起步」：你不用手写 webpack 配置，因为框架已经预设了最合理的默认值，只有偏离默认时才需要显式配置。

「约定优于配置」这四个字你在前端工程化里已经体会过了：pages/ 目录下的文件自动成为路由、public/ 下自动成为静态资源。Spring Boot 的自动配置就是同样的哲学。

在体系中的位置

它是现代 Java 项目的默认起点。你后续所有层（数据层、缓存、消息队列、监控）的集成，都以「引入一个 starter、写几行配置」的形式完成。 可以说：L2 与 L3~L5 的粘合剂就是 Spring Boot。

最容易踩的坑 把「自动配置生效了」当成理所当然。当某个功能不生效时（缓存没生效、事务没生效、数据源被覆盖），你必须知道去哪查「自动配置报告」、怎么排除某个自动配置类。
更根本的坑：只会用 Boot 而不会 Spring。面试问「自动配置原理」，答不上来说明你只学了皮毛。
判断你是否掌握
  • 能说清「自动配置」大致是怎么实现的（条件注解 + 配置类 + 元数据）
  • 知道配置文件的优先级顺序，以及多环境配置（dev / test / prod）怎么组织
  • 知道内嵌容器模式与打 war 包部署的区别，以及为什么前者成为主流
3.7分层架构：Controller / Service / DAOL2 · 结构纪律纵向
角色后端代码的空间秩序。它不是一种技术，而是一种「把不同性质的责任放在不同地方」的组织方式 —— 也是你判断一个后端项目是否规范的第一眼标准。
Controller
接入层 —— 只做「接待」
接收参数、解析当前用户、调用 Service、包装返回值。不应该有业务判断，不应该直接碰数据库。它的存在意义是「让 HTTP 语义止步于此」—— 以后换成 RPC 或 MQ 入口，业务逻辑一行都不用改。
典型代码长度：3~8 行
Service
业务层 —— 系统的大脑
业务规则、流程编排、事务边界、多表协作、调用外部服务，全部在这里。这是唯一应该写 if/else 业务分支的地方。分层架构的好坏，80% 取决于 Service 层的职责是否纯粹 —— 一旦出现「Controller 里偷偷写了业务」「Service 里直接返回 HTTP 响应对象」，就说明分层已经破了。
典型代码：事务注解在这一层；一个方法 = 一个完整的业务动作
DAO / Mapper
数据访问层 —— 只和存储对话
只负责「把对象变成 SQL，把结果变成对象」。不应该有业务逻辑（比如「如果库存小于 10 就走特殊逻辑」——这是业务，不属于 DAO）。
MyBatis Mapper / JPA Repository
Entity / DTO / VO
数据模型层 —— 三种对象各司其职
后端有几套「长得像但职责不同」的对象，前端转后端时经常混淆：
Entity 与数据库表一一对应，只在数据层内部流转；DTO 是接口的入参出参，是对外契约；VO 是返回给前端展示的视图对象。
为什么不全用 Entity？因为一旦用 Entity 直接对外，数据库加个字段就会泄漏到接口上，甚至把密码字段返回给前端 —— 这是真实发生过的安全事故。
边界转换通常由 MapStruct / 手写 Converter 完成
它解决什么问题

代码分层，本质是在回答：「当需求变化时，我要改几处？」

如果业务逻辑散落在 Controller 和 SQL 里，那么换一个入口（HTTP → MQ 消费者）、换一个存储（MySQL → 其他）、加一个复用场景（同一个业务给两个接口用），都要重写一遍。分层把「变化」隔离在单层内部。

前端视角

你其实一直在做同样的事：组件（Controller 层）→ hooks / store（Service 层）→ API 请求模块（DAO 层）。

「为什么组件里不直接写 fetch？」——和后端「为什么 Controller 里不直接写 SQL」是完全同一个问题，答案也一样：为了让逻辑可以被复用、被测试、被替换。

最容易踩的坑 ① Controller 变胖。这是新手代码最典型的特征：参数校验、业务判断、数据库操作、结果拼装全挤在一个方法里。
② Service 直接返回 Entity。导致「前端看到数据库结构」，字段增删都是破坏性变更。
③ 贫血模型。所有对象只有 getter/setter，所有逻辑写在 Service 里，导致 Service 无限膨胀。这是 Java 后端最普遍的设计问题，也是你从「能写」到「写得好」需要跨过的一道坎。
判断你是否掌握
  • 拿到一个需求，能先说出「它属于哪一层」，再动手写代码
  • 能解释 DTO / VO / Entity 三者的边界，以及为什么必须分开
  • 看得出「事务方法里调用了外部 HTTP 接口」这类隐藏的风险
3.8统一响应结构与全局异常处理L2 · 规范
角色接口对外的一致性契约。它让前端能写出一套通用的请求处理逻辑，也让后端能保证「任何异常都不会裸奔到用户面前」。
它解决什么问题

两个问题：

一是响应结构不统一。有的接口返回数组、有的返回对象、有的返回 null，前端要为每个接口写特殊判断。统一成 {code, message, data} 之后，前端的请求层可以统一处理错误提示与登录失效。

二是异常处理散落。如果每个方法都 try/catch，代码会充满重复逻辑，而且总有漏网之鱼会导致 500 页面或堆栈泄漏。全局异常处理器把所有异常收口到一处，统一转成规范响应、统一记录日志。

前端视角

这就是服务端的 ErrorBoundary。你在 React 里写一个顶层 ErrorBoundary，是为了让任何组件抛错都不会白屏 —— 全局异常处理器是同一思路的另一侧。

同时它对应你写的 axios 响应拦截器：那里你做「统一处理 401 跳登录、500 弹提示」，这里是它的服务端对偶。

在体系中的位置

它是 L2 与 L0 的接缝处：把 L0 的异常体系，翻译成 L2 的 HTTP 语义。它还是一个团队技术规范的核心载体 —— 错误码怎么定义、业务异常怎么分类、日志怎么记录，都在这里体现。

最容易踩的坑 ① 把系统异常当业务异常返回。数据库连接失败应该返回 500 并告警，而不是伪装成「系统繁忙，请稍后重试」的 200 —— 这会让监控完全失灵。
② 异常吞掉不记日志。统一处理了但没打日志，等于事故现场被清理干净了。
③ 把堆栈返回给前端。堆栈里有类名、SQL、甚至连接串，是最常见的信息泄漏方式之一。
判断你是否掌握
  • 能设计一套错误码体系（系统级 / 业务级 / 参数级），并说清编号规则
  • 能区分「该重试的错误」与「不该重试的错误」，并在响应结构中体现出来
  • 知道 4xx 与 5xx 的监控告警策略应该如何区分
3.9RESTful 接口设计与 API 契约L2 · 设计
角色接口的通用语言。好的设计让接口自解释、可预测；差的设计让每个接口都要靠文档理解。
它解决什么问题

接口一旦发布就很难改（前端、其它服务、第三方都在依赖），所以设计阶段的决策成本远低于后期修改。

RESTful 的核心主张：用名词表示资源、用 HTTP 方法表示动作、用状态码表示结果。它带来的实际好处是：URL 结构可预测、语义清晰、天然契合缓存与网关策略。

但要注意：REST 是风格不是标准。真实业务里常常会遇到「动作型接口」（如 /order/{id}/cancel）——强行套 REST 反而更差。务实比教条重要。

前端视角

你一直在消费接口，现在要生产接口。有一个视角切换很关键：现在你是那个被抱怨的人。

你会切身体会到：接口字段命名不一致、时间格式不统一、分页参数每次都不一样、null 和空数组混用 —— 这些你曾经吐槽过的事情，现在都由你决定了。「不要给下一个调用者添麻烦」是最好的设计准则。

在体系中的位置

它是接口层的方法论，横跨 L2（实现）与纵向能力（契约设计）。在微服务架构下（L4），接口契约的重要性进一步上升为「服务之间的法律」—— 契约不兼容的变更会直接打挂上游。

最容易踩的坑 ① 破坏性变更。删字段、改字段类型、改字段含义 —— 都会让老版本前端直接崩。正确做法是新增字段 + 双轨过渡 + 明确下线时间。
② 用业务字段兼作状态判断。导致状态机越来越乱，最终没人说得清一个订单到底有几种状态。
③ 接口没有版本管理意识。App 老版本还在线上跑，你没法和用户说「请升级」。
判断你是否掌握
  • 能为一组业务设计出可预测的 URL 结构，并说明理由
  • 能判断一次接口变更是否会打挂既有调用方，并给出兼容方案
  • 能设计出「前端一次请求拿到页面所需全部数据」的接口，而不是让前端串行请求五个接口
3.10跨域、编码与请求上下文L2 · 工程细节
角色三件「不起眼但天天遇到」的事。它们的共同特点是：错误现象诡异、根因却在很底层的地方。
① 跨域（CORS）

同源策略是浏览器的安全机制，服务端并不阻止请求。所以「跨域」这个问题，本质是「服务端没有告诉浏览器允许这个来源访问」。

你现在站到了解决方：配置允许的来源、方法、头，处理预检请求，并在需要携带 Cookie 时正确设置凭证相关头。一个高频坑是：网关和应用都配了跨域，导致响应头重复，浏览器反而报错。

② 字符编码

中文乱码是后端经典问题，根因通常是链路中某一环的编码不一致（容器、响应头、数据库连接、客户端）。

建议记住一个原则：全链路统一 UTF-8，并在入口处就固化下来，而不是出了问题再逐个环节去试。

③ 请求上下文（ThreadLocal）

一个非常有后端特色的工具。它解决的问题是：如何在不层层传参的前提下，让同一次请求的所有代码都能拿到公共信息（当前用户、traceId、租户 ID）。

它之所以能工作，正是因为「一次请求由一个线程处理」—— 这又一次说明并发与线程模型贯穿整个后端体系。

在体系中的位置：它是 L5 链路追踪与 L2 鉴权的公共基础设施。但也要注意它的经典陷阱：线程池复用线程会导致 ThreadLocal 数据串号，必须在使用后清理。

最容易踩的坑 ThreadLocal 未清理导致的数据串号是极高危的生产事故 —— Tomcat 线程复用时，下一个请求会读到上一个请求的用户信息，造成越权。这个坑几乎每个人都要踩一次，提前知道就能避开。
判断你是否掌握
  • 能解释「预检请求（OPTIONS）」什么时候会触发，以及如何减少它的开销
  • 知道 ThreadLocal 为什么在线程池场景下必须手动清理
  • 遇到乱码问题，能按链路顺序快速定位是哪一环的编码不一致

4数据层（L3）

这是后端所有复杂度的源头，也是前端转后端最需要补课的地方。 前端世界里数据是「随用随取」的；后端世界里，数据是有成本、有并发、有一致性约束的稀缺资源。 这一章的每一个知识点，都在回答同一个问题：如何保证数据正确，同时访问得足够快。

4.1JDBC 与数据库连接池L3 · 基础
角色Java 访问数据库的唯一标准通道，以及对这个通道的限流器。连接池是后端最容易被忽视、也最容易致命的资源瓶颈。
它解决什么问题

JDBC 是 Java 定义的一套数据库访问接口规范：建立连接、执行 SQL、处理结果集。所有 ORM 框架（MyBatis、JPA）本质上都是在它之上做的封装。

连接池解决的是性能与资源问题：建立一个数据库连接需要 TCP 握手 + 认证 + 会话初始化，成本极高。如果每次查询都新建连接，QPS 会上不去。连接池预先建好一批连接循环复用，把成本摊薄。

但连接池的另一个作用是限制：数据库能承受的连接数是有限的，池子大小就是在给应用「限流」。连接池打满，请求就会全部堵在「等连接」这一步 —— 这是服务雪崩最常见的直接原因之一。

前端视角

你熟悉浏览器对同一域名的并发连接数限制（通常是 6 个），超出的请求必须排队。连接池是同一件事的服务端版本，只是池子大小是你自己定的，而且后果严重得多。

前端请求排队只是慢；后端连接池打满意味着整个服务的线程都在挂起等待，最终连不查数据库的接口也一起响应不了。

在体系中的位置

它是 L3 的入口，也是 L0（线程）与 L3（数据库）的交汇点：连接池大小 × SQL 耗时 = 数据库并发能力上限，而应用线程数与连接池大小的配比关系，直接决定了服务在压力下的表现。

最容易踩的坑 ① 连接池设得太大。很多人以为连接池越大越好，实际上数据库端的处理能力才是瓶颈。池子过大反而会造成数据库线程争抢、性能下降。
② 连接泄漏。借了连接没归还（异常路径没释放），池子里的连接会逐渐耗尽，服务最终「静默死掉」。
③ 连接池等待时间设得过长。导致请求一直挂起而不快速失败 —— 快速失败通常比长时间等待对整体更有利。
判断你是否掌握
  • 能解释「为什么连接池不是越大越好」，以及如何估算合理大小
  • 知道连接池打满时，服务的表现是什么样（线程栈会显示什么）
  • 理解为什么慢 SQL 的影响远不止「这一个接口慢」，而是会波及全局
4.2ORM 思想：MyBatis vs JPAL3 · 实践选型
角色Java 对象与数据库表之间的翻译层。它决定了你写业务代码时，到底是在「写 SQL」还是在「操作对象」。
它解决什么问题

数据库里是「行和列」，Java 里是「对象和属性」。ORM 自动完成这个转换，省掉手写大量 JDBC 样板代码（取值、类型转换、资源关闭）。

两种主流路线，代表了两种哲学：

  • MyBatis（半自动）：SQL 由你写，框架只负责参数映射与结果映射。可控性极强，适合复杂查询、需要精细优化 SQL 的场景。国内互联网公司的主流选择。
  • JPA / Hibernate（全自动）：你操作对象，框架自动生成 SQL。开发效率高，简单 CRUD 几乎不用写代码，适合业务模型规整、查询简单的系统。海外与部分企业级系统更主流。
前端视角

类比：MyBatis 像手写 SQL 的查询构建器（可控、可优化），JPA 像「操作对象就自动同步到后端」的响应式状态库（省心，但生成的东西你看不见）。

你熟悉的类比还有 Prisma / TypeORM 之类 —— ORM 概念是跨语言的。

在体系中的位置

它坐在 4.1（连接池）与业务层之间，是 L3 的「用户界面」。同时它决定了你团队里「SQL 能力」的重要性：用 MyBatis 就意味着SQL 是核心生产力，每个人都要会写会优化。

最容易踩的坑 ① 用 JPA 就以为不用懂 SQL。这是最危险的认知 —— ORM 生成的 SQL 可能非常糟糕（N+1 查询是经典问题：查 100 条主记录，附带发出 100 条子查询）。
② 把 ORM 当成万能查询工具。复杂统计、多表聚合用 ORM 拼出来往往又难读又慢，正确做法是直接写 SQL。
③ 不了解「懒加载」的触发时机，导致 SQL 在预料之外的地方执行（比如序列化时），引发性能问题或连接已关闭异常。
判断你是否掌握
  • 能说清 MyBatis 与 JPA 各自的适用场景，并能在团队里给出有理由的选型建议
  • 知道什么是 N+1 查询问题，以及它的典型表现与解决思路
  • 能看懂 ORM 框架实际发出了哪些 SQL（这是排查性能问题的必备技能）
4.3关系型数据库与 MySQL 架构L3 · 核心
角色数据的最终归宿与唯一真相来源。整个后端系统里，只有这里的数据是不可丢的 —— 其它一切（缓存、索引、搜索结果）都是它的衍生物，随时可以重建。

图 4-1　一次 SQL 查询穿过应用与数据库的完整链路 —— 每一段都可能成为瓶颈

它解决什么问题

关系型数据库用「表 + 关系 + 事务」这套模型，把业务数据可靠地存下来，并提供强大的查询能力。它同时保证三件事：持久化（断电不丢，靠 WAL 日志）一致性（约束、事务）并发访问（锁与 MVCC）。

现代 MySQL 默认存储引擎 InnoDB 的几个核心机制：Buffer Pool（内存缓存数据页，命中就不用读磁盘）、Undo / Redo Log（实现回滚与崩溃恢复）、B+ 树索引（让查询不扫全表）。

前端视角

前端的「数据源」通常是后端接口，再往下你就不关心了。现在你要关心的是：这份数据在物理上如何组织、如何被找到、如何在崩溃后恢复。

一个心智转换：前端状态管理里，「状态是短暂的」；后端数据库里，「数据是永恒的，任何一次写入都会被历史记住」。设计后端功能时，先问「这个操作在数据层面意味着什么变更」，再问「接口怎么写」—— 顺序反了就会产生难维护的系统。

最容易踩的坑 把数据库当成「一个可以随便加字段的地方」。表结构一旦上线，改动成本远高于代码：已有数据要迁移、上下游要同步、回滚要谨慎。
另一个认知误区：认为「加了索引就一定快」—— 索引本身占空间、拖慢写入、且可能因为写法问题根本用不上。
判断你是否掌握
  • 能说出一条 SQL 从发出到返回结果，中间经过了哪些环节
  • 知道索引为什么能加速查询，代价是什么
  • 理解「为什么表数据量大了性能会下降」，以及几种应对思路
4.4索引：B+ 树与「为什么这句话用不上索引」L3 · 生死线
角色数据库性能的第一杠杆。一条 SQL 走不走索引，性能差异通常是「毫秒」与「几十秒」的差别 —— 也常常直接决定一个接口是否可用。
它解决什么问题

没有索引，查一条数据要扫描整张表（全表扫描）。索引把数据按某个字段预先排好序，让查找从 O(n) 降到 O(log n)。

MySQL 的 InnoDB 使用 B+ 树：所有数据存在叶子节点并连成链表，非叶子节点只存索引键。这个结构同时满足两个需求 —— 等值查询快（树上二分）与范围查询快（叶子链表顺序遍历）。这也解释了为什么「用范围查询会导致后面字段用不上索引」。

另一个关键概念：聚簇索引与回表。主键索引的叶子节点直接存放整行数据；普通索引的叶子节点只存主键值 —— 所以查非索引字段要「先查索引拿到主键、再回表查数据」，这就是「覆盖索引」优化的原理。

前端视角

类比：在 10 万条数据的数组里 find 一个对象是 O(n)；如果预先按 id 建好 Map，就是 O(1)。索引就是数据库层面的 Map / 有序表。

你在前端做列表优化时懂的取舍在这里同样成立：加缓存/索引能加速查询，但每次写入都要同步维护索引，写入变慢、空间变大。工程上永远没有只有好处没有代价的方案。

在体系中的位置

它是 L3 性能的核心，同时深刻影响你的表结构设计能力（建什么索引、联合索引字段顺序怎么定）。在 L4 层，它也是「为什么加了缓存还是慢」这类问题的答案来源之一。

最容易踩的坑（索引失效的常见原因）
  • 在索引列上做运算或函数处理，或做隐式类型转换（字符串列传数字）
  • 联合索引不满足「最左前缀」原则
  • 使用 !=、NOT IN、以 % 开头的模糊匹配
  • OR 连接了未建索引的字段
共同规律：只要数据库无法通过索引「定位到范围」，就只能全表扫。 理解这一点，就不用背规则。
判断你是否掌握
  • 能解释联合索引的最左前缀原则，并能为一个查询设计出合适的索引
  • 知道什么是「回表」与「覆盖索引」，能判断一条 SQL 是否需要回表
  • 能对一条慢查询做出初步判断：是索引问题、数据量问题还是 SQL 写法问题
  • 知道索引不是越多越好，能说出至少三个代价
4.5事务：ACID 与隔离级别L3 · 一致性基石
角色把「多个数据操作」捆绑成一个不可分割的整体。它是后端保证数据正确的核心武器，也是「事务边界画在哪里」这个设计问题的答案。
它解决什么问题

「从 A 账户转 100 元到 B 账户」包含两个操作。如果扣款成功、入账失败（服务崩了、网络断了），数据就错了。事务保证这类组合操作要么全部生效，要么全部不生效。

四个特性（ACID）：原子性（全成功或全回滚）、一致性（约束不被破坏）、隔离性（并发事务互不干扰）、持久性（提交后不丢）。

而「隔离性」是有代价的：隔离越强，并发性能越差。所以数据库提供了几档隔离级别让业务自己权衡。

前端视角

你在前端做「乐观更新」时，如果请求失败会回滚本地状态 —— 那是内存里的回滚，重渲染即可。数据库的回滚是物理撤销已写入的磁盘数据，靠 Undo Log 实现。这也是为什么后端对「操作顺序」和「失败处理」如此谨慎。

四种隔离级别与它们各自要防的问题
隔离级别脏读不可重复读幻读典型使用
读未提交可能可能可能几乎不用
读已提交不可能可能可能Oracle 默认；部分互联网业务主动选它换取并发
可重复读不可能不可能InnoDB 基本避免MySQL 默认，绝大多数项目的实际选择
串行化不可能不可能不可能几乎不用，性能极差

三个问题的通俗解释：脏读 = 读到了别人还没提交的数据；不可重复读 = 同一事务内两次读同一条数据结果不同；幻读 = 同一事务内两次查询「符合条件的行数」变了。

在体系中的位置

它是 L3 与 L2 的接缝点：在 Spring 里你通过 @Transactional 声明事务，但注解只是一个包装，背后的隔离级别、锁行为、回滚规则才是真正要理解的东西。

事务边界的设计是后端最重要的能力之一。边界太大 → 长事务持锁，并发骤降；边界太小 → 中间失败导致数据不一致；跨服务 → 变成分布式事务问题（见 5.7）。

最容易踩的坑 ① 长事务。在事务里做 HTTP 调用、发消息、读大文件 —— 锁被长时间持有，其他请求全部排队，一个慢下游能拖垮整个数据库。
② 事务不生效。由于 AOP 代理机制，同类内部调用、方法非 public、异常被自己 catch 掉，都会导致事务静默失效。
③ 回滚规则搞错。默认只对运行时异常回滚，受检异常不回滚 —— 于是「出错但没回滚」，数据就脏了。
判断你是否掌握
  • 能说清「脏读 / 不可重复读 / 幻读」三者的区别，并知道各自被哪种隔离级别解决
  • 能列出至少四种 @Transactional 失效的场景
  • 拿到一个业务动作，能判断事务边界应该画在哪里，为什么
  • 知道什么是长事务，以及它为什么是严重的性能问题
4.6锁与 MVCC：并发写入的协调机制L3 · 深水区
角色让「多个事务同时读写同一份数据」这件事变得可控。它是死锁、超时、并发性能问题的根因所在。
它解决什么问题

两个维度：

① 写与写的冲突 —— 靠锁。InnoDB 提供行级锁（共享锁 S / 排他锁 X）、间隙锁（防止范围内插入新数据，用于解决幻读）、表级意向锁等。锁的粒度决定了并发度：锁一行并发高，锁一张表并发低。

② 读与写的冲突 —— 靠 MVCC（多版本并发控制）。InnoDB 为每行数据保存多个版本，读操作读取符合自己事务可见性的那个快照版本，因此普通查询不加锁、不阻塞写入。这正是「可重复读」能实现的原理。

前端视角

前端几乎没有这个概念，因为浏览器不会有两个线程同时改一个变量。但在 React 的并发特性（Concurrent Rendering）里，你见过类似思想：不同优先级的状态更新基于「快照」进行，而不是直接互相覆盖。MVCC 就是这个思路在数据库层面的规模化实现。

在体系中的位置

它是 4.5（事务）的实现基础，也是 L4（分布式锁）的思想源头 —— 分布式锁本质上就是「把数据库的互斥能力搬到跨机器场景」。理解单机锁，才能理解分布式锁解决了什么、又引入了什么新问题。

最容易踩的坑 ① 死锁。两个事务以相反顺序锁住两行数据，互相等待。数据库会自动检测并回滚其中一个，但业务侧必须能正确处理这种「被强制回滚」，通常需要重试。
② 以为「加了索引就用行锁」。实际上如果更新条件没走索引，InnoDB 会锁住扫描过的所有行，甚至升级为锁表 —— 这是线上真实事故的常见原因。
③ 用查询结果做判断再更新（先查后改）。在并发下必然出问题，正确做法是用一条带条件的更新语句（把判断写进 WHERE）或加锁。
判断你是否掌握
  • 能解释 MVCC 如何让「读不阻塞写、写不阻塞读」
  • 知道「更新条件没走索引」会带来什么锁范围，以及为什么危险
  • 能识别出「先查再改」的并发漏洞，并给出正确写法
  • 知道出现死锁后，业务代码应该怎么做（不是不管，也不是死循环重试）
4.7慢 SQL 与执行计划：定位性能问题的方法L3 · 诊断能力
角色后端最实用的一项「体检技能」。线上接口变慢时，80% 的原因最终都能追到某条 SQL 上。
它解决什么问题

问题不是「怎么优化」，而是「怎么知道该优化哪里」。后端性能排查有一套标准的观察链路：

  • 慢查询日志：数据库把超过阈值的 SQL 记下来 —— 问题清单的来源
  • 执行计划：让数据库告诉你它「打算怎么执行这条 SQL」—— 是否走索引、扫描了多少行、用了什么连接方式
  • 应用侧耗时埋点：区分慢在数据库、慢在外部调用，还是慢在自身逻辑

关键认知：优化必须基于测量，不能基于猜测。「我觉得这里慢」是最危险的工作方式。

前端视角

你在前端做性能优化时的流程是完全一样的：先打开 Performance 面板测量 → 找到真正的瓶颈帧 → 再动手优化 → 再测一次验证。

后端没有这样的可视化面板，替代品就是慢查询日志 + 执行计划 + 链路追踪。方法论一模一样，只是工具不同。

在体系中的位置

它是 L3 与 L5 的结合点：慢 SQL 日志是「可观测性」体系中的重要信号源，而排查动作则依赖 L3 的索引/事务/锁知识。它也是后端工程师日常工作中最高频、最直接产生价值的能力之一。

最容易踩的坑 ① 只看单条 SQL 不看整体。一个接口可能发出 50 条 SQL，每条都不慢，加起来就超时了 —— 这是 N+1 问题的典型特征。
② 盲目加索引。没搞清楚慢的原因就加索引，可能解决不了问题，还会拖慢写入。
③ 环境差异。测试环境数据量小，全表扫描也很快；上线后数据量涨上来，同一句 SQL 直接超时。测试环境的数据量与分布必须尽量接近生产。
判断你是否掌握
  • 能说清一次完整的性能排查流程（从现象到根因）
  • 看得懂执行计划中的关键信息，并能判断索引是否被正确使用
  • 知道「接口变慢」的几种典型归因，以及如何用数据区分它们
4.8读写分离、分库分表与数据量增长L3 · 规模问题
角色当单库撑不住时的手段。它的核心原则是：先优化，后拆分 —— 拆分是最后的选择，不是第一反应。
它解决什么问题

单机数据库有两个天花板：读压力和数据量。对应两类手段：

读写分离：一主多从，主库负责写、从库负责读。缓解读压力，代价是主从延迟 —— 刚写完立刻读从库可能读不到。

分库分表：把大表按规则拆到多个库/表。解决单表数据量过大的问题，代价是引入巨大复杂度：跨库 JOIN 没了、分布式事务来了、全局 ID 要自己生成、分页查询变复杂、扩容要重新分配数据。

在拆分之前，还有大量更简单的优化空间：加索引、优化 SQL、加缓存、归档冷数据、垂直拆分（把大字段/不常用字段拆出去）。

前端视角

类比：前端处理超大列表时，不会一上来就虚拟滚动 + 分片渲染，而是先看能不能分页、懒加载、减少渲染量。分库分表就是后端版的「终极方案」——先穷尽简单手段。

在体系中的位置

它是 L3 向上通往 L4 的桥梁：一旦拆库，你立刻需要分布式 ID、分布式事务、跨库查询、数据同步 等 L4 的整套能力。 所以它是一种「不可逆的复杂度升级」—— 这也是为什么它必须排在最后考虑。

最容易踩的坑 过早拆分。很多系统在数据量还很小的时候就被拆成 8 个库，结果开发效率断崖下降，而性能瓶颈根本不在数据库上（可能在慢接口、在没优化好的 SQL、在缺失的缓存）。
正确顺序永远是：先测量 → 优化 SQL 与索引 → 加缓存 → 归档冷数据 → 再考虑读写分离 → 最后才是分库分表。
判断你是否掌握
  • 能按优先级列出一个「数据库撑不住时的应对清单」，并说清每一步的适用条件
  • 能说清读写分离带来的主从延迟问题，以及业务上如何处理它
  • 知道分库分表后会新增哪些技术难题
4.9NoSQL 家族的定位：不是替代，是分工L3 · 视野
角色理解「不同数据用不同存储」的判断力。核心不是记住有哪些数据库，而是知道什么问题该用什么类型的存储。
类型代表它擅长什么 / 在体系中的位置
键值存储Redis内存级读写，拿来做缓存、分布式锁、计数器、排行榜。后端性能优化的第一手段（详见 5.1）。
文档存储MongoDB结构灵活、字段不固定，适合日志、内容、事件类数据。省去了频繁改表结构的心智负担，代价是事务与关联查询能力弱。
搜索引擎Elasticsearch全文检索、模糊匹配、多条件聚合分析。典型用法：商品搜索、日志检索。本质是「从数据库同步一份专门用于搜索的副本」。
列式存储ClickHouse / HBase海量数据的聚合分析（OLAP）。与 MySQL 的「单行读写」相反，它擅长「扫描千万行做统计」，常用于报表与数据看板。
图数据库Neo4j关系网络类数据（社交关系、知识图谱），擅长多跳关系查询。业务中使用面较窄。
最重要的一条认知

关系型数据库是「唯一的真相来源」，其它存储几乎都是它的衍生物：Redis 缓存从它同步、ES 索引从它同步、数仓从它同步。 数据先落 MySQL，再同步到别处 —— 这条心智非常关键，它解释了为什么缓存一致性问题总是存在，也解释了为什么「数据丢了要能从库里重建」是基本要求。

最容易踩的坑 把 NoSQL 当成「更好的数据库」用来存核心业务数据，结果发现需要事务、需要关联、需要可靠持久化时，能力都缺。选型的正确姿势是：先明确要解决的具体问题，再选工具。
判断你是否掌握
  • 拿到一个需求，能判断「用 MySQL 还是 Redis 还是 ES」，并说出理由
  • 理解为什么缓存与搜索结果都只是「副本」，可以随时重建
  • 知道 OLTP 与 OLAP 的本质差异

5中间件与分布式层（L4）

前四层解决的是「一个程序怎么正确工作」，这一层解决的是「一个系统怎么在压力与故障下继续工作」。 它是前端知识迁移最少、认知增量最大的一段，也是后端薪资的主要增长区间。 但请记住一个前提：这一层的每一项技术都在引入复杂度，只有在问题真实存在时才值得引入。

5.1缓存（Redis）：性能的第一杠杆L4 · 高频
角色用内存速度换取数据库压力。它是性价比最高的性能优化手段，也是「一致性难题」的引入者。
它解决什么问题

数据库的读写速度受限于磁盘与锁，而内存快了几个数量级。缓存把「热点数据」放在内存里，通常能挡掉 90% 以上的读请求。

但引入缓存后，你多了一个必须回答的问题：数据变了，缓存怎么办？这就是「缓存一致性」问题 —— 它没有完美解，只有「可接受的方案 + 明确的不一致窗口」。

常见策略包括：更新数据库后删除缓存（主流做法）、设置过期时间兜底、延迟双删、订阅数据库变更日志（binlog）异步刷新。

前端视角

你把 localStorage 或 SWR / React Query 的缓存当性能优化手段 —— 这个直觉是对的，后端同理。

但差异在于：前端缓存的失效范围是你自己一个用户，后端缓存的失效范围是所有用户共享的一份数据。所以「谁的缓存脏了」在后端是全局问题。你在 React Query 里写的 invalidateQueries 是本地失效，后端需要处理的是跨进程的、分布式的失效。

缓存的三个经典问题（面试必问，生产必遇）
问题现象本质与应对思路
缓存穿透查询一个根本不存在的数据，每次都绕过缓存打到数据库；恶意攻击可用此方式打垮数据库本质是「缓存里永远没有它」。思路：缓存空值 + 短期过期、参数合法性校验、布隆过滤器提前拦截。
缓存击穿某个热点 key 突然过期，瞬间大量并发请求同时打到数据库本质是「一个热 key 的并发重建」。思路：互斥锁保证只有一个请求去重建、热点数据逻辑过期永不过期。
缓存雪崩大量 key 同时过期，或缓存服务整体不可用，流量全部压向数据库，数据库瞬间被打垮本质是「大批量失效」或「缓存层整体故障」。思路：过期时间加随机值打散、多级缓存、缓存服务高可用、数据库限流兜底。
在体系中的位置

它站在 L3 前面，是保护数据库的第一道防线。同时它自身也演进为 L4 的多种能力：分布式锁（5.8）、计数器与限流、会话共享、消息队列（Redis 也能做简易 MQ）。

最容易踩的坑 ① 把缓存当数据库用。缓存是副本，随时可能丢失（重启、淘汰、故障）。核心数据必须能从未命中的存储重新加载。
② 大 key 与热 key。一个 key 存几 MB 数据，或某个 key 被百万 QPS 访问，都会造成单节点压力倾斜甚至阻塞。
③ 不考虑缓存与数据库的一致性影响面。在交易类场景中，「读到旧数据」可能是业务不可接受的结果 —— 这时正确的选择可能是「不缓存关键数据」。
判断你是否掌握
  • 能画出「读请求 + 写请求」两条链路上缓存的完整处理流程
  • 能说清穿透 / 击穿 / 雪崩三者的区别，以及各自的应对手段
  • 能回答「缓存和数据库怎么保证一致」，并说清什么场景下允许不一致
  • 知道为什么缓存服务本身也需要高可用设计
5.2消息队列（MQ）：解耦、异步、削峰L4 · 架构级
角色系统之间的异步缓冲带。它把「必须同时完成的事」变成「可以先后完成的事」，是分布式架构里最重要的解耦手段。
它解决什么问题

三个核心价值：

① 解耦：下单后要发短信、加积分、通知仓配。如果同步串行调用，任何一个下游故障都会导致下单失败。改成发消息后，下单只依赖「消息发出」，下游各自消费、互不影响。

② 削峰：秒杀时瞬时流量可能是平时的百倍。消息队列把请求先攒起来，下游按自己的能力匀速消费 —— 用「延迟」换「不崩溃」。

③ 异步：把不必立刻完成的事情挪出主链路，直接降低接口响应时间。

主流选择：Kafka（高吞吐、日志与流处理）、RocketMQ（阿里系、事务消息支持好）、RabbitMQ（灵活路由、中小规模）。

前端视角

近似前端的事件总线 / EventEmitter / 消息订阅机制 —— 发布者不用知道谁在听，这是你非常熟悉的解耦思路。

但后端版本多了几个硬约束：消息会丢、会重复、会乱序、会积压。所以后端用 MQ 时必须回答「消息丢了怎么办」「消费者重复消费怎么办」「消息堆积了怎么告警」。前端事件总线是内存级的、进程内的、可以不管这些；MQ 是跨进程跨机器的，必须管。

在体系中的位置

它是 L4 的中枢：向上支撑微服务间的解耦通信，向下依赖 L3（消费消息往往要写数据库，涉及幂等与事务），同时它是 L5 监控的重点对象（积压量是关键告警指标）。

最容易踩的坑 ① 消息重复消费。MQ 通常保证「至少一次投递」，所以消费者必须做幂等处理（同一业务单号处理多次与一次效果相同）。这不是可选项，是必须项。
② 消息丢失。生产端发送失败、Broker 未持久化、消费端处理完但没提交位点 —— 三个环节都可能丢，需要分别设计。
③ 消息积压。消费能力跟不上生产速度，积压越来越多，最终导致磁盘写满、消息过期丢失。必须监控积压量。
④ 用 MQ 做同步调用。「发消息然后等结果」是把异步做成了更差的同步，正确做法是回调或轮询查询。
判断你是否掌握
  • 能说清「为什么用 MQ」的三个理由，并能为一个具体业务判断该不该用
  • 理解「至少一次投递」意味着什么，以及为什么必须做幂等
  • 知道消息从生产到消费可能丢失的所有环节
  • 能说出使用 MQ 后系统新增了哪些运维负担
5.3RPC：服务之间怎么互相调用L4 · 通信
角色让「调用远程服务」这件事看起来像调用本地方法。它是微服务拆分的通信基础。
它解决什么问题

服务拆分后，服务 A 需要数据在服务 B 里，必须跨网络调用。直接写 HTTP 请求是可行的，但很啰嗦：拼 URL、序列化、处理超时、重试、负载均衡，每个调用点都要写一遍。

RPC 框架把这层复杂度封装掉：你只定义接口，框架自动生成客户端代理，负责网络通信、序列化、服务发现、负载均衡、超时重试、熔断。主流有 Dubbo（Java 生态、国内主流）与 gRPC（跨语言、高性能，基于 HTTP/2）。

前端视角

你熟悉「远程调用看起来像本地调用」的感觉 —— 前端的 API 封装就是这样：userApi.getById(id) 明明是一次网络请求，但写起来像本地函数。

RPC 是这个思路的双向版本：不仅是调用端封装得像本地方法，服务提供者也只是「实现一个 Java 接口」，不关心网络细节。相当于前端后端共同遵守一份接口定义，各自生成代码。

在体系中的位置

它是 L4 的通信骨架，与 5.4（服务发现）、5.6（容错）共同构成微服务基础设施。 一个关键判断：RPC 适合内部服务间的高频调用；对外的开放接口仍然用 HTTP/REST —— 因为外部调用方无法共享你的接口定义与序列化协议。

最容易踩的坑 ① 把 RPC 当本地调用，忽略网络的存在。本地方法调用不会失败、不会超时、延迟以纳秒计；RPC 会失败、会超时、会返回不一致的结果。每一个 RPC 调用点都必须考虑「失败了怎么办」。
② 循环调用。A 调 B、B 调 C、C 调 A，一个请求打三圈，放大压力并可能导致死锁式等待。
③ 接口粒度过细。拆成十几个细粒度 RPC 调用，网络往返耗时的总和远超业务处理本身。
判断你是否掌握
  • 能说清 RPC 与 HTTP/REST 的适用场景差异
  • 知道「本地方法调用」和「远程调用」在失败模型上的本质差异
  • 能识别出一次业务操作中隐藏的调用链深度与串行次数
5.4注册中心与配置中心L4 · 基础设施
角色解决「我怎么知道对方在哪」和「我怎么改配置不用重启」两个分布式基础问题。
它解决什么问题

注册中心（Nacos / Eureka / Consul）：服务实例的地址是动态的 —— 扩容时新增实例、故障时实例消失、容器重建后 IP 变化。硬编码 IP 完全不可行。注册中心充当「通讯录」：服务启动时登记自己，调用方从这里拿地址列表并感知变化。

配置中心（Nacos / Apollo）：配置分散在几十个实例上时，改一个参数要重新打包发布，代价极高。配置中心把配置外置并支持动态推送 —— 改完立即生效，不用重启。

前端视角

注册中心 ≈ 前端的服务发现 / 动态 endpoint 管理；配置中心 ≈ 远程配置（Remote Config），类似你在 App 里做的远程开关、灰度配置下发。

你熟悉「功能开关」这个手段 —— 配置中心就是后端版的开关中心，而且它承载着更重的责任：一个错误的配置推送可能导致全站故障。所以它通常需要灰度、审批、版本回滚。

在体系中的位置

它是 L4 的寻址与配置基座，几乎所有其它 L4 组件都依赖它（网关要拿地址列表做路由，RPC 要拿地址列表做负载均衡）。它自身的高可用极其关键 —— 注册中心挂了，整个服务调用的寻址能力就瘫痪了。

最容易踩的坑 ① 健康检查与摘除延迟。实例已经不可用但注册中心还没摘除，流量仍会打过去，请求持续失败。这个时间窗口是分布式系统故障扩散的重要原因。
② 配置推送的爆炸半径。一个全局配置的误改可以让全部实例同时进入异常状态 —— 比单个服务故障严重得多。
判断你是否掌握
  • 能解释「为什么需要服务注册与发现」，以及它不存在时的替代方案有多糟
  • 知道服务实例的下线过程（优雅停机）需要注意什么
  • 理解配置中心为什么需要灰度与回滚能力
5.5API 网关：流量的统一入口L4 · 入口
角色所有流量的总闸门。把「每个服务都要做的事」上提到一处集中完成。
它解决什么问题

如果每个微服务各自实现鉴权、限流、日志、跨域、灰度，会带来重复实现、标准不一、无法统一管控三个问题。网关把这些横切能力集中起来：

  • 路由转发：按路径/域名把请求分发给对应服务
  • 统一鉴权：在业务代码之前完成身份校验，业务服务只关心「谁在调用」
  • 限流与防护：抵御恶意流量、保护后端
  • 协议转换、灰度发布、请求日志

常见实现：Spring Cloud Gateway、Kong、Nginx + Lua、云厂商网关。

前端视角

你在前端开发时配过的 Vite Proxy / Nginx 反向代理，就是网关的简化形态。BFF（Backend For Frontend）更进一步 —— 专门为某一端前端定制聚合接口的网关。

你会很熟悉「一个入口，后面多个服务」这个模式：它对应前端微前端架构里的「主应用 + 子应用」的入口层。

在体系中的位置

它位于整个系统的最外层，是 L4 的守门人，也是 L5 观测数据的采集点（QPS、响应时间、错误率都在这里统一统计）。它是安全与稳定性的第一道，也是最后一道防线。

最容易踩的坑 ① 网关成为单点。所有流量都经过它，它挂了全都挂了。必须做高可用与健康检查。
② 在网关里写业务逻辑。网关应该只做「通用的、与业务无关的」事。一旦开始写「如果是 VIP 用户就路由到 X」，就变成了难以维护的隐式业务层。
③ 超时与重试配置层层叠加。网关重试 3 次、RPC 重试 3 次、数据库重试 3 次 —— 请求量被放大 27 倍，故障时反而造成雪崩。
判断你是否掌握
  • 能列出网关承担的职责，并说明为什么这些事不该放在业务服务里
  • 知道「重试放大」问题，以及如何避免
  • 能解释 BFF 与网关的区别与适用场景
5.6限流、熔断、降级：让系统在故障中活着L4 · 稳定性
角色系统的自我保全机制。目标不是「不出故障」，而是「局部故障不扩散成整体故障」。
它解决什么问题

分布式的现实是：任何一个下游都可能变慢或挂掉。而最危险的不是故障本身，是故障的连锁反应。

典型雪崩链条：下游 B 变慢 → 服务 A 的线程都被阻塞在等 B → A 的线程池耗尽 → A 也无法响应 → 上游 C 也被拖垮 → 全站不可用。一个非核心服务的问题，最终导致整个系统崩溃。

三件武器分别针对不同环节：

  • 限流：控制入口流量，超出部分直接拒绝。保护自己不被压垮。
  • 熔断：下游错误率超阈值时，直接「断开」对它的调用，快速失败，不再浪费线程等待。给下游恢复的时间。
  • 降级：非核心功能不可用时返回兜底结果（缓存值、默认推荐、友好提示），保证核心链路可用。
前端视角

你熟悉「功能降级」这个产品思路：服务端接口挂了，前端展示兜底内容而不是白屏 —— 这是同一个哲学，只是后端把它系统化成了基础设施。

前端还有一个更贴切的类比：React 的 Suspense + ErrorBoundary 把故障限制在局部，而不是让整页崩掉。熔断与降级做的就是这件事，只不过边界是「服务」而不是「组件」。

在体系中的位置

它是 L4 的安全气囊，通常实现为 RPC / HTTP 客户端的拦截层（如 Sentinel、Resilience4j、Hystrix）。它也是 L5 告警体系的触发源 —— 熔断被打开本身就是一条重要告警。

最容易踩的坑 ① 资源隔离没做。「给下游 B 的调用」和「给下游 C 的调用」如果没有使用独立的线程池 / 连接池，B 的慢会占满所有资源，C 也跟着不可用。
② 超时时间设置不合理。层层调用的超时应该逐层递减（上游超时必须短于下游），否则上游已经超时返回，下游还在继续执行，白白浪费资源。
③ 降级逻辑本身也会失败。降级返回缓存值时，如果缓存也挂了，整个兜底就失效。兜底方案必须比被兜底的方案更简单可靠。
判断你是否掌握
  • 能画出一条完整的雪崩链路，并指出每个环节可以用什么手段阻断
  • 能说清限流与熔断的区别（一个是入口控制，一个是出口控制）
  • 知道「快速失败」为什么通常优于「长时间等待」
  • 能为一个业务系统划分核心链路与非核心功能，并给出降级方案
5.7分布式事务：跨服务的一致性问题L4 · 难题
角色解决「一次业务操作跨越多个服务 / 多个数据源」时的一致性问题。它是分布式系统里最难的题之一，也是最容易被过度设计的领域。
它解决什么问题

下单场景：订单库写一条订单 → 库存服务扣库存 → 积分服务加积分。这三个操作在不同的库、不同的服务里，本地事务管不了它们。中间任何一步失败，怎么保证数据不脏？

主流思路分三个层次：

  • 规避：通过业务设计让「需要的事务」不发生 —— 这是最优解。比如把相关数据放在同一个库里。
  • 最终一致（主流）：允许短暂不一致，通过重试、补偿、对账达到最终正确。常用方案：本地消息表、事务消息、Saga、TCC。
  • 强一致：如两阶段提交（2PC），代价是性能差、可用性差，生产环境很少用于高并发场景。
前端视角

类比前端多端同步场景：本地乐观更新 → 后台请求 → 失败回滚或标记待同步 → 定时任务补偿对齐。后端分布式事务的核心思想就是这个思路的企业级版本：接受中间态，靠补偿与对账收敛到一致。

关键认知转变：「一致」不是瞬时的，而是「最终会一致」。前端做乐观 UI 时你已经接受了这个前提。

在体系中的位置

它是 L4 中「把 L3 的事务能力推广到跨服务场景」的产物，通常与 5.2（MQ 事务消息）紧密配合。 它也是「分布式系统复杂度爆炸」最典型的体现 —— 一个本地事务只需要一行注解，分布式事务需要一整套方案与运维。

最容易踩的坑 ① 为了技术而引入。业务上其实可以容忍短暂不一致（用户晚几秒看到积分到账完全没问题），却硬上强一致方案，白白增加系统复杂度与故障率。
② 忽略幂等与重试。补偿和重试是分布式事务的必备机制，而它们要求所有参与者都支持幂等 —— 这是前提不是附加项。
③ 没有对账兜底。所有自动补偿机制都可能失效，必须有一条「定时对账、发现并修复不一致」的最终防线。
判断你是否掌握
  • 能判断一个跨服务业务「是否真的需要分布式事务」，并说出业务上可接受的方案
  • 理解「最终一致性」的含义，以及它为什么在实践中比强一致更常用
  • 知道补偿机制必须搭配什么才真正可靠（幂等 + 重试 + 对账）
5.8分布式锁：跨进程的互斥L4 · 经典
角色把一个进程内的互斥能力，扩展到多台机器之间。它是「单机思维」到「分布式思维」最简单直观的一次跨越。
它解决什么问题

当服务部署了 8 个实例，本地锁完全失效 —— 每个实例各锁各的，根本拦不住跨实例的并发。

分布式锁需要一个所有实例都能访问的「公共裁判」：Redis（性能好，最常用）或 ZooKeeper / etcd（一致性更强）。核心原理是「在共享存储上做一次原子的占位操作」，占位成功者获得锁。

难点全部在于「异常情况」：持锁者崩溃了怎么办（需要过期时间）、业务执行时间超过了锁过期时间怎么办（需要续期/watchdog）、释放锁时如何确保只释放自己的锁（需要唯一标识校验）。

前端视角

前端没有这个概念，但有一个很接近的场景：多标签页 / 多设备之间如何避免重复提交。

你可能会用 localStorage 打个标记 —— 这就是一个「共享存储上的占位」。分布式锁的复杂度全部来自「这个标记可能因为持有者崩溃而永远留在那里」，所以必须加上过期与续期机制。

在体系中的位置

它是 4.6（数据库锁）在分布式场景的镜像，也是 L4 中「一致性协调」能力的基础。 但要建立一条重要的判断：能用数据库唯一约束、乐观锁、状态机解决的并发问题，就不要用分布式锁 —— 锁是最后的兜底手段，不是首选方案。

最容易踩的坑 ① 锁过期时间小于业务执行时间。锁提前释放，第二个线程进来，两个线程同时执行 —— 互斥彻底失效，且这种 bug 极难复现。
② 释放锁不加校验。线程 A 超时释放了锁，线程 B 刚拿到锁，A 的 finally 又把 B 的锁删了。
③ 锁粒度太大。用一个全局锁保护所有操作，系统彻底串行化，性能毁于一旦。锁的范围应该是「业务主键」级别。
④ 把锁当作万能方案。过度使用分布式锁会导致系统变成一个串行系统，丧失分布式的全部意义。
判断你是否掌握
  • 能说清「为什么本地锁在分布式下失效」
  • 能列出分布式锁必须处理的所有异常场景（崩溃、超时、误删、网络分区）
  • 遇到一个并发问题，能判断「该用唯一索引 / 乐观锁 / 状态机 / 分布式锁」中的哪一个
5.9理论基础：CAP、分布式 ID 与一致性哈希L4 · 内功
角色分布式系统的世界观。它不是某个工具，而是你在做架构决策时的底层判断依据。
CAP 定理：分布式系统的三选二

一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance）三者不可兼得。 关键认知：网络分区（P）在分布式系统中是必然发生的，所以真正的选择只在 C 和 A 之间。

  • 选 CP（保一致，牺牲可用）：网络分区时宁可拒绝服务也不返回可能错误的数据。典型：ZooKeeper、etcd、注册中心。
  • 选 AP（保可用，牺牲强一致）：网络分区时继续提供服务，允许返回旧数据，事后收敛。典型：Eureka、Cassandra、DNS。

实践中的延伸是 BASE 理论：Basically Available（基本可用）、Soft state（软状态）、Eventually consistent（最终一致）。 它承认「强一致代价太高」，转而追求最终一致 —— 这也是今天绝大多数互联网系统的实际选择，5.7 的分布式事务方案正是 BASE 的落地。

分布式 ID

问题：分库分表后，自增主键不再唯一（每个库都从 1 开始）。同时，自增 ID 还会泄露业务量、容易被遍历。

方案：UUID（简单但无序，影响索引性能）→ 数据库号段模式（批量取号，性能好）→ 雪花算法（时间戳 + 机器 ID + 序列号，趋势递增且高性能，最常用）→ 各中间件自带的全局 ID 服务。

在体系中的位置：它是分库分表（4.8）的必备配套，也是「顺序写入」这一数据库性能优化原则的保障 —— 主键无序会导致索引页频繁分裂，写入性能大幅下降。

一致性哈希

问题：缓存分片时，如果用 hash(key) % 节点数，一旦增删节点，几乎所有 key 的归属都会改变 —— 缓存集体失效，数据库瞬间被打垮。

方案：把节点和 key 都映射到一个环上，key 顺时针归属于第一个节点。这样增删一个节点只影响环上的相邻区间（约 1/N 的数据），其余不动。虚拟节点技术进一步解决「节点分布不均」的问题。

在体系中的位置：它是 Redis Cluster、分库分表路由、负载均衡的共同理论基础。它解决的是「扩容时如何只迁移最少的数据」这个分布式核心命题。

最容易踩的坑 把 CAP 当成「选两个」的口号。真实系统不是纯 CP 或纯 AP，而是在不同数据、不同操作上做不同的取舍：订单金额必须强一致，商品浏览量可以最终一致。能按业务做分级取舍，才是真正理解 CAP。
判断你是否掌握
  • 能解释为什么「分区容错」通常是被动接受的而非主动选择的
  • 能判断一个业务场景该倾向 CP 还是 AP，并说出理由
  • 知道主键无序为什么会拖慢数据库写入
  • 能说清一致性哈希解决的具体问题是什么
5.10微服务 vs 单体：什么时候该拆L4 · 架构判断纵向
角色这一节不是讲一个技术，而是讲一个判断。它是 L4 全部知识的收敛点：你知道的所有分布式技术，都是为拆服务付出的代价。

图 5-1　单体与微服务的对称结构 —— 注意右侧多出来的整块基础设施，那都是「拆」的代价

拆分的判断标准

该考虑拆分的信号：不同模块的流量特征差异巨大（某些模块需要单独扩容）；不同模块的迭代节奏差异巨大（互相阻塞发布）；某个模块的故障会拖垮全局且它是非核心的；团队规模大到单仓库协作已产生明显冲突。

不该拆的信号：团队不到十个人；业务还在快速试错阶段、领域边界还没稳定；性能瓶颈其实是 SQL 或缺少缓存；「因为大厂这么做」。

一条务实的中间路线：模块化单体。在一个应用内通过清晰的模块边界与包结构把耦合控制住，等到真的需要时再拆出去。先有清晰的边界，才有拆分的基础。

最容易踩的坑 「分布式单体」：拆成了十几个服务，但它们之间调用关系混乱、共享数据库、必须同时发布——既丢掉了单体的简单，又承担了分布式的全部代价。这是拆分失败最典型的形态。
另一个更根本的坑：在团队还没建立好工程纪律（自动化测试、监控告警、CI/CD）之前就上微服务 —— 微服务会放大一切已有的工程问题。
判断你是否掌握
  • 能列出一个系统该拆与不该拆的具体判断依据（而不是「大厂都拆」）
  • 能说清微服务带来的每一项新增成本（通信、事务、运维、排查）
  • 知道什么是「分布式单体」，以及它为什么会发生

6部署与运维层（L5）

写代码只占后端工作的三分之一，剩下三分之二是让它在生产环境稳定运行。 这一层的关键转变是：生产环境会暴露一切你在本地看不到的问题 —— 内存泄漏、连接池打满、时钟漂移、依赖的服务挂掉、磁盘写满。 有前端部署经验的你，在这一层反而有优势：你对 CI/CD 和「构建产物不可信」这类概念已经很熟。

6.1Linux 与服务器基本功L5 · 必备
角色后端服务的栖息地。绝大多数 Java 服务跑在 Linux 上，所以「能不能登录上去看到问题」是后端的基本生存技能。
你需要的不是「会 Linux」，而是「会诊断」

不需要背命令手册，需要的是一套按现象排查的动作序列：

  • 服务变慢 / 无响应：看 CPU、内存、线程栈、网络连接
  • 服务挂了：看进程还在不在、有没有 OOM 记录、日志最后几行是什么
  • 磁盘告警：看是哪个目录在涨、是不是日志没轮转
  • 连不上数据库：看网络是否通、端口是否可达、防火墙规则

常用工具围绕这些场景：进程与资源查看、连接与端口查看、日志检索、文件与磁盘管理。

前端视角

前端开发者通常对服务器是「黑盒」：git push 之后 Vercel 自动构建上线，你从不登录服务器。

后端的现实是：你必须能登上那台机器。因为最高效的排查方式往往就是「上机器看一眼」。这不是倒退，是因为后端问题的现场信息（线程栈、内存快照、连接数）很难通过日志完整传递。

在体系中的位置

它是 L5 的操作面。你不会 Linux，就无法执行容器排查、无法看系统日志、无法分析 JVM 的运行状态 —— 前面的所有知识都会变成纸上谈兵。

最容易踩的坑 直接在生产服务器上改配置、改代码、重启服务，且不做记录。正确做法是：所有变更走流程、可追溯、可回滚。「临时改一下」是技术债和事故的共同源头。
判断你是否掌握
  • 听到「线上服务无响应」，能立刻说出一套排查动作（而不只是「去看看日志」）
  • 知道如何判断一个进程是 CPU 密集还是 IO 密集问题
  • 能解释为什么生产环境的时钟同步很重要
6.2Docker：把环境和代码一起打包L5 · 交付
角色解决「在我机器上是好的」。它把运行环境本身变成了可以版本化、可以复制的产物。
它解决什么问题

Java 应用的运行依赖 JDK 版本、系统库、时区、字符编码、字体、环境变量 —— 任何一项不一致都可能导致「本地正常、线上异常」。

Docker 把「应用 + 依赖 + 环境」一起打成镜像，在任何装了容器运行时的地方跑出来的行为完全一致。同时它带来另外三个好处：启动快（秒级）、资源占用低（相比虚拟机，共享内核）、天然契合弹性伸缩（要扩容就多跑几个容器）。

镜像还引入了分层复用：基础层（JDK）被所有服务共享，只有业务代码那层不同，因此构建和分发都更高效。

前端视角

你的构建产物（静态文件）本身是「无环境依赖」的，所以你对环境问题不敏感。后端产物是有依赖的二进制 —— 这就是为什么后端必须发明 Docker 这类工具。

一个你会很有共鸣的点：前端经历过「Node 版本不一致导致构建失败」「node_modules 删了重装就好」这类问题，Docker 就是这类问题的终极解法。

在体系中的位置

它是 L5 的交付单元：CI/CD 流水线的产物是一个镜像，K8s 调度的对象是容器。它也是「一次构建、多处部署」这条原则的实现基础。

最容易踩的坑 ① 镜像里的时区与编码没设置，导致时间显示错误、中文乱码 —— 极其常见。
② 容器里的 JVM 内存配置没设上限，JVM 会按宿主机内存来分配堆，导致容器被 OOM Kill（这是容器化 Java 应用最经典的坑）。
③ 镜像过大。把构建工具、源码、缓存全打进镜像，导致分发慢、攻击面大。
判断你是否掌握
  • 能说清「镜像」与「容器」的区别，以及镜像分层的意义
  • 知道为什么容器里的 Java 应用必须显式限制堆内存
  • 能说出 Docker 解决了部署中的哪几类具体问题
6.3Kubernetes：容器编排L5 · 编排
角色当你有几十个服务、几百个容器时，手动管理已经不可能。K8s 负责「让声明数量的实例一直健康运行着」。
它解决什么问题

Docker 解决了「单个容器怎么跑」，但没解决「跑多少、挂在哪、挂了怎么办、怎么扩容、怎么发布」。K8s 把这些自动化：

  • 调度：决定容器跑在哪台机器上（考虑资源、亲和性、分布均衡）
  • 自愈：容器挂了自动重启，机器挂了自动迁移
  • 扩缩容：按 CPU / QPS 指标自动增减实例
  • 服务发现与负载均衡：内置的，不需要额外搭一套
  • 滚动发布与回滚：新版逐个替换旧版，出问题一键回滚

核心理念是声明式：你描述「期望状态」（我要 5 个实例），K8s 负责让它变成现实，并持续维持。

前端视角

你在 React 里描述「UI 应该长什么样」，框架负责把 DOM 变成那样 —— 这是声明式的同一思想。K8s 是「基础设施的 React」。

另一个贴切类比：你期望 5 个实例 = 你期望 list 里有 5 个 item。框架负责收敛，你只描述目标状态。

在体系中的位置

它是 L5 的调度中枢。它让「水平扩容」从一件需要人工操作的事，变成一个可以自动完成的动作 —— 这也是微服务架构能在中小团队落地的关键基础设施。

但要客观认识它的门槛：K8s 本身有很高的学习与运维成本。中小项目用「容器 + 简单编排 / 云托管服务」往往更划算。不要为了用 K8s 而用 K8s。

最容易踩的坑 ① 健康检查配错导致滚动更新失败或反复重启。「存活探针」和「就绪探针」的语义不同，配置错误会造成「服务在跑但不可用」或「还没启动好就接流量」。
② 没有设置资源请求与限制。导致调度不均，或某个服务吃掉全部资源影响其他服务。
③ 把 K8s 当银弹。它不能解决你的代码问题、SQL 问题、架构问题 —— 它只解决「部署与调度」的问题。
判断你是否掌握
  • 能解释「声明式」与「命令式」的区别，并说出它的好处
  • 知道滚动发布（Rolling Update）的流程，以及优雅停机为什么重要
  • 能说清存活探针与就绪探针的差异
6.4Nginx 与负载均衡L5 · 流量
角色流量进入系统的第一站。它做四件事：反向代理、负载均衡、静态资源、TLS 卸载。
它解决什么问题

负载均衡：把请求分发到多个应用实例。策略不同，效果差异很大 —— 轮询（平均但没考虑实例能力差异）、加权、最少连接数（适合长连接）、一致性哈希（适合需要会话保持的场景）。

反向代理：客户端只知道 Nginx 的地址，真正的服务实例隐藏在内部 —— 这本身就是一层安全边界。

其他能力：静态资源服务（比 Java 应用快得多）、TLS 卸载（证书只配在一处）、请求限流与缓冲、压缩。

前端视角

你本地开发时配的 vite.config 里的 proxy、或者项目里用过的 Nginx 配置，就是它的简化版。你会对「上游服务器列表」「路径重写」「透传请求头」这些概念有天然熟悉感。

有一件事你在前端可能没意识到：Nginx 是解决跨域、解决 Cookie 域问题、解决 HTTPS 的最简单方案，很多时候比在后端改代码更合适。

在体系中的位置

它站在 L5 的最前端，与 L4 的网关形成两层入口（通常 Nginx 做通用代理与静态资源，网关做业务路由与鉴权）。它也是可观测性的第一个数据采集点。

最容易踩的坑 ① 转发时丢失原始客户端 IP 与协议，导致后端日志里的 IP 全是 Nginx 的、生成的链接协议错误。必须正确透传相关请求头。
② 超时配置与应用不匹配，导致「应用还在处理，Nginx 已经返回 504」。
③ 缓冲区与请求体大小限制导致大文件上传失败 —— 这类问题排查起来非常费时。
判断你是否掌握
  • 能说出几种负载均衡策略，以及各自适合什么场景
  • 知道「正向代理」与「反向代理」的区别
  • 能解释为什么线上日志里的客户端 IP 需要专门处理才会正确
6.5CI/CD：自动化流水线L5 · 工程
角色把「提交代码」到「服务上线」之间的所有手工动作自动化。这是团队工程成熟度最直观的体现。
它解决什么问题

CI（持续集成）：每次提交都自动构建、跑测试、做静态扫描。目的是尽早发现集成问题 —— 而不是等到发布前一天才发现「几个人的代码合不到一起」。

CD（持续交付/部署）：自动把通过验证的构建产物发布到环境。目的是让发布变成一件廉价、频繁、低风险的事。

后端流水线通常还包含：数据库变更脚本的执行与校验、镜像构建与推送、灰度发布、健康检查、失败自动回滚。

前端视角

这是你最有优势的一层，经验几乎可以完整平移：Jenkins / GitLab CI / GitHub Actions 的使用方式、流水线阶段划分、环境变量与密钥管理、构建缓存优化，你都已经很熟。

差异在于流水线的末端：前端的产物是静态文件，发布即生效；后端要执行容器编排、要管数据库变更、要处理「新老版本同时在线」的兼容问题（灰度期间两个版本共存）。

在体系中的位置

它是 L5 的流水线中枢，同时是 L1（构建）、L3（数据库变更）、L4（服务发布）三者的汇合点。 它还有一个隐性价值：它把「上线流程」变成了可审查的代码 —— 谁在什么时候发布了什么版本，全部有记录。

最容易踩的坑 ① 灰度期间的新老兼容。发布过程中新旧版本同时在线，如果新版本改了数据格式或接口契约，旧版本就会出错。这就要求所有变更必须向后兼容，必要时分多次发布（先兼容读、再切写、最后清理）。
② 绕过流水线手工发布。一次「紧急修复」直接上生产，从此流水线形同虚设，并留下无法追溯的变更。
③ 没有回滚能力。发布失败后只能手忙脚乱地改代码再发一次 —— 这是最危险的发布状态。
判断你是否掌握
  • 能为一个 Java 服务设计一条完整的流水线（从提交到上线）
  • 知道什么是蓝绿发布、金丝雀发布、滚动发布，各自的风险与适用场景
  • 能说清「向后兼容」在发布过程中的具体含义
6.6可观测性三件套：日志、指标、链路追踪L5 · 眼睛纵向
角色把「服务出问题了」从一个无从下手的现象，变成一条可定位、可量化的证据链。它是后端工程师与「玄学」之间的分界线。
日志
发生了什么（What）
离散的事件记录。回答「这个请求经历了什么、报了什么错、带着什么参数」。在微服务下必须集中收集（几十个实例无法逐个登录查看），并支持按 traceId 关联检索。
关键点：结构化输出、统一 traceId、分级管控、脱敏
指标
整体健康状况（How much）
聚合的数值趋势。回答「现在 QPS 多少、错误率多少、P99 延迟多少、内存涨得正不正常」。它适合做告警，因为它有明确阈值且成本低。
关键点：QPS / 错误率 / 响应时间分位数（P95、P99）/ 资源水位 / 队列积压 / 连接池使用率
链路
慢在哪里 / 断在哪里（Where）
一次请求在多个服务之间的完整调用路径与各段耗时。回答「这 800ms 里，是网关 20ms、服务 A 500ms、还是数据库 240ms」。
关键点：traceId 贯穿全链路、Span 记录每段耗时、能定位到具体 SQL 与具体下游
一个必须建立的直觉：看分位数，不只看平均值

「平均响应时间 50ms」是一个极具欺骗性的指标。如果 1% 的请求耗时 5 秒（而正是这 1% 决定了用户是否流失），平均值依然很好看。 所以后端看 P99 / P95 而不是平均值 —— 这也是为什么「用户体验变差」和「监控一切正常」可以同时成立。

在体系中的位置

它是横向贯穿所有层的神经系统：L2 的请求日志、L3 的慢 SQL 与连接池水位、L4 的消息积压与熔断状态、L5 的容器资源 —— 全部靠它被观测到。 在微服务架构下，没有可观测性就等于没有运维能力。

最容易踩的坑 ① 只有日志没有指标。出问题时靠人肉翻日志，故障发现依赖用户投诉 —— 这是完全被动的运维。
② 日志没有 traceId。微服务下无法把一次请求的日志串起来，排查效率极低。
③ 告警泛滥。配置了几百条告警，结果大家都把告警静音了 —— 没有区分严重等级的告警等于没有告警。
判断你是否掌握
  • 能说清日志、指标、链路追踪各自回答什么问题，为什么不能互相替代
  • 知道为什么看 P99 而不看平均值
  • 能为一个新服务设计出最小可用的监控告警方案
6.7安全：认证、授权与常见攻击L5 · 底线纵向
角色不是「加了更好」，而是不做就是事故。安全问题的特点是：平时完全看不出来，一旦暴露就是最高优先级事故。
认证与授权（两件事，别混）

认证（Authentication）：你是谁？—— 校验用户名密码、Token、证书。

授权（Authorization）：你能做什么？—— 校验角色与权限。

两种主流会话方案：Session（服务端存状态）——简单，但多实例需要共享存储；JWT（客户端存 Token）——无状态、适合分布式，但无法主动失效（签发后到期前一直有效），所以通常要配合黑名单或短有效期 + 刷新令牌。

更完整的方案是 OAuth2 / OIDC，用于「第三方授权登录」这类场景。

前端视角

你是「存 Token 的那一端」，知道要防 XSS 所以把 Token 放 HttpOnly Cookie。现在你变成了校验 Token 的那一端：要处理过期、续期、刷新、并发刷新、注销失效、越权访问。

有一个认知升级很重要：前端的权限控制只是「隐藏入口」，不是安全措施。任何前端校验都可以被绕过，真正的权限校验必须在后端逐次执行。这是前端转后端最容易忽略的一条铁律。

必须知道的三类攻击
攻击类型原理后端如何防
SQL 注入把 SQL 片段拼进用户输入，让数据库执行攻击者构造的语句永远使用参数化查询（预编译），绝不拼接 SQL 字符串。这是唯一可靠的防线。
XSS注入脚本，在他人浏览器中执行，窃取 Cookie / Token输出转义、输入过滤、设置 HttpOnly Cookie、配置内容安全策略。后端也有责任，不能全推给前端。
越权访问修改请求里的 ID，访问不属于自己的数据（水平越权）；普通用户调用管理员接口（垂直越权）每次数据访问都校验「这条数据属不属于当前用户」，权限判断不能只在入口做一次。
另外几条底线
  • 敏感数据加密存储：密码必须用加盐哈希（bcrypt 等），绝不能明文或简单 MD5。
  • 不信任任何外部输入：包括前端传来的价格、用户 ID、角色、状态。所有会影响业务结果的值必须在服务端重新校验。
  • 敏感信息不进日志、不进响应体：手机号、身份证、密码、Token、完整银行卡号。
  • 内部接口也要鉴权：不能因为「在内网」就默认可信，内网被攻破后横向移动是常见路径。
判断你是否掌握
  • 能说清 Session 与 JWT 的取舍，以及「JWT 无法主动失效」这个问题的应对方案
  • 能识别出代码里所有「需要校验数据归属」的位置
  • 知道为什么不能信任前端传来的任何与权限或金额相关的字段
6.8压测与容量评估L5 · 预判
角色在流量到来之前先知道系统能扛多少。它是「运维」升级为「保障」的分界线。
它解决什么问题

每一次大促、每一次推广活动，流量都会上涨。如果不提前压测，你只能在故障发生后才知道系统的实际上限 —— 而那时用户已经在流失了。

压测要回答三个问题：① 单机能扛多少 QPS？② 瓶颈在哪一环（应用 CPU、数据库、连接池、下游、带宽）？③ 到达瓶颈时，系统是「变慢」还是「崩溃」？

第三个问题最关键。好的系统在过载时表现为「响应变慢、部分请求被拒绝」；差的系统直接整体崩溃、无法恢复。

前端视角

前端做性能优化的对象是「单个用户的体验」，优化目标通常是首屏时间、交互延迟 —— 本质上是「一个人的快」。

后端性能是「一群人的快」：单次请求 50ms 很容易做到，但 5000 QPS 下维持 50ms 需要完全不同的设计（连接池、缓存、异步、限流、水平扩展）。这是量变引起的质变。

在体系中的位置

它是 L5 与所有其它层的综合检验：压测暴露出的瓶颈可能来自 L0（GC 停顿）、L3（慢 SQL 与锁）、L4（缓存命中率、MQ 积压）、L5（容器资源与网络）。 能读懂压测报告并定位瓶颈，是后端综合能力的试金石。

最容易踩的坑 ① 只压应用不压链路。只测单个接口很快，实际上完整业务链路可能涉及十几个调用 —— 要按真实业务场景压。
② 压测数据和生产不一致。数据量小、缓存全命中，压出来的漂亮数字在生产上完全失效。
③ 压测流量打到生产环境且未做隔离，直接把线上打挂。
④ 不做「过载测试」。只测了极限 QPS，没测超过极限后的行为 —— 而故障往往发生在超限时刻。
判断你是否掌握
  • 能设计一个压测方案，并说明需要观测哪些指标
  • 知道系统在过载时的两种行为模式，以及哪种更可取
  • 理解为什么「单机 1000 QPS」和「集群 10000 QPS」不是简单的乘法关系

7纵向能力与架构思维

前面六章是「知识」，这一章是判断力。同一个需求，两个人都能实现， 但三年后一个系统能继续演进、另一个变成没人敢改的泥潭 —— 差别就在这一章。 这也是面试中「你能不能独立负责一个系统」这个问题的真正考察点。

7.1领域建模与设计模式的落地纵向 · 设计
角色把「业务语言」翻译成「代码结构」。它决定了你的系统能不能跟上业务变化 —— 对后端来说，这是最有复利的一项能力。
它解决什么问题

后端代码的复杂度，绝大部分不来自技术，而来自业务规则的复杂度与变化速度。

如果状态用字符串散落各处、规则写在几十个 if/else 里、数据模型和数据库表严格一一对应，那么每次业务调整都要改几十处，还容易漏。优秀的建模会让「业务规则的变化」只影响一两个地方。

几个关键洞察：
① 状态机思维：订单、支付、审批这类对象，本质是状态机。把「合法状态流转」显式建模，能消灭大量非法状态与脏数据。
② 值对象与实体：金额、时间范围这类应该封装成不可变的值对象，避免「裸用 double 表示金额」这种经典错误。
③ 充血模型：让对象自己承载与它强相关的行为，而不是全是 getter/setter，把逻辑都堆在 Service 里。

前端视角

这完全是你在前端做过的抽象工作：把散落的 useState 收敛成一个 useReducer / 状态机； 把散落的类型定义收敛成强类型模型；把重复的渲染逻辑抽成组件。

前端和后端在建模上的唯一差异是：前端的模型生命周期是一屏，后端的模型生命周期是几年 —— 所以后端建模错了的代价大得多。

常被提及的后端设计模式（不必背诵，要能识别）

策略模式：消灭大量 if/else 分支，把「不同规则」变成「不同实现」。这是后端业务代码里收益最大的一个模式。

模板方法：固定流程骨架、变化步骤下沉到子类。适合「流程一致、细节不同」的批处理与审批流。

责任链：依次处理请求，可中断可传递。网关、过滤器、审批流都是它。

工厂 / 建造者：统一复杂对象的创建，降低使用方的心智负担。

观察者 / 发布订阅：事件驱动的解耦，MQ 的代码层面基础。

代理：Spring AOP 的底层机制。

关键提醒：设计模式是「识别工具」，不是「强制套路」。先有痛点，再引入模式。为了用模式而用模式，只会让代码更难懂。

最容易踩的坑 ① 过度设计。业务还在验证阶段就先建三层抽象 + 五个扩展点，结果业务方向一变全部作废。抽象要滞后于需求，不要提前预付复杂度。
② 贫血模型泛滥。所有类都只有 getter/setter，逻辑全挤在 Service —— Java 后端最普遍的设计问题，也是「代码越写越乱」的根源。
判断你是否掌握
  • 能把一个真实业务流程先写成状态机，再开始编码
  • 看到一段超过 10 个分支的 if/else，能判断该用什么模式重构
  • 能说清「什么时候不该抽象」
7.2高可用设计思想纵向 · 稳定性
角色一套设计原则，而不是具体技术。它让你在设计阶段就预判故障，而不是等它发生。
原则含义对应的具体手段
冗余任何单点都可能失败，所以要有多份多实例部署、主从数据库、多可用区、缓存集群
隔离故障不能扩散，要把它关在笼子里线程池隔离、服务隔离、数据隔离、机房隔离
快速失败与其慢慢失败，不如立刻失败超时设置、熔断、连接池等待时间上限、参数前置校验
限流保护主动拒绝一部分，保全大部分入口限流、队列限长、降级开关
幂等与重试网络不可靠，所以操作要可重复执行唯一约束、幂等表、业务单号去重
可观测看不见的问题无法被修复日志、指标、链路追踪、告警分级
可回滚任何变更都要能撤销灰度发布、版本回滚、配置开关、DB 变更兼容设计
一个必须建立的思维方式：从「不要出错」到「出错时怎么办」

新手写代码的思维是「这个操作会成功」；有经验的后端写代码的思维是「这个操作如果失败了，会发生什么」。

具体到每一个外部调用，都要问四个问题：会不会超时？超时了怎么办？失败了重试几次？重试会不会造成重复操作？ 这四个问题问下来，代码的健壮性会有质的提升。

判断你是否掌握
  • 拿到一个系统设计，能主动指出它的单点在哪里
  • 能说清「雪崩」是怎么形成的，以及可以从哪几层阻断
  • 写代码时会本能地考虑「失败路径」，而不只是「成功路径」
7.3技术选型与方案权衡纵向 · 判断力
角色技术决策的质量，在写第一行代码之前就已经决定了系统的上限。选型的本质不是「选最好的」，而是「选最适合当前约束的」。
选型的四个维度

① 团队能力：团队不熟的技术，学习成本与踩坑成本都是真实代价。「业界最佳实践」在能力不足的团队里可能是灾难。

② 业务阶段：早期业务要的是「快速验证」，别提前做高可用架构；成熟业务要的是「稳定与成本」，别再用临时方案糊。

③ 运维成本：每引入一个中间件，就多一套要部署、监控、扩容、升级、排障的系统。这个成本经常被严重低估。

④ 可逆性：这个决策以后改起来难不难？可逆的决策可以快，不可逆的决策必须慎重。

常见的权衡对

性能 vs 一致性：缓存与最终一致换来性能，代价是短暂的不一致。业务能不能接受？

开发效率 vs 可控性：ORM 省事但生成的 SQL 不可控；手写 SQL 可控但要写更多代码。

复杂度 vs 弹性：微服务换来独立扩容与故障隔离，代价是分布式复杂度。

成本 vs 冗余：多副本高可用要多花钱，但单点故障的代价往往更高。

一个极其重要的现实认知

大多数「性能问题」根本不需要架构级方案。加个索引、加个缓存、改一句 SQL 写法、消除一个 N+1 查询，往往就能把接口从 3 秒降到 50ms。

先测量，再优化；先做简单的事，再做复杂的事。过早引入分布式方案，是后端最常见的过度设计 —— 而且它带来的新问题通常比原问题更难解决。

判断你是否掌握
  • 面对两个技术方案，能列出各自的代价而不仅是好处
  • 能判断一个决策是「可逆」还是「不可逆」，并据此调整决策速度
  • 在提出方案前，会先问「这个问题真的存在吗？有多大？」
7.4读源码与自我进化能力纵向 · 元能力
角色后端知识体系永远在变化，能持续自我更新才是长期竞争力。这是唯一一个「学会之后能加速学会其它一切」的能力。
为什么必须读源码

框架的文档只告诉你「怎么用」，源码才告诉你「什么时候不生效」「为什么偶发」「性能瓶颈在哪」。

后端遇到的所有诡异问题，最终都要回到框架或 JVM 的实现细节上找答案。而读源码这项能力是复利的：Spring 读懂了，读 MyBatis、读 Netty 都会快很多，因为它们共享同一套 Java 生态的设计范式。

怎么做：不要从第一行读起。用一个具体问题驱动（比如「@Transactional 到底在哪里开启事务」），从注解出发、顺藤摸瓜、打断点验证。问题驱动的源码阅读效率是没有目的的通读的十倍以上。

前端视角

你在前端也有类似经验：读 React / Vue 源码、读一个 npm 包的实现。方法论完全一样 —— 找到入口、验证假设、用调试器辅助。

一个有价值的差异：Java 的调试体验比前端更好。IDE 的断点、变量查看、条件断点、表达式求值能力更强，你可以直接「看」到框架内部在做什么。学会用调试器读源码，是性价比极高的投入。

建立知识体系的方法
  • 每个技术都问三个问题：它解决什么问题？没有它之前是怎么做的？它引入了什么新问题？
  • 用「故障」当学习入口：每次线上问题都是一次高强度的学习机会，把根因和解决方案记录下来。
  • 动手做完整项目，而不只是刷知识点。后端的能力高度依赖「整体感」，只有做过完整系统才会形成。
  • 定期回看自己的旧代码。如果三个月前写的代码你现在看不出问题，说明你这三个月没有进步。
判断你是否掌握
  • 能带着一个具体问题去读框架源码，并找到答案
  • 能说清「一个技术解决了什么」而不只是「它怎么用」
  • 有自己的问题记录与复盘习惯

812 周学习路径

这是一条以「能独立交付一个后端服务」为目标的路径，按依赖关系排列，每周产出一个可见成果。 核心原则：每周都必须有能跑起来的东西，因为后端的能力高度依赖整体感，只看不练等于没学。

开始之前的三条建议
  • 所有前置知识：只用一周，不要恋战。你有编程底子，Java 语法不需要啃完整本书。基础不牢的地方，等项目里遇到再补。
  • 每一周都产出可运行的东西，哪怕是极简陋的。后端知识一旦脱离项目就会变成「背过的概念」。
  • 项目选题建议直接对标你的目标：一个带用户体系 + 权限 + 数据统计的后台管理系统。它是 Java 就业市场最主流的项目形态，也能自然覆盖全部六层知识。
第 1 周语言基础
Java 语法与集合框架

跳过「变量 / 循环」这些前置，直接进入差异部分：面向对象、接口与抽象类、异常体系、集合框架的选型。

重点：不要第 1 周就学并发。先用单线程思维写代码，等到第 7 周有了真实场景再回来学，效果完全不同。

产出：能用 Java 写一个命令行小程序（如通讯录管理）
第 2 周工程化
Maven + Git + 日志 + 单测

这一周的目标是「具备职业开发环境」。Maven 的依赖管理、多模块结构、Git 分支模型、SLF4J 日志规范、JUnit 写第一个测试。

重点：主动制造一次依赖版本冲突并解决它 —— 这个经验以后会反复用到。

产出：一个结构规范的多模块 Maven 工程
第 3 周Web 原理
HTTP + Servlet + Tomcat

这一周不讲业务，只讲原理：HTTP 报文结构、状态码语义、Servlet 生命周期、Tomcat 的线程模型。

重点：手写一个 Servlet（不用 Spring），体会一下「没有框架的时候多麻烦」。这一周的「痛苦体验」是理解 Spring 的前提。

产出：一个纯 Servlet 实现的接口
第 4 周框架入门
Spring IoC + AOP + Spring Boot

理解 IoC 解决了什么、AOP 如何实现、Boot 的自动配置做了什么。

重点：反复确认「Bean 默认是单例」这件事意味着什么。写下你的第一份「不能往 Bean 里放成员变量」的纪律。

产出：一个 Spring Boot 应用，用注解把依赖装配起来
第 5 周接口开发
Spring MVC + RESTful + 统一响应 + 全局异常

完成第一个完整的 CRUD 接口。同时建立规范意识：统一响应结构、参数校验、错误码、全局异常处理、日志埋点。

重点：不要只做「能跑」，要按规范做一遍。规范意识的建立越早越好。

产出：一个符合团队规范的 CRUD 接口（内存存储即可）
第 6 周数据层上
SQL 与 MySQL 基础 + JDBC 与连接池

先把 SQL 写熟（增删改查、多表关联、聚合、子查询），再理解 JDBC 与连接池的作用与代价。

重点：不要跳过 SQL 直接上 ORM。SQL 是后端最核心的硬技能之一，ORM 只是它的便捷封装。

产出：用 JDBC 手写一套数据访问代码
第 7 周数据层下
MyBatis 接入 + 索引 + 事务 + 锁

把第 6 周的项目接入 MyBatis，然后深入数据库的关键机制：索引与最左前缀、事务隔离级别、行锁与 MVCC。

重点：用真实数据量（十万级以上）复现一次「没走索引导致接口超时」，再用索引把它优化到毫秒级。这个体验会彻底改变你对 SQL 的态度。

产出：数据落库的完整项目 + 一份索引优化记录
第 8 周并发
并发编程 + JVM 基础

带着前七周的真实项目来学：为什么单例 Bean 有并发问题、线程池怎么配、加锁后为什么还出错。然后是 JVM 内存结构、GC、常见异常排查。

重点：刻意写一个「多线程下计数错误」的程序，再分别用锁和原子类修复它。亲手复现比看十篇文章更有用。

产出：一份并发问题复现与修复记录
第 9 周缓存
Redis 与缓存设计

Redis 常用数据结构与适用场景、缓存读写策略、穿透/击穿/雪崩的复现与防治。

重点：把「缓存与数据库的一致性」当成一个开放问题去研究，理解为什么没有完美答案、工程上如何在二者间取舍。

产出：项目接入缓存，并输出一份缓存设计说明
第 10 周异步与运维
消息队列 + Docker + Linux

用 MQ 把项目里的非核心流程异步化（发通知、记日志、统计）。同时把服务容器化，学会在 Linux 上排查问题。

重点：亲手制造一次消息重复消费，然后实现幂等处理。

产出：Docker 化部署的完整服务 + 异步流程
第 11 周稳定性
可观测性 + 限流降级 + 安全

接入日志与监控、给关键接口加限流、让重要流程有降级方案。同时把安全加固一遍：认证授权、参数校验、越权防护。

重点：给自己的服务写一份「故障排查手册」——列出常见故障现象与对应排查动作。

产出：带监控告警与安全加固的服务
第 12 周收口
性能压测 + 架构复盘 + 分布式视野

对项目做一次压测，找到瓶颈并优化。然后回头把第 0 章的六层模型重新画一遍，用自己的语言标注每一层你实际用到了什么。

最后再读第 5 章 —— 此时你会发现自己能真正理解微服务与分布式在解决什么问题了。

产出：一份完整的项目复盘文档 + 压测报告
12 周结束后你应该达到的状态 不是「学会了所有知识点」，而是：拿到一个新需求，你能独立完成从表结构设计、接口设计、编码实现到部署上线的全过程，并且知道在这个过程中有哪些坑需要提前规避。 剩下的深度（JVM 调优、源码、复杂分布式方案），都是在真实项目里靠问题驱动的，不可能靠看书学完。

9能力自检清单

用来自查，不要用来「打勾交差」。判断标准很简单：能不能不看资料，用自己的话把这件事讲清楚，并且举出一个具体例子。 如果只能复述名词，说明还没真正掌握。

第一档：能写出能跑的功能

  • 能用 Maven 建起一个结构规范的多模块工程，并解释依赖冲突怎么排查
  • 能说清 IoC 容器解决了什么问题，以及 Bean 默认单例意味着什么
  • 能独立设计一组 RESTful 接口，并说明统一响应结构与错误码的规则
  • 能讲清 Filter / Interceptor / AOP 三者的执行顺序与适用场景
  • 能解释 Controller / Service / DAO 的职责边界，以及 DTO 与 Entity 为什么必须分开
  • 能不用资料画出 Spring MVC 处理一个请求的完整流程

第二档：能把功能写对

  • 能列出至少四种 @Transactional 失效的场景，并解释原因
  • 能说清索引的最左前缀原则，并能为一个慢查询设计出合适的索引
  • 能解释「脏读 / 不可重复读 / 幻读」的区别，以及四种隔离级别的取舍
  • 看到一段代码能指出所有线程安全风险点，并知道如何修复
  • 能说清线程池四要素如何共同决定行为，以及队列选错会发生什么
  • 能从现象出发，用一套流程定位「接口变慢」的真正原因
  • 能解释为什么连接池不是越大越好，以及它是怎么拖垮整个服务的

第三档：能把系统撑住

  • 能说清缓存穿透 / 击穿 / 雪崩的区别与防治，以及缓存一致性的取舍
  • 能说清「为什么用 MQ」并把三个理由对应到具体业务场景
  • 能画出一条雪崩链路，并指出每个环节可以用什么手段阻断
  • 能说清分布式锁必须处理的所有异常场景，以及什么时候不该用它
  • 能判断一个业务是否需要分布式事务，以及业务上可接受的替代方案
  • 能说清日志、指标、链路追踪各自回答什么问题，为什么看 P99 不看平均值
  • 能列出微服务带来的全部新增成本，并判断什么情况不该拆
  • 拿到一个系统设计，能主动指出它的单点与失败路径

A附录：后端黑话词典

这些词你在技术分享和面试里会高频听到，但很多资料默认你已经懂了。这里给出一句话解释， 它们绝大多数在前文都有对应章节，可以回去细看。

Beanbean
被 Spring 容器管理的对象。默认单例，所以不要往里放请求相关的成员变量。
IoC / DI控制反转 / 依赖注入
对象的创建与装配交给框架，你只声明需要什么。同一件事的两种说法。
AOP面向切面编程
在不改业务代码的前提下环绕插入增强逻辑。事务、日志、缓存都靠它。
代理 / Proxy
容器给你的其实是包装对象，调用先经过它。这是注解失效类问题的根本原因。
Starter起步依赖
一个依赖带齐某类功能所需的全部库与兼容版本。
自动配置
根据类路径与配置自动决定创建哪些 Bean，是 Boot 省事的核心机制。
DTO / VO / Entity
接口入参 / 接口出参 / 数据库映射对象。三者职责不同，不要混用。
DAO / Mapper
数据访问层，负责对象与 SQL 之间的转换，不该有业务逻辑。
ORM
对象与关系表的映射层。MyBatis 是半自动，JPA 是全自动。
连接池
复用数据库连接，同时也是对数据库的并发限流器。打满是常见故障。
慢 SQL
执行超过阈值的查询，线上性能问题最主要的来源。
回表
普通索引只存主键，查其它字段要再查一次主键索引。
覆盖索引
索引里已经有查询需要的全部字段，不需要回表，性能更好。
MVCC
多版本并发控制，让读不加锁、读写互不阻塞。可重复读的实现基础。
长事务
持续很久的事务，长时间持锁，会严重拖垮数据库并发。
缓存穿透
查一个根本不存在的数据，缓存永远不命中，每次都打库。常见于恶意攻击。
缓存击穿
单个热点 key 过期瞬间，大量并发同时去重建它。
缓存雪崩
大批 key 同时失效或缓存服务整体故障，流量全部砸向数据库。
大 key / 热 key
单个 key 数据过大或访问过于集中，会造成节点压力倾斜甚至阻塞。
MQ消息队列
异步通信中间件，三大价值是解耦、异步、削峰。
削峰填谷
用队列把瞬时高峰流量缓冲下来，让下游匀速消费。
幂等
同一操作执行多次与执行一次效果相同。重试与消息重复消费的前提。
RPC
远程过程调用，让跨服务调用写起来像本地方法调用。
注册中心
服务实例的通讯录，解决「对方在哪」的动态寻址问题。
配置中心
把配置外置并支持动态推送，改配置不用重新发布。
网关Gateway
流量统一入口，集中做路由、鉴权、限流、日志。
BFF
Backend For Frontend，为某一端前端定制的聚合网关。
限流
控制入口流量，超出部分直接拒绝，保护自己不被压垮。
熔断
下游错误率超阈值就断开对它的调用，快速失败，给下游恢复时间。
降级
非核心功能不可用时返回兜底结果，保证核心链路可用。
雪崩
一个下游变慢导致线程被占满，进而拖垮全部服务。
分布式事务
跨服务 / 跨库的一致性保障，实践中多为「最终一致」方案。
分布式锁
用公共存储实现的跨进程互斥，难点全在异常场景处理。
CAP
一致性、可用性、分区容错三者不可兼得，真实系统按业务分级取舍。
BASE
基本可用 + 软状态 + 最终一致。CAP 的工程化落地。
雪花算法
分布式全局 ID 生成方案，趋势递增且高性能。
一致性哈希
让节点增删时只迁移少量数据，避免缓存集体失效。
traceId
贯穿一次请求全链路的唯一标识，日志检索与链路追踪的基础。
P99 / P95
99% / 95% 的请求在该耗时以内。比平均值更能反映真实体验。
灰度 / 金丝雀发布
先让一小部分流量用新版本，验证正常后再逐步放量。
优雅停机
先停止接收新请求，等处理中的请求做完再退出，避免请求被中断。
OOM
内存溢出。容器时代更常见的是「容器内存超限被系统杀掉」。
Full GC
一次涉及全堆的垃圾回收，会造成明显的停顿，频繁发生通常意味着内存问题。
分布式单体
拆成了多个服务但耦合依旧，既失去单体的简单又承担了分布式的全部代价。

附录 B · 最后的一句话总结

把整个后端体系压缩成一段话

后端做的事情，本质是在一个会失败、会并发、会增长的系统里，保证数据的正确与可用。 L0~L1 让你有能力写出代码并把它组织成工程；L2 让代码能被外部调用；L3 让数据可靠地存下来； L4 让系统在压力与故障下继续工作；L5 让它能被观测、被部署、被信任。而纵向能力决定这一切做得是好还是坏。

学习顺序的心法只有一句：每学一个东西，先问「它在解决什么问题」，再问「没有它人们是怎么忍的」。 能回答这两个问题，你就不会被技术名词牵着走，也不会陷入「学了很多但串不起来」的困境。
